021. 이중화 회선 구성 - 부하 분산, 장애 대비, 다중 경로 라우팅

1. 이중화 회선 구성

1-1. 이중화의 정의

이중화(Redundancy): 네트워크 장애에 대비하기 위해 동일한 기능을 하는 회선이나 장비를 중복으로 구성하는 방식이다.

1-2. 이중화의 목적
목적 설명
장애 대비 주 회선 장애 시 백업 회선으로 자동 전
환
부하 분산 두 회선을 동시에 활용하여 트래픽 분산
1-3. 회선의 특성

실제 네트워크 회선의 특성:

회선의 속도는 비용에 비례한다. 더 높은 비용을 내면 더 빠른 속도를 제공받는다.

항목 설명
대역폭 한정 회선은 정해진 속도만 제공 가능
트래픽 몰림 일시적으로 트래픽이 몰리면 장애 발생 가능
속도 차이 회선마다 속도가 다를 수 있음
1-4. 추가 회선 설치
물리적 모듈 추가 절차
⌘Text
1. 저장 ← 반드시 먼저 설정 저장
2. 전원 차단 ← 장비 전원 끔
3. 모듈 설치 ← Physical 섹션에서 시리얼 모듈 추가
4. 전원 재시동 ← 장비 전원 켬

설정 저장 명령어:

⌘Text
write memory ← 간단한 방식

또는

⌘Cisco IOS
configure terminal
copy running-config startup-config ← 표준 방식

저장 후 전원을 끄지 않으면 모든 설정이 손실된다.

설정 미저장의 위험
⌘Text
설정 미저장 → 전원 차단 → 모든 설정 초기화

결론: 물리적 작업 전에 반드시 저장이 필수이다.

1-5. 라우터별 추가 인터페이스 설정

새로운 회선에 대한 IP 주소 설정:

네트워크 주소: 30.30.30.0/24

A 라우터 설정:

⌘Cisco IOS
configure terminal
interface serial 0/3/1 ← 새로운 시리얼 인터페이스
ip address 30.30.30.30 255.255.255.0
no shutdown
exit

B 라우터 설정:

⌘Cisco IOS
configure terminal
interface serial 0/2/0 ← 새로운 시리얼 인터페이스
ip address 30.30.30.60 255.255.255.0
no shutdown
exit
1-6. 새 회선을 통한 라우팅 설정
스태틱 라우팅에 경유지 추가

기존 라우팅 설정에 새로운 경유지를 추가한다.

A 라우터 - 150.0 네트워크로의 경로:

기존 경로:

⌘Text
ip route 192.168.150.0 255.255.255.0 10.10.10.20
← 기존 고속 회선

추가 경로:

⌘Text
ip route 192.168.150.0 255.255.255.0 30.30.30.60
← 이중화 회선 추가

결과: 동일한 목적지에 두 개의 경유지 존재

A 라우터 - 100.0 네트워크로의 경로:

⌘Text
ip route 192.168.100.0 255.255.255.0 30.30.30.60
← 이중화 회선으로도 도달 가능

2. 라우팅 테이블의 변화

2-1. 이중화 설정 전
⌘Text
S 192.168.150.0/24 [1/0] via 10.10.10.20
S 192.168.100.0/24 [1/0] via 10.10.10.20

특징:

항목 내용
경유지 하나만 존재
트래픽 모두 동일 경로로 이동
단점 해당 회선 장애 시 통신 불가능
2-2. 이중화 설정 후
⌘Text

S 192.168.150.0/24 [1/0] via 30.30.30.60
S 192.168.100.0/24 [1/0] via 10.10.10.20
S 192.168.100.0/24 [1/0] via 30.30.30.60

변화:

항목 내용
경유지 동일 목적지에 두 개 존재
트래픽 두 회선 모두 활용
효과 부하 분산 및 장애 대비 가능

3. 부하 분산(Load Balancing)

3-1. 부하 분산의 정의

로드 밸런싱(Load Balancing): 네트워크 트래픽을 여러 경로에 분산시키는 기법이다.

3-2. 동작 원리

동일 목적지로의 네트워크 트래픽이 여러 경로로 분산된다.

⌘Text
일부 데이터: 아래쪽 회선 (10.10.10.20 경유)
일부 데이터: 위쪽 회선 (30.30.30.60 경유)

예시: A 라우터 → B 라우터 간 데이터 이동 시

패킷 1, 3, 5... → 10.10.10.20으로 전송

패킷 2, 4, 6... → 30.30.30.60으로 전송

3-3. 부하 분산의 효과

성능 향상:

항목 효과
트래픽 분산 두 회선에 걸쳐 분산
각 회선 부하 감소
전체 대역폭 활용도 극대화
항목 효과
응답 시간 개선
안정성 향상
3-4. 속도 차이가 있는 회선의 부하 분산

회선별 속도가 다를 경우:

상황:

회선 1: 고속 (10.10.10.0)

회선 2: 저속 (30.30.30.0)

문제점:

저속 회선 사용 시 클라이언트가 느린 속도 체감

전체 성능이 저속 회선에 의해 제한됨

해결 방안: Floating Static Routing (부동 스태틱 라우팅)

항목 설명
주 경로 고속 회선만 활성 (10.10.10.20)
백업 경로 저속 회선은 예비로 대기
(30.30.30.60)
동작 주 경로 정상 시 사용, 장애 시 자동 전
환

원칙:

5. 다중 회선의 라우팅 복잡성

5-1. 복수 인터페이스 관리

라우터에 여러 회선이 연결될 때 인터페이스 구성:

인터페이스 용도 설명

022. DHCP 동적 호스트 주소 할당 프로토콜의 개념과 설정

1. DHCP 개요

1-1. DHCP 개념

DHCP는 Dynamic Host Configuration Protocol(다이나믹 호스트 컨피규레이션 프로토콜)의 약자로, 동적으로 호스트를 설정하는 프로토콜이다. 네트워크에 연결된 클라이언트에게 IP 주소, 게이트웨이 주소, DNS 서버 주소 등을 자동으로 할당한다.

2. DHCP 설정 명령어

2-1. 주요 명령어 구조

비교·분류 항목은 아래 표와 같이 정리된다.

명령어 역할
service DHCP DHCP 서비스 시작 (먼저 입력 필요)
ip dhcp pool [이름] DHCP 풀(정책) 생성, 이름은 임의로 지정 가능
network [주소] [마스크] IP 할당 범위 지정
default-router [게이트웨이] 클라이언트에게 전달할 게이트웨이(default-route) 주소
ip dhcp excluded-address [주소] 할당 제외 범위 설정 (prevent: 거부/제외)
2-2. 설정 순서 및 예시

DHCP 설정 시 service DHCP 를 먼저 입력하고, 이후 풀 설정을 진행한다.

⌘Cisco IOS
service DHCP                              ← DHCP 서비스 시작
ip dhcp pool [풀이름]                     ← 풀(정책) 이름 지정 (임의)
  network 192.168.100.0 255.255.255.0     ← IP 할당 범위
  default-router 192.168.100.254          ← 게이트웨이 주소
ip dhcp excluded-address [제외할 주소]    ← 할당 제외 범위

⚠️ default-router 는 게이트웨이 주소를 클라이언트에게 할당해 주기 위한 명령어이다. 예를 들어 게이트웨이가 192.168.100.254라면 해당 값을 입력한다.

2-3. Excluded Address (할당 제외)

할당 범위에서 제외하고 싶은 주소가 있을 경우 excluded-address 명령어로 지정한다.

명령어 뒤에 제외할 주소(또는 범위)를 입력하면 해당 주소는 클라이언트에게 할당되지 않는다.

3. DHCP 동작 원리

3-1. 클라이언트-서버 통신 과정

DHCP는 클라이언트와 서버 간의 요청-응답 구조로 동작한다.

단계 방향 내용
Request(리퀘스트) 클라이언트 → 서버 IP 주소 요청
Reply(리플라이) 서버 → 클라이언트 IP 주소 제안 응답
Request(리퀘스트) 클라이언트 → 서버 제안된 주소 사용 확인 요청
Acknowledge(에크날리지) 서버 → 클라이언트 최종 승인

최종적으로 클라이언트가 서버로부터 주소를 수락하며 할당이 완료된다.

4. DHCP 테이블 확인

4-1. Binding 테이블 (임대 현황)

DHCP 서버에서 현재 임대 중인 IP 주소 목록을 확인할 수 있다.

⌘Cisco IOS
show ip dhcp binding    ← 서버에서 어떤 IP가 임대되고 있는지 확인
4-2. Conflict 테이블 (충돌 현황)

서로 다른 클라이언트가 동일한 IP 주소를 할당 받을 경우 충돌이 발생한다.

충돌이 발생한 주소는 Conflict 테이블에 저장되고, 이후 다른 클라이언트에게는 할당되지 않는다.

5. 고정 IP와 동적 IP

5-1. 동적 IP의 특성과 한계

DHCP로 자동 할당되는 동적 IP는 재접속 시 동일한 IP를 받는 경우가 많으나, 경우에 따라 주소가 변경될 수 있다.

일반 시스템은 주소 변경이 문제되지 않으나, 서버의 경우 주소가 바뀌면 관련 설정을 새롭게 해야 하는 문제가 발생한다.

서버와 같이 주소가 고정되어야 하는 장비는 고정 IP를 사용해야 한다. 해당 고정 IP 대역은 excluded-address 로 DHCP 할당 범위에서 제외한다.

⌘Cisco IOS

024. OSPF Virtual Link와 FHRP HSRP 게이트웨이 이중화

1. Virtual Link와 라우터 ID

1-1. OSPF Virtual Link

OSPF에서 Area 0(백본)에 물리적으로 직접 연결되지 않은 Area가 존재할 경우, 해당 Area의 라우터들은 정상적인 통신이 불가능하다.

에어리어 2에 있는 장비들이 물리적으로 에어리어 1을 통해 연결되어 있으나 에어리어 0과 직접 연결되지 않은 경우, 통신이 되지 않는다.

이러한 상황에서 Virtual Link를 사용하면 물리적으로 연결할 수 없는 경우에도 Area 0에 논리적으로 연결하여 통신이 가능하도록 할 수 있다.

⌘Cisco IOS
show ip ospf    ← Virtual Link 정보 포함한 OSPF 전반 확인
1-2. OSPF 라우터 ID 관련 인터페이스 정보 확인
⌘Cisco IOS
show ip ospf interface    ← 인터페이스별 OSPF 정보 및 라우터 ID 확인

이 명령어에서 라우터 아이디와 관련된 정보를 확인할 수 있다. Loopback 인터페이스를 설정한 경우 해당 주소가 라우터 아이디에 반영된다.

2. FHRP (First Hop Redundancy Protocol)

2-1. FHRP 개념

FHRP는 게이트웨이 이중화 프로토콜로, 두 대 이상의 라우터가 하나의 가상 게이트웨이 역할을 공유하는 방식이다.

FHRP에는 아래 세 가지 프로토콜이 존재한다.

프로토콜 전체명 특징
HSRP Hot Standby Router Protocol Cisco 독자 프로토콜
VRRP Virtual Router Redundancy Protocol 표준 프로토콜
GLBP Gateway Load Balancing Protocol Cisco 독자 프로토콜

3. HSRP (Hot Standby Router Protocol)

3-1. HSRP 개념

HSRP는 두 라우터가 하나의 가상 IP(Virtual IP)를 공유하여 게이트웨이 역할을 수행하는 프로토콜이다.

한 라우터는 Active 상태로 실제 트래픽을 처리

다른 라우터는 Standby 상태로 대기

Active 라우터에 장애가 발생하면 Standby 라우터가 자동으로 Active 역할을 이어받 음

3-2. Virtual IP (가상 IP) 개념

Virtual IP는 어떤 물리적 인터페이스에도 실제로 할당된 주소가 아니다. 이 네트워크 내에서 물리적인 어떤 장비나 인터페이스에도 Virtual IP로 설정한 곳이 없으며, 논리적으로 만 존재한다.

클라이언트는 이 가상 IP를 게이트웨이 주소로 사용한다.

3-3. HSRP 설정 명령어
명령어 역할
standby [그룹번호] ip [가상IP] 가상 IP 주소 설정 (Virtual IP)
standby [그룹번호] priority [값] 우선순위 설정 (높을수록 Active 선출 유리)

설정 예시:

⌘Cisco IOS
interface gi0/0/1
  standby 1 ip 192.168.100.254      ← 1번 그룹의 가상 게이트웨이 IP 설정
  standby 1 priority 105             ← 우선순위 105 설정
3-4. HSRP 상태 확인

HSRP 설정 후 확인 결과에서 아래 정보를 확인할 수 있다.

항목 내용
그룹 번호 1번 그룹에 속함
우선 순위 105
현재 상태 Active
Active 라우터 Local (자기 자신)
Standby 라우터 상대 장비의 IP 주소
3-5. 부하 분산 (Load Balancing)

평상시에는 Active 라우터 경로만 사용하므로 Standby 쪽 회선은 미사용 상태가 된다. 여러 그룹을 설정하여 서로 다른 경로로 트래픽을 분산시키는 방식으로 부하 분산을 구현할 수 있다.

한 라우터를 그룹 1의 Active, 그룹 2의 Standby로, 다른 라우터를 그룹 1의 Standby, 그룹 2의 Active로 설정하면 양쪽 회선을 동시에 활용할 수 있다.

025. VLAN 기반 서브네팅과 L3 스위치 설정

1. VLAN과 서브네팅

1-1. VLAN과 네트워크 분할

하나의 네트워크 대역을 받아 VLAN으로 논리적 그룹을 나누는 경우, 각 VLAN에 서로 다른 서브네트워크를 할당해야 한다. VLAN이 3개인 경우 최소 3개의 서브네트워크가 필요하다.

1-2. 서브네팅 계산 방식

호스트 비트에서 비트를 빌려 서브네트워크를 분할하는 방식이다.

예시: 하나의 대역을 4개의 서브네트워크로 분할하는 경우

2개의 비트를 빌리면 2² = 4개의 서브네트워크 분할 가능

남은 비트 수에 따라 각 서브네트워크의 범위 크기가 결정됨

서브네트워크 시작 주소 끝 주소
첫 번째 100.0 100.63
두 번째 100.64 100.127
세 번째 100.128 100.191
네 번째 100.192 100.255

각 범위의 크기가 64인 경우, 첫 번째 대역에서 64씩 더해가며 두 번째, 세 번째, 네 번째 대역이 결정된다.

각 VLAN에 맞는 서브네트워크 범위를 정확하게 파악한 후, 그 범위 안에서 중복되지 않는 주소를 사용해야 한다.

2. L3 스위치

2-1. L3 스위치 개념

관리자가 L3 스위치에 특정 설정을 하면 라우터와 동일한 역할을 할 수 있다.

2-2. L3 스위치 IP 설정 방법

L3 스위치에서 인터페이스에 IP 주소를 설정하려면 먼저 no switchport 명령어를 입력해야한다.

⌘Cisco IOS
no switchport        ← IP 주소 설정 전 필수 입력
ip address [주소] [마스크]   ← IP 주소 설정

라우팅 기능을 활성화하려면 Config 모드에서 ip routing 명령어를 입력한다.

⌘Text
ip routing    ← L3 스위치에서 라우팅 기능 활성화

3. 라우터 서브 인터페이스와 Encapsulation DOT1Q

3-1. 서브 인터페이스 개념

하나의 물리적 인터페이스를 여러 VLAN에 대응시키기 위해 서브 인터페이스를 사용한다. 서브 인터페이스 번호는 VLAN 번호와 맞추는 것이 인터페이스 이름만 보고도 어떤 VLAN 을 위한 것인지 알 수 있어 관리에 유리하다.

3-2. Encapsulation DOT1Q 설정

encapsulation dot1q 는 라우터의 서브 인터페이스에서 사용하는 명령어이다.

⌘Cisco IOS
interface gi0/0.100              ← 서브 인터페이스 (VLAN 100에 대응)
  encapsulation dot1q 100         ← DOT1Q 캡슐화, VLAN 번호 지정
  ip address [게이트웨이IP] [마스크]  ← 해당 VLAN의 게이트웨이 IP 설정
  no shutdown

IP를 설정하기 전에 encapsulation dot1q [VLAN번호] 를 먼저 입력해야 한다. 순서를 지키지 않으면 정상적으로 입력되지 않는다.

3-3. 스위치와 라우터 간 연결

스위치와 라우터 간에 연결된 스위치 포트는 트렁크(Trunk) 모드로 동작시켜야 여러 VLAN 트래픽을 전달할 수 있다.

4. 라우터와 스위치의 역할 구분

4-1. 핵심 개념 정리
장비 역할
라우터 주소를 바탕으로 경로를 설정하는 장비. IP 주소를 부여하는 것은 관리자의 역할
스위치 패킷을 분류하는 장비가 아님. 스위치 포트를 통해 VLAN 분리 처리

IP는 주소일 뿐이며, 주소를 바탕으로 라우터가 경로를 설정한다. IP 주소를 부여하는 것은 라우터가 아닌 관리자가 하는 작업이다.

026. 라우터 ID, Loopback 인터페이스, DR BDR 개념

1. 라우터 아이디(Router ID) 심화

1-1. 라우터 아이디에 관여하는 인터페이스

라우터 아이디는 물리적인 인터페이스 값만 관여하는 것이 아니라, 논리적인 인터페이스 (Loopback)도 관여한다.

2. Loopback 인터페이스

2-1. Loopback 인터페이스 개념

논리적인 인터페이스로, 물리적으로 존재하지 않지만 IP 주소를 할당할 수 있다.

주소가 할당되면 해당 네트워크가 존재하는 것으로 인식된다.

Loopback은 논리적 인터페이스이지만, 명령어는 물리적 인터페이스와 동일하게

interface 로 시작한다.

2-2. Loopback 인터페이스 생성 및 설정
⌘Cisco IOS
interface loopback 0            ← Loopback 인터페이스 생성
  ip address [IP주소] [서브넷마스크]  ← IP 주소 할당

설정 예시:

⌘Cisco IOS
interface loopback 0
  ip address 150.100.100.1 255.255.255.0

주소만 설정하면 별도로 no shutdown 없이도 해당 네트워크가 존재하는 것으로 인식된다.

2-3. OSPF에 Loopback 네트워크 광고

Loopback 인터페이스의 네트워크도 OSPF에 참여시키려면 network 명령어로 광고해야한다.

⌘Cisco IOS
router ospf 10
  network 100.100.100.0 0.0.0.255 area 1    ← Loopback 네트워크를 Area 1로 광고

광고 후 시간이 경과하면 다른 라우터의 라우팅 테이블에 해당 네트워크가 반영된다.

3. 확장형 핑 (Extended Ping)

3-1. 개념 및 사용법

라우터 장비에서는 일반 핑과 달리 확장형 핑을 사용할 수 있다.

⌘Text
ping          ← ping 입력 후 엔터
[Target 주소 입력]    ← 대상 IP 입력
[반복 횟수 입력]      ← 기본값 5회

장비에서의 기본 핑 횟수: 5회 (윈도우는 기본 4회, 리눅스는 관리자가 종료할 때까지)

통신이 가능한지 확인할 때 사용한다.

예시: D 라우터에서 150.100 주소로 확장형 핑을 사용하여 통신 가능 여부를 확인한다.

4. DR / BDR (Designated Router / Backup Designated

Router)

4-1. DR/BDR 개념

OSPF 네트워크에서 라우터 수가 많을 경우, 네트워크 변화가 발생했을 때 모든 라우터가 서 로에게 직접 전파하면 트래픽이 과다해질 수 있다. 이를 해결하기 위해 DR과 BDR을 선출한 다.

역할 명칭 설명
DR Designated Router (대장 라우터) 네트워크 변화 정보를 수집하여 다른 라
우터에게 배포
BDR Backup Designated Router (부대
장 라우터)		 DR 장애 시 DR 역할을 이어받음
4-2. DR/BDR 동작 방식

네트워크 변화가 발생한 라우터는 모든 이웃 라우터에게 직접 전파하는 대신, DR에게만 전달한다. DR이 해당 변화를 다른 라우터들에게 배포하는 방식으로 동작한다.

DR이 선출되어 있는 경우, 라우터는 DR에게만 변화를 알리면 된다. 이를 통해 네트워크 트래픽을 줄일 수 있다.

4-3. Point-to-Point 구간에서의 DR/BDR

시리얼 등 1:1(Point-to-Point) 연결 구간에서는 DR/BDR이 필요하지 않다.

1대1 연결에서는 굳이 대장, 부대장을 선출할 필요가 없다.

4-4. DR/BDR 확인 명령어
⌘Cisco IOS
show ip ospf interface    ← 인터페이스별 OSPF 정보 확인 (DR/BDR 포함)

이더넷 구간: DR, BDR 정보 표시됨

Point-to-Point 구간: DR/BDR 없음으로 표시됨

027. ACL 규칙의 순서와 정책 관리

1. ACL 규칙의 순서 중요성

1-1. 규칙 매칭의 원리

ACL 규칙들은 위에서부터 아래로 순서대로 적용된다. 패킷이 도착하면:

  1. 첫 번째 규칙과 비교

  2. 일치하면 해당 규칙 적용 후 더 이상의 규칙은 검사하지 않음

  3. 일치하지 않으면 다음 규칙으로 진행

따라서 규칙의 순서가 정책의 결과를 크게 좌우한다.

1-2. 순서 변경의 영향

ACL에 포함된 규칙들의 순서를 변경하면, 동일한 정책 내용이라도 실제 적용 결과가 달라질 수 있다.

예시:

규칙 1: IP 10.0.0.1 허용

규칙 2: IP 10.0.0.0/24 (10.0.0.0~10.0.0.255) 차단

이 두 규칙의 순서를 바꾸면:

순서대로 적용: IP 10.0.0.1은 허용됨

순서 반대로 적용: IP 10.0.0.1은 차단됨

2. ACL 규칙 추가와 라인 번호

2-1. 라인 번호 체계

Cisco IOS의 현대적 ACL 관리에서는 라인 번호 개념을 도입했다. 이전에는 정책 번호만 있 었지만, 현재는 라인 번호를 통해 더 유연한 관리가 가능하다.

정책 번호: ACL 자체의 식별자 (예: ACL 100)

라인 번호: ACL 내 각 규칙의 순서 번호 (예: 10, 20, 30...)

2-2. 라인 번호 간격의 설정

일반적으로 라인 번호는 10단위로 설정된다:

⌘Text
10  permit ...
20  permit ...
30  deny ...
40  permit ...

이렇게 간격을 두는 이유는 중간에 새로운 규칙을 삽입할 여유를 남기기 위함이다.

2-3. 새로운 규칙의 삽입

새로운 규칙이 필요할 때:

기존 방식: 새 규칙은 항상 맨 마지막에 추가된다

라인 번호를 이용한 삽입: 특정 라인 번호를 지정하여 원하는 위치에 규칙을 삽입할 수 있다

예) 10번 규칙과 20번 규칙 사이에 새로운 규칙을 삽입하려면:

⌘Text
(새로운 규칙을 15번으로 삽입)
10  permit ...
15  permit ... (새로 추가)
20  permit ...
30  deny ...

3. 실무에서의 ACL 관리 방법

3-1. 문서화의 중요성

실무 환경에서 ACL을 설정할 때는 다음 단계를 따른다:

  1. 계획 단계: 메모장이나 문서 작성 프로그램에 ACL 정책 전체를 작성

  2. 검증 단계: 클라이언트 요구사항 및 조직의 보안 정책과 일치하는지 확인

  3. 적용 단계: 검증이 완료된 후 라우터에 입력

3-2. ACL 규모의 현실

실제 필드 환경에서:

소규모 조직: 10줄 미만의 ACL

중규모 조직: 수십 줄의 ACL

대규모 기업(많은 클라이언트): 수백 줄에 이르는 ACL도 존재

규칙이 많아질수록 순서 관리의 중요성이 극대화된다.

3-3. 규칙 변경과 관리

ACL 정책이 이미 수백 줄이 설정된 라우터에서:

매번 새로운 정책을 추가하려면 전체 정책을 점검해야 함

기존 정책과의 중복, 충돌, 상충 가능성을 검토해야 함

따라서 라인 번호를 이용한 중간 삽입 기능이 매우 중요

4. 라인 번호를 이용한 규칙 관리

4-1. 라인 번호 지정 방식

현대의 Cisco IOS와 많은 네트워크 장비들은 이전의 제한을 극복했다:

과거: 새로운 정책은 반드시 맨 마지막에만 추가 가능

현재: 라인 번호를 명시하여 원하는 위치에 삽입 가능

4-2. 예시 시나리오

초기 ACL 설정:

⌘Text
10  permit 10.0.0.0 0.0.0.255   ← 10.0.0.0/24 허용
20  deny 10.0.0.0 0.0.0.255     ← (나중에 추가, 충돌 가능)

라인 번호를 사용한 수정:

⌘Text
10  permit 10.0.0.1              ← 특정 IP만 허용
15  deny 10.0.0.10               ← 새로 삽입: 특정 IP 차단
20  permit 10.0.0.0 0.0.0.255    ← 나머지 네트워크 허용

5. ACL 설정의 Best Practice

주의사항: 운영 환경에서 ACL을 변경할 때는 다음 원칙을 따르자

변경 전 현재 정책을 문서로 백업

변경 사항을 별도 문서에 명시

변경 후 테스트를 통해 의도한 결과 확인

특히 트래픽 차단 규칙은 신중하게 검토

6. ACL 다음 단계: NAT의 필요성

ACL은 패킷 필터링을 통해 네트워크 접근을 제어한다. 다음 주제인 NAT(Network Address Translation)는 IP 주소 자체를 변환하여 다른 보안 및 운영상의 목적을 달성한 다.

028. ACL 및 NAT 개념과 역할 이해

1. ACL(접근 제어 목록; Access Control List) 개요

1-1. ACL의 정의 및 목적

ACL은 네트워크 트래픽을 필터링하는 기능이다. 관리자가 특정 출발지나 목적지로부터의 트래픽을 허용(permit) 또는 차단(deny)하는 정책을 설정할 수 있다.

ACL이 필요한 이유는 다음과 같다:

클라이언트나 기업의 상황에 따라 필터링을 수행

DDoS(분산 서비스 거부) 공격 시 특정 출발지로부터의 트래픽 차단 가능

불필요한 트래픽 제거 및 보안성 강화

2. ACL의 분류

2-1. 표준 ACL vs 확장 ACL
구분 표준 ACL 확장 ACL
번호 범위 1~99 100~199
필터링 기준 출발지 주소만 확인 출발지, 목적지, 프로토콜, 포트 번호 모두 확인
유연성 낮음 높음
용도 기본적인 필터링 세부적인 필터링

3. ACL 설정의 기본 개념

3-1. 주소 표현 방식

단일 호스트: host 키워드 사용 (예: host 192.168.1.100)

대역대: 네트워크 주소와 와일드카드 마스크 사용 (예: 192.168.1.0 0.0.0.255)

3-2. ACL 설정 요소

ACL 규칙은 다음 요소로 구성된다:

  1. 허용/차단 여부 (permit 또는 deny)

  2. 프로토콜 종류 (TCP, UDP, ICMP 등)

  3. 출발지 주소 (source)

  4. 목적지 주소 (destination)

  5. 특정 서비스 (포트 번호 또는 키워드)

4. ACL의 동작 원리

4-1. 매칭 규칙

첫 번째로 매칭되는 규칙이 적용된다

모든 규칙에 매칭되지 않은 트래픽은 암시적 deny가 적용된다

규칙의 순서가 중요하다

4-2. ICMP와 서비스

ICMP: ping 기능을 수행하는 프로토콜

echo: ping 요청

echo-reply: ping 응답

FTP: 파일 전송 프로토콜로, 포트 21 사용

5. Named ACL

5-1. Named ACL의 특징

번호 대신 이름으로 ACL 정책을 구분할 수 있다

표준 또는 확장 중 선택 가능하다

가독성이 높고 관리하기 용이하다

5-2. Named ACL 설정 형태
⌘Cisco IOS
ip access-list extended [정책이름]
permit tcp 192.168.1.100 192.168.0.200 eq 21 ← FTP(포트 21)
permit icmp 192.168.1.100 192.168.0.200 echo echo-reply
deny icmp 192.168.1.200 192.168.0.10 echo echo-reply
permit ip any any ← 나머지 트래픽 허용

6. NAT(Network Address Translation) 개요

6-1. NAT의 정의

NAT는 네트워크 주소 변환(Network Address Translation)으로, 한 주소 영역의 IP를 다른 주소로 변환하는 기능이다. 일반적으로 사설 IP를 공인 IP로 변환하는 데 사용된다.

6-2. NAT가 필요한 이유

  1. IP 부족: 사설 IP 대역을 사용하면서 공인 IP를 효율적으로 활용

  2. 보안: 내부 네트워크 구조를 외부에 노출하지 않음

  3. 네트워크 독립성: 내부 주소 변경 시 외부 영향 최소화

7. IP 주소의 분류

7-1. 공인 IP vs 사설 IP
구분 공인 IP 사설 IP
특징 인터넷 전체에서 유일 조직 내에서만 유일
할당 관리 ISP 또는 IANA 관리 자유롭게 사용 가능
외부 통신 직접 가능 NAT를 통해서만 가능
사설 대역 N/A 10.x.x.x, 172.16.x.x, 192.168.x.x
7-2. 사설 IP의 특징

누구나 사용 가능하지만, 같은 조직 내에서는 중복 불가

공인되지 않았으므로 인터넷에서 직접 라우팅되지 않음

같은 네트워크 내에서만 통신 가능

8. NAT의 종류

8-1. 정적 NAT(Static NAT)

관리자가 사설 IP와 공인 IP를 1:1로 수동 설정

특정 서버에 고정적인 공인 IP를 할당할 때 사용

8-2. 동적 NAT(Dynamic NAT)

사설 IP의 범위를 지정하고, 공인 IP의 범위를 지정하여 자동으로 변환

변환되는 IP들이 자동으로 매핑됨

9. PAT(Port Address Translation)

9-1. PAT의 필요성

여러 대의 사설 IP 장치가 하나의 공인 IP로 나갈 때 포트 번호를 이용하여 구분한다.

9-2. NAT vs PAT
구분 NAT PAT
IP 변환 IP 주소만 변환 IP + 포트 번호 변환
대상 호스트 수 비슷한 규모 1개의 공인 IP에 많은 사설 IP 대응
사용 사례 기업 내부 통신 가정용 공유기

10. 가정용 공유기의 NAT/PAT

10-1. 동작 원리

LAN 포트: 내부 네트워크 연결

WAN 포트: 외부 인터넷 연결

공유기는 내부 여러 장치를 하나의 공인 IP로 변환하여 통신

10-2. 포트 포워딩

내부 사설 IP 기반 서비스에 외부에서 접근하려면 공유기의 포트 포워딩 설정이 필요하다.

11. ACL과 NAT의 관계

11-1. 동적 NAT 설정 절차

  1. ACL 정책으로 변환할 사설 IP 범위 정의

  2. NAT 풀(pool)로 공인 IP 범위 정의

  3. ACL과 NAT 풀을 연결하는 명령 실행

11-2. 동작 과정

정책의 ACL에 일치하는 트래픽이 들어오면 NAT 풀의 IP로 변환

변환되지 않은 트래픽은 원래대로 통신

12. NAT의 보안 측면

12-1. 보안 이점

내부 네트워크 구조가 외부에 노출되지 않음

기업의 시스템 정보 보호

해킹이나 공격 시 직접 대상을 파악하기 어려움

12-2. 사용 사례

일부 기업은 공인 IP 여유가 있어도 보안 목적으로 사설망 + NAT 구성을 사용한다.

1. ACL(접근 제어 목록) 개요

030. ACL의 유형별 특징 및 필터링 기준

1. 스탠다드 ACL(Standard ACL)

1-1. 정의

스탠다드 ACL은 출발지 IP 주소만을 기준으로 패킷 필터링을 수행하는 가장 단순한 형태의 ACL이다.

1-2. 특징

필터링 기준이 출발지 IP 주소로만 제한된다

구성이 간단하고 설정하기 쉽다

세밀한 필터링은 불가능하다

특정 네트워크 또는 호스트의 접근만 제어할 수 있다

1-3. 적용 범위의 제한

출발지 IP 주소만으로 필터링하므로, 특정 포트나 서비스를 선택적으로 차단하기 어렵다. 예를 들어, 특정 IP에서의 HTTP 접속만 차단하고 HTTPS는 허용하는 것이 불가능하다.

2. 확장 ACL(Extended ACL)

2-1. 정의

확장 ACL은 출발지 IP, 목적지 IP, 프로토콜, 포트 등 여러 기준을 조합하여 패킷 필터링을 수행한다.

2-2. 특징

출발지 IP 주소와 목적지 IP 주소 모두 고려한다

프로토콜 타입(TCP, UDP, ICMP 등)을 지정할 수 있다

포트 번호(예: HTTP의 80번, HTTPS의 443번)를 기반으로 필터링 가능하다

훨씬 세밀한 트래픽 제어가 가능하다

설정은 복잡하지만, 보안 정책을 더 효과적으로 구현할 수 있다

2-3. 활용 예시

특정 IP의 특정 포트 접근만 차단

특정 프로토콜(예: Telnet, SSH)만 제한

복합적인 보안 정책 구현 가능

3. ACL의 분류 비교

항목 스탠다드 ACL 확장 ACL
필터링 기준 출발지 IP 주소만 출발지 IP, 목적지 IP, 프로토콜, 포트
복잡도 낮음 높음
세밀도 낮음 높음
적용 위치 목적지에 가까운 위치 출발지에 가까운 위치
성능 영향 낮음 상대적으로 높음
사용 시나리오 특정 네트워크 전체 접근 제어 특정 서비스/포트 기반 제어

4. ACL 번호 체계

Cisco IOS에서 ACL은 번호로 식별된다.

스탠다드 ACL: 1~99 또는 1300~1999 범위

확장 ACL: 100~199 또는 2000~2699 범위

ACL 번호는 정책을 구분하고 관리하기 위한 식별자로 사용된다.

5. 필터링의 동작 원리

5-1. 패킷 처리 과정

  1. 라우터에 패킷이 도착한다

  2. 적용된 ACL 규칙과 패킷 정보를 비교한다

  3. 규칙과 일치하면 허용(permit) 또는 거부(deny) 결정을 수행한다

  4. 결정에 따라 패킷을 전달하거나 폐기한다

5-2. 규칙 매칭 순서

ACL의 규칙들은 위에서부터 순서대로 적용된다

첫 번째로 일치하는 규칙이 적용되며, 이후 규칙들은 무시된다

따라서 ACL 규칙의 순서가 중요하다

6. 프로토콜과 포트의 이해

6-1. 주요 프로토콜

TCP: 신뢰성 있는 연결 기반 통신 (예: HTTP, HTTPS, FTP, SSH)

UDP: 신뢰성 없는 비연결 통신 (예: DNS, VoIP)

ICMP: 진단 및 오류 보고 (예: PING)

6-2. 주요 포트 번호

80번: HTTP (웹)

443번: HTTPS (보안 웹)

21번: FTP (파일 전송)

22번: SSH (보안 셸)

25번: SMTP (메일 송신)

7. Packet Tracer의 서버 시스템

7-1. 웹 서비스(HTTP/HTTPS)

Packet Tracer의 서버 시스템은 웹 서비스를 제공한다.

HTTP (80번 포트)와 HTTPS (443번 포트)가 활성화되어 있다

기본 페이지는 index.html이며, 여러 페이지를 포함할 수 있다

테스트용 기본 웹 페이지가 제공된다

7-2. FTP 서비스

FTP는 파일 전송 프로토콜로서 서버에서 제공된다

서비스는 자동으로 시작되어 있다

7-3. 기타 서비스

서버 시스템은 간단한 웹 페이지 관리 기능을 제공한다.

웹 페이지 추가, 삭제 가능

여러 HTML 파일 관리

031. IPv6 주소 체계 이해 및 듀얼 스택 개념, 라우팅

1. IPv4와 IPv6의 차이

1-1. 주소 길이 비교
항목 IPv4 IPv6
비트 수 32비트 128비트
주소 개수 약 43억 개 약 2^128개
표기 십진수 점 표기 16진수 콜론 표기
1-2. IPv6가 필요한 이유

IPv4 주소 고갈

IoT 및 다양한 디바이스의 확산

일반 가전제품도 인터넷 연결 필요

2. IPv6 주소의 구조

2-1. 기본 표기법

IPv6 주소는 128비트를 16비트씩 8개 부분으로 나누어 표기한다.

⌘Text
2001:0DB8:0000:0000:0000:0000:1111:2222

각 부분: 16비트 (16진수 4자리)

구분자: 콜론(:)

전체: 8개 부분

3. IPv6 주소 축약 표기법

3-1. 선행 0 제거

16진수 각 부분의 맨 앞 0은 생략 가능하다.

⌘Text
2001:0DB8:0000:0001  →  2001:DB8:0:1
↑                          ↑
선행 0 제거됨
3-2. 연속된 0 제거 (double colon)

연속되는 0만으로 이루어진 부분은 :: 으로 표기 가능하다.

⌘Text
2001:0DB8:0000:0000:0000:0000:0000:0001

축약하면:

⌘Text
2001:DB8::1
또는
2001:DB8::0001

규칙:

:: 은 주소 내에서 한 번만 사용 가능

맨 앞 또는 맨 뒤의 0만 생략 가능

4. IPv6 주소의 분류

4-1. 글로벌 주소 (Global Address)

역할: IPv4의 공인 IP에 해당

용도: 인터넷 통신

시작 대역: 2001::/16, 2002::/16, 2003::/18 등

특징:

전 세계에서 유일

인터넷 통신 가능

4-2. 링크 로컬 주소 (Link Local Address)

시작: FE80::/10

프리픽스: /10

특징: 동일 네트워크(서브넷) 내에서만 통신 가능

설정: 자동으로 할당됨

예시:

⌘Text
FE80::1 (자동 생성)
4-3. 사이트 로컬 주소 (Site Local Address)

역할: IPv4의 사설 IP에 유사

범위: 특정 조직/사이트 내에서만 사용

프리픽스: FEC0::/10

특징:

조직 내부 통신만 가능

링크 로컬, 글로벌 주소와 통신 불가

5. IPv6 주소 통신 범위

5-1. 같은 유형의 주소 간 통신
출발지 목적지 통신 가능 여부
글로벌 주소 글로벌 주소 가능
링크 로컬 링크 로컬 (같은 네트워크) 가능
사이트 로컬 사이트 로컬 (같은 사이트) 가능
5-2. 다른 유형의 주소 간 통신

글로벌 ↔ 링크 로컬: 불가능

글로벌 ↔ 사이트 로컬: 불가능

링크 로컬 ↔ 사이트 로컬: 불가능

6. IPv4와 IPv6 혼용: 듀얼 스택

6-1. 듀얼 스택의 개념

하나의 인터페이스에 IPv4 주소와 IPv6 주소를 동시에 설정하는 방식이다.

⌘Text
인터페이스 GigabitEthernet 0/0
  IPv4: 192.168.1.1
  IPv6: 2001:DB8:1::1/64

장점:

레거시 IPv4와 새로운 IPv6 동시 지원

점진적 마이그레이션 가능

6-2. IPv4와 IPv6 미지원 네트워크 간 통신

네트워크 구성:

네트워크 A: IPv4만 지원

네트워크 B: IPv4만 지원

네트워크 C: IPv6만 지원

네트워크 D: IPv6만 지원

결과:

A ↔ B 통신: 가능 (IPv4)

C ↔ D 통신: 가능 (IPv6)

A/B ↔ C/D 통신: 불가능 (변환 필요)

7. IPv4와 IPv6 간 변환: 터널링

7-1. 터널링의 개념

IPv4와 IPv6 간 통신이 필요할 때 변환 기술을 사용한다.

기술 설명

6to4 터널 IPv6 네트워크를 통해 IPv4 패킷 전송
7-2. 터널링 사용 시기

IPv4와 IPv6가 모두 존재하는 혼합 환경

완전한 IPv6 전환 전 과도기

8. IPv6의 장점

032. VPN 개념

7. VPN(Virtual Private Network) 개요

7-1. VPN의 정의

Virtual Private Network는 공개 네트워크(인터넷) 위에 가상의 사설 네트워크를 구축하는 기술이다.

7-2. VPN의 역할

데이터 암호화: 전송되는 데이터의 기밀성 보장

인증: 통신 양쪽의 신원 확인

무결성 검증: 데이터 변조 여부 확인

8. VPN의 분류

8-1. 사이트 투 사이트 VPN (Site-to-Site VPN)

목적: 원격지 사무실 간 안전한 통신

대상: 네트워크 대 네트워크 간 연결

사용처: 기업 지사 간 통신

8-2. 리모트 액세스 VPN (Remote Access VPN)

목적: 원격 사용자의 기업 네트워크 접근

대상: 개별 사용자 대 네트워크

사용처: 재택근무, 출장 중 접근

033. 동적 NAT 및 PAT 설정의 원리와 동작 메커니즘 이해

1. 동적 NAT 설정의 기본 구조

1-1. 동적 NAT의 구성 요소

동적 NAT를 설정하기 위해서는 다음 세 가지가 필요하다:

  1. ACL 정책: 변환할 사설 IP 범위 지정

  2. NAT 풀: 변환되는 공인 IP 범위 정의

  3. 연결 명령: ACL과 NAT 풀을 연결

2. NAT 설정 전 준비

2-1. IP 주소 계획

토폴로지 예시:

사설 IP 대역: 192.168.1.0/24 (내부 네트워크)

공인 IP 대역: 20.0.0.0/24 (외부 인터페이스)

1:1 매핑: 내부 254대 + 외부 254대 (1:1 대응 가능)

1-2. 인터페이스 역할 정의

inside: 내부 네트워크 연결 인터페이스

outside: 외부 네트워크 연결 인터페이스

내부 주소 → 외부 주소로의 변환이 일어남

3. 동적 NAT 설정 과정

3-1. 1단계: ACL 정책 정의 (표준 ACL)

변환할 사설 IP 범위를 허용(permit)으로 지정한다.

⌘Cisco IOS
access-list 10 permit 192.168.1.0 0.0.0.255
← 192.168.1.0/24 네트워크의 모든 호스트를 허용

번호 10: ACL 정책의 이름(1~99는 표준 ACL)

permit: 이 주소를 NAT 변환 대상으로 지정

3-2. 2단계: NAT 풀 정의

변환될 공인 IP 범위를 지정한다.

⌘Text
ip nat pool NAT-TEST 20.0.0.1 20.0.0.254 netmask 255.255.255.0
← NAT-TEST라는 이름의 풀에 20.0.0.1~254를 할당

NAT-TEST: 풀의 이름

시작 IP: 20.0.0.1

끝 IP: 20.0.0.254

netmask: 서브넷 마스크 값

3-3. 3단계: ACL과 NAT 풀 연결

정의된 ACL과 NAT 풀을 연결하여 실제 변환을 수행한다.

⌘Text
ip nat inside source list 10 pool NAT-TEST
← ACL 10에 해당하는 출발지는 NAT-TEST 풀의 IP로 변환

6. 동적 NAT의 한계

6-1. IP 부족 문제

변환할 사설 IP 대역이 공인 IP 대역보다 크면 모든 호스트가 동시에 통신할 수 없다.

예시:

사설 IP: 254대

공인 IP: 62개만 할당

결과: 처음 62대만 변환 가능, 나머지는 불가능

7. PAT(Port Address Translation)

7-1. PAT의 개념

하나의 공인 IP에 여러 사설 IP를 대응시키기 위해 포트 번호를 함께 변환한다.

7-2. NAT와 PAT의 차이
항목 NAT PAT
변환 대상 IP 주소만 IP 주소 + 포트 번호
1:N 대응 불가능 가능
동시 통신 제한적 광범위
7-3. PAT 설정

동적 NAT 설정에서 마지막 명령에 overload 옵션만 추가한다.

⌘Text
ip nat inside source list 10 pool NAT-TEST overload
← overload 옵션이 PAT를 활성화

8. 가정용 공유기의 NAT/PAT

8-1. 공유기의 NAT/PAT 동작

외부 공인 IP: 하나만 할당받음 (예: 1.1.1.1)

내부 사설 IP: 여러 장치 (PC, 스마트폰, 태블릿 등)

포트 변환: 각 장치의 포트를 다르게 변환하여 구분

8-2. 일반적인 공유기 스펙

제품 사양에서 흔히 볼 수 있는 내용:

DHCP 기능

NAT 기능

PAT 기능 (최대 250세대 이상 대응 가능)

9-2. 실제 필드와의 차이

034. 확장 ACL 포트와 프로토콜 기반 세밀한 필터링

1. 확장 ACL의 실전 구성

1-1. 기본 구조

확장 ACL의 명령어 구조:

⌘Cisco IOS
access-list [ACL번호] [permit/deny] [프로토콜]
            [출발지IP] [출발지마스크] [목적지IP] [목적지마스크]
            [포트 조건] [포트번호]
1-2. 주요 파라미터

ACL번호: 100~199 범위 (확장 ACL)

permit/deny: 허용(permit) 또는 거부(deny)

프로토콜: tcp, udp, icmp 등

출발지: 패킷의 원본 주소

목적지: 패킷의 대상 주소

포트조건: eq(같음), gt(크다), lt(작다) 등

포트번호: 해당 서비스의 포트 (80, 443, 등)

2. 포트 번호와 서비스 매핑

2-1. 주요 포트와 프로토콜
포트 서비스 프로토콜 설명
80 HTTP TCP 일반 웹 서비스
443 HTTPS TCP 보안 웹 서비스
21 FTP TCP 파일 전송 프로토콜
포트 서비스 프로토콜 설명
22 SSH TCP 보안 셸 접속
25 SMTP TCP 메일 송신
53 DNS TCP/UDP 도메인 이름 해석
8 ICMP ICMP 핑(ping) 진단
2-2. ICMP와 PING

ICMP(Internet Control Message Protocol): 진단 및 오류 보고 프로토콜

PING: ICMP echo와 echo reply를 이용한 연결 진단

ICMP echo: 요청 메시지 (PING 명령)

ICMP echo reply: 응답 메시지 (라우터 또는 호스트의 응답)

따라서 양방향 PING이 작동하려면 두 개의 규칙이 필요할 수 있다:

⌘Cisco IOS
permit icmp [출발지] [목적지]      ← echo 허용
permit icmp [목적지] [출발지]      ← echo reply 허용

3. 포트 필터링의 실전 예제

3-1. HTTP(웹) 트래픽 필터링

특정 IP(예: 192.168.0.0/24)에서 웹 서버로의 웹 접속을 차단하는 예:

⌘Cisco IOS
access-list 100 deny tcp 192.168.0.0 0.0.0.255 [웹서버IP] eq 80

프로토콜: TCP (HTTP는 TCP 기반)

출발지: 192.168.0.0/24 (192.168.0.0부터 192.168.0.255까지)

목적지: 웹서버 IP 주소

조건: eq(equal, 같음) 80번 포트

결과: HTTP 웹 접속만 차단, 다른 포트는 허용

3-2. 특정 호스트와 네트워크 구분

ACL 설정 시 호스트와 네트워크를 구분하여 사용:

단일 호스트: IP 주소 + 와일드카드 마스크 0.0.0.0

⌘Cisco IOS
access-list 100 permit tcp 192.168.1.10 0.0.0.0 ...

네트워크 범위: IP 주소 + 와일드카드 마스크 (0이 아닌 부분)

⌘Cisco IOS
access-list 100 permit tcp 192.168.0.0 0.0.0.255 ...

host 키워드 (현대 IOS): 호스트를 명시적으로 표시

⌘Cisco IOS
access-list 100 permit tcp host 192.168.1.10 ...

2. ACL 관련 주요 사항

2-1. Extended ACL 적용 위치

Extended ACL은 목적지에 가까운 인터페이스에 적용하는 것이 효율적이다.

2-2. ACL 정책 추가 시 주의 사항

ACL 정책을 같은 번호(예: 100번)로 추가하면, 새 정책은 기존 목록의 맨 마지막에 추가된다. 덮어쓰기가 아니다.

⚠️ ACL 정책 중간에 잘못된 항목이 있을 경우, 기존 정책 전체를 삭제( no access-list 번

호)하고 처음부터 다시 입력해야 한다.

2-3. 호스트 주소와 대역 주소의 와일드카드
유형 표기 방법
단일 호스트 host [IP주소] 또는 [IP주소] 0.0.0.0
대역대(네트워크) [네트워크 주소] [와일드카드 비트값]

3. NAT와 ACL의 상호작용

NAT가 적용된 환경에서 ACL을 테스트할 때 주의할 점이 있다. NAT에 의해 출발지 IP가 변환된 이후에 ACL에서 확인하는 출발지 주소가 달라질 수 있다.

상황 결과
NAT 적용 전 ACL 테스트 내부 IP(사설 IP)를 출발지로 ACL 규칙 적용
NAT 적용 후 ACL 테스트 변환된 외부 IP를 출발지로 인식 → ACL 규칙 불일치 가능

⚠️ NAT와 ACL을 함께 사용할 경우, ACL을 먼저 테스트하고 이후 NAT를 적용하거나, NAT 변환 후 주소를 기준으로 ACL 규칙을 재설정해야 한다.

4. L2 스위치 동작 원리

L2 스위치는 물리적으로 정상 연결된 상태라면 VLAN 등 별도 설정 없이도 통신이 가능하다. VLAN 설정이 필요한 경우에는 스위치에서 별도로 설정을 진행해야 한다.

037. NAT 개념 정리 및 가상화 환경 소개

1. NAT(Network Address Translation) 개념 정리

1-1. NAT가 필요한 이유

사설(Private) IP는 인터넷으로 직접 나갈 수 없는 주소이다. 인터넷에 접속하려면 공인 (Public) IP로 변환되어야 하며, 이 변환 과정을 담당하는 것이 NAT이다.

구분 설명
사설 IP 인터넷 직접 통신 불가. 내부 네트워크 전용 주소
공인 IP 인터넷 통신에 사용되는 주소
NAT 사설 IP ↔ 공인 IP 간의 주소 변환
1-2. NAT의 종류
종류 설명
다이나믹 NAT 공인 IP 범위(풀)를 지정하고, 사설 IP가 나갈 때 풀에서 하나를 자동으로 매핑
스태틱 NAT 특정 사설 IP를 특정 공인 IP에 1:1로 고정 매핑
1-3. NAT 설정 구조
항목 내용
ACL 설정 변환 대상이 될 사설 IP 대역을 퍼미트(permit) 처리
NAT Inside 변환되어야 할 내부 IP가 있는 인터페이스에 적용
NAT Outside 공인 IP(외부)가 있는 인터페이스에 적용

설정 완료 후 show ip nat translations 명령으로 주소 변환 테이블을 확인할 수 있다.

2. 클라이언트-서버 네트워크

현재 대부분의 네트워크는 클라이언트-서버(C/S) 구조로 이루어져 있다.

구분 역할
서버(Server) 정보나 서비스를 제공하는 쪽
클라이언트(Client) 정보나 서비스를 요청·이용하는 쪽

예를 들어, 특정 장비가 웹 서버 역할을 할 경우 해당 장비에 웹 요청을 보내는 PC가 웹 클라이언트가 된다. 동일한 장비가 FTP 서버 역할도 동시에 수행할 수 있다.

3. 가상화(Virtualization) 개념

3-1. 가상 머신(VM)이란

가상 머신(VM, Virtual Machine)은 실제 운영체제 위에 소프트웨어적으로 생성한 가상의 컴퓨터이다. 윈도우즈가 설치된 호스트 컴퓨터 위에 가상 머신을 생성하여 그 안에서 다른 운영체제(리눅스 등)를 설치하고 운용할 수 있다.

용어 설명
호스트 OS 실제 물리적 컴퓨터에 설치된 운영체제 (예: Windows)
게스트 OS 가상 머신 안에 설치된 운영체제 (예: Rocky Linux)
VM(Virtual Machine) 가상 머신. 소프트웨어로 만들어진 가상 컴퓨터
3-2. 가상 머신 생성 도구

2. VPN(Virtual Private Network) 개념

2-1. VPN이 필요한 이유

본사와 지사 간 데이터를 전송할 때, 두 사이트를 연결하는 회선은 신뢰성이 없는 공용망 (퍼블릭망, 인터넷망)을 통과하게 된다.

구분 설명
가장 이상적인 방
법		 본사와 지사를 물리적인 전용선으로 직접 연결 → 외부 망을 거치지 않아 보안상
최적
현실적인 제약 지리적 거리(서울↔부산, 국내↔해외 등), 비용 문제로 인해 전용선 연결이 불가
능한 경우가 대부분
VPN의 역할 인터넷망을 통과하지만, 가상의 전용선(터널)을 만들어 전용선과 유사한 효
과를 제공

⚠️ V(Virtual)는 '가상'을 의미한다. 물리적으로는 인터넷 회선을 따라 데이터가 이동하지만, 외부에서는 터널 안으로 들어가는 것처럼 보인다.

3. VPN 터널링

3-1. 터널의 역할

VPN 터널을 구축하면 본지사 간 데이터가 물리적 회선을 따라 이동하면서도, 외부에서는 어떤 경로를 거쳐 어떤 데이터가 이동하는지 확인할 수 없다.

기차가 터널에 진입하면 외부에서 기차의 위치나 경로를 알 수 없는 것과 유사하다.

3-2. VPN 터널이 제공하는 기능
기능 내용
터널링 데이터 경로를 숨겨 외부 노출 방지
인증(Authentication) 데이터를 주고받는 상대방이 맞는지 검증
암호화(Encryption) 주고받는 데이터를 암호화하여 내용 보호

4. GRE 터널링

4-1. GRE란

GRE(Generic Routing Encapsulation)는 일반적인 경로 캡슐화 프로토콜이다. 패킷을 캡 슐화하여 터널로 전송하는 방식이다.

⚠️ GRE 자체는 암호화나 인증 기능을 제공하지 않는다. '일반적(Generic)'이라는 이름에서 알 수 있듯이, 단순히 터널만 생성하는 방식이다. 암호화가 필요할 경우 별도로 IP Security(IPSec)를 적용해야 한다.

4-2. 터널 인터페이스의 특성

라우터에서 GRE 터널을 구성할 때는 터널 인터페이스(Tunnel Interface)라는 논리적 인터페이스를 생성한다.

구분 설명
물리적 인터페이스 실제 케이블이 연결된 인터페이스 (Serial, GigabitEthernet 등)
논리적 인터페이스 관리자가 소프트웨어적으로 생성하는 인터페이스 (루프백, 터널 등)
터널 인터페이스 VPN 터널 구축에 사용하는 논리적 인터페이스

터널 인터페이스는 이전에 학습한 OSPF에서 사용하던 루프백(Loopback) 인터페이스와 유사한 논리적 인터페이스이다.

4-3. 터널 구성 요소

터널 인터페이스 설정 시 지정해야 하는 주요 항목은 다음과 같다.

항목 내용
IP 주소 터널 전용 네트워크 대역의 주소를 할당
터널 모드 GRE 방식 및 대상 프로토콜(IPv4) 지정
터널 소스(Source) 터널의 출발점이 되는 물리적 인터페이스
항목 내용
터널 목적지(Destination) 터널이 향하는 상대방 라우터의 IP 주소

5. VPN 라우팅 설정

5-1. 스태틱 라우팅과 터널

터널을 구축하더라도, 어떤 트래픽이 터널로 전송되는지를 라우팅으로 명시해 주어야 한다. 본지사 간 단일 경로 구성에서는 일반적으로 스태틱 라우팅을 사용한다.

본사 라우터에서는 지사 네트워크로 가는 경로를 터널 인터페이스의 IP를 경유지로 설정

지사 라우터에서도 동일하게 본사 네트워크로 가는 경로를 터널 인터페이스의 IP를 경유지로 설정

⚠️ 스태틱 라우팅은 양방향으로 모두 설정해야 통신이 가능하다. 한쪽에만 설정하면 통신이 이루어지지 않는다.

5-2. 터널 구축 전후 경로 비교
구분 트레이스루트 결과
터널 구축 전 물리적 시리얼 회선을 따라 중간 경유지(라우터 IP)들이 표시됨
터널 구축 후 게이트웨이 → 터널 인터페이스 IP 순서로 표시되어, 중간 경로가 은폐됨

6. IP Security(IPSec) 개요

GRE 터널만으로는 암호화와 인증이 제공되지 않는다. 터널 안에서 주고받는 데이터의 암호화 및 인증을 위해서는 IP Security(IPSec)를 터널에 별도로 적용한다.

기능 구분 제공 여부
GRE 터널링 (기본) 경로 은폐 ○ / 암호화 ✕ / 인증 ✕
GRE + IPSec 적용 경로 은폐 ○ / 암호화 ○ / 인증 ○

082. ACL 심화

1. ACL 기본 적용 방향

네트워크 경계에 있는 라우터(예: R2)에 ACL 정책을 설정하여 내부망과 외부망 간의 트래픽을 제어한다. 내부망(R1, R2)과 외부망(R3, R4)의 경계에 위치한 장비에 정책을 적용하는 것이 원칙이다.

2. TCP Established 옵션

2-1. Established의 의미

TCP는 데이터 전송 전 3-Way Handshaking 과정을 거쳐 연결을 수립한다. established 옵션은 이 연결 수립이 완료된 상태, 즉 TCP 연결이 성립된(established) 패킷에만 정책을 적용한다.

2-2. Established 옵션의 효과

permit tcp any any established 를 설정하면, 내부에서 먼저 시작한 TCP 세션의 응답 패킷은 허용되고, 외부에서 먼저 시작한 TCP 연결 시도는 차단된다.

시나리오 결과
내부 → 외부 TCP 연결 후 응답 패킷 귀환 허용
외부 → 내부 TCP 연결 시도 차단
2-3. Established 옵션의 한계
프로토콜 Established 옵션 적용 여부
TCP 적용 가능
UDP 적용 불가
ICMP 적용 불가

TCP Established는 TCP 트래픽에만 효과가 있으며, UDP·ICMP에는 동일한 효과를 기 대할 수 없다. 이러한 한계를 보완한 것이 Reflected ACL(RACL)이다.

2-4. ACL 정책 설정 확인

적용 전·후 상태 비교를 위해 아래 명령어로 정책 및 매치 수를 확인할 수 있다.

⌘Cisco IOS
show access-list       ← 전체 ACL 정책 및 매치 수 확인
show ip access-list    ← IP ACL 정책 확인

3. Reflected ACL (RACL)

3-1. 개념

Reflected ACL은 내부 사용자를 위한 ACL이다.

내부에서 출발하여 외부로 나간 패킷이 돌아올 때는 허용한다.

외부에서 먼저 시작해서 내부로 들어오는 패킷은 차단한다.

TCP뿐만 아니라 UDP, ICMP 등 모든 프로토콜에 적용된다.

실제 환경에 RACL을 적용하면 내부 사용자는 인터넷 등 외부 통신이 자유롭고, 외부에서는 어떤 트래픽도 내부로 진입할 수 없다.

3-2. RACL 동작 원리: 임시 ACL

RACL은 고정된 ACL 외에 임시 ACL(Reflexive ACL)을 자동으로 생성한다.

구분 설명
일반 ACL (관리자 설정) reflect 키워드를 사용하여 반사 대상 트래픽을
정의
임시 ACL (시스템 자동 생성) 내부에서 시작한 패킷의 출발지·목적지 정보를 기
반으로 동적으로 생성됨

임시 ACL의 내용은 테스트 내용에 따라 계속 변경된다.

임시 ACL은 show access-list 결과의 Reflexive 항목으로 확인할 수 있다.

외부에서 차단된 패킷은 임시 ACL에 등록되지 않는다(드랍 처리).

3-3. RACL 정책 구조

RACL은 두 개의 ACL 정책으로 구성된다.

ACL 이름 (예시) 키워드 역할 인터페이스 적용 방향
RACL (메인 정책) reflect 내부에서 출발하는 트
래픽을 반사 대상으로
지정		 out 방향
test (보조 정책) evaluate 반사 정책을 점검(확인) in 방향
⌘Cisco IOS
permit tcp any any reflect RACL-test    ← TCP 반사 설정
permit udp any any reflect RACL-test    ← UDP 반사 설정
permit icmp any any reflect RACL-test   ← ICMP 반사 설정

reflect 뒤에 입력하는 이름은 임시 ACL의 이름이 된다. 관리자가 임의로 지정할 수 있다.

3-4. RACL 정책의 OSPF 허용

RACL 정책이 적용된 인터페이스에서는 OSPF 헬로 패킷도 영향을 받는다. OSPF 라우팅이 중단되지 않도록 OSPF 트래픽을 명시적으로 허용하는 규칙을 정책의 첫 번째 줄에 작성해야 한다.

⌘Text
permit ospf host [R3의 IP] any    ← OSPF 헬로 패킷 허용

외부 → 내부 HTTP(TCP) TCP 차단 (Unreachable)

4. Dynamic ACL (DACL)

4-1. 개념

Dynamic ACL은 외부 사용자를 위한 ACL이다.

외부 사용자가 내부 망에 접속을 시도할 때, 경계 라우터에서 인증(Authentication) 절차를 요구한다.

인증에 성공하면 내부 접속을 허용하는 임시 ACL을 생성한다.

인증에 실패하면 내부 접속을 차단한다.

4-2. DACL 동작 원리
단계 설명
1 외부 사용자가 내부로 트래픽 시도 → DACL 정책
적용으로 차단
2 외부 사용자가 경계 라우터(R2)로 텔넷 접속 →
인증 요구
3-A 인증 성공 → 임시 ACL 생성 → 내부 트래픽 허용
3-B 인증 실패 (3회 실패 시 연결 종료) → 내부 트래
픽 계속 차단
4-3. DACL 정책의 키워드
⌘Cisco IOS
permit ip any any dynamic DACL    ← dynamic 키워드로 동적 ACL 지정

dynamic 키워드 뒤에 오는 이름은 동적 ACL의 이름이다.

RACL의 reflect 에 대응하는 역할을 한다.

4-4. DACL에서의 인증 설정

별도의 인증 서버 없이 테스트할 경우, 경계 라우터 자체에 텔넷 인증을 설정하여 사용한다.

⌘Text
enable password [패스워드]     ← Enable 모드 진입 패스워드 설정
line vty 0 4
  password [패스워드]          ← 텔넷 접속 시 인증 패스워드 설정
  login
4-5. 임시 ACL 생성 확인

DACL도 RACL과 마찬가지로 인증 성공 후 show access-list 결과에서 임시 ACL이 생성된 것을 확인할 수 있다. 인증 실패 시에는 임시 ACL이 생성되지 않는다.

⚠️ 한번 인증에 성공하여 생성된 임시 ACL은 캐시에 일정 시간 남아있을 수 있다. 이후 인증 실패를 테스트할 때는 시간 경과 후 또는 장비 재부팅 후에 확인한다.

6. 정책 삭제 방법

ACL 정책 삭제 시에는 인터페이스에 적용된 정책을 먼저 제거한 후 ACL 정책 자체를 삭제해야 한다.

⌘Cisco IOS
# 1단계: 인터페이스 적용 제거
interface f0/1
  no ip access-group [정책이름] in
  no ip access-group [정책이름] out
# 2단계: ACL 정책 삭제
no ip access-list extended [정책이름]

삭제 후 show access-list 로 정책이 모두 제거되었는지 확인한다.

1. GNS3 개요

4. 장비 시작과 인터페이스 활성화

4-1. 녹색 불과 no shutdown의 차이

GNS3에서 장비를 시작하면 토폴로지 창의 연결선이 녹색으로 표시된다. 그러나 이 녹색 불 은 장비가 켜진 상태(Power On)를 의미할 뿐, 인터페이스가 활성화된 상태를 의미하지 않는다.

⚠️ 패킷트레이서와 달리 GNS3에서는 장비를 시작한 후 반드시 각 인터페이스에서 no

shutdown 명령을 직접 입력해야 인터페이스가 활성화된다. 녹색 불만 보고 no shutdown 이 된 것으로 착각해서는 안 된다.

4-2. 콘솔 창 접근 방법
방법 설명

5. 디버깅 기능

5-1. GNS3 디버깅의 특징

GNS3는 실제 장비의 IOS 이미지를 사용하기 때문에 debug 명령어를 통한 디버깅이 가능하다. 이 기능을 통해 장비끼리 실시간으로 주고받는 패킷 내용을 콘솔에서 확인할 수 있다.

5-2. 주요 디버깅 명령어

아래 명령어는 모두 Enable 모드에서 실행한다.

명령어 설명
debug ip packet 장비에서 주고받는 모든 IP 패킷 정보 출력
debug ip ospf hello OSPF Hello 패킷 송수신 내용 출력
debug ip ospf adj OSPF 인접 관계(Adjacency) 이벤트 출력
undebug all 모든 디버깅 중지 ( u all 로 단축 입력 가능)
5-3. 디버깅 출력 내용 이해

OSPF 디버깅 시 목적지 IP로 224.0.0.x 형태의 주소가 나타날 수 있다. 이는 D클래스(멀티 캐스트) 주소로, OSPF가 라우터 그룹에 정보를 일제히 전달할 때 사용하는 예약된 주소이다.

OSPF 멀티캐스트 주소 용도
224.0.0.5 모든 OSPF 라우터에게 전달
224.0.0.6 DR/BDR 라우터에게 전달

⚠️ 디버깅을 켜둔 상태로 계속 두면 메시지를 출력하기 위해 장비 자원을 지속 소모한다. 실제 현장에서도 필요한 정보를 확인한 후 반드시 undebug all 로 디버깅을 중지해야 한다.

6. 프로젝트 저장 방법

6-1. GNS3의 저장 단위

GNS3는 패킷트레이서와 달리 프로젝트 단위로 파일을 저장한다. 단일 파일 저장(Save)이 없으며, File 메뉴에는 Save 항목이 없고 New Blank Project 및 Open Project만 존재한다.

6-2. 올바른 저장 절차
단계 내용
1단계 각 장비 콘솔에서 write memory 또는 copy
run start 명령으로 장비별 설정 저장
2단계 상단 도구 모음의 정지(Stop) 버튼을 클릭하여 모
든 장비를 중지 상태로 전환
3단계 모든 장비가 중지된 상태에서 창(X)을 닫으면
GNS3가 프로젝트 경로에 자동 저장

⚠️ 장비를 중지하지 않은 상태에서 창을 닫으면 저장이 정상적으로 이루어지지 않는다.

6-3. 저장된 프로젝트 불러오기

  1. GNS3 실행 후 데스크탑 서버 녹색 불 확인

  2. File → Open Project 또는 도구 모음의 Open 클릭

  3. 저장된 프로젝트 폴더(GNS3 → projects → 프로젝트명)에서 아이콘 더블클릭

6-4. 변경사항 저장 습관

GNS3 장비 설정 변경 시 변경사항이 생길 때마다 write memory 또는 copy run start 로 즉시 저장하는 습관이 필요하다.

7. 기본 토폴로지 구성 요건

RACL, DACL, Zone-Based FW 등 보안 정책 실습을 진행하기 위한 사전 조건으로, GNS3 토폴로지에서 R1부터 R4까지 모든 구간에 통신이 가능해야 한다. 통신이 가능한 상태를 만들기 위해서는 IP 주소 설정과 라우팅(OSPF) 설정이 선행되어야 한다.

라우팅이 완료되지 않으면 이후 보안 정책 실습을 정상적으로 진행할 수 없다.
