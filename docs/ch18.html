043. Apache 설정 적용과 재시작, 웹 문서 구조, MariaDB 초기 보안 설정

1. 설정 파일 변경 후 서비스 재시작

httpd.conf 설정 파일에서 단 한 글자라도 변경하면 반드시 서비스를 재시작해야 변경 내용이 적용된다.

systemctl restart httpd    ← 웹 서비스 재시작
명령 동작
systemctl start 서비스명 서비스 시작
systemctl stop 서비스명 서비스 중지
systemctl restart 서비스명 서비스 재시작
systemctl status 서비스명 서비스 상태 확인

설정 파일 수정 후 재시작하지 않으면 변경 내용이 반영되지 않는다.

2. 웹 문서 디렉토리 구조

2-1. Document Root 아래 디렉토리 생성

클라이언트에게 제공할 웹 문서는 모두 /var/www/html 디렉토리 안에 위치한다. 하위 디렉토리를 생성하여 파일을 분류할 수 있다.

mkdir /var/www/html/test               ← test 디렉토리 생성
cd /var/www/html                       ← Document Root로 이
동
ls                                     ← 현재 파일 목록 확인
2-2. 파일 복사 — cp

리눅스에서 파일 복사 명령어는 cp 이다.

cp 원본파일 대상파일    ← 기본 형식
cp test/test.html index.html    ← test 디렉토리의 test.html을
현재 디렉토리에 index.html로 복사

대상 경로에 디렉토리 경로가 없으면 현재 작업 디렉토리를 의미한다.

2-3. 시작 페이지(index.html)

브라우저 주소창에 파일 이름 없이 서버 IP만 입력했을 때 자동으로 표시되는 페이지가 있다. 이는 Apache가 시작 페이지로 등록된 파일 이름을 자동으로 찾기 때문이다.

자동 인식되는 시작 페이지 파일명

index.html
index.php

/var/www/html 디렉토리 안에 index.html 또는 index.php 파일이 있으면, 브라우저에서 파일 이름을 생략해도 해당 파일이 자동으로 표시된다.

3. 웹 서버와 데이터베이스 서버의 관계

3-1. 프론트엔드와 백엔드
구분 역할 예시
프론트엔드 클라이언트에게 보여지는 화면 HTML, CSS, JavaScript
백엔드 데이터 처리 및 저장 PHP, DB 서버

데이터베이스(DB) 서버는 백엔드에 해당하며, 사용자 정보·게시글 등 다양한 데이터를 저장하고 질의(Query)에 응답하는 역할을 한다.

3-2. 웹 서버와 DB 서버 간 동작 흐름

클라이언트가 로그인 페이지에서 아이디와 패스워드를 입력하면 다음과 같이 처리된다.

클라이언트 → (로그인 정보 전송) → 웹 서버 → (SQL 질의) → DB 서버
         ←  (로그인 성공/실패)  ←           ← (결과 반환) ←

웹 서버와 DB 서버는 물리적으로 별도의 시스템으로 구성하는 것이 보안상 권장된다. 하나의 시스템에 모두 구성하면 보안 위험이 높아진다.

3-3. SQL이란

SQL (Structured Query Language) — 구조화된 질의 언어. 데이터베이스에 데이터를 저장하고, 검색하고, 관리하기 위한 언어이다.

종류 설명
MySQL 오픈소스 RDBMS
MariaDB MySQL 기반 오픈소스 RDBMS
MSSQL Microsoft의 SQL 서버
NoSQL 정형화되지 않은 데이터 처리에 적합 (빅데이터 환경)

4. MariaDB 서비스 시작

systemctl start mariadb    ← MariaDB 서비스 시작
systemctl status mariadb   ← 서비스 상태 확인

5. MariaDB 초기 보안 설치 —

mysql_secure_installation

MariaDB 설치 직후에는 초기 보안 설치 작업이 필요하다.

mysql_secure_installation

실행하면 아래 순서로 질문이 나타난다.

질문 입력값 설명
현재 root 패스워드 입력 Enter (입력 없이) 초기에는 패스워드 없음
Unix socket 인증 방식 사용 여부 Y Unix socket 방식 인증 사용
root 패스워드 변경 여부 Y DB 접속용 root 패스워드 설정
질문 입력값 설명
익명 사용자 제거 여부 Y 보안상 익명 사용자 제거
원격에서 root 로그인 금지 여부 Y 원격에서 root 접속 차단
테스트 DB 제거 여부 Y 불필요한 테스트 DB 제거
권한 테이블 재로드 여부 Y 변경사항 즉시 적용

⚠️ 여기서 변경하는 root 패스워드는 데이터베이스에 접속하는 root 사용자의 패스워드이다. 리눅스 시스템 로그인 패스워드와는 별개이다. 혼동하지 않도록 주의한다.

원격에서 root 계정으로 DB에 직접 접속하는 것은 보안상 권장하지 않는다. 일반 사용자를 별도로 생성하여 접속하는 것이 원칙이다.

6. MariaDB 접속

mysql -u root -p    ← root 사용자로 DB 접속 (-u: user, -p: pa
ssword 입력)

접속 성공 시 MariaDB [(none)]> 프롬프트가 표시된다. (none) 은 현재 선택된 데이터베이스가 없음을 의미한다.

7. 데이터베이스 목록 확인

show databases;    ← 현재 존재하는 데이터베이스 목록 출력

SQL 구문 마지막에는 반드시 세미콜론( ; )을 입력한다.

MariaDB 설치 직후에는 기본으로 3개의 데이터베이스가 존재한다.

8. 외부에서 MariaDB에 접속하기 위한 조건

MariaDB의 기본 서비스 포트는 3306이다. 외부에서 DB 서버에 접속하려면 방화벽에서 해당 포트를 허용해야 한다.

firewall-cmd --permanent --add-port=3306/tcp
firewall-cmd --reload

앞으로 배우는 모든 서버 서비스에서 공통으로 적용되는 원칙: 서비스 시작 → 방화벽 포트 허용 순서로 진행한다.

045. MariaDB SQL 기초 CRUD 개념, 데이터베이스·테이블 생성, 필드 추가

1. MariaDB 기본 데이터베이스 구조

MariaDB 설치 후 기본으로 존재하는 데이터베이스 3개는 다음과 같다.

데이터베이스 이름 역할
information schema
_		 MySQL/MariaDB 내부 테이블·필드 정보 저장
performance schema
_		 데이터베이스 성능 관련 정보 저장
mysql 사용자 계정 및 패스워드 정보 저장

mysql 데이터베이스 안에 보안 설치 시 설정한 사용자 정보와 패스워드(암호화 형태)가 저장된다.

2. 데이터베이스 구조 개념

데이터베이스의 기본 계층 구조는 다음과 같다.

데이터베이스 (Database)
  └── 테이블 (Table)
        └── 필드 / 칼럼 (Field = Column)
              └── 실제 데이터 (Data)

필드(Field)와 칼럼(Column)은 동일한 개념이다.

3. SQL 주요 명령어 — 데이터 조회

3-1. 데이터베이스 선택 — use
use 데이터베이스명;    ← 사용할 데이터베이스 선택

접속 후 프롬프트가 MariaDB [(none)]> 에서 MariaDB [데이터베이스명]> 으로 변경된다.

3-2. 테이블 목록 확인 — show tables
show tables;    ← 현재 데이터베이스 안의 테이블 목록 출력
3-3. 테이블 데이터 조회 — select
select * from 테이블명;               ← 모든 필드의 데이터 조회
select 필드1, 필드2 from 테이블명;    ← 지정한 필드의 데이터만 조
회
  • (별표)는 모든 필드를 의미한다.
3-4. 테이블 필드 구조 확인 — desc
desc 테이블명;    ← 테이블의 필드(칼럼) 구조 출력

desc 실행 결과에서 확인할 수 있는 정보는 다음과 같다.

항목 설명
Field 필드 이름
Type 데이터 자료형 및 자릿수
Null 값이 비어 있어도 되는지 여부 (YES/NO)
Key 기본 키(Primary Key) 등 키 설정

4. CRUD — 데이터베이스 4대 기본 기능

약자 이름 의미
C Create 데이터 생성 (삽입, INSERT)
R Read 데이터 조회 (검색, SELECT)
U Update 데이터 수정 (변경, UPDATE)
D Delete 데이터 삭제 (제거, DELETE)

데이터베이스에서 사용하는 모든 SQL 명령어는 이 CRUD 기능 중 하나에 해당한다.

5. 데이터베이스 생성과 삭제

create database 데이터베이스명;    ← 데이터베이스 생성
drop database 데이터베이스명;      ← 데이터베이스 삭제
show databases;                    ← 데이터베이스 목록 확인

SQL 구문 마지막에는 반드시 세미콜론( ; )을 입력한다.

6. 테이블 생성 — create table

테이블은 생성 시 반드시 최소 하나의 필드(칼럼)를 함께 정의해야 한다.

create table 테이블명 (
  필드명1 자료형(자릿수),
  필드명2 자료형(자릿수),
  필드명3 자료형(자릿수)
);
6-1. 주요 자료형
자료형 설명 예시
char(n) 고정 길이 문자형 (n글자) char(10)
varchar(n) 가변 길이 문자형 (최대 n글자) varchar(20)
int(n) 정수형 (최대 n자리) int(4)
6-2. 테이블 생성 예시
create table student (
  name varchar(10),
  date int(4),
  phone int(10)
);

두 개 이상의 필드는 쉼표( , )로 구분하고, 전체를 괄호( () )로 감싼다.

필드 이름과 자료형 사이에는 반드시 공백이 있어야 한다.

7. 필드 추가 — alter table ... add

기존 테이블에 새로운 필드를 추가할 때 alter table 명령어를 사용한다.

7-1. 기본 추가 (마지막 위치)
alter table 테이블명 add 필드명 자료형(자릿수);

위치를 지정하지 않으면 추가된 필드는 테이블의 맨 마지막에 위치한다.

7-2. 특정 필드 뒤에 추가 — after
alter table 테이블명 add 필드명 자료형(자릿수) after 기존필드명;
7-3. 첫 번째 위치에 추가 — first
alter table 테이블명 add 필드명 자료형(자릿수) first;
7-4. 여러 필드 동시 추가
alter table 테이블명 add (
  필드명1 자료형(자릿수),
  필드명2 자료형(자릿수)
) after 기존필드명;
7-5. 필드 추가 명령 예시 요약
목적 명령어 예시
마지막에 age 필드 추가 alter table student add age int(3);
date 뒤에 address 필드 추
가		 alter table student add address varchar(10) after
date;
맨 앞에 mbti 필드 추가 alter table student add mbti char(4) first;

046. MariaDB 필드 수정·삭제, 데이터 삽입·수정·삭제 SQL

1. 필드 이동(재정렬) — alter table ... modify

이미 존재하는 필드의 순서를 변경할 때 modify 를 사용한다.

-- 특정 필드를 맨 앞으로 이동
alter table 테이블명 modify 필드명 자료형(자릿수) first;
-- 특정 필드를 지정 필드 뒤로 이동
alter table 테이블명 modify 필드명 자료형(자릿수) after 기준필드
명;
작업 명령어 키워드
새 필드 추가 add
기존 필드 순서 변경 modify

add 는 없던 필드를 추가할 때, modify 는 이미 있는 필드를 수정하거나 순서를 바꿀 때 사용한다.

2. 필드 삭제 — alter table ... drop

기존 테이블에서 특정 필드를 삭제할 때 drop 을 사용한다.

alter table 테이블명 drop 필드명;

필드를 삭제할 때는 자료형을 지정하지 않아도 된다.

테이블이나 데이터베이스 자체를 삭제할 때도 drop 을 사용한다. ( drop table , drop

database )

3. 필드/데이터 관련 명령어 비교

대상 작업 명령어
필드(열) 추가 alter table ... add
필드(열) 수정/이동 alter table ... modify
필드(열) 삭제 alter table ... drop
데이터(행) 삽입 insert into
데이터(행) 수정 update ... set
데이터(행) 삭제 delete from

4. 데이터 삽입 — insert into

4-1. 모든 필드에 데이터 삽입
insert into 테이블명 values (값1, 값2, 값3, ...);

문자 데이터는 작은 따옴표( ' )로 감싼다. 숫자 데이터는 따옴표 없이 입력한다.

4-2. 특정 필드에만 데이터 삽입
insert into 테이블명 (필드명1, 필드명2) values (값1, 값2);

지정하지 않은 필드에는 NULL (빈 값)이 자동으로 입력된다. 단, 해당 필드의 Null 설정이

YES 인 경우에만 허용된다.

4-3. NULL 값 처리
desc 결과의 Null 값 의미
YES 값이 비어있어도(NULL) 허용
NO 반드시 값이 있어야 함

5. 데이터 수정 — update ... set

5-1. 특정 필드의 모든 데이터 일괄 변경
update 테이블명 set 필드명=새값;
5-2. 특정 조건의 데이터만 변경 — where
update 테이블명 set 필드명=새값 where 조건필드명='조건값';
5-3. 여러 필드 동시 변경
update 테이블명 set 필드명1=새값1, 필드명2=새값2 where 조건필드명
='조건값';

where 를 생략하면 해당 테이블의 모든 행이 일괄 변경된다.

where 를 사용하면 조건에 해당하는 특정 행만 선택적으로 변경된다.

6. 데이터 삭제 — delete from

6-1. 특정 조건의 데이터 삭제
delete from 테이블명 where 조건필드명='조건값';
6-2. 테이블 내 모든 데이터 삭제
delete from 테이블명;

where 를 생략하면 테이블 안의 모든 데이터(행)가 삭제된다. 테이블 구조(필드)는 남아있다.

테이블 자체를 삭제하려면 drop table 테이블명을 사용한다.

065. rsyslog 연결 확인과 MariaDB 연동 준비

1. rsyslog 클라이언트-서버 연결 확인

1-1. tail 명령을 통한 실시간 로그 모니터링

서버에서 tail -f 명령으로 로그 파일을 실시간으로 모니터링하면서 클라이언트에서 이벤트를 발생시키면, 클라이언트 로그가 서버에 실시간으로 기록된다.

클라이언트에서 이벤트 발생 시 서버의 /var/log/messages 에 해당 내용이 자동으로 수 신된다.

수신된 로그에는 클라이언트의 호스트 네임이 함께 표시된다.

클라이언트에서 발생한 이벤트가 서버에 기록되는 것이지, 서버에서 직접 이벤트가 발생한 것이 아님을 구분해야 한다.

1-2. 연결 상태 확인 명령어
lsof -i tcp::514         ← TCP 514번 포트 연결 목록 확인
netstat -natp | grep 514 ← 514번 포트 연결 상태 필터링

로그를 주고받은 직후에는 ESTABLISHED 상태가 표시된다.

상태 의미
LISTEN 연결 대기 중 (아직 클라이언트가 연결하지 않음)
ESTABLISHED 연결이 성립된 상태 (로그 전송 중 또는 직후)

⚠️ TCP와 UDP 중 하나만 연결이 성립된다. 두 개가 동시에 ESTABLISHED 상태가 되 지는 않는다.

2. rsyslog 연결 문제 체크리스트

연결이 되지 않을 경우 다음 항목을 순서대로 확인한다.

항목 확인 내용
패키지 설치 서버·클라이언트 양쪽에 rsyslog , rsyslog-doc 설치 여부
서버 설정 파일 /etc/rsyslog.conf 의 TCP/UDP 입력 모듈 추가 여부 (대소문자 확인)
클라이언트 설정 파일 /etc/rsyslog.conf 마지막 줄에 서버 IP 및 포트 설정 여부
방화벽 서버에서 TCP/UDP 514번 포트 허용 및 reload 여부
서비스 시작 서버·클라이언트 양쪽에서 rsyslog 서비스 실행 여부
클라이언트 IP 입력 클라이언트 설정 파일에 서버의 IP가 올바르게 입력되었는지 확인

⚠️ Syntax error(문법 오류)는 철자 오류로 발생하며, connection refused 는 서버 설정 또는 방화벽 문제일 가능성이 높다.

3. 서비스 상태의 enable/disabled 개념

systemctl enable rsyslog    ← 재부팅 후에도 자동 시작 등록

systemctl status 명령에서 disabled 상태로 표시되어 있어도, 현재 서비스가 running (활성화) 상태라면 당장의 운영에는 문제가 없다. 다만 disabled 는 재부팅 후 서비스가 자동으로 시작되지 않음을 의미하므로, 영구 운용을 위해서는 enable 로 설정해야 한다.

4. MariaDB와 rsyslog 연동 준비

4-1. MariaDB 서비스 확인 및 시작

로그를 데이터베이스에 저장하려면 서버에서 MariaDB 서비스가 실행 중이어야 한다.

systemctl status mariadb       ← MariaDB 서비스 상태 확인
dnf install -y mariadb-server  ← MariaDB가 없을 경우 설치
systemctl start mariadb        ← MariaDB 서비스 시작
4-2. rsyslog-mysql 패키지

rsyslog와 MariaDB(MySQL 계열)를 연결하기 위한 전용 패키지가 필요하다.

dnf install -y rsyslog-mysql    ← rsyslog와 MariaDB를 연결하
는 패키지 설치

이 패키지는 rsyslog에서 발생하는 로그 데이터를 MariaDB에 저장할 수 있도록 연결하는 역할을 한다.

092. MariaDB 리플리케이션 슬레이브 설정 및 복제 동작 확인

1. 슬레이브 환경 설정 파일 수정

슬레이브 역할을 하는 DB 서버의 환경 설정 파일에도 server-id 를 추가해야 한다. 마스터와 슬레이브는 반드시 서로 다른 server-id 값을 가져야 한다.

# 파일 경로: /etc/my.cnf.d/mariadb-server.cnf
[mysqld]
server-id = 2   ← 마스터가 1이면 슬레이브는 2 등 다른 값 사용

마스터와 슬레이브의 server-id 가 동일하면 복제가 동작하지 않는다.

2. server-id 확인 명령어

MariaDB 접속 후 아래 명령으로 현재 설정된 server-id 값을 확인할 수 있다.

SHOW VARIABLES LIKE 'server_id';

마스터에서는 1, 슬레이브에서는 2가 출력되어야 한다.

계정명

좌표값(Position)

1. 리플리케이션 계정 생성 위치 정정

복제 전용 계정( GRANT REPLICATION SLAVE )은 마스터 DB 서버에서 생성해야 한다. 슬레이브가 마스터에 접속하여 복제를 수행하는 구조이므로, 복제 권한이 있는 계정은 마스터에 존재해야 한다.

복제 전용 계정 생성 ( GRANT REPLICATION SLAVE ) 마스터 DB
server-id 설정 마스터·슬레이브 모두 (값 다르게)

2. 마스터 상태 확인 — SHOW MASTER STATUS

마스터 DB에서 아래 명령으로 현재 바이너리 로그 파일명과 포지션 값을 확인한다.

SHOW MASTER STATUS;

출력 결과에서 File (바이너리 로그 파일명)과 Position (현재 로그 좌표값)을 확인하여 슬레 이브의 CHANGE MASTER TO 명령에 입력한다.

마스터에서 DB 작업이 발생할 때마다 포지션 값이 변경된다. 복제 설정 중 포지션 값이 달라지는 것을 방지하려면 FLUSH TABLES WITH READ LOCK; 명령으로 임시로 쓰기를 잠글 수 있다.

3. 슬레이브 복제 시작 — START SLAVE

슬레이브에서 CHANGE MASTER TO 설정 후, 아래 명령으로 복제를 시작한다.

START SLAVE;

4. 복제 동작 확인 방법

복제가 정상적으로 동작하는지 확인하는 방법은 다음과 같다.

  1. 마스터 DB에서 새로운 데이터베이스 또는 테이블을 생성한다.

  2. 슬레이브 DB에서 SHOW DATABASES; 또는 SHOW TABLES; 를 실행하여 마스터에서 생성한

내용이 자동으로 나타나는지 확인한다.

  1. 슬레이브에서 자동으로 동일한 내용이 나타나면 복제가 정상 동작하는 것이다.

복제 확인 시, 기존에 존재하던 데이터베이스가 아닌 마스터에서 새로 생성한 데이터베이스를 기준으로 확인해야 한다.

5. 바이너리 로그 좌표값(Position) 개념

마스터 DB에 변경이 발생하면 바이너리 로그 파일에 해당 변경 내용과 위치(좌표값, Position)가 기록된다. 슬레이브는 이 좌표값을 기준으로 어느 지점부터 복제할지 결정한다.

바이너리 로그 파일은 mysql-bin.000001 , mysql-bin.000002 등으로 순차 생성된다.

파일 크기가 max_binlog_size 를 초과하거나 서비스 재시작 시 새 파일이 생성된다.

MASTER_LOG_POS 값이 마스터의 실제 포지션 값과 다를 경우 복제가 정상 동작하지 않을 수 있다.

6. 패키지 삭제 명령어 — dnf remove

리플리케이션 재설정 등을 위해 MariaDB를 완전히 제거하고 처음부터 다시 설치할 때 사용한다.

dnf remove mariadb-server   ← MariaDB 서버 패키지 완전 삭제

삭제 후 다시 설치하면 초기 상태로 시작할 수 있다.

094. MariaDB 리플리케이션(복제) 개념 및 마스터 서버 설정

1. DB 리플리케이션(Replication) 개념

리플리케이션(Replication)은 두 대 이상의 DB 서버 사이에서 한쪽의 변경 내용을 자동으로 동기화하는 복제 기능이다.

DB 안에 중요한 데이터가 저장된 경우, 단일 서버에 장애가 발생하면 데이터 손실 또는 서비스 중단이 발생할 수 있다. 리플리케이션은 이러한 상황에 대비하기 위해 사용한다.

1-1. 마스터-슬레이브 구조
역할 설명
마스터(Master) 원본 DB 서버. 쓰기·변경이 주로 발생하는 서버이며, 바이너리 로그를 생성하여
슬레이브에 전달한다.
슬레이브(Slave) 복제 DB 서버. 마스터의 바이너리 로그를 읽어 동일한 변경사항을 반영한다.

⚠️ 실제 운영 환경에서 DB 리플리케이션을 적용하려면 마스터·슬레이브 서버 모두 고성 능 하드웨어가 요구된다. 복제 동기화 과정에서 상당한 컴퓨팅 자원을 소모하기 때문이다.

2. 리플리케이션 사전 준비 조건

두 DB 서버 간 리플리케이션이 동작하려면 아래 조건이 모두 충족되어야 한다.

조건 설명
양쪽 MariaDB 서치 실행 마스터·슬레이브 모두 MariaDB 서비스가 구동 중이어야 함

슬레이브 복제 계정 및 권한

3. MariaDB 환경 설정 파일

MariaDB의 서버 환경 설정 파일 위치는 다음과 같다.

/etc/my.cnf.d/mariadb-server.cnf   ← MariaDB 서버 환경 설정
파일

설정 파일 내부는 섹션으로 구분되며, [mysqld] 섹션 아래에 서버 관련 파라미터를 추가한다.

환경 설정 파일은 자체적인 문법을 따르므로 대소문자, 철자, 들여쓰기 등을 정확히 입력해야 한다. 오류 발생 시 MariaDB 서비스가 재시작되지 않는다.

마스터 역할을 하는 DB 서버의 [mysqld] 섹션에 아래 파라미터를 추가한다.

5. 슬레이브 복제 전용 계정 및 권한

슬레이브가 마스터에 접속하여 데이터를 복제하기 위한 전용 계정과 권한을 마스터 DB에서 설정해야 한다.

GRANT REPLICATION SLAVE ON *.* TO 'slave_db'@'%' IDENTIFIED
BY '패스워드';
FLUSH PRIVILEGES;

REPLICATION SLAVE : 복제 동작을 수행할 수 있는 전용 권한

'%' : 어떤 IP에서도 접속 허용 (실제 운영 환경에서는 슬레이브 IP로 제한 권장)

095. MariaDB 사용자 계정 관리 및 권한 설계

1. DB 사용자 계정과 시스템 사용자 계정의 구분

DB에서 생성하는 사용자 계정은 시스템(운영체제)에 로그인하는 계정과 완전히 별개이다.

구분 생성 명령 용도
시스템 사용자 useradd 운영체제(리눅스)에 로그인하는 계정
DB 사용자 CREATE USER 또는 GRANT 데이터베이스에 접속하는 계정

DB에서 만든 계정으로는 시스템에 로그인할 수 없으며, 반대로 시스템 계정으로 DB에 접속하는 것도 아니다.

2. 데이터베이스 계층 구조

MariaDB(MySQL 계열)의 데이터베이스 계층 구조는 다음과 같다.

데이터베이스(Database)
    └─ 테이블(Table)
           └─ 필드(Field)
                  └─ 데이터(Data)

권한을 부여할 때 이 계층 구조를 기준으로 DB명.테이블명.필드명 형식으로 범위를 지정한다.

3. DB 사용자 계정 생성

DB 사용자 계정을 생성하는 방법은 두 가지가 있다.

3-1. CREATE USER 명령으로 생성
CREATE USER '사용자명'@'접속허용호스트' IDENTIFIED BY '패스워
드';
3-2. GRANT 명령으로 생성과 권한 부여를 동시에 처리
GRANT ALL PRIVILEGES ON *.* TO '사용자명'@'접속허용호스트' IDE
NTIFIED BY '패스워드';

두 방법은 결과가 동일하며, GRANT 명령은 CREATE USER와 권한 부여를 한 번에 처리한다.

4. 접속 허용 호스트(Host) 설정

사용자 생성 시 @ 뒤에 지정하는 호스트는 해당 사용자가 DB에 접속할 수 있는 위치(IP 또는 범위)를 의미한다.

호스트 설정 의미
'localhost' DB가 설치된 서버 내부(로컬)에서만 접속 가능
'192.168.100.91' 지정된 IP 주소를 가진 시스템에서만 접속 가능
'%' 모든 IP 주소에서 접속 가능 (제한 없음)

이 설정이 DB의 접근 제어 역할을 담당한다.

5. 권한 부여 — GRANT

GRANT 권한목록 ON DB명.테이블명 TO '사용자명'@'호스트';
5-1. 권한 목록 지정 방식
권한 지정 방법 예시 의미
ALL
PRIVILEGES		 GRANT ALL PRIVILEGES ON east db.*
_
TO ...		 지정된 DB의 모든 테이블에 모든 권
한 부여
특정 명령어 지정 GRANT CREATE, DROP ON east db.*
_
TO ...		 CREATE와 DROP 명령만 허용
특정 테이블 지정 GRANT ALL ON east db.student TO
_
...		 지정된 테이블에만 권한 부여

관리자 계정 외의 일반 사용자 계정에는 필요한 최소 권한만 부여해야 한다. 모든 계정이 모든 DB에 모든 권한을 가지는 것은 보안상 위험하다.

5-2. 권한 적용 — FLUSH PRIVILEGES

권한을 추가하거나 제거한 후에는 반드시 FLUSH PRIVILEGES 를 실행하여 변경사항을 즉시 적용해야 한다.

FLUSH PRIVILEGES;

6. 권한 조회 — SHOW GRANTS

SHOW GRANTS;                              ← 현재 접속 계정의
권한 조회
SHOW GRANTS FOR '사용자명'@'호스트';      ← 특정 사용자의 권한
조회

7. 권한 회수 — REVOKE

REVOKE 권한목록 ON DB명.테이블명 FROM '사용자명'@'호스트';

권한 부여: GRANT ... TO

권한 회수: REVOKE ... FROM

권한 회수 후에도 FLUSH PRIVILEGES 로 적용해야 한다.

8. 사용자 계정 삭제 — DROP USER

DROP USER '사용자명';               ← 사용자명만으로 삭제 (버전
에 따라 가능)
DROP USER '사용자명'@'호스트';      ← 호스트 정보 포함 삭제 (오류
발생 시 이 방법 사용)

삭제 오류 발생 시 메시지에 호스트 정보까지 포함하라는 안내가 출력되므로 오류 메시지를 확인하고 호스트를 추가하면 된다.

9. 데이터베이스 생성 시 문자셋 지정

데이터베이스 생성 시 기본 문자셋을 지정하지 않으면 시스템 기본값이 적용된다. 한글 지원 이 필요한 경우 UTF-8 문자셋을 명시적으로 지정해야 한다.

CREATE DATABASE DB명 DEFAULT CHARACTER SET utf8;

10. 패스워드 변경 — UPDATE

특정 사용자의 패스워드를 변경할 때는 UPDATE 명령을 사용하며, 사용자 정보가 저장된

mysql 데이터베이스로 이동한 후 작업한다.

USE mysql;
UPDATE user SET password=PASSWORD('새패스워드') WHERE user
='사용자명' AND host='호스트';
FLUSH PRIVILEGES;

096. 데이터베이스 보안 개요 및 시스템 하드웨어 점검 명령어

1. 데이터베이스(DB) 보안 개요

데이터베이스 보안은 일반적인 시스템 보안과 동일한 구조를 가진다. 데이터베이스도 하나의 시스템이기 때문에 아래의 보안 영역이 동일하게 적용된다.

보안 영역 설명
계정 관리 DB에 접근하는 사용자 계정을 생성·수정·삭제하는 관리
권한 관리 각 계정에 대해 허용되는 작업 범위를 지정하는 관리 (GRANT 등)
로그 관리 DB에서 발생하는 이벤트 로그를 수집·보관·분석하는 관리
접근 제어 허가된 계정 또는 호스트만 DB에 접근할 수 있도록 제한하는 관리

데이터베이스를 시스템에 구축하기 전에는 해당 시스템의 저장 공간, 메모리, CPU 등 하드웨어 사양이 충분한지 반드시 사전 점검해야 한다.

2. 커널(Kernel) 개념

커널은 리눅스 운영체제에서 하드웨어와 소프트웨어를 연결하는 핵심 계층이다. 사용자가 터미널(셸)에서 내린 명령을 받아 하드웨어와의 통신을 담당한다.

[사용자] → [셸(Shell)] → [커널(Kernel)] → [하드웨어(Hardware)]

⚠️ 커널 파라미터를 임의로 변경하면 하드웨어와의 통신 이상 또는 시스템 동작 불능 상태가 발생할 수 있다. 커널 설정 변경은 반드시 신중하게 수행해야 한다.

3. 시스템 하드웨어 점검 명령어

3-1. 커널 파라미터 조회 및 변경 — sysctl

sysctl 은 현재 실행 중인 커널의 파라미터 값을 조회하거나 변경할 수 있는 명령어이다.

명령어 설명
sysctl -a 모든 커널 파라미터 값 출력
sysctl -w vm.swappiness=40 특정 파라미터 값을 즉시 변경 (재부팅 시 초기화)

변경된 커널 파라미터를 영구 적용하려면 설정 파일을 직접 수정해야 한다.

vi /etc/sysctl.conf   ← 커널 파라미터 영구 설정 파일

파일 내에 적용할 파라미터를 직접 입력하면 재부팅 후에도 유지된다.

⚠️ 커널 파라미터 파일은 하드웨어 동작과 직결되므로, 내용을 잘 이해하지 않은 상태에서 변경하거나 저장하면 안 된다.

3-2. 메모리 확인 — free 및 /proc/meminfo
free            ← 메모리 사용량 기본 출력
free -g         ← 기가 단위로 출력
free -m         ← 메가 단위로 출력
free -h         ← 사람이 읽기 편한 단위로 출력
cat /proc/meminfo       ← 메모리 상세 정보 파일 출력
grep MemTotal /proc/meminfo   ← 전체 메모리 용량만 검색

/proc/meminfo 는 전체 메모리, 사용 가능 메모리, 활성화된 메모리 등 메모리에 대한 세부 정보를 담고 있는 파일이다.

3-3. CPU 및 운영체제 버전 확인
cat /proc/version       ← 운영체제 및 리눅스 커널 버전 확인
cat /proc/cpuinfo       ← CPU 모델, 코어 수, 클럭 등 상세 정보
확인

/proc/version 에 표시되는 버전은 로키 리눅스(Rocky Linux)의 배포판 버전이 아니라 리눅스 커널 버전이다.

리눅스에서 서비스를 설치하고 운영할 때 사용하는 이름이 명령어에 따라 다르다.

5. MariaDB 초기 보안 설치

MariaDB 설치 후에는 초기 보안 설정 작업을 반드시 수행해야 보안성을 높일 수 있다.

mysql_secure_installation   ← DB 초기 보안 설치 명령어

이 명령을 실행하면 아래 항목들을 순서대로 설정하게 된다.

설정 항목 보안 권장 사항
DB 루트(root) 계정 패스워드 설정 패스워드 변경(Y)
익명(Anonymous) 사용자 제거 제거(Y)
원격 루트 로그인 비허용 비허용(Y)
테스트 DB 및 관련 접속 제거 제거(Y)
권한 테이블 즉시 적용(Flush Privileges) 적용(Y)
