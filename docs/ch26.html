CHAPTER 26

공식 문서 대조

강의 자료와 노트를 최신 공식 문서와 대조한 결과입니다. 원문은 고치지 않았습니다. 어느 쪽이 맞는지, 왜 달라졌는지를 여기 모읍니다.

각 항목은 다음 형식입니다.

원문 → 자료에 적힌 내용 공식 → 확인한 사실과 출처 왜 → 왜 달라졌는지, 실습에서 무엇이 달라지는지

대조 시점은 2026년 8월입니다. 도구 버전은 계속 바뀌므로 실습 전에 다시 확인하십시오.

1. SNMP 포트 — 169가 아니라 161·162

원문 — 「과정 개요」 OSI·TCP/IP 대응표에 SNMP (169) 공식 — SNMP는 UDP 161, SNMP Trap은 UDP 162입니다. RFC 1157이 "trap을 제외한 모든 메시지는 UDP 161에서 받고, trap을 보고하는 메시지는 UDP 162에서 받아야 한다"고 규정하고, IANA 포트 레지스트리에도 snmp 161/udp, snmptrap 162/udp로 등록돼 있습니다. 왜 — 169는 오타로 보입니다. 방화벽에서 SNMP를 열 때 169를 열면 통신이 되지 않습니다.

# 방화벽 열 때
firewall-cmd --permanent --add-port=161/udp   # SNMP 질의·응답
firewall-cmd --permanent --add-port=162/udp   # SNMP Trap 수신 서버에서만
firewall-cmd --reload

2. ip access-group의 방향 기본값 — 지금은 생략하면 안 됩니다

원문 — 「과정 개요」 표준 ACL 절에 Default = outbound 공식 — Cisco 명령 참조는 "키워드를 지정하지 않으면 out이 기본"이라고 하면서도, 초기 소프트웨어 릴리스에서만 그랬고 이후 릴리스에서는 방향을 반드시 지정해야 한다고 명시합니다. 왜 — 옛 IOS 기준 서술입니다. 지금은 in/out을 안 쓰면 명령이 거부되거나 의도와 다르게 걸릴 수 있습니다. 항상 방향을 적으십시오.

Router(config-if)#ip access-group 110 in    ← 들어오는 트래픽을 검사
Router(config-if)#ip access-group 110 out   ← 나가는 트래픽을 검사

방향 선택은 성능이 아니라 어느 지점에서 걸러지느냐의 문제입니다. 「통합 Lab 결과보고서」의 ACL 110처럼 출발지가 여러 곳이면 목적지 쪽 인터페이스 out에 거는 편이 규칙 수가 적습니다.

3. FTPS 포트 — 원문 설명이 https와 섞여 있습니다

원문 — 「8/27 보강」의 ftps: "보안이 추가된 웹 페이지의 정보를 주고 받는 통신 프로토콜" 공식 — FTPS는 파일 전송입니다. 방식이 둘로 갈립니다. - 명시적(Explicit) — 평문 21번으로 붙은 뒤 AUTH TLS 명령으로 TLS로 올림 (RFC 4217) - 암시적(Implicit) — 접속하자마자 TLS. 관례적으로 990번

왜 — https 설명 문장이 그대로 복사된 것으로 보입니다. 포트 숫자(21/990)는 맞습니다.

RFC 4217은 명시적 방식만 규정합니다. 암시적 990은 표준이 아니라 관례이며, RFC 8314는 이런 방식을 일반적으로 Implicit TLS라 부릅니다.

4. Kali Linux 기본 계정 — root 아니라 kali

원문 — 「핵심키워드 103강」에 "root 직접 로그인 불가 → 일반 사용자 계정 생성 필요" 공식 — 맞습니다. 다만 한 걸음 더 있습니다. 2020.1 릴리스부터 Kali는 기본 비루트 사용자 모델로 바뀌었고, 배포되는 VMware·VirtualBox·ARM 이미지의 기본 자격 증명은 kali / kali 입니다. root 계정은 보안상 기본 비활성입니다. 왜 — 직접 설치하면 설치 중 계정을 만들지만, 제공된 VM 이미지를 쓰면 kali/kali로 로그인합니다. 실습에서 둘을 헷갈리기 쉽습니다.

root가 필요하면 sudo를 쓰고, 정말 root 로그인이 필요하면 공식 문서의 「Enabling Root」 절차대로 현재 사용자와 다른 비밀번호를 지정합니다.

5. yum → dnf (Rocky Linux 9 이후)

원문 — 「과정 개요」 YUM 도구 명령어 표 전체가 yum ... 공식 — Rocky Linux 9는 DNF를 씁니다. yum은 dnf로 넘겨주는 호환 이름으로 남아 있어 그대로 쳐도 동작합니다. Rocky Linux 10에서는 차세대 dnf5로 옮겨 가며 dnf module 명령이 제거되고 모듈러리티(AppStream 모듈) 자체가 폐기됐습니다. 왜 — 표가 CentOS 7 시절 기준입니다. 명령 이름만 바꾸면 대부분 그대로 통합니다.

원문 (yum) Rocky 9에서 권장
yum list installed [패키지] dnf list installed [패키지]
yum check-update dnf check-update
yum install -y [패키지] dnf install -y [패키지]
yum grouplist dnf group list
yum -y groupinstall "Development Tools" dnf -y group install "Development Tools"
yum clean all dnf clean all

6. RHEL 9 계열에서 SELinux 완전 비활성화 방법이 바뀌었습니다

원문 — 「8/25 NFS·Samba」에 이미 짚혀 있으나, 실습에서 자주 틀리는 곳이라 다시 적습니다. 공식 — /etc/selinux/config의 SELINUX=disabled만 고치는 런타임 비활성화는 폐기(deprecated) 됐습니다. 그렇게 하면 SELinux가 켜진 채 정책만 없는 상태로 부팅합니다. 정말 꺼야 한다면 커널 명령줄에 selinux=0 을 넣으라는 것이 Red Hat의 안내입니다. 왜 — RHEL 8까지의 습관이 그대로 남아 "껐는데 왜 막히지?"가 생깁니다.

문제를 볼 때는 끄지 말고 permissive로 잠시 내리는 것이 공식 권고입니다.

sudo setenforce 0          # 지금만 permissive (재부팅하면 원복)
sudo getenforce            # 현재 모드 확인
sudo ausearch -m avc -ts recent    # 무엇이 막혔는지 확인

끄는 대신 필요한 것만 여는 방법은 「8/25 NFS·Samba」의 semanage fcontext / setsebool -P 절을 보십시오.

7. MariaDB 명령 이름 — mysqldump는 11.0에서 제거됐습니다

원문 — 「8/27 MariaDB」는 mariadb-dump를 쓰고 있어 최신입니다. 다만 인터넷 자료 대부분이 아직 mysqldump라 헷갈리기 쉽습니다. 공식 — 예전 이름 mysqldump는 심볼릭 링크로 남아 있었으나 MariaDB 11.0에서 제거됐고, 공식 Docker 이미지에서도 빠졌습니다. 지금 이름은 mariadb-dump 입니다. 왜 — MariaDB가 MySQL 계열 이름을 정리하는 과정입니다. 클라이언트도 mysql → mariadb로 바뀌었습니다.

옛 이름 지금 이름
mysql mariadb
mysqldump mariadb-dump
mysql_upgrade mariadb-upgrade
mysqladmin mariadb-admin

주의할 점 하나 더 — mariadb-dump는 덤프 앞머리에 샌드박스 모드를 켜는 명령을 넣습니다. 그래서 만들어진 덤프를 옛 클라이언트(mysql)로 복원하면 오류가 납니다. 덤프를 뜬 쪽과 복원하는 쪽의 클라이언트 버전을 맞추십시오.

8. Snort 버전 — 실습 자료 기준과 현재가 다릅니다

원문 — 「핵심키워드 101·105강」의 Snort3 설치·룰 탐지 실습 공식 — 2026년 8월 기준 배포되는 Snort 3는 3.12.2.0 계열이며, Snort 2와 일부 Snort 3 버전은 End of Life 공지가 나와 있습니다. 왜 — 설치 문서의 버전 문자열을 그대로 복사하면 다운로드가 실패합니다. 항상 공식 다운로드 페이지에서 현재 파일명을 확인하고 받으십시오 (libdaq, libml 같은 의존 라이브러리도 함께 버전이 올라갑니다).
