2. 웹 문서 디렉토리 구조

2-1. Document Root 아래 디렉토리 생성

클라이언트에게 제공할 웹 문서는 모두 /var/www/html 디렉토리 안에 위치한다. 하위 디렉토 리를 생성하여 파일을 분류할 수 있다. mkdir /var/www/html/test ← test 디렉토리 생성 cd /var/www/html ← Document Root로 이 동 ls ← 현재 파일 목록 확인

2-2. 파일 복사 — cp

리눅스에서 파일 복사 명령어는 cp 이다. cp 원본파일 대상파일 ← 기본 형식 cp test/test.html index.html ← test 디렉토리의 test.html을 현재 디렉토리에 index.html로 복사 대상 경로에 디렉토리 경로가 없으면 현재 작업 디렉토리를 의미한다.

2-3. 시작 페이지(index.html)

브라우저 주소창에 파일 이름 없이 서버 IP만 입력했을 때 자동으로 표시되는 페이지가 있 다. 이는 Apache가 시작 페이지로 등록된 파일 이름을 자동으로 찾기 때문이다. 자동 인식되는 시작 페이지 파일명 index.html index.php /var/www/html 디렉토리 안에 index.html 또는 index.php 파일이 있으면, 브라우저에서 파일 이름을 생략해도 해당 파일이 자동으로 표시된다.

3. 웹 서버와 데이터베이스 서버의 관계

3-1. 프론트엔드와 백엔드
  • 구분
  • 역할
  • 예시
  • 프론트엔드
  • 클라이언트에게 보여지는 화면
  • HTML, CSS, JavaScript
  • 백엔드
  • 데이터 처리 및 저장
  • PHP, DB 서버
  • 데이터베이스(DB) 서버는 백엔드에 해당하며, 사용자 정보·게시글 등 다양한 데이터를 저장
  • 하고 질의(Query)에 응답하는 역할을 한다.
3-2. 웹 서버와 DB 서버 간 동작 흐름

클라이언트가 로그인 페이지에서 아이디와 패스워드를 입력하면 다음과 같이 처리된다. 클라이언트 → (로그인 정보 전송) → 웹 서버 → (SQL 질의) → DB 서버 ← (로그인 성공/실패) ← ← (결과 반환) ← 웹 서버와 DB 서버는 물리적으로 별도의 시스템으로 구성하는 것이 보안상 권장된다. 하 나의 시스템에 모두 구성하면 보안 위험이 높아진다.

3-3. SQL이란

6. MariaDB 접속

mysql -u root -p ← root 사용자로 DB 접속 (-u: user, -p: pa ssword 입력) 접속 성공 시 MariaDB [(none)]> 프롬프트가 표시된다. (none) 은 현재 선택된 데이터베이스 가 없음을 의미한다.

7. 데이터베이스 목록 확인

show databases; ← 현재 존재하는 데이터베이스 목록 출력 SQL 구문 마지막에는 반드시 세미콜론( ; )을 입력한다. MariaDB 설치 직후에는 기본으로 3개의 데이터베이스가 존재한다.

8. 외부에서 MariaDB에 접속하기 위한 조건

MariaDB의 기본 서비스 포트는 3306이다. 외부에서 DB 서버에 접속하려면 방화벽에서 해당 포트를 허용해야 한다. firewall-cmd --permanent --add-port=3306/tcp firewall-cmd --reload

앞으로 배우는 모든 서버 서비스에서 공통으로 적용되는 원칙: 서비스 시작 → 방화벽 포 트 허용 순서로 진행한다.

045. MariaDB SQL 기초 CRUD 개념, 데이터베이스·테이블 생성, 필드 추가

MariaDB SQL 기초: CRUD 개념, 데이터베이스·테이블 생성, 필드 추가

1. MariaDB 기본 데이터베이스 구조

  • MariaDB 설치 후 기본으로 존재하는 데이터베이스 3개는 다음과 같다.
  • 데이터베이스 이름
  • 역할
  • information_schema
  • MySQL/MariaDB 내부 테이블·필드 정보 저장

  • 데이터베이스 성능 관련 정보 저장

  • 저장된다.

2. 데이터베이스 구조 개념

데이터베이스의 기본 계층 구조는 다음과 같다. 데이터베이스 (Database) └── 테이블 (Table) └── 필드 / 칼럼 (Field = Column) └── 실제 데이터 (Data) 필드(Field)와 칼럼(Column)은 동일한 개념이다.

3. SQL 주요 명령어 — 데이터 조회

3-1. 데이터베이스 선택 — use

use 데이터베이스명; ← 사용할 데이터베이스 선택 접속 후 프롬프트가 MariaDB [(none)]> 에서 MariaDB [데이터베이스명]> 으로 변경된다. MariaDB SQL 기초: CRUD 개념, 데이터베이스·테이블 생성, 필드 추가

3-2. 테이블 목록 확인 — show tables

show tables; ← 현재 데이터베이스 안의 테이블 목록 출력

3-3. 테이블 데이터 조회 — select

select * from 테이블명; ← 모든 필드의 데이터 조회 select 필드1, 필드2 from 테이블명; ← 지정한 필드의 데이터만 조 회 * (별표)는 모든 필드를 의미한다.

3-4. 테이블 필드 구조 확인 — desc
  • desc 테이블명; ← 테이블의 필드(칼럼) 구조 출력

065. rsyslog 연결 확인과 MariaDB 연동 준비

준비

1. rsyslog 클라이언트-서버 연결 확인

1-1. tail 명령을 통한 실시간 로그 모니터링

서버에서 tail -f 명령으로 로그 파일을 실시간으로 모니터링하면서 클라이언트에서 이벤 트를 발생시키면, 클라이언트 로그가 서버에 실시간으로 기록된다. 클라이언트에서 이벤트 발생 시 서버의 /var/log/messages 에 해당 내용이 자동으로 수 신된다. 수신된 로그에는 클라이언트의 호스트 네임이 함께 표시된다. 클라이언트에서 발생한 이벤트가 서버에 기록되는 것이지, 서버에서 직접 이벤트가 발생 한 것이 아님을 구분해야 한다.

1-2. 연결 상태 확인 명령어

lsof -i tcp::514 ← TCP 514번 포트 연결 목록 확인 netstat -natp | grep 514 ← 514번 포트 연결 상태 필터링 로그를 주고받은 직후에는 ESTABLISHED 상태가 표시된다. 상태 의미 LISTEN 연결 대기 중 (아직 클라이언트가 연결하지 않음) ESTABLISHED 연결이 성립된 상태 (로그 전송 중 또는 직후) ⚠️ TCP와 UDP 중 하나만 연결이 성립된다. 두 개가 동시에 ESTABLISHED 상태가 되 지는 않는다.

2. rsyslog 연결 문제 체크리스트

연결이 되지 않을 경우 다음 항목을 순서대로 확인한다.

항목 확인 내용 패키지 설치 서버·클라이언트 양쪽에 rsyslog , rsyslog-doc 설치 여부 서버 설정 파일 /etc/rsyslog.conf 의 TCP/UDP 입력 모듈 추가 여부 (대소문자 확인) 클라이언트 설정 파일 /etc/rsyslog.conf 마지막 줄에 서버 IP 및 포트 설정 여부 방화벽 서버에서 TCP/UDP 514번 포트 허용 및 reload 여부 서비스 시작 서버·클라이언트 양쪽에서 rsyslog 서비스 실행 여부 클라이언트 IP 입력 클라이언트 설정 파일에 서버의 IP가 올바르게 입력되었는지 확인 ⚠️ Syntax error(문법 오류)는 철자 오류로 발생하며, connection refused 는 서버 설정 또는 방화벽 문제일 가능성이 높다.

3. 서비스 상태의 enable/disabled 개념

systemctl enable rsyslog ← 재부팅 후에도 자동 시작 등록 systemctl status 명령에서 disabled 상태로 표시되어 있어도, 현재 서비스가 running (활성 화) 상태라면 당장의 운영에는 문제가 없다. 다만 disabled 는 재부팅 후 서비스가 자동으로 시작되지 않음을 의미하므로, 영구 운용을 위해서는 enable 로 설정해야 한다.

3. 슬레이브 복제 시작 — START SLAVE

슬레이브에서 CHANGE MASTER TO 설정 후, 아래 명령으로 복제를 시작한다. START SLAVE;

4. 복제 동작 확인 방법

복제가 정상적으로 동작하는지 확인하는 방법은 다음과 같다.

1. 마스터 DB에서 새로운 데이터베이스 또는 테이블을 생성한다.

2. 슬레이브 DB에서 SHOW DATABASES; 또는 SHOW TABLES; 를 실행하여 마스터에서 생성한

내용이 자동으로 나타나는지 확인한다.

3. 슬레이브에서 자동으로 동일한 내용이 나타나면 복제가 정상 동작하는 것이다.

복제 확인 시, 기존에 존재하던 데이터베이스가 아닌 마스터에서 새로 생성한 데이터베이 스를 기준으로 확인해야 한다.

5. 바이너리 로그 좌표값(Position) 개념

마스터 DB에 변경이 발생하면 바이너리 로그 파일에 해당 변경 내용과 위치(좌표값, Position)가 기록된다. 슬레이브는 이 좌표값을 기준으로 어느 지점부터 복제할지 결정한다. 바이너리 로그 파일은 mysql-bin.000001 , mysql-bin.000002 등으로 순차 생성된다. 파일 크기가 max_binlog_size 를 초과하거나 서비스 재시작 시 새 파일이 생성된다. MASTER_LOG_POS 값이 마스터의 실제 포지션 값과 다를 경우 복제가 정상 동작하지 않을 수 있다.

6. 패키지 삭제 명령어 — dnf remove

리플리케이션 재설정 등을 위해 MariaDB를 완전히 제거하고 처음부터 다시 설치할 때 사용 한다. dnf remove mariadb-server ← MariaDB 서버 패키지 완전 삭제 삭제 후 다시 설치하면 초기 상태로 시작할 수 있다.

094. MariaDB 리플리케이션(복제) 개념 및 마스터 서버 설정

및 마스터 서버 설정

1. DB 리플리케이션(Replication) 개념

리플리케이션(Replication)은 두 대 이상의 DB 서버 사이에서 한쪽의 변경 내용을 자동으 로 동기화하는 복제 기능이다. DB 안에 중요한 데이터가 저장된 경우, 단일 서버에 장애가 발생하면 데이터 손실 또는 서비 스 중단이 발생할 수 있다. 리플리케이션은 이러한 상황에 대비하기 위해 사용한다.

1-1. 마스터-슬레이브 구조

역할 설명 마스터(Master) 원본 DB 서버. 쓰기·변경이 주로 발생하는 서버이며, 바이너리 로그를 생성하여 슬레이브에 전달한다. 슬레이브(Slave) 복제 DB 서버. 마스터의 바이너리 로그를 읽어 동일한 변경사항을 반영한다. ⚠️ 실제 운영 환경에서 DB 리플리케이션을 적용하려면 마스터·슬레이브 서버 모두 고성 능 하드웨어가 요구된다. 복제 동기화 과정에서 상당한 컴퓨팅 자원을 소모하기 때문이 다.

2. 리플리케이션 사전 준비 조건

두 DB 서버 간 리플리케이션이 동작하려면 아래 조건이 모두 충족되어야 한다. 조건 설명 양쪽 MariaDB 서치 실행 마스터·슬레이브 모두 MariaDB 서비스가 구동 중이어야 함 방화벽 포트 허용 마스터에서 MySQL/MariaDB 기본 포트(3306/TCP)를 허용해야 슬 레이브가 접속 가능 마스터 환경 설정 마스터 DB의 설정 파일에 복제 관련 파라미터를 추가해야 함 슬레이브 복제 계정 및 권한 설정 슬레이브가 마스터에 접속하여 복제할 수 있는 전용 계정과 권한이 필 요

3. MariaDB 환경 설정 파일

MariaDB의 서버 환경 설정 파일 위치는 다음과 같다. /etc/my.cnf.d/mariadb-server.cnf ← MariaDB 서버 환경 설정 파일 설정 파일 내부는 섹션으로 구분되며, [mysqld] 섹션 아래에 서버 관련 파라미터를 추가한 다. 환경 설정 파일은 자체적인 문법을 따르므로 대소문자, 철자, 들여쓰기 등을 정확히 입력 해야 한다. 오류 발생 시 MariaDB 서비스가 재시작되지 않는다.

4. 마스터 DB 환경 설정 파라미터

마스터 역할을 하는 DB 서버의 [mysqld] 섹션에 아래 파라미터를 추가한다. [mysqld] server-id = 1 ← 서버 고유 식별자 (마스터와 슬레이브는 서로 다른 ID 사용) log_bin = /var/log/mariadb/mariadb-bin ← 바이너리 로그 파일 경로 및 이름 expire_logs_days = 10 ← 바이너리 로그 보관 기간 (10일 경과 시 자동 삭제) max_binlog_size = 10M ← 바이너리 로그 파일 최대 크기 (초과 시 새 파일 생성)

4-1. 파라미터 설명

파라미터 설명 server-id 동일 복제 그룹 내에서 각 서버를 구별하는 고유 ID. 마스터는 1, 슬레이브는 2 등 서로 다른 값 사용 log_bin 복제 동기화에 사용되는 바이너리(이진) 로그 파일의 저장 경로 expire_logs_days 바이너리 로그 파일의 자동 삭제 기한. 지정 일수 초과 시 삭제됨 max_binlog_size 단일 바이너리 로그 파일의 최대 크기. 초과 시 새 파일이 자동 생성됨

4-2. 추가 선택 파라미터
  • 파라미터
  • 설명
  • sync_binlog
  • 바이너리 로그 동기화 빈도. 1로 설정 시 매 커밋마다 동기화 (안정성 최고, 속도
  • 느림)
  • binlog_format
  • 바이너리 로그 기록 형식 지정 (ROW, STATEMENT, MIXED 등)

5. 슬레이브 복제 전용 계정 및 권한

슬레이브가 마스터에 접속하여 데이터를 복제하기 위한 전용 계정과 권한을 마스터 DB에서 설정해야 한다. GRANT REPLICATION SLAVE ON . TO 'slave_db'@'%' IDENTIFIED BY '패스워드'; FLUSH PRIVILEGES; REPLICATION SLAVE : 복제 동작을 수행할 수 있는 전용 권한 '%' : 어떤 IP에서도 접속 허용 (실제 운영 환경에서는 슬레이브 IP로 제한 권장)

2. 데이터베이스 계층 구조

MariaDB(MySQL 계열)의 데이터베이스 계층 구조는 다음과 같다. 데이터베이스(Database) └─ 테이블(Table) └─ 필드(Field) └─ 데이터(Data) 권한을 부여할 때 이 계층 구조를 기준으로 DB명.테이블명.필드명 형식으로 범위를 지정한다.

3. DB 사용자 계정 생성

DB 사용자 계정을 생성하는 방법은 두 가지가 있다.

3-1. CREATE USER 명령으로 생성

CREATE USER '사용자명'@'접속허용호스트' IDENTIFIED BY '패스워 드';

3-2. GRANT 명령으로 생성과 권한 부여를 동시에 처리

GRANT ALL PRIVILEGES ON . TO '사용자명'@'접속허용호스트' IDE NTIFIED BY '패스워드'; 두 방법은 결과가 동일하며, GRANT 명령은 CREATE USER와 권한 부여를 한 번에 처리한 다.

4. 접속 허용 호스트(Host) 설정

  • 사용자 생성 시 @ 뒤에 지정하는 호스트는 **해당 사용자가 DB에 접속할 수 있는 위치(IP
  • 또는 범위)**를 의미한다.
  • 호스트 설정
  • 의미
  • 'localhost'
  • DB가 설치된 서버 내부(로컬)에서만 접속 가능
  • '192.168.100.91'
  • 지정된 IP 주소를 가진 시스템에서만 접속 가능
  • '%'
  • 모든 IP 주소에서 접속 가능 (제한 없음)
  • 이 설정이 DB의 접근 제어 역할을 담당한다.

SHOW GRANTS; ← 현재 접속 계정의 권한 조회 SHOW GRANTS FOR '사용자명'@'호스트'; ← 특정 사용자의 권한 조회

8. 사용자 계정 삭제 — DROP USER

DROP USER '사용자명'; ← 사용자명만으로 삭제 (버전 에 따라 가능) DROP USER '사용자명'@'호스트'; ← 호스트 정보 포함 삭제 (오류 발생 시 이 방법 사용) 삭제 오류 발생 시 메시지에 호스트 정보까지 포함하라는 안내가 출력되므로 오류 메시지를 확인하고 호스트를 추가하면 된다.

9. 데이터베이스 생성 시 문자셋 지정

데이터베이스 생성 시 기본 문자셋을 지정하지 않으면 시스템 기본값이 적용된다. 한글 지원 이 필요한 경우 UTF-8 문자셋을 명시적으로 지정해야 한다.

CREATE DATABASE DB명 DEFAULT CHARACTER SET utf8;

10. 패스워드 변경 — UPDATE

특정 사용자의 패스워드를 변경할 때는 UPDATE 명령을 사용하며, 사용자 정보가 저장된 mysql 데이터베이스로 이동한 후 작업한다. USE mysql; UPDATE user SET password=PASSWORD('새패스워드') WHERE user ='사용자명' AND host='호스트'; FLUSH PRIVILEGES;

096. 데이터베이스 보안 개요 및 시스템 하드웨어 점검 명령어

드웨어 점검 명령어

1. 데이터베이스(DB) 보안 개요

데이터베이스 보안은 일반적인 시스템 보안과 동일한 구조를 가진다. 데이터베이스도 하나 의 시스템이기 때문에 아래의 보안 영역이 동일하게 적용된다. 보안 영역 설명 계정 관리 DB에 접근하는 사용자 계정을 생성·수정·삭제하는 관리 권한 관리 각 계정에 대해 허용되는 작업 범위를 지정하는 관리 (GRANT 등) 로그 관리 DB에서 발생하는 이벤트 로그를 수집·보관·분석하는 관리 접근 제어 허가된 계정 또는 호스트만 DB에 접근할 수 있도록 제한하는 관리 데이터베이스를 시스템에 구축하기 전에는 해당 시스템의 저장 공간, 메모리, CPU 등 하드 웨어 사양이 충분한지 반드시 사전 점검해야 한다.

2. 커널(Kernel) 개념

커널은 리눅스 운영체제에서 하드웨어와 소프트웨어를 연결하는 핵심 계층이다. 사용자가 터 미널(셸)에서 내린 명령을 받아 하드웨어와의 통신을 담당한다. [사용자] → [셸(Shell)] → [커널(Kernel)] → [하드웨어(Hardware)] ⚠️ 커널 파라미터를 임의로 변경하면 하드웨어와의 통신 이상 또는 시스템 동작 불능 상 태가 발생할 수 있다. 커널 설정 변경은 반드시 신중하게 수행해야 한다.

3. 시스템 하드웨어 점검 명령어

3-1. 커널 파라미터 조회 및 변경 — sysctl

sysctl 은 현재 실행 중인 커널의 파라미터 값을 조회하거나 변경할 수 있는 명령어이다.

명령어 설명 sysctl -a 모든 커널 파라미터 값 출력 sysctl -w vm.swappiness=40 특정 파라미터 값을 즉시 변경 (재부팅 시 초기화) 변경된 커널 파라미터를 영구 적용하려면 설정 파일을 직접 수정해야 한다. vi /etc/sysctl.conf ← 커널 파라미터 영구 설정 파일 파일 내에 적용할 파라미터를 직접 입력하면 재부팅 후에도 유지된다. ⚠️ 커널 파라미터 파일은 하드웨어 동작과 직결되므로, 내용을 잘 이해하지 않은 상태에 서 변경하거나 저장하면 안 된다.

3-2. 메모리 확인 — free 및 /proc/meminfo

free ← 메모리 사용량 기본 출력 free -g ← 기가 단위로 출력 free -m ← 메가 단위로 출력 free -h ← 사람이 읽기 편한 단위로 출력 cat /proc/meminfo ← 메모리 상세 정보 파일 출력 grep MemTotal /proc/meminfo ← 전체 메모리 용량만 검색 /proc/meminfo 는 전체 메모리, 사용 가능 메모리, 활성화된 메모리 등 메모리에 대한 세부 정 보를 담고 있는 파일이다.

3-3. CPU 및 운영체제 버전 확인

cat /proc/version ← 운영체제 및 리눅스 커널 버전 확인 cat /proc/cpuinfo ← CPU 모델, 코어 수, 클럭 등 상세 정보 확인 /proc/version 에 표시되는 버전은 로키 리눅스(Rocky Linux)의 배포판 버전이 아니라 리눅스 커널 버전이다.
