1. Admin 차단 룰

1-1. 룰 적용

1-3. 테스트

접속한 웹서버 URL 뒤에 /login , 이어서 admin 이라는 문자열을 포함시켜 요청한다. http://[웹서버 IP]/login/admin

1-4. 결과 확인

    5-2. CRS 프로젝트 및 업데이트

    175. WAF(웹 방화벽)

    네트워크 인프라 4교시 강의 교안 WAF(웹 방화벽)의 개념과 ModSecurity 설치, 룰 문법 이해

    1. WAF(Web Application Firewall) 개요

    1-1. WAF의 정의

    WAF는 방화벽(Firewall)이다. F와 W가 각각 파이어(Fire), 월(Wall)에 해당하여 기본적으 로 방화벽 역할을 하는 것을 나타낸다.

    1-2. 기존 보안 장비와 WAF의 차이

    이미 방화벽, IDS, IPS 등 기존 보안 장비들이 네트워크 경계망에 존재하고 있다. 일반적인 네트워크 레이어 구조는 다음과 같다. 외부 - 방화벽(경계망) - IDS/IPS - L3/L4 장비 - L2 장비 - 호스트/시스템 웹 서버는 이러한 구조 내부의 특정 존(zone)에 존재하게 되는데, 외부에서 방화벽과 IPS 장비를 우회하여 내부로 들어온 트래픽이 웹 서버에 도착했을 때, 애플리케이션 계층의 내용 까지 룰을 이용해 탐지 또는 차단하기 위한 솔루션이 WAF이다. WAF는 방화벽이나 IPS를 우회해서 들어오더라도 웹 서버 바로 앞단에서 실행되기 때문 에, 웹 서버를 지킬 수 있는 최후의 보루가 된다.

    1-3. ModSecurity와 모듈(Module)의 개념

    아파치(Apache)나 엔진X(Nginx) 계열 웹 서비스에서 WAF 구축 시 가장 많이 사용하는 것이 ModSecurity이다. MOD 로 시작하거나 끝나는 것들은 모듈(Module)을 의미하며, 단 독으로 실행되는 것이 아니라 아파치(HTTPD 또는 apache2) 같은 웹 서비스에 모듈처럼 동작하는 방식이다.

    1-4. OWASP CRS(Core Rule Set)

    OWASP 프로젝트 안에 ModSecurity가 포함되어 있으며, 그 안에 OWASP에서 제공하는 코어 룰셋인 CRS가 존재한다. 이는 스노트(Snort)에서 snort.org가 제공하는 코어 룰셋과 유사한 개념으로, 다운로드하여 테스트할 수 있다. 본 실습에서는 우분투에 아파치2를 구동 하고 ModSecurity 모듈을 설치하여 관리자가 직접 룰을 작성하는데, 이렇게 관리자가 작성 하는 룰을 커스텀 룰이라고 한다.

    176. WebGoat SQL Injection 취약점

    1. SQL Injection 개요

    1-1. 실습 범위

    WebGoat의 인젝션(Injection) 카테고리에서는 누메릭(Numeric) 기반 SQL Injection과 스트링(String) 기반 SQL Injection 문제를 다룬다. 수동 점검을 통해 전체 DB에 대한 내용 이 나오는 것까지 확인한 이후, 자동화 도구인 sqlmap을 이용한 점검을 진행한다.

    2. sqlmap 개요

    2-1. sqlmap의 역할

    수동 점검 외에 SQL Injection 취약점을 자동으로 점검할 수 있는 강력한 도구로 sqlmap이 있다. 이 도구는 터미널에서 실행하여 사용한다.

    2-2. 세션 값 확인

    WebGoat는 자바(Java) 기반이기 때문에 PHP 기반 애플리케이션에서 사용하던 PHPSESSID 가 아니라 JSESSIONID 라는 세션 값을 사용한다. JSESSIONID=[프락시 툴에서 확인한 값]

    3-1. 페이지 동작 방식 분석

    // 해당 파일을 data_dir 디렉토리에서 cat 명령어로 출력 cat data_dir/ + $_GET['id'] + ".txt" 각 id에 해당하는 유머 글은 txt 파일로 이 디렉토리 밑에 저장되어 있는 것으로 확인된다.

    3-2. Command Injection 테스트

    명령어 두 개 이상을 연결할 때 사용하는 세미콜론(;)을 이용하여 테스트를 진행한다.

    id 파라미터에 세미콜론으로 명령어를 연결하여 삽입

    id=100;cat /etc/hosts 이 경우 결과에 /etc/hosts 내용이 출력되지 않으며, id 뒤에 입력한 값 전체가 일반 문자열 처럼 인지된다. 뒤에 .txt 가 붙어버리면서 명령어로 인식되지 않은 것이 원인이다. 이를 우회하기 위해, 실제 존재하는 id 값을 명령어 마지막에 배치하는 방식을 사용한다.

    마지막에 실제 조회 가능한 id 값을 배치하여 명령어가 먼저 실행되도

    록 함 id=;cat /etc/passwd;cat data_dir/36 이렇게 입력하면 앞의 명령어( cat /etc/passwd )가 먼저 정상적으로 실행되고, 이후 마지막에 조회 가능한 값에 .txt 가 붙으면서 "파일을 찾을 수 없다"는 메시지가 출력되지만 실제로는 앞의 명령어가 이미 실행된 상태이다. 이러한 취약점이 발생하는 이유는 웹서버의 설정이나 코드에서 입력 값에 대한 검증을 하 지 않았기 때문이다. 만약 id 값의 범위(예: 10~38)만 지정하여 선택하도록 했다면 다른 값은 입력할 수 없었을 것이다.

    3. 이미지에 웹셸 코드 삽입 공격

    3-1. 공격 개요

    GmEdit는 확장자를 검증하지 않고 이미지 파일인지 여부만 검증하므로, 다음과 같은 공격 이 가능하다.

    1. 실제 이미지 파일을 준비한다.

    2. 이미지 뒤에 PHP 웹셸 코드를 삽입한다.

    3. 확장자를 .php 로 변경한 후 업로드한다.

    4. 업로드된 파일의 경로로 접근하여 명령어를 실행한다.

    3-2. ImageMagick 설치

    이미지 파일의 크기를 조정하고 뒤에 코드를 삽입하기 위해 imagemagick 도구를 설치한다.

    imagemagick 설치 전 업데이트

    sudo apt update

    imagemagick 설치

    sudo apt install -y imagemagick
