## 078. Docker 컨테이너 기술과 Linux 패키지 저장소(Repository) 개념

키지 저장소(Repository) 개념

### 1. Docker 개요

#### 1-1. Docker와 Docker Hub

Docker와 Docker Hub는 두 가지로 구분된다. Git과 GitHub의 관계와 유사하다.


| 구분 | Docker 생태계 | Git 생태계 |
|---|---|---|
| 도구 | Docker (컨테이너 관리) | Git (형상·버전 관리) |
| 저장소 | Docker Hub (이미지 원격 저장소) | GitHub (코드 원격 저장소) |
| 사이트 | hub.docker.com | github.com |

Docker: 컨테이너를 관리하기 위한 도구 Docker Hub: 다양한 이미지가 저장된 사이트 (hub.docker.com)

#### 1-2. 컨테이너 기반 개념

사용하고자 하는 시스템의 이미지와 운용체제를 컨테이너에 넣고 실행한다

사용이 끝나면 컨테이너를 중지하여 프로세스를 반환하고, 이미지를 삭제하면 용량도 회수된다

기존 VirtualBox, VMware Player 등 가상머신 도구에 비해 하드웨어적으로 더 자유롭게 사용할 수 있다

Docker가 설치된 어떤 시스템에서든 원하는 이미지를 다운받아 동일한 환경을 즉시 사용할 수 있다

Kubernetes 등을 이용한 클라우드 서비스도 컨테이너 기반 기술을 핵심으로 사용한다.

### 2. Docker Hub 활용

Docker Hub에는 기업 및 개인이 업로드한 공개 이미지가 다수 존재한다

이미지 이름 앞의 계정명: Docker Hub 가입 시의 계정 아이디 다운로드 수가 표시됨 (예: 1M+ = 100만 이상 다운로드)

내가 직접 만든 이미지도 나의 계정 밑에 업로드 가능하다

인터넷이 되고 Docker가 설치된 시스템이라면 어디서든 동일한 환경을 사용할 수 있다

Docker Hub에서 찾을 수 있는 이미지 예시는 다음과 같다.


| 이미지 예시 | 설명 |
|---|---|
| tensorflow | AI·머신러닝 환경 |
| python | 파이썬 실행 환경 |
| nginx | 웹 서버 |
| wordpress | WordPress 블로그 플랫폼 |
| loganalyze | 로그 분석 도구 |
| rockylinux | Rocky Linux 운용체제 |
| ubuntu | Ubuntu 운용체제 |

WordPress를 직접 설치하려면 웹 서버, PHP, 설치 파일 다운로드 등 복잡한 과정이 필 요하지만, Docker Hub에서 이미지를 받아 컨테이너에 넣고 실행하면 즉시 사용할 수 있다.

### 3. Docker 기본 명령어

#### 3-1. 핵심 명령어

모든 Docker 명령어 앞에는 공통으로 docker 를 입력한다.


| 명령어 | 기능 |
|---|---|
| docker pull <이미지명> | Docker Hub에서 이미지 다운로드 |
| docker push <이미지명> | 이미지를 Docker Hub에 업로드 |
| docker run <이미지명> | 컨테이너 실행 |
| docker ps | 실행 중인 컨테이너 프로세스 상태 확인 |
| docker images | 로컬에 다운로드된 이미지 목록 확인 |
| docker rm <컨테이너> | 컨테이너 삭제 |
| docker rmi <이미지> | 이미지 삭제 |
| docker --help | 사용 가능한 명령어 전체 목록 확인 ( -h 로도 사용 가능) |

docker run hello-world     ← 이미지가 없으면 자동으로 pull(다운 로드)한 후 실행 docker ps                  ← 실행 중인 컨테이너 목록 확인 (컨테이너 ID, 이미지명, 생성 시간, 포트 등 표시) docker images              ← 로컬에 저장된 이미지 목록 확인 docker pull ubuntu         ← Docker Hub에서 ubuntu 이미지 다운로드 docker push myimage        ← 나의 이미지를 Docker Hub에 업로드 (로그인 필요)

docker run 을 실행할 때 해당 이미지가 로컬에 없으면, Docker가 자동으로 Docker Hub에서 이미지를 pull(다운로드)한 후 실행한다.

push 작업은 기본적으로 Docker Hub에 로그인이 되어 있어야 한다.

#### 3-2. 이미지 태그

이미지 이름과 태그는 콜론( : )으로 구분한다

태그를 지정하지 않으면 기본값은 latest (최신 버전)

특정 버전을 받으려면 콜론 뒤에 태그를 명시한다

docker pull ubuntu             ← 태그 미지정 → latest(최신 버전) 다운로드 docker pull ubuntu:noble       ← ubuntu 24.04 (코드네임: nob le) 버전 다운로드 docker pull rockylinux:9       ← Rocky Linux 9 버전 다운로드

명령어 중심이 아닌 GUI 환경을 제공하는 도구 탐색기처럼 이미지를 탐색하고, 다운로드·업로드 작업을 쉽게 수행할 수 있다

Git의 GitHub Desktop과 유사한 개념이다

### 6. 저장소(Repository) 개념

#### 6-1. 패키지 관리 도구와 저장소

패키지 관리 도구는 외부 주소(저장소)에 있는 경로를 통해 패키지의 존재 여부를 확인한 후 다운로드 및 설치를 진행한다. 이때 필요한 것이 저장소(Repository, 레포) 파일이다.


| OS 계열 | 패키지 관리 도구 | 비고 |
|---|---|---|
| Ubuntu / Debian 계<br>열 | apt (또는 apt-<br>get ) | apt 가 apt-get 보다 개선된 버전; 현재는 apt<br>사용 권장 |
| Rocky / RHEL 계열 | dnf (이전: yum ) | dnf 가 yum 의 후속 버전 |

#### 6-2. 저장소 파일 위치


| OS | 저장소 파일 경로 | 비고 |
|---|---|---|
| Ubuntu (현재 버<br>전) | /etc/apt/sources.list.d/ 디렉토리<br>내 파일 | 기본 파일명: ubuntu.sources |
| Ubuntu (이전 버<br>전) | /etc/apt/sources.list | 현재 버전에서는 .d 디렉토리로 이<br>동됨 |
| Rocky / RHEL 계<br>열 | /etc/yum.repos.d/ 디렉토리 내<br>.repo 확장자 파일 | 파일명은 무관하며 확장자가<br>.repo 이면 저장소 파일로 인식 |

Ubuntu 현재 버전에서 /etc/apt/sources.list  파일을 조회하면, /etc/apt/sources.list.d/ubuntu.sources 로 이동되었다는 메시지가 표시된다.

#### 6-3. 저장소 파일 형식

Ubuntu 저장소 파일은 데비안(Debian) 계열이므로 Types: deb  형식을 사용한다. 파일 안에는 패키지를 다운로드할 수 있는 URL 경로와 키(key) 값이 포함되어 있다.

Rocky/RHEL 계열 저장소 파일도 URL 경로와 키 값이 포함되는 점은 동일하다

형식(포맷)이 다를 뿐, 저장소 추가·변경·삭제의 개념은 동일하다

#### 6-4. 저장소를 통한 패키지 설치 흐름

패키지 설치 명령 입력 ↓ 저장소 파일의 URL 경로 참조 ↓ 해당 경로에서 패키지 존재 여부 확인 ↓ 패키지 다운로드 및 설치 (의존성 패키지 포함)

#### 6-5. 저장소 추가 방법

저장소 파일에 없는 패키지는 경로가 없어 설치가 불가능하다. 이 경우 다음 두 가지 방법으로 저장소를 추가할 수 있다.


| 방법 | 설명 |
|---|---|
| 명령어를 통한 추가 | 저장소 추가 명령어 사용 |
| 파일 직접 편집 | 저장소 파일을 편집기로 열어 URL 경로와 키 값을 직접 추가·삭제·변경 |

저장소는 언제든지 추가·변경·삭제가 가능하다.

#### 6-6. 패키지 설치 불가 시 대처 방법


| 상황 | 대처 방법 |
|---|---|
| 기본 저장소에 패키지 없음 | EPEL 저장소 설치 후 재시도 |
| EPEL에도 없음 | wget 또는 curl 명령어로 소스를 직접 다운로드하여 설치 |

EPEL (Extra Packages for Enterprise Linux): 기본 저장소에서 설치되지 않는 패키지 대부분을 지원하는 대표적인 외부 저장소이다. EPEL을 설치하면 거의 대부분의 패키지를 설치할 수 있다.

### 7. sudo 명령어

sudo : 관리자 권한으로 뒤에 오는 명령어를 실행하는 명령 Ubuntu: 일반 사용자 계정으로 로그인 시 관리자 권한이 필요한 명령어에 반드시 sudo 를 앞에 붙여야 한다

Rocky/RHEL: 애초에 루트 계정으로 접속하는 경우가 많으므로 sudo 가 불필요한 경우가 있다

sudo apt update     ← 관리자 권한으로 패키지 목록 업데이트 (정상)

apt update          ← Permission denied (권한 거부) 오류 발생 sudo 를 붙이지 않고 관리자 권한이 필요한 명령을 실행하면 Permission denied 오류가 발생한다.

#### 7-1. apt vs apt-get


| 명령어 | 특징 |
|---|---|
| apt | 현재 권장하는 명령어; apt-get 의 기능이 통합되어 개선된 버전 |
| apt-get | 초창기에 나왔던 별도의 패키지 관리 도구; 현재도 사용 가능 |

### 8. wget과 curl 비교

저장소나 파일을 명령어로 다운로드할 때 대표적으로 사용하는 도구이다.


| 도구 | 특징 |
|---|---|
| wget | 특별한 옵션 없이 뒤에 URL 주소를 입력하면 해당 파일을 다운로드한다 |
| curl | URL 주소에 대한 요청 결과를 화면에 출력한다; 옵션 fsSL 을 사용하면 wget<br>과 같은 다운로드 역할을 수행할 수 있다 |

## 079. NMS(Zabbix)를 활용한 네트워크 관리 시스템 구축

관리 시스템 구축

### 1. NMS 개요

NMS: Network Management System (네트워크 관리 시스템)

단순히 네트워크만 관리하는 것이 아니라, 시스템 자산 전체를 관리하는 데 초점을 둔다

기업 내 다수의 노드를 효율적으로 관리하기 위한 솔루션이다

### 2. NMS의 필요성

#### 2-1. 대규모 노드 관리의 어려움

300개 노드를 보유한 기업을 예시로 생각해 보면, 관리 대상은 서버, 데스크탑, 노트북, 직원 휴대폰 등 모든 자산이 된다. 각 시스템에 대해 운용체제, 메모리, IP 주소, 담당 부서 등의 정보를 기록하는 대장(목록)이 필요하다.

수동 관리 시의 문제점:


| 상황 | 문제점 |
|---|---|
| 초기 등록 | 300개 노드를 직원이 직접 방문하여 정보를 확인하고 기입해야 함 |
| 변경 발생 | 장비 교체, 부품 업그레이드, OS 버전 변경, IP 변경, ISP 교체 시 다시 직접 방문<br>하여 수정 필요 |

네트워크는 항상 유동적으로 변화한다. 수동 관리만으로는 수백 개 이상의 노드를 효율적으로 유지하기 어렵다.

#### 2-2. NMS 도입 효과

최초 1회 등록만으로 이후 정보를 자동으로 수집한다

운용체제, CPU, 메모리, IP 주소 등의 변경 사항이 일정 주기마다 서버에 자동으로 반영된다

관리자는 NMS 서버 대시보드 한 곳에서 모든 노드의 정보를 확인할 수 있다

### 3. Zabbix 소개

Zabbix: 대표적인 NMS 솔루션 (zabbix.com 제공)

지원 범위: 클라우드, 네트워크, 서비스, IoT 등 다양한 환경 모니터링 웹 대시보드를 통해 정보를 표시한다

### 4. Zabbix 서버 구성 요소 (APM)

Zabbix는 웹 대시보드를 제공하므로 서버에 APM 구성이 필요하다.


| 구성 요소 | Ubuntu 패키지명 | 설명 |
|---|---|---|
| 웹 서버 (Apache) | apache2 | 웹 서비스 제공 (RedHat 계열은 httpd ) |
| PHP | php , php-fpm | Zabbix 웹 페이지가 PHP 언어로 구성됨 |
| DB (MariaDB) | mariadb-server | 수집된 데이터를 저장 |

PHP 8.3 버전 이상에서는 PHP-FPM이 추가로 필요하다.

### 5. Zabbix 관련 패키지


| 패키지명 | 역할 |
|---|---|
| zabbix-server-mysql | Zabbix 서버 본체 (MySQL/MariaDB 연동) |
| zabbix-frontend-php | 웹 프론트엔드 |
| zabbix-apache-conf | Apache 웹 서버 연동 설정 |
| zabbix-sql-scripts | DB 자동 생성 스크립트 |
| zabbix-agent2 | 에이전트 (클라이언트 모니터링용) |

zabbix-sql-scripts  패키지: Zabbix가 동작하기 위해 필요한 DB, 테이블, 필드를 자동으로 생성해 주는 스크립트 파일을 포함한다. 이 패키지가 실행되면 DB 구조를 수동으로 만들 필요가 없다.

### 6. Zabbix 저장소

Zabbix 공식 사이트(zabbix.com)에서 .deb  형식의 저장소 파일을 직접 제공한다

기본 저장소에는 포함되어 있지 않으므로, 저장소 파일을 먼저 설치해야 Zabbix 패키지를 설치할 수 있다

저장소 파일 설치 도구: dpkg  또는 debian-package 저장소 설치 후에는 반드시 apt update 로 저장소 목록을 갱신해야 한다

### 7. Zabbix 주요 기능

#### 7-1. 모니터링 대시보드

등록된 노드의 CPU, 메모리, 디스크, 네트워크 등을 시각화하여 표시한다

그래프, 바 차트 등 다양한 형태로 정보를 제공한다

일정 주기로 자동 업데이트된다

#### 7-2. 노드별 세부 기능

등록된 각 호스트를 클릭하면 다음과 같은 세부 기능을 이용할 수 있다.


| 기능 | 설명 |
|---|---|
| 대시보드 | 해당 노드의 상태 요약 표시 |
| 문제 확인 | 발생한 문제(이슈) 목록 |
| 그래프 | 시간별 성능 그래프 |
| 인벤토리 | 노드 자산 정보 추가·관리 |
| 호스트 정보 | 등록된 호스트 상세 정보 |
| 아이템 정보 | 수집 항목 정보 |
| Ping | 네트워크 연결 테스트 |
| Traceroute | 경로 추적 |
| OS 탐지 | 운용체제 자동 탐지 |

### 13. 시스템 로케일(Locale) 설정

PHP 환경 설정에서 타임존을 Asia/Seoul 로 설정했더라도, 시스템 로케일이 맞지 않으면 Zabbix 설치 화면에서 System locale 오류가 발생할 수 있다

이 경우 locales  패키지를 설치하고 로케일을 수동으로 재설정해야 한다


| 단계 | 명령어 |
|---|---|
| locales 패키지 설치 | sudo apt install locales |
| 로케일 재설정 | sudo dpkg-reconfigure locales |

재설정 후 Apache와 PHP-FPM 서비스를 재시작해야 변경 사항이 적용된다.

### 14. 가상머신 스냅샷 활용

|---|---|

## 080. PMM을 활용한 DB 모니터링

### 1. PMM 개요

PMM: Percona Monitoring and Management의 약자 Percona: PMM을 개발한 회사 (percona.com/monitoring)

기존에 존재하는 다양한 DB 시스템을 모니터링하고 관리하기 위한 툴이다

Docker 이미지 방식으로 설치를 지원한다

### 2. PMM 구조

PMM은 서버와 클라이언트 두 가지로 구성된다.


| 구성 요소 | 역할 |
|---|---|
| PMM 서버 | 모니터링 데이터를 수집·시각화·관리하는 서버; Docker 컨테이너로 실행된다 |
| PMM 클라이언트 | 모니터링 대상 시스템에 설치; 서버로 데이터를 전송한다 |

클라이언트에서 발생하는 DB 데이터를 서버가 수집하여 대시보드에 표시한다

서버와 클라이언트 간 통신이 가능해야 모니터링이 이루어진다

### 3. 모니터링 대상 항목

DB 모니터링의 핵심은 시스템 전체가 아닌 DB 자체에 집중한다는 점이다.


| 분류 | 모니터링 항목 |
|---|---|
| 하드웨어 | CPU 사용률, 메모리 사용량, 디스크 퍼포먼스 |
| 네트워크 | 네트워크 사용량 |
| DB 쿼리 | 쿼리 수량, 응답 속도, 지연 시간 |

### 4. PMM 기본 계정 정보


| 항목 | 기본값 |
|---|---|
| 사용자 이름 | admin |
| 패스워드 | admin |

최초 로그인 시 패스워드 변경 화면이 나타난다. 변경하지 않으려면 Skip을 선택한다. 실제 운영 환경에서는 패스워드를 변경하는 것이 원칙이다.

### 5. PMM 주요 기능

#### 5-1. OS 대시보드

모니터링 중인 시스템의 하드웨어 및 네트워크 자원(리소스)을 시각화하여 표시한다

세부 항목별 확인이 가능하다


| 확인 가능 항목 | 설명 |
|---|---|
| CPU | CPU 사용률 개요 |
| 디스크 | 디스크 입출력 및 사용량 |
| 메모리 | 메모리 사용량 |
| 네트워크 | 네트워크 트래픽 |

#### 5-2. Query Analytics (쿼리 분석)

DB로 들어오는 쿼리에 대한 통계 및 분석 결과를 제공한다

두 가지 모드로 운용된다


| 모드 | 설명 |
|---|---|
| Stored Metrics | 저장된 메트릭 기반 분석; 부하가 적다 |
| Real-time | 실시간 쿼리 분석; 시스템 부하 발생 가능 |

원하는 검색어를 통해 현재 들락날락하는 쿼리를 확인할 수 있다

DB에 쿼리가 발생하면 통계치(응답 속도, 지연 시간 등)가 이 화면에 나타난다

#### 5-3. Explorer (탐색)

로그, 트레이스(Trace), 프로파일(Profile)을 탐색하고 출력하는 기능이다

쿼리를 작성하여 특정 로그나 데이터를 조회할 수 있다

사용 가능한 데이터 소스: Metrics, 로그 등 Grafana와 연동이 가능하다

#### 5-4. Alert 룰 (경고 규칙)

임계값을 설정하여 조건이 충족되면 경고를 발생시키는 기능이다.

설정 가능한 Alert 항목:


| 항목 | 설명 |
|---|---|
| Alert Rules | 경고 조건(쿼리·임계값) 설정 |
| Contact Point | 경고를 전달할 대상 및 방식 지정 |
| Notification Policy | 경고 전달 정책 설정 |
| Silences | 경고 음소거 설정 |
| Alert Groups | 경고 그룹화 |
| Alert Settings | 전체 경고 설정 |
| Templates | 경고 템플릿 활용 |

Alert 룰 조건 예시는 다음과 같다.


| 예시 조건 | 의미 |
|---|---|
| 메모리 사용률 80% 초과 | 메모리가 80% 이상이 되면 경고 발생 |
| CPU 사용률 70% 이상 | CPU가 70% 이상이 되면 경고 발생 |
| 초당 쿼리 수 만 개 초과 | 쿼리가 초당 만 개 이상 들어오면 알람 발생 |

#### 5-5. All Dashboard (전체 대시보드)

기존 대시보드 항목을 추가·제거·수정할 수 있다

원하는 항목만 선택하여 커스텀 대시보드를 구성할 수 있다

우측 상단의 메뉴를 통해 새로운 대시보드를 직접 작성할 수도 있다

### 6. 오토 리프레시(Auto Refresh) 설정

기본값: 1분 초·분·시 단위로 리프레시 주기를 조정할 수 있다

수동 리프레시도 가능하다

리프레시 주기마다 수치 및 값이 실시간으로 업데이트된다

### 7. PMM 서버 자체 모니터링

PMM 서버 자기 자신도 모니터링 대상에 포함된다

서버 내부에서 사용하는 PostgreSQL DB가 기본으로 모니터링된다

모니터링 노드(Node) 수는 PMM 서버 자신 포함하여 카운트된다

### 8. MySQL(MariaDB) 연동 모니터링

MariaDB는 MySQL 계열에 해당한다

클라이언트에 MariaDB를 설치하고 PMM 전용 계정을 생성한 후 적절한 권한을 부여한다

클라이언트 등록 후 PMM 서버 대시보드의 MySQL 노드 수가 증가하면 연동 성공이다

기본 서비스 포트: 3306 (MySQL 계열 기본 포트)

PMM 모니터링에 필요한 권한 예시:


| 권한 | 설명 |
|---|---|
| SELECT | 데이터 조회 권한 |
| PROCESS | 실행 중인 프로세스 확인 |
| REPLICATION CLIENT | DB 복제 관련 정보 확인 |
| RELOAD | 설정 리로드 권한 |

동시 접속자 수에 대한 제한( MAX_USER_CONNECTIONS )을 설정하여 모니터링 계정의 접속 수를 제어할 수 있다.

### 9. 쿼리 소스(Query Source) 설정

기본값: 로그를 생성하여 서버로 전송 (부하 발생 가능)

Slow Log 옵션 사용 시: 부하를 줄이면서 모니터링 가능

### 10. 실제 운영 환경에서의 고려사항

실제 환경(웹 서버 + DB 서버 운영 중)에서는 DB로 들어오는 쿼리가 매우 많다

많은 쿼리를 처리하려면 충분한 하드웨어 사양이 필요하다

한 대가 아닌 다수의 머신(노드)을 동시에 등록하여 모니터링할 수 있다

노드가 추가될수록 대시보드의 노드 수 카운트가 증가한다

| — | Antivirus | 백신 | 악성코드를 탐지하고 제거한다. 알<br>약, V3 등 국내외 다양한 제품이 존<br>재한다. |
| DPI | Deep Packet<br>Inspection | 심층 패킷 검사 | 네트워크 트래픽에서 패킷의 헤더<br>뿐만 아니라 콘텐츠 데이터까지 심<br>층 분석하여 악성코드, DDoS 공<br>격, 인젝션 공격 등을 탐지하고 차<br>단하거나 통과시키는 장비이다. |
| EDR | Endpoint<br>Detection and<br>Response | 엔드포인트 탐지<br>및 대응 | PC, 노트북, 스마트폰, 프린터 등<br>엔드포인트에 설치된다. 사용자의<br>시스템 환경, 접근 습관, 사용 습관<br>등을 정밀 조사하며, 문제 발생 시<br>즉시 차단하거나 실시간 알림을 제<br>공한다. |
| DRM | Digital Rights<br>Management | 문서 보안 | PC에서 문서를 생성하면 실시간으<br>로 암호화하고, 인증된 사용자만 열<br>람할 수 있도록 하는 솔루션이다. |
| DLP | Data Loss<br>Prevention | 데이터 유출 방지 | HDD, USB, 메신저, 이메일 첨부파<br>일 등 데이터 이동 경로를 감시하여<br>정보 유출을 방지하는 솔루션이다. |
| NAC | Network Access<br>Control | 네트워크 접근 제<br>어 | 엔드포인트 단에 위치하며, 정책에<br>따라 각 엔드포인트의 네트워크 접<br>근을 허용하거나 차단한다. |
| SIEM | Security<br>Information and<br>Event<br>Management | 보안 정보 및 이벤<br>트 관리 | 연결된 서버·시스템으로부터 로그<br>를 수집하고, 시각화·분석·통계·백<br>업 및 대시보드를 통해 확인할 수<br>있도록 하는 솔루션이다. |
| ESM | Enterprise<br>Security<br>Management | 기업 보안 관리 | SIEM의 이전 명칭. 동일하게 로그<br>관리를 위한 시스템으로, 이름만 다<br>를 뿐 역할은 유사하다. |
| UTM | Unified Threat<br>Management | 통합 위협 관리 시<br>스템 | 방화벽, DDoS 장비, IDS, IPS 등<br>개별 보안 장비의 기능을 하나로 통<br>합한 장비이다. |
| VPN | Virtual Private<br>Network | 가상 사설망 | 보안 솔루션의 하나. Site-to-Site<br>VPN과 Remote Access VPN 유<br>형이 있다. |

### 2. 주요 솔루션 세부 설명

#### 2-1. NG 방화벽 (Next Generation Firewall)

기존 방화벽에서 발전한 다음 세대 방화벽 방화벽의 기본 역할 외에 여러 가지 보안 기능을 추가로 담당한다

#### 2-2. WAF (Web Application Firewall)

웹 서버 앞단에 위치하는 IPS 역할의 솔루션 룰을 통해 7계층(애플리케이션 계층)까지의 다양한 위협을 탐지한다

웹 해킹 기법에 대한 탐지를 목적으로 구축된다

#### 2-3. APT (Advanced Persistent Threat)

공격자가 기간 제한 없이 하나의 시스템을 고정 타겟으로 삼아, 느린 속도로 장기간 정보를 수집하면서 공격하는 방식이다

APT 보안 시스템은 이러한 공격을 탐지·분석·차단하는 역할을 한다

#### 2-4. EDR 엔드포인트 개념

엔드포인트: PC, 노트북, 스마트폰, 프린터 등 사용자가 직접 사용하는 장치 EDR이 설치되면 사용자 시스템 환경에 대해 정밀하게 조사를 진행하고, 이후 발생하는 문제에 대해 엔드포인트 단에서 차단하거나 실시간으로 알림을 제공한다

#### 2-5. SIEM vs ESM 비교


| 항목 | SIEM | ESM |
|---|---|---|
| 정식 명칭 | Security Information and Event<br>Management | Enterprise Security<br>Management |
| 주요 역할 | 로그 수집·시각화·분석·통계·백업·룰 설정·대<br>시보드 | 로그 관리 (동일한 역할) |
| 비고 | 현재 주로 사용되는 명칭 | 이전 명칭 |

#### 2-6. UTM (Unified Threat Management)

개별 보안 장비들을 하나로 통합한 장비 PFSense: 대표적인 UTM 장비 중 하나 원래 시작점은 방화벽이며, 추가적으로 IPS 역할·Anti-DDoS 역할 등을 패키지를 통해 기능 확장 가능 기능이 확장되면 UTM 장비로서의 역할을 수행한다

ASA: 방화벽만 하는 것이 아니라 방화벽 외에 여러 가지 일들을 담당한다

#### 2-7. VPN

이 과목에서는 Remote Access VPN 구축을 진행한다

PFSense를 통해 구축을 진행할 예정이다

### 3. 보안 솔루션 구축 전략

#### 3-1. 기업 환경에서의 기본 구성

기업 규모와 상관없이 가장 기본으로 도입되는 장비: 방화벽 방화벽을 기본으로, 내부 자산(에셋)의 중요도에 따라 추가적인 솔루션을 도입한다

통상적으로 하나의 보안 장비만으로 연결하는 경우는 거의 없으며, 두 세 개 이상의 솔루션을 레이어화하여 연결한다

DB가 있는 경우: DB 보안을 위한 솔루션을 별도로 구성해야 한다

#### 3-2. 보안의 한계와 비용 대비 효율

보안은 100%가 없다: 세상에 존재하는 모든 솔루션을 도입하더라도 100% 보안은 불가능하다

기업에서 솔루션 구축의 중심 기준: 비용 대비 효율성 사용하는 시스템과 내용에 따라 필요한 장비와 솔루션은 천차만별이다

⚠️ 모든 솔루션을 도입하면 보안은 강화되지만, 유지보수 및 관리 부담이 증가하고 비용이 상당히 올라간다. 투자 비용 대비 효율성이 얼마인지를 반드시 따져봐야 한다.

## 084. Zabbix

### 1. 클라이언트 등록 개요

#### 1-1. 등록 대상 OS

Zabbix NMS에 모니터링 대상으로 등록할 수 있는 클라이언트 운영체제는 리눅스 (Ubuntu)와 윈도우 두 종류이다. 서버 역할을 하는 머신과 클라이언트 역할을 하는 머신은 물리적으로 구분된 별도의 시스템이다.


| 구분 | 역할 | 설명 |
|---|---|---|
| Zabbix 서버 | NMS 서버 | 모니터링 데이터를 수집·관리하<br>는 중앙 서버 |
| Zabbix 에이전트 (클라이언트) | 모니터링 대상 | 서버에 등록되어 데이터를 전송<br>하는 시스템 |

#### 1-2. Zabbix Server 동작 상태 확인

클라이언트가 서버에 등록되거나 연결되려면 Zabbix 서버가 반드시 실행 중이어야 한다. 웹 대시보드 System Information 항목에서 Zabbix Server is running 값이 Yes인지 확인해야 한다. 값이 No인 경우, 해당 머신에서 Zabbix 서버 서비스를 재시작해야 한다.

### 2. 에이전트 환경 설정 파일

#### 2-1. 설정 파일 위치


| 운영체제 | 설정 파일 경로 |
|---|---|
| Linux (Ubuntu) | /etc/zabbix/zabbix agent2.conf<br>_ |
| Windows | 압축 해제 폴더 내 conf/zabbix agentd.conf<br>_ |

리눅스와 윈도우의 설정 파일은 동일한 구조와 항목으로 구성되어 있다.

#### 2-2. 주요 설정 항목


| 항목 | 설명 | 값 예시 |
|---|---|---|
| Server | 데이터를 전송할 Zabbix 서버<br>의 IP 주소 | 서버 IP (예:<br>192.168.100.110 ) |
| ServerActive | 능동 모드로 연결할 Zabbix 서<br>버의 IP 주소 | 서버 IP (예:<br>192.168.100.110 ) |
| Hostname | 대시보드에 등록할 때 지정한 호<br>스트 이름 | Zabbix server 또는 임의 지<br>정 |

⚠️ 서버(Zabbix Server) 자신을 모니터링할 때는 Server 항목에 127.0.0.1 (자기 자신)을 입력한다. 반면 클라이언트는 Server 항목에 Zabbix 서버의 IP를 입력해야 한다.

### 3. 포트 및 방화벽 정책

#### 3-1. 통신 포트 구조

Zabbix 서버와 클라이언트 간 통신에 사용되는 포트는 방향에 따라 다르다.


| 포트 | 방향 | 설명 |
|---|---|---|
| 10050/tcp | 서버 → 클라이언트 | 서버가 클라이언트에 데이터를<br>요청할 때 사용 |
| 10051/tcp | 클라이언트 → 서버 | 클라이언트가 서버로 데이터를<br>전송할 때 사용 |

#### 3-2. 방화벽 허용 정책


| 시스템 | 허용해야 할 포트/서비스 | 비고 |
|---|---|---|
| Zabbix 서버 | 10051/tcp | Zabbix 서버 수신 포트 |
| Zabbix 서버 | http (80), https (443) | 웹 대시보드 접속 허용 |
| Zabbix 서버 | 3306/tcp (MariaDB) | 데이터베이스 접속 허용 |
| Zabbix 클라이언트 (Linux) | 10050/tcp | 에이전트 수신 포트 |
| Zabbix 클라이언트<br>(Windows) | 10050/tcp | Windows Defender 방화벽에<br>서 허용 또는 방화벽 비활성화 |

firewall-cmd  명령어 사용 시, --permanent  옵션으로 정책을 영구 등록하고 --reload 로 적용해야 한다.

⚠️ 방화벽을 설치하지 않으면 모든 트래픽이 허용 상태가 되므로, 위와 같은 포트 허용 작업은 불필요하다. 방화벽 설치 후에는 SSH를 제외한 모든 포트가 기본적으로 차단된 상태가 된다.

#### 3-3. 서버 재시작 대상 서비스

방화벽 정책 변경 후, 서버에서 아래 서비스들을 재시작하여 정상 동작 여부를 확인한다.

# 서버에서 재시작해야 할 4개 서비스 systemctl restart zabbix-server     ← Zabbix 서버 systemctl restart zabbix-agent2     ← Zabbix 에이전트 (자기 자신 모니터링) systemctl restart apache2           ← 웹 서버 systemctl restart mariadb           ← 데이터베이스

### 4. 대시보드 호스트 등록

#### 4-1. 등록 위치

웹 대시보드에서 Data Collection → Hosts 메뉴로 이동하여 우측 상단 Create Host 버튼을 클릭한다. 최초 1회 등록 후에는 별도의 재등록이 필요 없다.

#### 4-2. Create Host 필수 항목


| 항목 | 설명 | 비고 |
|---|---|---|
| Host name | 식별할 호스트 이름 | 예: Ubuntu , Windows |
| Templates | 수집할 모니터링 항목 템플릿 | 별표(★) 표시 = 필수 항목 |
| Host groups | 소속 그룹 | 별표(★) 표시 = 필수 항목 |
| Interfaces → Agent | 에이전트 IP 주소 및 포트 | IP: 클라이언트 IP, Port:<br>10050 |
| Enabled | 활성화 여부 | 체크 확인 필수 |

#### 4-3. 템플릿 선택 기준


| 등록 대상 OS | 선택 템플릿 |
|---|---|
| Ubuntu / Linux | Template OS Linux by Zabbix Agent |
| Windows | Template OS Windows by Zabbix Agent |

템플릿은 Templates → Operating Systems 카테고리에서 선택한다.

템플릿은 해당 OS에서 수집 가능한 모니터링 항목들의 집합이다.

#### 4-4. 호스트 그룹 활용

실제 운영 환경에서는 부서별 또는 자산 분류별로 그룹을 생성하여 시스템을 구분·관리한다. 예를 들어 회계부 시스템은 회계부 그룹, 마케팅부 시스템은 마케팅부 그룹에 배치할 수 있다.

#### 4-5. 연결 상태 확인 (ZBX 버튼)

호스트 목록의 우측에 표시되는 ZBX 버튼 색상으로 연결 상태를 확인한다.


| 색상 | 의미 |
|---|---|
| 녹색 (Green) | 연결 정상, 모니터링 중 |
| 빨간색 (Red) | 등록은 됐으나 연결 불가 |
| 회색 (Gray, 비활성) | 에이전트 연결 자체가 안 된 상태 |

ZBX 버튼이 빨간색으로 표시될 경우, 방화벽 정책 및 에이전트 서비스 재시작 여부를 확인한다. 초기 연결 시 데이터가 수집되는 데 시간이 걸릴 수 있으므로, 잠시 후 다시 확인한다.

### 5. 모니터링 대시보드 기능

#### 5-1. 대시보드 접근 경로

등록된 호스트의 모니터링 데이터는 Monitoring → 호스트 선택 → 대시보드에서 확인할 수 있다.

#### 5-2. 기본 모니터링 항목


| 항목 | 설명 |
|---|---|
| File System (파일 시스템) | 디스크 사용량 및 여유 공간 (Linux: ext4 등) |
| Network Interface | 네트워크 인터페이스별 트래픽 현황 |
| System Performance | CPU 사용률, 메모리 사용률, 디스크 사용률 |

#### 5-3. 조회 기간 설정

우측 상단의 기간 설정 도구를 통해 확인하고자 하는 통계 기간을 지정할 수 있다.

어제, 오늘, 최근 5분, 최근 30분 등 단축 선택 가능 직접 날짜와 기간을 입력하여 조회 가능

#### 5-4. 아이템 추가

기본 제공 모니터링 항목 외에 관리자가 원하는 항목을 추가하거나 변경할 수 있다. 추가 가능한 항목은 인벤토리(Inventory) 메뉴에서 관리한다.

### 6. 알림(Alert) 및 보고서(Reports)

#### 6-1. Alert와 Trigger 개념


| 구성 요소 | 설명 |
|---|---|
| Trigger (트리거) | 경보를 발생시키는 조건의 시발점. CPU 사용률,<br>파일 시스템 사용률, 네트워크 트래픽 등에 임계값<br>을 설정한다. |
| Action (액션) | 트리거 조건이 충족됐을 때 수행할 동작. 관리자<br>휴대폰 알림, 이메일 발송, 모니터링 대시보드 알<br>림창 표시 등을 설정한다. |

Alert는 이전에 실습한 PMM(Percona Monitoring and Management)의 알림 기능과 동일한 개념이다.

#### 6-2. Reports(보고서)

Reports 메뉴를 통해 모니터링 결과 보고서를 생성할 수 있다.

스케줄 설정, 감사 로그 조회 등 다양한 보고 기능을 포함한다.

충분한 데이터가 수집된 후(최소 2~3일 이상) 활용하는 것이 적절하다.

### 7. 서버 성능 요구사항

Zabbix 서버를 포함한 관제 솔루션은 기본적으로 고사양 하드웨어를 요구한다. 서버의 CPU, 메모리, 저장 용량이 부족하면 모니터링 데이터 수집과 대시보드 표시가 느려지거나 비정상 동작이 발생할 수 있다. PMM을 비롯한 대부분의 관제 솔루션이 동일하게 높은 사양을 요구한다.

### 8. Windows 에이전트 설치 방식 비교

Zabbix 공식 사이트(zabbix.com)에서 윈도우용 에이전트를 다운로드할 때 두 가지 방식을 선택할 수 있다.


| 방식 | 설명 | 비고 |
|---|---|---|
| Archive (압축 파일) | 압축 해제 후 conf 폴더에서<br>설정 파일을 수동 수정하고, | 설정 파일 직접 편집 가능 |


| 방식 | 설명 | 비고 |
|---|---|---|
|  | bin 폴더에서 서비스를 직접<br>실행 |  |

MSI 방식은 설치 과정에서 서버 IP를 직접 입력하는 창이 나타나므로 설정이 간편하다. 단, 관리자 권한으로 실행하지 않으면 설정 창이 나타나지 않을 수 있다.

## 099. 클라우드 서비스의 개념과 유형, 클라우드 보안 및 AI 보안

우드 보안 및 AI 보안

### 1. 클라우드(Cloud) 개념

클라우드(Cloud)는 원래 '구름'을 의미하며, 네트워크 구성도에서 내가 관리하지 않는 인터넷 구간을 구름 모양으로 표현한 데서 유래한다. 이로부터 클라우드는 내가 관리하지 않는 다른 영역에 자원을 두고 서비스를 제공하는 방식을 의미하게 되었다.

관련 용어는 다음과 같이 구분된다.


| 용어 | 설명 |
|---|---|
| 클라우드 컴퓨팅 | 클라우드를 이용해 컴퓨팅 자원(서버, 스토리지, 네트워크 등)을 활용하는 기술적<br>방법 |
| 클라우드 서비스 | 클라우드 컴퓨팅을 기반으로 제공되는 다양한 서비스(저장장치, 소프트웨어 등 포<br>함) |

### 2. 클라우드 서비스 유형

#### 2-1. 서비스 모델 분류

클라우드 서비스는 공급업체가 관리하는 영역에 따라 아래와 같이 구분된다.


| 서비스 유형 | 약어 | 공급업체 제공 범<br>위 | 사용자 관리 범위 | 예시 |
|---|---|---|---|---|
| 인프라형 서비스 | IaaS | 네트워킹, 스토리<br>지, 서버, 가상화 | OS, 미들웨어, 애<br>플리케이션 | AWS EC2, S3 |
| 플랫폼형 서비스 | PaaS | IaaS 범위 + OS,<br>미들웨어까지 | 애플리케이션 개<br>발만 | AWS ECS |
| 소프트웨어형 서<br>비스 | SaaS | 전 영역(네트워킹<br>~ 애플리케이션) | 로그인 후 사용만 | MS Office 365 |
| AI형 서비스 | AIaaS | AI 개발·관리를 위<br>한 컴퓨팅 자원 | AI 서비스 개발 및<br>API 연결 | AWS Bedrock<br>등 |

⚠️ 예전 방식인 온프레미스(On-Premise)는 기업 내부에 서버, 네트워크, 스토리지 자원을 직접 구축하여 관리하는 방식이다. 장비 업그레이드, 장애 처리, 유지보수 비용이 지속적으로 발생한다는 단점이 있다.

#### 2-2. 클라우드 서비스의 비용 구조

클라우드 서비스는 사용량에 따라 비용이 책정된다. AWS 등 주요 서비스는 무료 기간을 제 공하나, 지정된 트래픽·용량 초과 시 또는 보안 장비 추가 시 일별로 비용이 즉시 청구된다.

⚠️ AWS EC2 등의 서비스를 이용할 경우, 예상치 못한 트래픽 발생이나 설정 오류로 인해 과금 폭탄이 발생할 수 있다. 반드시 과금 정책을 사전에 확인해야 한다.

### 3. 클라우드 배포 유형

클라우드는 운영 주체와 공개 범위에 따라 아래와 같이 구분된다.


| 유형 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 퍼블릭 클라우드 | AWS, 구글 클라우드, MS<br>Azure, 네이버 클라우드 등 외<br>부 업체가 제공하는 공개형 서<br>비스 | 확장 용이, 사용량 기반<br>비용 절감 | 커스터마이징 제한,<br>보안성 낮음 |
| 프라이빗 클라우드 | 기업 내부에서 자체 구축·운영<br>하는 비공개형 클라우드 | 높은 보안성, 대역폭 확<br>보, 커스터마이징 자유 | 구축·유지 비용 과다 |
| 하이브리드 클라우<br>드 | 퍼블릭 + 프라이빗을 혼합 운영<br>하는 방식 | 보안 요구도에 따라 자<br>원 분리 가능 | 운영 복잡성 증가 |
| 멀티 클라우드 | 두 개 이상의 클라우드(동일 또<br>는 이종 업체)를 함께 사용하는<br>방식 | 특정 업체 의존도 분산 | 관리 복잡성 |

현재 대부분의 기업은 중요도가 높은 정보는 프라이빗으로, 그 외 자원은 퍼블릭으로 운 영하는 하이브리드 또는 멀티 클라우드 방식을 채택하고 있다.

### 4. 클라우드 보안

클라우드 보안은 별개의 분야가 아니라, 로컬 환경에서 배우는 보안과 동일한 개념이 적용된다. 방화벽, 침입탐지 시스템 등 동일한 보안 요소를 클라우드 자원 앞단에 배치하여 운영하 며, 메뉴 또는 명령어 방식의 차이만 존재한다.

클라우드 계약 시에는 장애·사고 발생 시 서비스 업체의 책임 범위와 사용자의 책임 범위를 명확히 규정하는 계약서가 포함된다. 예를 들어, IaaS 서비스 이용 중 인프라 단에서 문제가 발생했다면 이는 클라우드 업체의 책임이 된다.

### 5. AI 보안

AI가 확산됨에 따라 AI 자체에 대한 보안 필요성도 높아지고 있다. AI 보안은 AI 활용 보안과 구별되며, AI 모델·데이터·프롬프트 자체의 취약점을 탐지하고 개선하는 것을 목적으로 한다.

주요 AI 공격 기법은 다음과 같다.


| 공격 기법 | 설명 |
|---|---|
| 프롬프트 인젝션 (Prompt<br>Injection) | 원래의 프롬프트 대신 악의적인 프롬프트를 삽입하여 AI로부터 의도<br>치 않은 결과를 도출하는 공격 |
| 데이터 결함 공격 | 학습 데이터에 결함을 유발하여 AI 모델이 잘못된 내용을 학습하도록<br>유도하는 공격 |
| 모델 어택 (Model Attack) | AI 모델 자체가 가진 취약점을 직접 공격하는 기법 |

AI를 활용한 보안 자동화는 'AI를 활용한 정보 보안'이며, AI 보안과는 구별된다. AI 보안은 AI 모델의 취약점 자체를 다루는 분야이다.

## 113. GoAccess를 활용한 웹서버 전용 실시간 로그 분석

시간 로그 분석

### 1. GoAccess 개요

#### 1-1. 특성

GoAccess는 웹서버 전용 로그 분석기이다.

웹서버와 관련된 로그만 추출하여 분석·시각화한다.

터미널에서 동작하기 때문에 빠른(Fast) 처리 속도를 제공한다.

오픈소스이므로 누구나 무료로 사용할 수 있다.

실시간 로그 분석을 지원한다.

터미널 출력 외에 HTML 파일로 저장하여 웹브라우저에서 시각화된 형태로 확인할 수 있다.

#### 1-2. 분석 대상 로그

아파치(Apache2) 기준 로그 경로는 다음과 같다.


| 로그 파일 | 내용 |
|---|---|
| /var/log/apache2/access.log | 웹 접속 성공 기록 |
| /var/log/apache2/error.log | 웹 접속 실패·에러 기록 |

로키 리눅스(RHEL 계열)에서는 httpd  디렉토리에 위치한다. 우분투·칼리·데비안 계열은 apache2  디렉토리를 사용한다.

### 2. GoAccess 설치

#### 2-1. 전제 조건

GoAccess 패키지는 기본 APT 저장소에 포함되어 있지 않으므로 별도 저장소를 먼저 설치해야 한다.

#### 2-2. 저장소 설치 순서

# 1단계: GoAccess 공식 저장소 키 및 설정 파일 다운로드 sudo wget -O - <https://deb.goaccess.io/gnupg.key> | sudo a pt-key add # 2단계: 저장소 목록 파일 등록 (echo 명령어 사용) # 채팅창에 제공된 명령어 사용 (deb.goaccess.io 경로 포함)

# 3단계: 저장소 업데이트 sudo apt update # 업데이트 후 dev.goaccess.io 경로가 목록에 등록되는 것을 확인 # 4단계: GoAccess 설치 sudo apt install goaccess ⚠️ 저장소 등록 명령어에서 대괄호( [ )가 하나 더 들어가거나 빠지는 경우 not assignment  오류가 발생한다. 명령어를 그대로 복사하여 사용할 것을 권장한다.

### 3. GoAccess 사용 — 터미널 모드

#### 3-1. 기본 실행

goaccess /var/log/apache2/access.log -c # -c: 터미널(컬러 출력) 모드로 로그 분석 결과 출력

#### 3-2. 로그 포맷 선택 메뉴

GoAccess 실행 시 로그 포맷을 선택하는 메뉴가 나타난다.


| 포맷 | 설명 |
|---|---|
| NCSA Combined Log Format | 혼합형(국제 표준), 가장 일반적으로 사용 |
| W3C | 윈도우 서버(IIS)에서 주로 사용하는 포맷 |

키보드로 항목을 이동하고 스페이스바로 선택(X 표시)한다.

선택 후 Enter 키를 누르면 분석이 시작된다.

종료하려면 Q 키를 누른다.

#### 3-3. 출력 정보

터미널 모드에서 확인할 수 있는 주요 항목은 다음과 같다.


| 항목 | 설명 |
|---|---|
| 날짜별 방문 수 | 일별 접속 통계 |
| Hits | 요청 횟수 |
| Transferred | 전송 데이터 크기 |
| Not Found | 404 오류 발생 수 |

새로고침 등 실제 접속이 발생하면 Hits 수치가 실시간으로 증가하는 것을 확인할 수 있다.

### 4. GoAccess 사용 — HTML 파일 저장 모드

#### 4-1. 정적 HTML 리포트 생성

현재까지 쌓인 로그를 HTML 파일로 저장한다.

sudo goaccess /var/log/apache2/access.log \\ --output report.html \\               ← 출력 파일명 지정 --log-format=COMBINED                ← 로그 포맷: 조합형(CO MBINED)

#### 4-2. 웹서버에서 HTML 파일 열기

생성된 report.html 을 웹서버의 Document Root에 복사하면 브라우저에서 접근 가능하다.

sudo cp report.html /var/www/html/report.html # 이후 브라우저에서: http://<서버 IP>/report.html 또는 처음부터 Document Root 경로를 출력 파일로 지정할 수 있다.

sudo goaccess /var/log/apache2/access.log \\ --output /var/www/html/report2.html \\ --log-format=COMBINED

#### 4-3. HTML 리포트 화면 구성


| 요소 | 설명 |
|---|---|
| 테마 선택 | 다크, 그레이 등 색상 테마 변경 가능 |
| 패널 옵션 | 표시할 패널(항목) 체크/해제 가능 |
| 레이아웃 | 와이드(Wide) / 버티컬(Vertical) 선택 가능 |
| 막대 그래프 | 날짜별·요청별 통계 시각화 |

### 5. GoAccess 사용 — 실시간 HTML 모드

#### 5-1. 실시간 옵션 추가

HTML 파일에서도 로그 변화를 실시간으로 반영하려면 --real-time-html  옵션을 추가한다.

sudo goaccess /var/log/apache2/access.log \\ --output /var/www/html/report2.html \\ --log-format=COMBINED \\ --real-time-html                     ← 실시간 갱신 옵션

#### 5-2. 동작 방식

명령 실행 후 터미널에 WebSocket Server Ready 메시지가 나타난다.

브라우저에서 해당 HTML 파일에 접속하면 로그 변경사항이 실시간으로 반영된다.

access.log 에 새로운 접속 기록이 추가될 때마다 브라우저의 수치가 업데이트된다. 단, 성능에 따라 약간의 시간 차이가 발생할 수 있다.

#### 5-3. 패널 옵션

브라우저 화면의 각 패널에는 Panel Options 버튼이 있으며, 이를 통해 차트·표 등 표시 형식을 개별적으로 조정할 수 있다.

### 6. GoAccess vs Wazuh 비교


| 항목 | GoAccess | Wazuh |
|---|---|---|
| 분석 대상 | 웹서버 로그 전용 | 시스템 전반 |
| 하드디스크 요구사항 | 별도 최소 사양 없음 | 최소 50GB 이상 |
| 시각화 | HTML 출력 지원 | 관제 솔루션 수준 대시보드 |
| 설치 난이도 | APT로 간편 설치 | 설치 사양 충족 필요 |


| 항목 | GoAccess | Wazuh |
|---|---|---|
| 사용 빈도 | 웹 서비스 전용 로그 분석에 자주 사용 | 종합 보안관제에 활용 |

GoAccess는 현장에서도 실제로 많이 사용되는 도구이다. 대부분의 서비스가 웹 기반으로 운영되기 때문에 웹 로그 분석 도구로서 활용도가 높다.

## 114. 나기오스(Nagios) 설치 및 웹 인터페이스 구성

이스 구성

### 1. 모니터링·로그 관리 도구

#### 1-1. 주요 도구 목록

아래 모니터링 및 로그 관리·분석·시각화 도구들은 보안관제 솔루션으로도 불린다.


| 도구 | 분류 | 특징 |
|---|---|---|
| Wazuh | SIEM | 하드디스크 최소 50GB 이상 요<br>구 |
| Nagios | 소규모 SIEM | 하드웨어 사양이 낮은 환경에서<br>사용 가능 |
| GoAccess | 웹서버 전용 로그 분석기 | 실시간 로그 분석, 터미널 동작 |
| Graylog | SIEM | 이전 프로젝트에서도 구축 사례<br>있음 |
| Splunk | 로그 관리·분석 | — |

#### 1-2. Wazuh 사양 요건

⚠️ Wazuh는 하드디스크가 최소 50GB 이상이어야 설치가 가능하다. 50GB 미만일 경우 설치 중간에 에러 메시지가 나타난다.

### 2. 나기오스(Nagios) 개요

#### 2-1. 특성

소규모 환경에서 사용할 수 있는 SIEM 수준의 도구이다.

Wazuh 등 상위 도구에 비해 비주얼적인 부분이 다소 낮다.

다양한 플러그인을 제공하며, 관리자가 원하는 플러그인을 추가 설치하면 비주얼 및 성능 면에서 확장이 가능하다.

기본 제공(무료) 버전으로 테스트 및 운영이 가능하다.

#### 2-2. 웹 인터페이스 기능

로그인 후 왼쪽 메뉴에서 다음 항목을 확인할 수 있다.


| 메뉴 항목 | 설명 |
|---|---|
| 현재 상태 | 호스트·서비스 현황 조회 |
| 문제 목록 | 발생한 문제 확인 |
| 보고서 | 로그 파일 기반 보고서 작성 |
| 경고 | 경고 이벤트 조회 |
| 시스템 명령어 | 시스템 관련 명령어 실행 |

기본 제공 기능 외에 추가로 보고 싶은 정보가 있으면 플러그인(nagios-plugins.org)을 다운로드하여 설치한다.

#### 2-3. 플러그인 추가

나기오스 공식 플러그인 저장소(nagios-plugins.org)에서 다양한 플러그인을 제공한다.


| 카테고리 | 수량 |
|---|---|
| 플러그인 전체 | 4,405개 |
| 테마·스킨 | 13개 |
| 애드온 | 755개 |
| 그래픽·로고 | 36개 |

리눅스에서 다운로드할 때는 브라우저 하단에 표시되는 다운로드 경로를 확인한 뒤 wget 또는 curl  명령어를 이용한다.

### 3. 나기오스 설치 절차 개요

#### 3-1. 사전 준비

나기오스 설치에 앞서 다음 두 가지를 먼저 수행해야 한다.

### 1. APT 업데이트 수행

### 2. 의존성 패키지 일괄 설치 ( build-essential , php , php-gd  등 포함)

#### 3-2. 사용자·그룹 생성

나기오스 운영에 필요한 전용 사용자와 그룹을 생성한다.

sudo useradd nagios          # nagios 사용자 생성 sudo groupadd nagcmd         # nagcmd 그룹 생성 # nagios 사용자를 nagcmd 그룹에 추가 sudo usermod -G nagcmd nagios # Apache 기본 웹 사용자(www-data)도 nagcmd 그룹에 추가 sudo usermod -G nagcmd www-data   ← 나기오스가 웹 기반으로 동작하므로 필요 www-data 는 아파치(Apache)의 기본 웹 사용자 계정이다. 나기오스가 웹 기반으로 동작하기 때문에 이 계정도 nagcmd 그룹에 포함시켜야 한다.

#### 3-3. 소스 다운로드 및 압축 해제

소스를 /tmp  디렉토리에 다운로드한 뒤 압축을 해제한다.

sudo wget <https://assets.nagios.com/downloads/nagioscore/r eleases/nagios-4.5.1.tar.gz> \\ -P /tmp                                        ← /tmp 디렉토리에 저장 tar -xf /tmp/nagios-4.5.1.tar.gz               ← 압축 해제 cd nagios-4.5.1                                  ← 소스 디렉토리로 이동 ls -a                                            ← 파일 목록 확인

#### 3-4. 컴파일 및 설치

소스 컴파일은 스노트(Snort) 등 다른 소스 패키지 설치와 동일한 흐름을 따른다: configure → make → make install.

# configure: 사용자·그룹 옵션 포함하여 환경 설정 sudo ./configure --with-nagios-group=nagios --with-commandgroup=nagcmd # make: 컴파일 수행 (워닝은 정상, 빨간 Fatal Error가 없으면 성공) sudo make all # make install: 빌드 결과물 설치 sudo make install

#### 3-5. 추가 설치 단계

make install  이후 나기오스 명령 모드·웹 인터페이스 등을 사용하기 위해 추가 설치가 필요하다.

sudo make install-init          ← 데몬 초기화 sudo make install-commandmode   ← 명령 모드 설치 sudo make install-config        ← 기본 설정 파일 설치 sudo make install-webconf       ← 아파치 웹 설정 파일 설치 ⚠️ 설치 중 make  과정에서 에러가 발생하면 sudo make all 처럼 sudo 를 반드시 포함하고 있는지 확인한다. 권한 관련 에러( permission denied )가 가장 흔한 원인이다.

#### 3-6. 플러그인 설치

기본 플러그인 패키지를 별도로 다운로드하여 동일하게 configure → make → make install 순서로 설치한다.

sudo wget <https://nagios-plugins.org/download/nagios-plugi ns-2.3.3.tar.gz> \\ -P /tmp tar -xzf /tmp/nagios-plugins-2.3.3.tar.gz cd nagios-plugins-2.3.3 # configure: 사용자·그룹 지정 sudo ./configure --with-nagios-user=nagios --with-nagios-gr oup=nagios sudo make                       ← 컴파일 sudo make install               ← 설치

### 4. 웹 인터페이스 접속 설정

#### 4-1. 아파치 모드 활성화

나기오스 설치 시 아파치 2가 자동으로 설치·실행된다.

# rewrite 모드 활성화 (URL 재작성 권한 부여) sudo a2enmod rewrite # cgi 모드 활성화 sudo a2enmod cgi # 아파치 서비스 재시작 sudo systemctl restart apache2 a2enmod 는 Apache2 Enable Module의 약자로, 특정 모드를 활성화하는 명령어이다.

#### 4-2. 웹 인터페이스 사용자(패스워드) 생성

웹 인터페이스 접속을 위한 전용 사용자를 생성한다.

sudo htpasswd -c /usr/local/nagios/etc/htpasswd.users nagiosadmin # nagiosadmin: 웹 인터페이스 접속용 사용자명 # 명령 실행 후 패스워드를 직접 설정 ⚠️ 여기서 생성하는 nagiosadmin  계정은 앞서 만든 nagios  시스템 사용자와 다르다.

nagios  사용자는 나기오스 데몬 운영용이고, nagiosadmin 은 웹 인터페이스 로그인용이 다.

#### 4-3. 나기오스 서비스 시작 및 활성화

# 서비스 시작 및 부팅 시 자동 시작 설정 sudo systemctl enable --now nagios

#### 4-4. 웹 브라우저 접속

http://<서버 IP>/nagios 사용자명: nagiosadmin 패스워드: 앞서 htpasswd 로 설정한 값

### 5. command not found  오류 원인

셸에서 명령어 실행 시 command not found  또는 pound  오류가 발생하는 경우는 주로 세 가지이다.


| 원인 | 설명 |
|---|---|
| 철자 오류 | 명령어 이름이 잘못 입력된 경우 |
| 미설치 | 해당 명령어가 시스템에 설치되어 있지 않은 경우 |
| 잘못된 디렉토리 | 명령어(또는 스크립트)가 있는 디렉토리가 아닌<br>곳에서 실행한 경우 |
