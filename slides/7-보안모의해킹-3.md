## 154. OWASP Juice Shop과 웹 취약점

### 1. OWASP Juice Shop 개요

#### 1-1. Juice Shop 소개

Juice Shop은 OWASP에서 제공하는 보안성이 약한(Insecure) 웹 애플리케이션이다. 쇼 핑몰 형태의 사이트이며, CTF(Capture The Flag) 방식으로 내부의 다양한 취약점을 찾아 해결하는 워게임(Wargame) 형식으로 구성되어 있다.

### 2. Juice Shop 설치 (Docker 이용)

#### 2-1. Docker 서비스 확인

# Docker 이미지 목록 확인 (서비스 동작 여부 확인) sudo docker images 현재 받아온 이미지가 없어도 명령어가 실행되면 Docker 서비스가 시작된 것이다.

#### 2-2. Juice Shop 이미지 풀링

Docker 이미지를 제공하는 사이트 경로에서 이미지를 다운로드한다. 계정명은 bkimminich 이며 이미지명은 juice-shop 이다.

실행 후 터미널에 Listening on port 3000 이 표시되면 정상 실행된 것이다.

## 155. XSS(Cross-Site Scripting) 취약점 유형별 실습

점 유형별 실습

### 1. XSS 취약점 개요

#### 1-1. XSS 정의 및 분류

XSS는 스크립트를 실행하는 취약점이다. 전체적으로 크게 두 가지로 분류된다.


| 유형 | 명칭 | 설명 |
|---|---|---|
| 반사형 | Reflected XSS | 입력한 스크립트가 즉시 반사되<br>어 출력 |
| 저장형 | Stored XSS | 입력한 스크립트가 서버에 저장<br>되어 이후 접속 시 자동 실행 |

세부적으로는 각각의 스크립트 삽입이 어디에서 이루어지는지에 따라 여러 가지 내용이 세 부적으로 나뉜다.

### 2. A3 - 반사형 XSS (Reflected XSS)

#### 2-1. Reflected GET

입력 폼에 이름을 입력하는 부분이 존재한다.

스크립트 태그로 document.cookie 를 삽입하면 쿠키 정보가 출력된다.

HTML 태그( h1  등)를 입력해도 적용된다.

반사형이기 때문에 기본적으로 나오는 부분들이 요청마다 달라진다.

검증하는 절차가 없기 때문에 스크립트가 실행된다.

<script>alert(document.cookie)</script>

#### 2-2. Reflected POST

GET 방식과 거의 동일하다.

차이점은 클라이언트가 서버에 요청할 때 메소드 값이 GET인지 POST인지 그 차이뿐 이다.

입력을 어디에서 하느냐의 차이만 존재한다.

### 3. A3 - Reflected JSON

#### 3-1. JSON 구조 이해

JSON은 파이썬이나 API 연결 시 활용하는 파일 형식이다. 키(key)와 해당 키에 대한 실제 값(value)으로 이루어진 구조를 JSON 구조라 한다.

#### 3-2. 실습 절차

영화 검색 폼이 존재하며 검색어에 따라 두 가지 반응이 나온다.


| 입력 결과 | 출력 |
|---|---|
| 없는 영화명 | 영화가 없다고 출력 |
| 있는 영화명 (예: Iron Man) | 해당 영화 정보 출력 |

페이지 소스(F12 → 개발자 도구)를 통해 처리 스크립트 확인 가능하다.

폼에서 사용자가 입력한 문자열이 리스폰스 JSON 형식에 삽입된다.

실행 중인 스크립트를 닫고, 새로운 스크립트를 삽입하여 실행 여부를 테스트한다.

// 처리 중인 스크립트를 닫고 새 스크립트 삽입 예시 </script><script>alert(document.cookie)</script> Low 레벨에서는 쿠키 정보가 정상적으로 출력되는 것을 확인할 수 있다.

JSON 형식의 데이터를 다룬다는 것 외에 스크립트를 실행하는 방식은 동일하다.

### 4. A3 - Ajax XSS

#### 4-1. Ajax JSON

문자 하나를 입력할 때마다 실시간으로 검색 결과가 나오는 방식을 Ajax라 한다.

페이지 소스 65번 라인에 결과를 출력하는 스크립트가 존재한다.

일반적인 스크립트 태그 삽입 시 아무 반응이 없다.

브라우저 자체에 XSS 보호 기능이 있을 수 있다.

이 경우 **프락시 툴(Burp Suite)**을 이용하여 해당 보호 기능을 우회한 후 진행해야 한다.

⚠️ Ajax JSON 페이지에서 일반적인 스크립트 삽입이 안 되는 경우, 프락시 설정을 통해 해당 기능을 무력화한 다음 동일한 방식으로 진행한다.

#### 4-2. Ajax XML

Ajax JSON과 유사하게 문자 하나씩 입력할 때마다 실시간으로 처리된다.

XML은 HTML과 동일한 ML(마크업 언어) 계열이며 웹브라우저에서 인식 가능한 언어 이다.

일반 스크립트 태그 삽입 시 반응이 없으면 이미지 태그를 활용한다.

<!-- 이미지 태그를 이용한 스크립트 삽입 시도 --> <img src=x onerror="alert(document.cookie)"> 특수 기호들이 URL 인코딩 또는 엔티티 값으로 변환되어 있을 가능성이 있다.

htmlspecialchars  함수에 의해 < 는 &lt; 로, > 는 &gt; 로 치환된다.

엔티티 값으로 치환하여 삽입하는 방법도 테스트해볼 수 있다.

<!-- 엔티티 변환 예시 --> &lt;img src=x onerror=&quot;alert(document.cookie)&quot;&g t;

프락시에서 요청을 잡아 해당 값을 직접 변경하는 방식으로도 진행할 수 있다.

### 5. A3 - Back Button (백버튼)

#### 5-1. 동작 원리

백버튼(뒤로 가기 버튼)을 클릭하면 이전 페이지로 이동한다.

#### 5-2. Burp Suite를 이용한 Referer 조작

Intercept ON 상태에서 Go Back 버튼을 클릭하면 트래픽이 캡처된다.

GET 방식으로 XSS_back_button.php  파일이 요청된다.

Referer 헤더에 이전 페이지 주소가 담겨 있다.

# Burp Suite Intercept에서 확인 가능한 Referer 헤더 Referer: http://[대상IP]/bWAPP/xss_ajax_1-1.php Referer 값을 삭제하고 스크립트를 삽입하여 Forward한다.

// Referer 조작 예시 (소스에서 확인된 따옴표 구조에 맞춰 작성) '';alert(document.cookie);' ⚠️ 따옴표의 짝을 맞추는 것이 핵심이다. 페이지 소스에서 document.location.href 에 사 용된 작은따옴표와 큰따옴표 구조를 먼저 확인한 후, 그에 맞게 구분자를 구성해야 한다.

### 7. A3 - eval()

#### 7-1. eval() 함수의 특성

eval() 은 함수가 아니라 PHP에서 지정된 예약 변수 중 하나이다.

eval()  뒤에 들어오는 값은 일반 문자열이 아니라 코드로 인식된다.

페이지 소스 확인 시 date()  함수를 eval() 로 실행하여 현재 날짜를 document.write() 로 출력한다.

표준 시간대(EST)로 설정되어 있어 날짜가 실제와 다르게 표시될 수 있다.

#### 7-2. 실습 절차

date  파라미터에 alert(document.cookie)  삽입 시 스크립트가 실행된다.

# URL 파라미터 조작 예시 ?date=alert(document.cookie)

OK를 누르면 undefined 가 출력된다. 이는 원래 실행되어야 할 date()  함수가 처리되지 않았기 때문이다.

eval()  안에 들어오는 인자 값을 코드로 인식하는 함수임을 확인할 수 있다.

### 10. A3 - phpMyAdmin (BB Code)

#### 10-1. phpMyAdmin 개요

phpMyAdmin은 웹브라우저 상에서 DB 서버에 접속하여 데이터를 수정하고, DB를 생성하 고, 테이블을 삭제하는 등의 작업을 할 수 있는 도구이다.

접속 경로: http://[대상IP]/phpmyadmin 로그인 후 DB 조작 메뉴가 표시된다.

2010년에 발생한 취약점(CVE 코드)과 관련된 공격 코드를 다운로드하여 활용 가능하 다.

#### 10-2. BB Code 개념

BB Code는 블로그나 게시판에서 글을 작성할 때 사용하는 HTML과 유사한 마크업 언어이 다.


| 구분 | 태그 형식 |
|---|---|
| HTML | <a href="URL">텍스트</a> |
| BB Code | [a@URL@]텍스트[/a] |

HTML은 꺾쇠 괄호( <> )를 사용하고, BB Code는 대괄호( [] )를 사용한다.

#### 10-3. BB Code를 이용한 XSS 실습

phpMyAdmin 로그인 창에 BB Code 형식으로 링크 태그를 삽입한다.

# BB Code 링크 삽입 예시 [a@http://[대상IP]@]클릭[/a]

삽입 후 엔터하면 자동으로 phpMyAdmin 사이트에 로그인된다.

### 11. A3 - PHP Self

#### 11-1. PHP_SELF 변수 개념

PHP_SELF 는 함수가 아니라 PHP에서 예약된 변수이다.

자기 자신의 PHP 파일 경로를 저장하고 있는 변수이다.

어떤 값을 입력하고 Go 버튼을 누르면 PHP_SELF 에 저장된 자기 자신의 경로 정보를 뿌 려주게 된다.

### 12. A3 - Referer

#### 12-1. Referer 헤더 개념

Referer는 참조 사이트를 나타내는 헤더 값이다.

어느 사이트에서 현재 페이지로 넘어왔는지를 표시한다.

#### 12-2. 실습 절차

Burp Suite Intercept ON 상태에서 새로고침하여 요청을 캡처한다.

Referer 헤더에 현재 페이지 링크가 담겨 있는 것을 확인한다.

Referer 값을 삭제하고 정상 URL 뒤에 스크립트를 이어 붙인다.

# Referer 조작 예시 http://[대상IP]/bWAPP/app/portal.php<script>alert(document.cookie)</script> Forward 시 스크립트가 정상적으로 실행되는 것을 확인할 수 있다.

Referer 외에도 Burp Suite에서 확인 가능한 다른 헤더 값도 얼마든지 수정 가능하다.

### 13. A3 - User-Agent

### 5. ARP (Address Resolution Protocol)

#### 5-1. ARP 개요

*ARP(주소 풀이 프로토콜)**은 IP 주소를 MAC 주소로 매핑하는 프로토콜이다. 반대 로 MAC 주소를 IP 주소로 매핑하는 것은 RARP(Reverse ARP)가 담당한다.

# ARP 테이블 확인 (Linux/Windows 동일) arp -a ARP 테이블은 영구적이지 않으며, 한 번이라도 통신에 사용된 시스템 또는 게이트웨이에 대 한 값들이 동적으로 나타난다. 명령을 내릴 때마다 개수나 내용이 달라질 수 있다.

#### 5-2. ARP 동작 원리

L2 스위치는 레이어 2에서 MAC 주소를 기반으로 통신한다. A PC(IP: .9)가 B PC(IP: .10) 로 통신하려 할 때:

### 1. A가 .10 번에 해당하는 ARP 테이블에서 MAC 주소를 조회한다.

### 2. .10 번의 MAC 주소가 BB 라면, 스위치의 MAC 주소 테이블에서 BB 가 5번 포트에 연

결되어 있음을 확인한다.

### 3. 5번 포트로 패킷을 전달한다.

#### 5-3. ARP 스푸핑 (ARP Spoofing)

공격자가 잘못된 ARP 정보를 네트워크에 계속해서 흘려보내면, 다른 시스템들이 잘못된 MAC-IP 매핑 정보를 받아들여 트래픽이 공격자에게 전달된다.

공격 시나리오:

실제 게이트웨이 IP: .1 , MAC: XX 공격자 IP: .100 , MAC: YY 공격자가 "MAC XX 는 .100 번이다"라는 잘못된 ARP 정보를 흘린다.

A, B PC들이 이 정보를 받아들여 게이트웨이로 트래픽을 보낼 때 공격자( .100 )에게 전 송하게 된다.

공격자는 ip_forward  기능을 활성화하면 프록시처럼 실제 인터넷까지 연결해주어, 피해자들 이 인터넷이 정상적으로 작동하는 것처럼 느끼게 만들 수 있다.

# ARP 스푸핑 실행 # 칼리 IP: 192.168.56.105 # 게이트웨이 IP: 192.168.56.1 arpspoof -i eth1 -r 192.168.56.1 192.168.56.105 ⚠️ 실제 네트워크 대역에서 ARP 스푸핑을 진행하면 당연히 문제가 된다. 실습 환경에서 만 진행한다.

#### 5-4. ARP 스푸핑의 영향

공격자가 망 사이에 ARP 스푸핑 정보를 계속 흘리면, 내부의 게이트웨이로 보내는 트래픽들 이 공격자 시스템으로 전달된다. 이렇게 ARP를 통해 중간에서 데이터를 가로채거나 변조하 는 것이 ARP 스푸핑이다.

### 6. SMTP 중간자 공격

### 2. Robots.txt 설정 미비 (A5 — robots.txt)

#### 2-1. robots.txt 개요

robots.txt는 검색봇(크롤러)들이 웹사이트에 들어왔을 때 어떤 디렉토리에 접근할 수 있는 지, 어떤 디렉토리는 가져가지 못하도록 할 것인지를 설정하는 파일이다. 보통 루트 디렉토 리에 위치한다.

웹사이트를 구축하는 이유 중 하나는 내 제품, 서비스, 글 등을 불특정 다수에게 잘 보이게 하 기 위함이다. 구글, 네이버, 다음 등 검색 엔진에 검색이 잘 되어야 하기 때문에 robots.txt가 필요하다. 숨기면 검색봇이 페이지를 수집해 가지 않아 검색 노출이 되지 않는다.

#### 2-2. robots.txt 문법

User-agent: *          # 모든 검색 엔진 봇에 적용 Disallow: /admin/      # 접근 금지 디렉토리 Disallow: /documents/  # 접근 금지 디렉토리 User-agent: Googlebot  # 구글봇에만 적용 Disallow: /            # 최상위 디렉토리 접근 금지 User-agent: Goodbot    # Goodbot에만 적용 Disallow:              # (아무것도 없으면) 모든 곳 접근 허용 Allow: /               # 허용


| 지시어 | 설명 |
|---|---|
| User-agent: * | 모든 검색 엔진 봇 |
| User-agent: Googlebot | 구글 검색봇 |
| Disallow: /경로/ | 해당 경로 접근 금지 |
| Allow: /경로/ | 해당 경로 접근 허용 |
| Disallow: (경로 없음) | 모든 경로 접근 허용 |

#### 2-3. Bee Box robots.txt 취약점 확인

Bee Box의 robots.txt를 확인하면, 특정 봇( Goodbot  등)에 대해 Disallow  없이 설정되어 있어 admin , documents , images , passwords  등의 디렉토리에 접근이 허용된 경우가 있다.

# Bee Box 접속 http://<Bee Box_IP>/bwapp/admin/ http://<Bee Box_IP>/bwapp/documents/ http://<Bee Box_IP>/bwapp/images/ http://<Bee Box_IP>/bwapp/passwords/ passwords  디렉토리에 들어가면 백업 파일들이 있으며, web.config.bak  파일 등을 다운로드 받아 확인할 수 있다.

# 다운로드된 파일 내용 확인 cd ~/Downloads ls # web.config.bak 파일이 존재 cat web.config.bak # 백업 파일 내용 확인 백업 파일에 중요한 정보(계정 정보, 설정값 등)가 들어가 있다면 당연히 문제가 된다.

⚠️ 직접 워드프레스나 웹사이트를 만들 때는 robots.txt 파일에서의 권한 설정을 신중하 게 해야 한다. 필요 없는 디렉토리나 접근하지 못해야 할 곳에 접근이 되지 않도록 Disallow를 정확히 설정해야 한다.

### 6. SSL 취약점 상세 분석

#### 6-1. BEAST (Browser Exploit Against SSL/TLS)

약자 풀이: Browser Exploit Against SSL/TLS TLS 1.0 이전 버전에서 암호를 생성할 때 블록 방식의 생성 방식을 사용하는데, 이 암호화 방식의 취약점을 이용한 공격 방식이 다.

현재는 거의 이 취약점이 없을 정도로 개선되어 있다.

#### 6-2. CRIME (Compression Ratio Info-leak Made Easy)

약자 풀이: C = Compression, R = Ratio, I = Info-leak, M = Made, E = Easy HTTPS 통신 시 데이터를 압축하면 대역폭을 줄일 수 있다. 예를 들어 1만 바이트를 100바이트로 압축하면 그 크기만큼 전송량이 줄어든다. 이 압축 기능의 취약점을 노려 공격하는 것이 CRIME이다.

압축 과정에서 중복되는 문자열(예: ABC , ABC )이 더 짧은 형태로 평문화되는 특성을 이용한다.

#### 6-3. BREACH (Browser Reconnaissance and Exfiltration via Adaptive Compression of

Hypertext)

약자 풀이: B = Browser, R = Reconnaissance, E = Exfiltration, A = Adaptive, C = Compression, H = Hypertext BREACH도 압축(Compression)이 포함되어 있으며, 본문 데이터를 압축할 때 gzip 등의 압축 방식에 대한 취약점을 노리는 공 격이다.

CRIME/BREACH를 막으려면: TLS 1.1 이상, 권장 사항은 TLS 1.3 이상 사용.

다만, 개발자가 최신 버전으로 설정해도 클라이언트가 최신 버전을 이용하지 않거나 브라우저에 설정이 되어 있지 않다면 접근 이 안 될 수 있다. 그렇기 때문에 낮은 버전도 함께 지원하는 설정을 하다 보면 문제가 발생할 수 있다.

#### 6-4. Heartbleed (하트블리드)

SSL 연결을 유지하기 위해 서버와 클라이언트 간에 주고받는 특별한 신호를 **하트비트(Heartbeat)**라고 한다. 심장이 뛰지 않으면 사람이 죽듯이, 이 신호가 계속해서 왔다 갔다 해야 두 시스템 간 연결이 유지된다.

하트블리드 취약점 원인: 하트비트 신호의 길이 정보를 제대로 검증하지 않는 구 버전의 OpenSSL에서 발생한다.

영향 범위: OpenSSL 버전 1.0.1 또는 1.0.2-베타 버전 Nmap을 이용한 Heartbleed 스캐닝:

# ssl-heartbleed NSE를 이용한 점검 sudo nmap -vv --script ssl-heartbleed -sV -p 8443 <Bee Box_IP> 스캐닝 결과:

대상: nginx 1.4.0 (8443 포트)

취약점: 있음 (OpenSSL 암호화 라이브러리에 버그 존재)

Risk Factor: High (위험도 높음)

OpenSSL 버전 1.0.1 또는 1.0.2-베타에서 발생 MSF 콘솔을 이용한 Heartbleed 스캐닝:

msf6 > search heartbleed # 8가지 도구 검색됨 BEAST/CRIME/BREACH/Heartbleed/POODLE 취약점 분석 # auxiliary/scanner/ssl/openssl_heartbleed 사용 msf6 > use 4 msf6 > show options msf6 > set rhosts <Bee Box_IP> msf6 > set rport 8443 msf6 > set verbose true msf6 > run 실행 결과에서 클라이언트 헬로 → 서버 헬로 핸드세이킹 과정과 함께 길이 정보를 조작하여 하트비트 신호를 보내고, 응답 내용 이 출력된다. 서버의 메모리에 있는 정보들이 응답으로 반환되는 것을 확인할 수 있다.

파이썬 공격 스크립트를 이용한 공격:

Bee Box 페이지에 있는 Attack Script 링크를 통해 파이썬 공격 코드를 다운로드받는다.

# 파이썬 2 버전으로 실행 (코드가 파이썬 2 기반인 경우) python2 heartbleed.py -p 8443 <Bee Box_IP> 실행 결과에서 클라이언트 헬로 → 서버 헬로 과정, 길이 정보, 하트비트 신호 전송, 응답 데이터가 출력된다. 서버가 검증하지 않 고 반환한 메모리 데이터를 통해 중요 정보를 획득할 수 있다.

python  명령어로 실행이 안 되면 python3 , python2 를 순서대로 시도한다. 파이썬 2로 만들어진 코드는 python2 로 실행해야 한다.

#### 6-5. POODLE (Padding Oracle On Downgraded Legacy Encryption)

약자 풀이:

P = Padding (여백)

O = Oracle On D = Downgraded (다운그레이드)

LE = Legacy Encryption 구글 보안 연구팀이 발견한 SSL 버전 3에서의 심각한 취약점이다. 암호화된 통신을 가로채서 비밀번호 등의 민감한 정보를 중간 에서 탈취하고자 하는 공격 방식이다.

Nmap을 이용한 POODLE 스캐닝:

# ssl-poodle NSE를 이용한 점검 sudo nmap -vv --script ssl-poodle -sV -p 443 <Bee Box_IP> 스캐닝 결과:

대상: Apache (443 포트)

SSL-POODLE 취약점 발생 가능 (정보 유출 가능, 약함)

CBC 코드를 패딩(여백)을 채워서 공격 가능 공격 도구 참조 사이트가 함께 출력 대응 방법: SSL 버전 3 대신 TLS 1.3 이상 사용

#### 6-6. SSL 2.0 (Deprecated Protocol)

Deprecated란 중요도가 떨어졌다는 의미다. 중요도가 떨어지면 앞으로 사용할 일이 점점 줄어들고 언젠가 사라진다. SSL 2.0 은 중요도가 점점 떨어져서 사라지게 되는 프로토콜이다.

대응 방법: SSL 2.0을 비활성화하고, SSL 3.0 또는 TLS 이상으로 전환.

## 160. SNMP 보안 설정 미비 취약점 및 WebDAV 설정 미비 취약점

WebDAV 설정 미비 취약점

### 1. SNMP (Simple Network Management Protocol)

#### 1-1. SNMP 개요

SNMP(Simple Network Management Protocol)는 단순 네트워크 관리 프로토콜이 다. 네트워크에 대한 관리를 위해 필요한 프로토콜로, NMS(Network Management System)를 구축할 때 사용하는 도구인 Zabbix에서 서버와 에이전트를 연결할 때 활용할 수 있다. SNMP를 통해 서버와 에이전트 간의 정보를 수집하고 저장한다.

#### 1-2. SNMP 설정 미비 취약점

SNMP에 설정에 대한 미비가 발생했을 때, 특정 시스템의 정보가 열거(Enumerate)되는 취 약점이 발생한다.

가장 큰 문제점: SNMP로 정보를 주고받을 때 사용하는 커뮤니티 그룹(Community Group)의 기본 이름이 public 과 private 이다. 이 이름을 변경하지 않으면, 공격자는 커뮤 니티 이름이 public 이나 private 임을 쉽게 추측할 수 있다.

⚠️ SNMP를 구성할 때는 반드시 public , private  등의 기본 커뮤니티 이름을 변경해야 한다. 또한 변경된 커뮤니티에 따라 접근 권한을 정확하게 설정하고, 접속할 수 있는 사용 자도 정확하게 지정해야 한다.

### 2. SNMP 실습

#### 2-1. SNMP 설치

sudo apt install -y snmp

#### 2-2. snmpwalk 명령어

snmpwalk 는 SNMP에서 커뮤니티 정보를 확인하는 명령어다.

# 옵션 설명 # -Os : 출력 형식 옵션 # -c public : 커뮤니티 이름 (public)

# -v 1 : SNMP 버전 1 sudo snmpwalk -Os -c public -v 1 <Bee Box_IP> snmpwalk 출력 결과 항목:


| 항목 | 내용 |
|---|---|
| 리눅스 버전 정보 | 최상단에 표시 |
| 타임 정보 | 시스템 가동 시간 |
| 문자열 값 | 아이디, 스트링 정보 |
| 네트워크 어댑터 정보 | ETH0, ETH1 등 |
| Hex값, IP 주소 | 네트워크 인터페이스 정보 |

## 161. XST(Cross-Site Tracing), DDoS 공격 기법, FTP 보안 취약점

공격 기법, FTP 보안 취약점

### 1. XST (Cross-Site Tracing)

#### 1-1. CORS와 XST 개요

A5 보안 설정 미비 항목 중 AJAX/CORS와 XST를 살펴본다.

CORS (Cross-Origin HTTP Request)란 클라이언트가 웹서버에 어떤 웹페이지를 요청 했을 때, 원래 요청한 도메인과 다른 도메인으로부터의 자원 연결이 필요할 때 발생하는 교 차 출처 HTTP 요청이다. 이 보안 설정을 잘못하거나 넘어가는 주소에 입력을 잘못하면 문제 가 될 수 있다.

#### 1-2. HTTP TRACE 메소드란

Bee Box A5에서 XST(Cross-Site Tracing) 항목을 보면 HTTP TRACE 메소드가 활성화되어 있 다고 나온다. 웹서버에 XST 취약점이 존재한다는 의미다.

TRACE 메소드는 루프백으로 가기 위한 경로를 추적할 때 사용하는 메소드다. 이러한 경로 추적을 하기 위한 메소드가 다른 보안 설정 없이 그냥 사용되면 쿠키 정보나 헤더에 들어가 있는 정보들을 찾아낼 수 있게 취약하게 만든다.

#### 1-3. Nmap NSE를 통한 TRACE 메소드 확인

전체 Nmap 스캐닝에서 80 포트를 살펴보면 http-methods  항목에서 TRACE 메소드가 사 용되고 있다고 취약점이 표시된다.

# Nmap 스크립트 엔진으로 메소드 확인 sudo nmap -p 80 --script http-methods <Bee Box_IP> 스캐닝 결과에서 지원되는 메소드와 함께 위험성이 있는 메소드로 TRACE가 표시된다.

GET, HEAD, POST, OPTIONS  — 사용 가능 TRACE                     — Potentially risky methods

#### 1-4. Burp Suite를 이용한 XST 확인

Burp Suite에서 인터셉트를 ON으로 설정하고, XST 관련 페이지를 요청한다.

# 요청 방식 변경 GET → TRACE GET 방식이 아닌 TRACE 메소드 값으로 변경한 후 Forward 하면, 웹브라우저에서 smxst.php  파일이 자동으로 다운로드된다.

다운로드된 파일의 내용을 확인하면 TRACE 방식으로 요청이 이루어진 것을 확인할 수 있 고, 요청했던 부분과 쿠키 정보가 그대로 저장되어 있는 것을 확인할 수 있다.

XST 취약점이 발생했을 경우, 경로 추적 메소드 값을 악용하여 기본적으로 쿠키나 헤더 에 있는 다른 값들을 가져올 수 있다. 헤더에 중요한 정보 값이 들어가져 있고 이런 식으로 다운로드가 이루어진다면 당연히 문제가 될 수 있다.

### 2. DDoS 공격 기법

A5 항목 중 Large Chunk Size, Slow HTTP, SSL Exhaustion, XML Bomb 등은 모두 DDoS 공격과 관련된 항목들이다.

#### 2-1. Large Chunk Size (청크 크기 공격)

덩치 큰 사이즈의 파일을 보내는 공격이다.

대상 포트: 8080 또는 8443 (nginx 웹서버)

공격 코드: CVE-2013-2028, 파이썬으로 작성 각각의 청크 사이즈와 데이터 값을 계속 증가시키면서 웹서버에 전송하여 Bee Box 머 신의 속도나 프로세서 처리율을 높인다.

#### 2-2. Slow HTTP DoS (슬로리스 HTTP 공격)

HTTP를 점점 느리게 하는 공격이다.

대상 포트: 80 (Apache 웹서버)

원리: 요청할 때 헤더값을 변조하여 웹서버에 보내면, 서버는 클라이언트가 요청하는 헤 더 정보가 완료되지 않았다고 판단하고 연결을 계속 유지하게 된다. 이러한 패킷을 여러 개 많이 보내면 서버의 가용성이 줄어든다.

Burp Suite에서의 확인 방법:

Burp Suite에서 요청 패킷을 캡처하면, 헤더 값들이 Hex 코드로 표시된다. 정상적인 요청 에서 헤더의 끝을 나타내는 Hex 코드( 20 75 3D 30 )를 서버가 확인하고 다음 단계로 넘어간 다.

공격자가 이 헤더 값들을 임의로 바꿔서 보내면, 서버는 헤더 정보가 완료되지 않았다고 판 단하여 클라이언트와의 연결을 계속 유지한다. 이러한 방식이 Slow HTTP DoS 공격이다.

Burp Suite의 Pretty/Raw/Hex 탭 중, Pretty는 복잡한 코드를 보기 좋게 정렬해주며, Raw는 원래 코드를 그대로 보여준다. Hex는 실제로 들어가는 코드 값들을 Hex 형식으 로 보여준다.

#### 2-3. SSL Exhaustion (SSL 고갈 공격)

SSL 연결 시 핸드세이킹 과정에서의 부하를 발생시키는 공격이다.

TCP 핸드세이킹 과정이 있듯이, SSL 연결 시에도 핸드세이킹 과정이 존재한다. SSL 핸드 세이킹 과정은 TCP보다 훨씬 더 많은 트래픽을 발생시킨다. 일반적인 상태에서도 15% 이 상의 부하가 발생한다.

# THC-SSL-DOS 도구 설치 apt install thc-ssl-dos # 도구 실행 sudo thc-ssl-dos <Bee Box_IP> <포트> --accept # 443번 포트 (HTTPS) sudo thc-ssl-dos <Bee Box_IP> 443 --accept # 8443번 포트 (nginx HTTPS) sudo thc-ssl-dos <Bee Box_IP> 8443 --accept Wireshark에서 동시에 패킷을 캡처하면, TLS 핸드세이킹 과정 패킷들이 대량으로 나타나 는 것을 확인할 수 있다.

Wireshark 관찰 내용:

클라이언트 → 서버: 서버 헬로(Server Hello) 메시지 전송 클라이언트 쪽에서 응답해야 할 부분이 없음 → 연결 상태를 계속 유지(플로딩)

#### 2-4. XML Bomb (XML 폭탄 공격)

XML 페이지를 요청할 때 악의적인 XML 코드를 계속 전송하여 서버의 CPU나 메모리 부하 를 발생시켜 속도를 느리게 하고 최종적으로 다운시키는 공격이다.

XML Bomb 코드는 엔티티(Entity) 값으로 구성되어 있다. HTML Special Characters  함수에 의해 < , >  등의 특수문자가 엔티티 값으로 변환된다. 서버는 요청된 엔티티 값을 확인하고 연결하기 위해 계속해서 자원을 소모하게 된다. 구글에서 XML Bomb 코드로 검색하면 다양한 공격 코드를 확인할 수 있다.

### 3. FTP 보안 취약점

#### 3-3. MSF 콘솔을 이용한 FTP 브루트포스 공격

#### 2-1. CGI 개념

CGI(Common Gateway Interface)는 웹 서버에서 외부 프로그램을 실행하여 그 결과를 웹 브라우저에 HTML로 반환하는 방식이다. PHP CGI 등에서 원격으로 코드를 실행할 수 있는 취약점을 나타낸다.

#### 2-2. 취약점 확인

Heartbleed, PHP-CGI RCE, eval 함수, phpMyAdmin XSS, Shell Shock 개념 Admin 디렉토리를 클릭하면 CGI 모드에서 PHP를 사용하고 있다는 안내와 함께 phpinfo 가 출력된다.

이는 Admin 디렉토리 안의 phpinfo.php 가 CGI 환경에서 PHP 코드가 실행된 결과임을 의미한다.

관련 취약점 코드로 CVE-2012-1823이 소개되었으며, Exploit-DB 등의 사이트에서 다운로드하여 대상 사이트에 공격을 시도할 수 있다.

#### 2-3. php.ini 설정과의 관계

PHP 환경설정 파일( php.ini )에서 allow_url_include  등의 기능을 켜거나(on) 끄는(off) 설 정이 잘못되어 있을 경우, 원격에서 코드를 실행할 수 있는 부분이 발생한다.

#### 2-4. php-cgi 옵션을 이용한 실습

### 3. A10 — Unvalidated Redirect and Forward

Shell Shock 실습, Unvalidated Redirect/Forward, bWAPP Extras 취약점 어딘가로 Redirect(재전송) 또는 Forward(전달)해 주는 기능과 관련된 취약점이다. 이 값 들은 헤드 또는 파라미터에 담겨 있다.

#### 3-1. 실습 1 (Redirect)

블로그 등 SNS 목록에서 항목을 선택하고 클릭하면 해당 사이트로 Redirect가 이루어 진다.

Burp Suite에서 Intercept를 켠 상태로 클릭 요청을 캡처하면, url 이라는 파라미터에 이동할 주소가 그대로 들어가 있는 것을 확인할 수 있다.

이 url  파라미터 값을 공격자가 준비한 피싱 사이트 주소로 변경하여 Forward하면, 사 용자가 의도하지 않은 사이트로 연결되는 것을 확인할 수 있다.

#### 3-2. 실습 2 (Forward)

fwd_2.php 와 같은 링크를 클릭하면 초기 사이트(포털 페이지)로 넘어가는 정상 동작을 먼저 확인한다.

Burp Suite로 요청을 캡처하면 ReturnURL 이라는 파라미터에 이동할 포털 페이지 주소 가 담겨 전달되는 것을 확인할 수 있다.

이 값을 임의의 도메인으로 변조하면 해당 도메인으로 연결이 이루어진다(실습 중 임의 도메인을 입력했을 때는 존재하지 않는 사이트라는 메시지가 표시되었다).

### 4. bWAPP 추가 취약점

#### 4-1. Click Hijacking (클릭재킹)

티켓 1개당 15유로, 10개 주문 시 클릭 체킹(Click Checking) 페이지로 이동하며, 확인 (컨펌)을 누르면 10개의 티켓을 주문했고 150유로가 발생했다는 메시지가 표시된다.

이 페이지가 정상적으로 동작한다는 것을 확인한 뒤, 앞서 계좌 정보 변경 실습에서 값 (갑, 티켓 수 등)을 변경했던 것과 동일하게 Burp Suite로 캡처하여 관련 정보를 변조할 수 있다.

클릭재킹은 사용자가 클릭하는 페이지에 대한 신뢰를 전제로, 실제로는 다른 페이지나 내 용이 나타나게 하는 방식의 공격이다.

#### 4-2. Client-side Validation (클라이언트 측 검증 우회)

비밀번호 변경 기능에서, 현재 비밀번호를 알고 있을 경우에만 새 비밀번호로 변경할 수 있 도록 되어 있다.

Shell Shock 실습, Unvalidated Redirect/Forward, bWAPP Extras 취약점 현재 패스워드를 일부러 틀리게 입력하고 새 패스워드를 입력한 뒤 변경을 시도하면, 현 재 패스워드가 맞지 않다는 메시지가 표시된다.

페이지 소스를 확인하면 특정 라인 구간에 걸쳐 스크립트 태그가 실행되며, 이 스크립트 가 현재 패스워드를 확인하는 함수, 새 패스워드와 확인용 패스워드가 동일한지 확인하 는 함수 등 유효성 검사를 담당하고 있다.

이러한 검증 로직은 클라이언트 측(브라우저)에서 실행되므로, 아래 두 가지 방식으로 우회할 수 있다.


| 우회 방식 | 설명 |
|---|---|
| Burp Suite로 파라미터 값 변조 | 요청을 캡처하여 서버로 전송되는 파라미터 값을 직접 변경 |
| 개발자 도구에서 검증 관련 태그<br>삭제 | 패스워드 체크 및 서브밋(submit) 관련 태그 값을 수동으로 삭제<br>하여 검증 자체가 동작하지 않도록 우회 |

#### 4-3. HTTP Parameter Pollution (HTTP 파라미터 폴루션)

파라미터 값을 오염(Pollution)시켜 공격하는 방법이다.

예를 들어 name 이라는 파라미터에 정상적으로 값을 입력하면 해당 값이 그대로 반영되 어 보여진다.

이 파라미터에 스크립트, HTML 태그, PHP 코드 등을 삽입하여 파라미터를 오염시키는 방식으로 테스트할 수 있다.

파라미터가 URL에 직접 노출되는 경우 Burp Suite 없이도 테스트가 가능하며, 노출되 지 않는 경우 Burp Suite 또는 ZAP Proxy로 캡처하여 진행해야 한다.

#### 4-4. HTTP Response Splitting (응답 분리)

응답(Response)에 대한 결과를 분리하여 클라이언트에 전달할 때 발생하는 취약점이다.

입력 값에 따라 응답하는 헤드가 그대로 반영될 때 사용되는 공격이며, 특히 계획 문자 (개행 문자, \r , \n  등)를 삽입하여 응답 자체를 분리시키고 악의적인 헤드나 본문을 주입하는 방식이다. 이를 CRLF라고도 한다.

이를 실습하기 위해서는 소스 코드나 PHP 코드 등을 통한 별도 작업이 필요하다.

현재는 서버의 방어 로직이 정교해져서 HTTP Response Splitting 자체를 실제로 수행 하기는 어려워진 편이다.

#### 4-5. Verb Tampering (메서드 값 변조)

새로운 패스워드로 변경하는 기능에서, 현재 패스워드를 입력하지 않아도 언제든지 비밀번 호를 변경할 수 있는 취약점이다.

Shell Shock 실습, Unvalidated Redirect/Forward, bWAPP Extras 취약점 화면 형태는 앞서 다룬 비밀번호 변경 기능과 동일하다.

Burp Suite로 요청을 잡아 사용자 이름 값이나 패스워드 값을 다른 값으로 변조하여 전 달하면, 실제로는 지정한 사용자가 아닌 다른 사용자의 패스워드가 변경되거나, 입력했 던 것과 다른 패스워드로 변경되는 결과가 나타난다.

이 방식은 주로 인증(認定)을 우회하는 데 사용된다.

용어는 다르지만 근본적으로 HTTP 요청의 값을 변조하는 방식이라는 점에서 앞서 다룬 취약점들과 동일하다.

|---|---|
| Headers | 헤더에 포함된 값들을 통한 정보 노출 |
| PHP Version /<br>phpinfo | phpinfo 함수가 실행되면 PHP 관련 정보가 노출됨 |
| Robots.txt | 어떤 디렉토리에 검색 봇이 접근 가능한지/불가능한지가 기록되어 있어 정<br>보 노출로 이어질 수 있음 |
| Favicon | 사이트 탭에 표시되는 아이콘 이미지 파일 |

Favicon과 관련된 실습은 다음과 같이 진행한다.

Burp Suite로 응답(Response) 메시지를 확인하면 헤드 태그 안에 Favicon 이미지 파 일(예: favicon_drupal.ico )의 경로가 href  속성으로 연결되어 있는 것을 확인할 수 있 다.

이 경로와 파일명을 알면, 실제로 노출되는 Favicon 이미지나 연결 경로를 다르게 조작 할 수 있다.

또한 개발자에 따라 Favicon 이미지 파일 안에 별도의 텍스트 등을 숨겨 두는 경우가 있 으며, 이 경우 스테가노그래피(Steganography) 관련 도구(예: 스테가노 시크)를 이용 해 이미지 안에 숨겨진 정보를 확인할 수 있다.

#### 4-7. Insecure iframe Login Form (안전하지 않은 iframe 로그인 폼)

로그인 폼이 iframe(액자) 형태로 만들어져 있으나 보안성이 확립되어 있지 않은 취약점이 다.

테스트 계정(예: test / 1234)으로 로그인을 시도하면 iframe 안에 로그인 폼 내용이 표 시되는 것을 확인할 수 있다.

F5(새로 고침)를 하면 원래 화면으로 돌아온다.

Shell Shock 실습, Unvalidated Redirect/Forward, bWAPP Extras 취약점 Burp Suite로 Intercept를 켜고 로그인 요청(헤드와 본문)을 캡처한 뒤, 본문에 iframe 태그를 삽입하는 방식으로 원하는 프레임 안의 콘텐츠(사이트, 그림 등)를 지정 할 수 있다.

원리 자체는 XSS와 동일하며, 삽입하는 대상이 스크립트인지 HTML 태그(iframe)인지 PHP 코드인지의 차이만 있을 뿐이다.

#### 4-8. Unrestricted File Upload (제한 없는 파일 업로드)

업로드되는 파일의 확장자나 내용에 대한 검증 절차가 없는 취약점이다.

공격에 이용할 수 있는 cmd.php  파일을 업로드하면 정상적으로 업로드는 되지만, 실행 할 수 없다는 메시지가 표시된다.

확장자를 이미지 형식( cmd.php.jpg )으로 위장하여 업로드를 시도하고, Burp Suite의 Intercept로 업로드 요청을 캡처한 뒤 .jpg  확장자를 삭제하고 Forward하면 cmd.php 파일이 그대로 업로드된다.

## 164. SSRF·XXE, CSRF, 그리고 Drupal SQL Injection

SQL Injection

### 1. SSRF (Server Side Request Forgery)

서버 측에서 요청을 대행하도록 만드는 취약점이다.

#### 1-1. CSRF와의 비교


| 구분 | 요청을 대행하는 주체 | 특징 |
|---|---|---|
| CSRF | 클라이언트(공격자가 권한 있는 관<br>리자에게 요청을 대행시킴) | 권한이 없는 클라이언트가 권한이 있는 관<br>리자에게 특정 작업을 수행하도록 유도 |
| SSRF | 서버 | 권한이 있는 서버에게 요청 대행을 시켜 공<br>격자가 원하는 결과를 만들어냄 |

#### 1-2. 관련 내용

스캐닝을 통해 RFI 여부를 확인하고, XXE를 통해 내부 네트워크에 침투하는 방식이 소 개되었다.

예시로 2013년에 발견된 삼성 스마트 TV의 SSRF 취약점(CVE)이 언급되었으나, 실습 환경에 스마트 TV가 없어 실제 공격 시연은 진행하지 않았다.

XXE를 통해 내부 네트워크 자원에 접근하는 것도 SSRF와 연관된 내용으로 소개되었 다.

### 2. XXE (XML External Entity)

XML 외부 객체(External Entity)를 이용한 공격이다. XML은 HTML과 유사한 마크업 언 어이다.

#### 2-1. 취약점 원리

XXE는 앞서 학습한 IDOR(Insecure Direct Object Reference, 객체 모델 참조)와 유사 한 개념으로, 여기서의 객체 모델이 XML 객체라는 점에서 차이가 있다.

#### 2-2. 실습 절차 (Secret Message 리셋 기능)

bWAPP의 리셋 기능(예: AnyBox 리셋)을 클릭하면, 로그인한 사용자의 Secret Message가 초기화된다.

Burp Suite로 Intercept를 켜고 해당 요청을 캡처하면, 본문(Body) 부분이 XML 태그 로 구성되어 있는 것을 확인할 수 있다.

이 XML 태그(사용자 계정, Secret Message 값 등)를 변조하여 전송하면, 다른 사용 자의 Secret Message를 임의로 변경할 수 있다.

### 3. A8 CSRF (Cross-Site Request Forgery)

권한이 없는 클라이언트가 권한이 있는 사용자(관리자 등)에게 특정 요청을 대행시키는 공격 이다.

#### 3-1. 공격 수단

메일, 문자메시지, 게시판, 메신저 등 다양한 수단을 통해 요청을 대행시킬 수 있다. 예를 들 어 XSS 취약점을 이용하여 공격자가 원하는 Secret Message나 패스워드로 변경되도록 요청을 유도할 수 있다.

#### 3-2. Transfer Amount 실습

계좌 정보 화면에서 현재 잔액(예: 1000유로)이 표시된다.

100유로를 송금하면 잔액이 900유로로, 이어서 200유로를 송금하면 700유로로 변경 되는 정상 동작을 먼저 확인한다.

이 송금 기능의 URL 또는 게시판에 URL을 삽입하는 방식으로 CSRF를 실습할 수 있 다.

실제 공격에서는 관리자의 메일로 피싱 메일(이벤트 당첨 등)을 보내거나, 메신저를 통 해 클릭을 유도하는 방식이 사용될 수 있으며, 메신저 내용에 iframe이나 이미지의 src 속성을 이용한 코드를 삽입해 둘 수 있다.

관리자가 클릭하는 순간 해당 요청이 전송되어 실제 계좌 변경 등의 작업이 이루어지게 된다.

계좌 정송(송금) 권한을 가진 관리자가 공격자가 의도한 요청을 대신 실행하게 만드는 것 이 CSRF의 핵심이다.

### 4. A9 — Buffer Overflow(BOF) 개념

버퍼 사이즈가 초과되었을 때 실제 수행해야 할 작업이 비정상적으로 동작하거나, 공격자가 원하는 코드가 실행되면서 완전히 다른 동작을 하도록 만드는 취약점이다. 이번 실습 환경에 서는 별도로 실습을 진행하지 않고 개념만 다루었다.

### 5. Drupal SQL Injection

Drupal(CMS)에서 2014년에 발견된 SQL Injection 취약점이다.

#### 5-1. 수동 점검

로그인 폼 등에 작은따옴표( ' )와 임의의 패스워드를 입력한 뒤 반응을 확인하고, 다른 값으 로도 반복 테스트하며 반응을 비교하는 방식으로 점검할 수 있다.

#### 5-2. SQLMap을 이용한 점검

파라미터( q  등)에 실제 어떤 취약점이 있는지 SQL 맵과 같은 점검 도구를 통해 테스트할 수 있다.

#### 5-3. MSF 콘솔을 이용한 공격 실습

# msfconsole 실행 후 Drupal 관련 공격 모듈 검색 search drupal search drupal type:exploit platform:multi 검색 결과 중 exploit  디렉토리의 multi/http  하위에 있는 Drupal 관련 모듈을 사용한 다.

해당 모듈은 파라미터 키 값에 SQL Injection을 수행하도록 되어 있으며, 공격에 성공 하면 기본 페이로드로 Meterpreter 세션을 생성한다.

# 공격 대상 및 옵션 설정 use [검색된 drupal 모듈 경로] set RHOST [Bee Box IP]

set LHOST [Kali IP] set TARGETURI /drupal show options run show options 로 설정값이 올바른지 확인한 뒤 run  또는 exploit  명령으로 공격을 실행 한다.

세션(session)이 생성되면 SQL Injection 공격이 성공한 것이며, 이후 Meterpreter 셸이 연결된다.

연결된 Meterpreter 셸에서 sysinfo , ls  등 다양한 명령어를 통해 정보를 확인할 수 있다.

동일한 취약점을 CVE 코드(2014년 발견, CVE-2014-3704)를 통해 다운로드한 PHP 공격 코드로도 직접 실행하여 검증할 수 있다.

#### 5-4. 대응 방안

모든 보안의 가장 기본은 최신 버전으로의 패치 또는 업그레이드이다. 최신 버전이라는 것은 이미 알려진 보안 취약점에 대한 패치가 적용되었다는 것을 의미한다.

## 165. 민감 데이터 노출(A6) 취약점

### 1. Clear Text HTTP / Text Files 취약점

평문(Clear Text)으로 데이터가 전송되는 두 가지 사례를 다룬다. 클리어 텍스트는 암호화 되지 않은 평문 데이터를 의미하며, 암호화된 데이터는 치퍼문(Cipher text)이라고 한다.

#### 1-1. Clear Text HTTP

로그인 트래픽을 Wireshark로 캡처하여 데이터 노출 여부를 확인할 수 있다.

애플리케이션에서 Wireshark를 실행하고 캡처를 시작한 상태에서 로그인을 진행한다.

캡처된 패킷에서 TCP 핸드셰이킹 과정 이후 실제 데이터가 확인된다.

캡처된 패킷을 우클릭하여 Follow  → HTTP Stream 을 선택하면 클라이언트와 서버 간 주고받은 HTTP 데이터 전체를 확인할 수 있다.

HTTP Stream 결과의 바디(Body) 부분에서 로그인 시 입력한 패스워드가 그대로 노 출되는 것을 확인할 수 있다.

Wireshark에서 스트림 정보를 확인할 때, 상단에 붉은색으로 표시되는 내용은 리퀘스트 (Request) 메시지이고, 하단은 응답(Response) 메시지를 나타낸다.

#### 1-2. Text Files

계정 정보를 텍스트 파일로 저장하는 기능(Insert 기능)에서도 동일한 취약점이 나타난다.

임의의 계정 정보(예: 아이디, 패스워드)를 입력하고 계정을 추가하면 계정이 생성되었 다는 메시지와 함께 파일을 다운로드하거나 삭제할 수 있는 기능이 제공된다.

다운로드한 파일을 확인하면 계정 정보가 암호화되지 않은 일반 텍스트 파일로 저장되 어 있는 것을 확인할 수 있다.

동일하게 Wireshark로 패킷을 캡처하여 HTTP Stream을 확인하면 입력했던 계정 정 보가 그대로 노출되는 것을 확인할 수 있다.

#### 1-3. 대응 방안

암호화 방식(알고리즘)을 통해 데이터를 암호화하여 전송해야 하며, 프로토콜 자체도 보안이 확립된 HTTPS를 통해 전송이 이루어져야 한다.

### 2. Host Header Attack (Post Head Attack)

이메일을 입력하고 리셋을 진행하면 로그인한 사용자의 Secret Message를 초기화하는 기 능에서 발생하는 취약점이다.

#### 2-1. 취약점 원리

HTTP 리퀘스트 메시지에는 여러 헤드(Head) 값이 존재하며, 그중 Host 헤드 값이 포함되 어 있다. 이 Host 헤드 값을 변조하는 방식의 공격이다.

웹브라우저에서 프락시(Proxy) 설정을 하고 Burp Suite를 실행한다.

리셋 버튼을 클릭하기 전에 인터셉트를 켜서(Intercept On) 요청을 잡는다.

패킷에서 헤드 부분과 바디(Body, 본문) 부분을 구분할 수 있으며, 헤드 값 중 Host 값 에는 현재 접속 중인 서버(Bee Box)의 IP가 들어가 있다.

이 Host 값을 공격자(Kali)의 IP로 변경하고, Kali에 동일한 경로와 이름으로 페이지를 만들어 두면 공격자가 의도한 페이지(피싱 사이트 등)로 연결을 유도할 수 있다.

⚠️ 실제로 테스트해 보려면 Kali에서 Python이나 Apache2를 이용해 웹서버를 구축하 고, 동일한 경로에 동일한 이름의 파일(예: 포털.php)을 만들어 Post Head 값을 변경하 여 공격을 진행했을 때의 결과를 확인해 볼 수 있다.

#### 2-2. Post Head Attack Reset Poisoning

리셋(Reset) 기능에서 Secret Message를 변경하고 초기화할 수 있는 페이지에서도 동일 하게 Post Head 값을 변조하는 방식의 공격이 이루어진다.

### 3. HTML5 Web Storage Secret

웹 저장소(Web Storage)에 Secret Message가 저장되는 것과 관련된 취약점이다.

#### 3-1. Web Storage 개념

웹 저장소는 브라우저가 아닌 클라이언트의 로컬에 저장되는 개념이 아니라, 웹 저장소 자체 를 나타낸다. 쿠키(Cookie)와는 저장 용량이나 유지 기간 등에서 차이가 있다.


| 저장소 구분 | 설명 |
|---|---|
| 캐시 스토리지 (Cache<br>Storage) | 개발자 도구의 Storage 항목에서 확인 가능 |
| 로컬 스토리지 (Local<br>Storage) | 로그인 사용자 이름, Secret Message 등이 저장되어 있는 것을 확<br>인 |


| 저장소 구분 | 설명 |
|---|---|
| 세션 스토리지 (Session<br>Storage) | 현재 연결과 관련된 기본 정보를 나타내며, 실습 시점에는 별도 정보<br>가 출력되지 않음 |

개발자 도구의 Storage 항목에서 Local Storage를 클릭하면 현재 서버(Bee Box)의 IP가 표시되고, 그 아래 사용자 이름과 Secret Message가 각각의 키(key)와 값 (value)으로 저장되어 있는 것을 확인할 수 있다.

#### 3-2. XSS를 이용한 Local Storage 값 탈취 실습

로컬 스토리지에 저장된 값을 XSS(A3, Reflected) 취약점을 이용해 탈취하는 실습이다.

bWAPP의 A3(XSS Reflected)에서 First Last Name을 입력하도록 되어 있는 폼을 이용한다.

아래와 같은 형식으로 로컬 스토리지의 값을 가져오는 스크립트를 작성한다.

// 로컬 스토리지에서 지정한 키(key)의 값을 가져오는 예시 형태 localStorage.getItem(키이름)

실제 실행을 위해서는 위 코드를 <script>  태그로 감싸 First Name 입력란에 삽입하 고, Last Name 입력란에는 임의의 값을 입력한 뒤 제출한다.

이렇게 하면 로컬 스토리지에 저장되어 있던 로그인 계정 아이디와 Secret Message 값을 가져올 수 있다.

실제 스크립트 삽입 및 실행 결과는 각자 실습을 통해 직접 확인해야 한다.

## 166. 장치·폴더 접근 제한 취약점 실습

### 1. Directory Traversal

경로 조작을 통해 실제로 보여지지 않아야 할 디렉토리와 파일이 노출되는 취약점이다. 디렉 토리가 노출되면 디렉토리 트래버설, 파일이 노출되면 파일 관련 취약점으로 구분할 수 있으 나 근본 원리는 동일하다.

#### 1-1. 경로 조작 기호

경로 조작에는 아래와 같은 기호가 사용된다.


| 기호 | 의미 |
|---|---|
| ../ | 상위 디렉토리로 이동 |
| ..\ | 상위 디렉토리로 이동(윈도우 계열 표기) |

의도하지 않은 디렉토리까지 접근이 가능하다는 것은, 관리자가 웹서버의 기능 수준에서 접 근 통제 설정을 누락했다는 것을 의미한다.

#### 1-2. 실습 절차 (PDF 파일 경로 조작)

bWAPP에서 PDF 파일을 클릭하면 bWAPP  디렉토리 아래 Documents 라는 디렉토리에 파일이 위치하고 있는 것을 확인할 수 있다.

페이지 소스 보기를 통해 실제 경로를 확인할 수 있다.

Burp Suite로 GET 요청을 캡처하여, 취약하다고 추측되는 파라미터 값에 ../ 를 삽입 하여 경로 조작을 시도한다.

# 예시: 파라미터 값에 상위 디렉토리 이동 기호를 추가하는 방식 파라미터=Documents/파일명.pdf → 파라미터=../파일명.pdf (상위 디렉토리로 이동)

../ 를 반복하여 적용하면 점차 상위 디렉토리로 이동하며, 최상위 문서 루트 (Document Root) 디렉토리에 도달할 수 있다.

문서 루트를 벗어나 추가로 ../ 를 적용하면 tmp , mail , local , spool  등 다른 시스템 디렉토리의 내용을 확인할 수 있다.

이 과정에서 백업 파일(예: bwapp_bak )과 같이 노출되어서는 안 되는 파일도 함께 확인 되는 경우가 있다.

#### 1-3. File 파라미터를 이용한 실습

특정 페이지에서 page 라는 파라미터에 message.txt  파일의 내용을 출력하는 기능이 있 는 경우, 이 파라미터 값을 경로 조작 기호로 대체하여 임의의 파일을 불러올 수 있는지 테스트할 수 있다.

파라미터에 대상 파일 경로를 직접 지정해야 하며, 예를 들어 /etc/passwd  경로를 지정 하면 해당 파일의 내용이 출력되는 것을 확인할 수 있다.

#### 1-4. 대응 방안

웹서버 설정 시( httpd.conf  등 환경설정 파일) 디렉토리별 접근 통제(허용/거부) 설정을 명 확히 해야 한다. 예를 들어 문서 루트가 /var/www/html 이라면, 클라이언트는 해당 디렉토리 하위에만 접근이 가능하도록 설정해야 하며, 그 외 디렉토리에 접근이나 읽기가 가능하도록 설정되어 있으면 디렉토리 트래버설 취약점이 발생하게 된다.

### 2. Cache Poisoning

Host 헤드 값을 조작하는 두 가지 유형(Reset Poisoning, Post Head Attack Reset Poisoning)이 있으며 조작 방식은 동일하다.

#### 2-1. 캐시의 동작 원리


| 구성 요소 | 역할 |
|---|---|
| 클라이언트 | 웹 서버에 페이지를 요청 |
| 웹 서버 | 클라이언트의 요청을 처리하고 응답 |
| 웹 캐시 | 이전 응답을 저장해 두었다가 동일 요청 시 서버 재요청 없이 캐시된 정보를 반환<br>하여 브라우징 속도를 높임 |

공격자가 웹 캐시에 저장된 정보를 변조하면, 이후 해당 페이지를 요청하는 사용자에게 의도 하지 않은 내용이 전달되는 문제가 발생할 수 있다.

#### 2-2. 실습 절차

Burp Suite에서 Intercept를 켠 상태로 리셋 버튼 등을 클릭하여 요청을 캡처한다.

캡처된 요청의 Host 헤드 값에는 현재 서버(Bee Box)의 IP가 들어가 있다.

이 값을 공격자(Kali)의 IP로 변경하고, Kali에 동일한 경로와 이름의 파일(예: 포 털.php)을 준비해 두면, 서버가 응답을 넘겨줄 때 Kali의 파일로 연결이 유도된다.

이 방식은 앞서 다룬 Host Header Attack(Post Head Attack)과 동일한 원리로, Host 헤드 값을 변조하여 공격자가 원하는 곳으로 연결을 유도하는 방식이다.

### 3. LFI / RFI (Local/Remote File Inclusion)

#### 3-1. SQLite Manager LFI 소개

SQLite Manager에서 로컬 파일 실행 취약점이 존재한다. SQLite는 경량의 모바일 앱 등 에서 사용하는 DBMS이며, SQLite Manager는 이를 관리하는 도구이다. SQLite Manager 관련 CVE 코드가 소개되었으며, Exploit-DB나 구글 검색을 통해 관련 공격 코드 를 확인할 수 있다.

SQLite Manager 사이트 내 여러 폼에 값을 입력해 가며 테스트하면 LFI 취약점이 존 재하는 지점을 확인할 수 있다.

Burp Suite로 요청을 캡처한 뒤 쿠키(Cookie) 값에 ../  등의 경로 조작 문자열을 삽 입하여 LFI 공격을 시도할 수 있다.

#### 3-2. LFI 실습 (bWAPP)

language 라는 파라미터에 선택한 값이 그대로 반영되는 기능에서, 해당 파라미터 값을 지우고 경로 조작 문자열로 대체하여 LFI를 시도한다.

#### 3-3. RFI 실습 (bWAPP)

Kali에서 웹서버를 실행시켜 두고, 파라미터 값에 http://[Kali IP]  형태의 URL을 삽입 하여 원격 파일을 포함시키는 방식으로 진행한다.

Burp Suite에서 값이 보이지 않는 경우, 헤드에서 바꾸거나 URL에서 바꾸거나 프락시 툴 본문에서 바꾸는 방식 모두 동일한 결과를 낸다.

### 4. Restrict Device Access (장치 접근 제한)

인가된 몇 개의 장치(스마트폰 또는 태블릿 컴퓨터, Apple/Android)만 접근할 수 있도록 되 어 있는 페이지의 취약점이다.

#### 4-1. 취약점 원리 및 실습

브라우저(또는 Burp Suite)는 User-Agent 정보를 통해 접속 장치가 스마트폰/태블릿인지 여부를 판단한다.

별도의 브라우저 탭에서 안드로이드 크롬 스마트폰의 User-Agent 값을 검색하여 확인 한다.

Burp Suite에서 Intercept를 켠 뒤 페이지를 새로 고침하여 요청을 캡처한다.

캡처된 요청의 User-Agent 값을 검색한 안드로이드 스마트폰 값으로 교체한 뒤 Forward한다.

변경된 User-Agent 값으로 요청이 전달되면 정상적으로 스마트폰 또는 태블릿 컴퓨터 로 인식되어 페이지 접근이 허용되는 것을 확인할 수 있다.

### 5. Restrict Folder Access (폴더 접근 제한)

인가된 사용자만 Documents 폴더에 접근할 수 있어야 한다는 것을 안내하는 취약점이다.

#### 5-1. 실습 절차

PDF 파일을 클릭했을 때 보여지는 경로(Documents 디렉토리 경로)를 미리 복사해 둔 다.

로그아웃을 진행한다.

로그인하지 않은 상태에서 복사해 둔 경로로 접속을 시도한다.

별다른 제한 없이 PDF 파일 및 Documents 디렉토리에 접근이 가능한 것을 확인할 수 있다.

#### 5-2. 원인

Documents 디렉토리는 인가된 사용자뿐만 아니라 로그인하지 않은 누구든지 접근이 가능 한 상태였으며, 이는 환경 설정에서 Documents 디렉토리에 대한 접근 권한 설정이 잘못되 어 있기 때문이다.

### 1. DLL (Dynamic Link Library)

#### 1-1. DLL의 개념

.dll  파일은 Dynamic Link Library의 약자로, 동적 연결 파일이다. 어떤 실행 파일이 실 행될 때 동적으로 연결되어 함께 동작하는 실행 파일이다.

윈도우 시스템 DLL 파일은 주로 C:\Windows\System32  디렉터리에 위치하며, 윈도우 시스템 을 동작시키기 위한 다양한 시스템 관련 파일들이 이곳에 저장된다.

악성코드를 분석할 때 내부를 들여다보면 DLL 파일 참조가 상당히 많이 나온다. DLL의 기능을 알면 해당 악성코드가 어떤 일을 하고 시스템에 어떠한 영향을 미치는지 파악할 수 있다.

#### 1-2. 주요 DLL 파일과 역할

악성코드 제작 또는 유포 시 많이 사용되는 주요 DLL 파일은 다음과 같다.


| DLL 파일명 | 역할 | 악성코드 감염 시 영향 예시 |
|---|---|---|
| kernel32.dll | 메모리 관리, 파일 입출력, 프로세스 실<br>행 코드 담당 | 이름 변조(예: kerne132.dll )로 시<br>스템 핵심 기능 장악 가능 |
| ntdll.dll | kernel32.dll 과 유사한 커널 수준 역<br>할 수행 | 커널 수준에서 비정상 동작 유발 가능 |
| GDI32.dll | 그래픽 디바이스 인터페이스(GDI) —<br>화면, 프린트 등 그래픽 출력 관리 | 화면 출력 오류 발생 가능 |

### 2. PE (Portable Executable) 파일

#### 2-1. PE 파일의 개념

PE는 Portable Executable의 약자로, 윈도우 운영 체제에서 사용되는 실행 파일 형식 전 체를 가리킨다. portable 은 경량의, 이동이 자유로운 실행 파일을 의미하며, 악성코드는 PE 파일 형태로 배포되는 경우가 많다.

#### 2-2. PE 파일에 해당하는 확장자


| 계열 | 확장자 |
|---|---|
| 실행 파일 | .exe , .scr |
| 라이브러리 | .dll , .ocx , .cpl |
| 드라이버 | .drv , .sys , .vxd |
| 객체 파일 | .obj |

.scr  파일도 실행 파일이다. 실제 악성코드 분석 사례에서 .scr  확장자의 악성코드가 한 글 채용 지원 문서로 위장하여 유포된 사례가 있다.

#### 2-3. PE 파일의 구조

PE 파일은 크게 **PE 헤드(Header)**와 PE 바디(Body) 두 부분으로 구성된다.

┌───────────────────────┐ │       DOS Header       │  ← 이미지 DOS 헤더 + DOS 스텁 포함 │       DOS Stub         │ ├───────────────────────┤ │       PE Header        │  ← 매직 넘버, 주소 정보 등 포함 │  (이미지 NT 헤더 등)   │ ├───────────────────────┤ │    Section Table       │  ← 섹션 헤더 + 섹션 데이터 │   (섹션 헤더 + 데이터) │ │    API, 실행 코드,     │ │    아이콘, 커서 등     │ └───────────────────────┘ PE 헤드 PE 바디


| 영역 | 포함 정보 |
|---|---|
| PE 헤드 | DOS 헤더, PE 헤더, 매직 넘버, 주소 정보 |
| PE 바디(섹션) | API, 실제 프로그램 실행 코드, 아이콘, 커서 등 |

#### 2-4. PE 구조의 세부 영역

DOS 헤드 (DOS Header)


| 구성 요소 | 내용 |
|---|---|
| 이미지 DOS 헤더 | 매직 넘버 포함 |
| DOS 스텁 (DOS Stub) | DOS 환경에서 실행되는 프로그램의 코드 및 데이터 혼합 포함 |

PE 헤드 내 주요 요소 이미지 NT 헤더, 파일 헤더 등 각각의 성격을 나타내는 구조체가 존재한다.

섹션 테이블 : 섹션 헤더와 섹션 데이터로 구성되며, 프로그램의 성격에 따라 내용이 달 라진다.

#### 2-5. 매직 넘버 (Magic Number)

매직 넘버는 파일의 성격을 나타내는 시그니처 값이다. CTF나 포렌식에서 파일 형식을 식별 할 때 사용하는 시그니처 문자(예: GIF89A )와 동일한 개념이다.


| 매직 넘버 | 의미 |
|---|---|
| MZ | 윈도우 실행 파일(PE 파일) |

#### 2-6. 주소 관련 개념

PE 분석 시 사용하는 주소 개념은 다음과 같다.


| 용어 | 설명 |
|---|---|
| Offset | 파일의 첫 바이트부터의 거리 |
| VA (Virtual Address) | 어떤 프로세스의 가상 메모리 절대 주소 — 실행 중인 프로세스의<br>절대 주소 |
| RVA (Relative Virtual<br>Address) | 기준 주소(Image Base)로부터의 상대 주소 — 메모리에 로드되었<br>을 때 위치 |

PE 파일이 실행되어 메모리에 로드되면 여러 DLL들과 함께 연결되므로, 각각의 가상 주 소(VA)가 필요하다.

## 171. 악성코드 분석 개요 및 FLARE VM 기반 분석 환경 구성

기반 분석 환경 구성

### 1. 악성코드 분석 방법론

#### 1-1. 분석 방법의 구분

악성코드 분석은 기초분석, 정적분석, 동적분석의 세 가지로 구분된다.


| 구분 | 핵심 방식 | 주요 분석 대상 |
|---|---|---|
| 정적분석 | 악성코드를 실행하지 않고 분석 | 패킹 여부, 내부 구조 |
| 동적분석 | 악성코드를 실행한 후 변화를 비<br>교 | 프로세스 변화, 성능 변화, 특정 폴더 내 파일<br>추가 여부 |

강의자료 뒤쪽에 수록된 도구들은 대부분 정적 또는 동적 분석에 해당한다.

#### 1-2. 분석 도구의 종류

분석 도구는 자동화 도구와 수동 도구로 나뉜다.


| 구분 | 설명 | 예시 |
|---|---|---|
| 자동화 도구 | 웹 기반으로 기본 분석 결과를 제공 | 바이러스 토탈(VirusTotal), 킴프(KimP) |
| 수동 도구 | 분석자가 직접 조작하여 사용 | FLARE VM 내 설치된 도구들 |

### 2. 악성코드 분석 환경 구성

#### 2-1. 가상 환경 사용의 이유

악성코드는 바이러스, 멀웨어 등 다양한 형태를 포함하며, 실제 호스트 시스템에서 분석을 수행하면 감염 및 문제가 발생할 수 있다. 또한 백신 툴이 설치되어 있는 경우 악성코드를 자 동으로 삭제한다. 따라서 가상 환경을 별도로 구축하여 분석 시스템으로 사용하는 것이 일반 적이다.

⚠️ 악성코드 분석은 반드시 가상 환경에서 진행해야 한다. 호스트 시스템에서 직접 실행 하면 감염된다.

#### 2-2. 악성코드 분석 전용 시스템


| 시스템 | 운영 체제 계열 | 비고 |
|---|---|---|
| FLARE VM | 윈도우 계열 | 악성코드 분석 도구 모음 배포판 |
| REMnux | 리눅스 계열 | 악성코드 분석 도구 모음 배포판 |
| 쿠쿠 샌드박스 (Cuckoo) / CAPE | 리눅스 계열 | 현재는 CAPE로 업데이트됨 |

위 시스템들은 칼리 리눅스가 여러 해킹 도구를 모아놓은 배포판인 것과 같이, 악성코드 분 석을 위한 다양한 도구가 기본 설치된 배포판이다.

#### 5-2. PowerShell을 통한 설치 실행

PowerShell은 반드시 관리자 권한으로 실행한다.

# 압축 해제한 FLARE VM 디렉터리로 이동 cd C:\flare-vm-main # 디렉터리 내 파일 확인 dir # install.ps1 파일 언블록 Unblock-File .\install.ps1 # 실행 정책 변경 Set-ExecutionPolicy Unrestricted -Force # 설치 스크립트 실행 .\install.ps1

#### 5-3. 설치 중 체크 항목 및 오류 대응

설치 스크립트 실행 시 사전 요건 확인 창이 나타나며, 항목별로 true/false 가 표시된다.


| 항목 | 의미 |
|---|---|
| windows.version — false | Windows 버전 요건 미충족 |
| windows.defender.disabled — false | Windows Defender가 비활성화되지 않음 |

위 항목이 false 로 나올 경우 해당 설정을 수정한 후 재부팅하고 Unblock-File 부터 재실행 한다.

⚠️ 설치 중 에러가 발생하면 에러 내용을 확인하여 해당 설정을 수정한 후, Unblock-File 부터 다시 진행하면 된다. 이전에 완료된 설정은 이미 적용되었다는 메시지가 표시된다.

#### 5-4. 설치 진행 과정

패키지 선택 창이 나타나며, 기본으로 선택된 항목만으로도 상당히 많은 도구가 설치된 다.

설치의 핵심 모듈은 Boxstarter이며, Chocolatey를 통해 패키지 다운로드가 진행된 다.

공통 파일은 _VM  디렉터리에, 분석 도구는 바탕화면의 tools  폴더에 설치된다.

설치 과정 중 자동 재부팅이 이루어지며, 재부팅 후에도 커맨드 창이 자동으로 열려 설치 가 계속된다.

최종적으로 log.txt  파일과 함께 type Enter to exit  메시지가 나타나면 엔터를 눌러 설치를 완료한다.

바탕화면이 FLARE VM 테마로 변경되면 설치 완료이다.

### 6. FLARE VM 설치 완료 후 도구 확인

## 172. PE 분석 도구 활용 및 디스어셈블러·디버거 입문

### 1. PE 분석 도구

#### 1-1. PEID

PEID는 PE 파일 구조를 분석하는 도구이다. 분석하고자 하는 악성코드를 파일 열기로 불러 오면 바로 결과가 나온다.

확인 가능한 정보


| 항목 | 내용 |

| 컴파일 도구 | 어떤 도구로 컴파일되었는지 |
| 실행 유형 | Win32 콘솔에서 실행되는 것인지 |

Lab01-01.exe  파일을 선택하면 Visual C++ 6.0에 의해서 기본적으로 컴파일이 되어졌다는 것을 확인할 수 있다.

스캔 옵션 오른쪽 최하단 화살표 버튼을 누르면 추가적으로 스캐닝할 수 있는 옵션이 나온다.


| 스캔 모드 | 설명 |
|---|---|
| Normal Scan | 기본값. 빠른 스캔 |
| Deep Scan | 더 세밀한 스캔. 시간이 오래 걸린다 |

Options에서 원하는 옵션을 체크한 다음 Save하면 다음부터 그 옵션 내용대로 스캐닝이 이 루어진다.

#### 1-2. PE Studio

PE Studio는 PEID보다 조금 더 복잡하지만 여러 가지를 묶어놓은 도구이다. 파일 열기 또 는 드래그 앤 드롭으로 파일을 불러올 수 있다.

연하게 표시되어 있는 부분들은 스캐닝이 안 되었거나 알 수 없거나 필요가 없는 부분들이 다. 진하게 활성화되어 있는 부분들을 주로 확인한다.

주요 메뉴 구성


| 메뉴 | 내용 |
|---|---|
| Fingerprint | 알고리즘 확인 |
| DOS Header | DOS 헤드 정보 |
| DOS Stub | DOS 스텁 정보 |
| Section | 섹션 정보 |
| Strings | 문자열 정보 |
| Imports | 임포트되는 DLL 및 함수 목록 |
| VirusTotal | 바이러스토탈 탐지 결과 |

바이러스토탈 항목에서 70개의 백신 중에서 55개의 백신에서 탐지가 이루어지고, 15개의 백신에서는 UNDETECTED 상태임을 확인할 수 있다.

임포트되는 항목에서 kernel32.dll 과 msvcrt.dll  두 개가 있었고, 각 DLL 안에서 참조하고 있는 함수들을 확인할 수 있다. create file , copy file  등의 함수들이 보여지며, 이 함수들 은 명령어 또는 실행하는 명령어가 된다. 더블클릭하면 해당 내용으로 바로 이동하여 확인할 수 있다.

익스포트되는 것이 없으면 시스템 내부에서만 뭔가 일이 일어난다는 것을 확인할 수 있다.

#### 1-3. Dependency Walker

Dependency Worker는 의존성(Dependency)을 확인하는 도구이다. 어떤 파일이 실행 될 때 어떤 것들이 같이 의존성을 가지고 실행되어야 하는지를 알려주는 도구이다.

드래그 앤 드롭 또는 파일 열기를 통해 실행한다. 처리 시 시간이 걸릴 수 있으며, 에러가 발 생해도 결과는 출력된다.

트리 구조 확인 임포트되고 있는 것이 트리 형태로 표시된다.

최상위에 kernel32.dll 과 msvcrt.dll  두 개의 DLL이 임포트되고 있다.

kernel32.dll 을 누르면 NTDLL 이 나온다. NTDLL도 커널 역할을 하는 DLL 파일이라고 했다.

각각의 의존성을 가지는 프로세스나 파일들을 클릭하면, API라고 되어 있는 DLL의 함 수들이 쭉 나온다.

kernel32.dll └── NTDLL.dll └── (의존 라이브러리들)

생성하고 카피하고 삭제하는 함수들이 이 API에 들어가져 있다. msvcrt.dll 도 눌러보면 의 존성을 가지는 핵심 파일들에 대해서 확인이 가능하다.

Dependency Walker를 사용하면 트리 형태로 최상위에서 임포트되어지는 것과 그 아래쪽 에서 같이 이루어지는 것들에 대해서 확인할 수 있다.

### 3. 디스어셈블러 (Disassembler)

#### 3-1. IDA

IDA는 자주 사용하는 유명한 디스어셈블러이다. 플레이어 VM 작업 표시줄에 별도로 나와 있을 수 있으며, Disassemblers 폴더 안에서도 실행 가능하다.

최초 실행 시 라이센스에 I agree를 해주고 OK를 진행한다. New를 선택하여 분석하고자 하는 악성코드 파일을 불러오면 된다.

IDA 프리 버전은 이메일 인증을 통한 라이센스 키 방식으로 현재 변경되었으며, 계정이나 요금 정책이 바뀌어지면 뜻하지 않게 요금이 나갈 수 있으므로 회원가입에 주의가 필요하 다.

#### 3-2. Binary Ninja

Binary Ninja는 코딩 환경처럼 구성된 디스어셈블러 도구이다.

실행 후 Open 또는 드래그 앤 드롭으로 파일을 불러오면 분석이 진행된다. 분석에 시간이 걸릴 수 있다.

주요 화면 구성


| 영역 | 내용 |
|---|---|
| 상단 탭 | 분석 중인 파일명 표시 (예: Lab01-01.exe ) |
| Address 컬럼 | 메모리 주소 |
| Code 영역 | 어셈블리 언어로 표시된 코드 |
| R-Data 영역 | 실제 데이터 영역 |

_start  함수에 의해서 스타트가 실행되고 있다는 것을 확인할 수 있다. 각각의 메모리 구조 뿐만 아니라 선택을 하게 되면 왼쪽 하단에 선택한 코드 부분에 대한 내용들이 나온다.

R-Data 부분에는 우리가 눈으로 봐도 확인할 수 있는 부분들이 존재한다.

가령 copy file A  부분을 더블클릭하게 되면 우측에 copy file A  함수의 내용과 메모리 주 소들이 나오게 된다. 여기서 kernel131 을 생성해서 맵핑하고 있는 것들이 보여진다.

디버그 기능 도구 모음 세 번째의 Debug 버튼을 클릭하면 실제 함수들을 가지고 선택하여 함수 실행이 어떻게 되는지 확인하거나, 어디에서 브레이크를 걸어서 어떤 함수가 어디까지만 실행되도 록 할지 등을 진행할 수 있다.

오른쪽 빨간 삼각형(F6)을 누르면 실행이 된다.

브레이크는 일시 중지, 스탑은 디버깅 자체를 중지하는 것이다.

IDA의 경우 Binary Ninja보다 조금 더 깔끔하게 보여지며, 딱 봐야 될 정보들만 깔끔하게 보여주는 편이다.

### 4. 디버거 (Debugger)

#### 4-1. WinDbg

WinDbg는 디버깅 도구로, 파일을 실행했을 때 여러 가지 내용들에 대해서 브레이크하거나 한 단계씩 실행할 수도 있다.

Open 메뉴에서 다음 항목을 선택할 수 있다.


| 항목 | 설명 |
|---|---|
| 소스 파일 (Open Source File) | 원본 파일, 코딩한 파일, 컴파일되지 않은 파일 |
| 덤프 파일 (Dump File) | 실행할 때 디버깅을 추적할 수 있도록 하는 파일 |

All Files( *.* )로 파일 형식을 바꾸어 Lab01-01.exe  파일을 불러오면 프로그램이 실행되기 시작한다.

Break 버튼이 비활성화가 되면 프로그램이 다 실행되었다는 것을 나타낸다.

리버싱을 하기 위해서는 프로그래밍 언어 한두 개 정도에 대한 이해가 필요하고, 메모리와 관련되어 있는 주소 체계에 대한 이해도 필요하다.

디버깅 결과 화면에서 확인 가능한 정보:

기본적으로 나오는 이 프로그램에 대한 기능들의 실행 여부가 출력된다.

실행 파일의 모듈들이 어떤 메모리 주소에 들어가고 있는지 보여진다.

EAX , EBX  등 Buffer Overflow에서 봤던 레지스터 포인터들이 보여진다.

#### 4-2. EarlyDBG (얼리DBG)

EarlyDBG는 조금은 쉽게 확인할 수 있도록 제공해주는 디버거이다. 공식 사이트에서 최신 버전(1.10)을 다운로드할 수 있다. 다운로드 후 압축을 해제하고 tools > debuggers  폴더 안 에 넣어놓으면 된다.

실행 파일( earlydbg.exe )을 더블 클릭하여 실행하고, 파일 열기를 통해 분석할 악성코드를 불러온다.

화면 구성


| 컬럼 | 내용 |
|---|---|
| 첫 번째 (왼쪽) | 메모리 주소 |
| 세 번째 | 어셈블리 언어 |
| 네 번째 | 데이터 |

여기에 있는 영어들은 다 어셈블리 언어가 된다. 어셈블리 언어는 기계어에 가깝게 메모리 주소들을 처리할 수 있도록 만들어진 언어가 된다.

주요 어셈블리 명령어


| 명령어 | 역할 |
|---|---|
| PUSH | 스택에 값을 저장 |
| MOVE | 데이터 이동 |
| CALL | 함수 호출 |
| TEST | 조건 검사 |
| POP | 스택에서 값을 꺼냄 |

CALL 이라고 하는 어셈블리 언어가 실제 함수를 실행하기 위해서 호출하는 부분이 된다.

Lab01-01.exe 를 콜하는 부분을 더블클릭하고 어셈블을 누르면 넘어가는 곳이 어디인지 차례 대로 확인할 수 있다.

데이터 영역(네 번째 필드)을 눌러보면 create file A , create file mapping A  등 아까 봤던 영어 단어들이 나온다.

EarlyDBG를 이용하면 현재 함수들이 어떻게 실행되는지 관계도를 알 수 있다. 프로그램이 실행되는 주소는 10000 에서 1004 , 1006 , 1008  이렇게 순차대로 들어가고 있다.

여러 가지 색깔들이 나오고 있는데 이 색깔들에 대한 내용들도 여기서 지정해 줄 수 있다. 선택하는 것에 대한 여러가지 내용들을 색깔로 조금은 더 알기 쉽게 진행할 수 있다.

### 5. 파일 정보 확인 도구

#### 5-1. EXE InfoPE

EXE InfoPE는 file information  폴더에 있는 도구로, 파일의 정보를 보여주는 도구이다. 파 일을 삽입하면 기본 정보가 나온다.

확인 가능한 정보


| 항목 | 내용 |
|---|---|
| 실행 유형 | Windows Console |
| 컴파일 도구 | Visual C++ 6.0 |
| Unpack Info | 패킹 여부 (패킹됨 / 패킹 안됨) |
| OLYDBG | 제공 여부 표시 |

스캔 버튼을 클릭하면 스캔된 결과들이 세부적으로 나온다. P 버튼을 클릭하면 PE 헤드에 대한 정보(헤드 인포)가 주로 나온다. 각각의 헤드에 어떤 정보들이 어떤 메모리 주소에 들어 가져 있는지 확인할 수 있다.

제로 바이트 테스트 차트 모양 아이콘에 마우스를 올려보면 Zero Byte Test 라고 되어 있다. 이 프로그램을 처음 부터 끝까지 바이트 단위로 실행해가면서 테스트를 해보는 도구가 된다.

분석을 할 때는 CTF를 할 때도 마찬가지고 하나의 도구가 아니라 여러 개의 다양한 도구 를 통해서 나오는 것들을 취합해서 확인을 해봐야 한다.

### 6. 헥사 에디터 (Hex Editor)

#### 6-1. HxD

HxD는 16진수 헥사코드로 파일을 편집하고 볼 때 사용하는 도구이다. hex editors  폴더 안 에 있다.

파일 열기를 통해 Lab01-01.exe 를 불러온다.

화면 구성


| 컬럼 | 내용 |
|---|---|
| OFFSET | 오프셋(주소). 00으로 시작 |
| 가운데 영역 | 16진수 데이터 |
| 오른쪽 영역 | 텍스트로 표현된 데이터 |

매직 넘버 (Magic Number / Signature Number)

파일의 오프셋 제일 처음에 4D5A 가 표시된다. 이에 해당되는 오른쪽 표시는 MZ 이다.

MZ 4D5A 가 있으면 실행 파일임을 먼저 인지한다. 이것이 파일의 성격을 먼저 파악하는 방법 이다.

제일 먼저 이 부분을 읽어서 이 파일의 성격을 먼저 파악한다. 그래서 MZ/4D5A가 있으면 이 파일은 실행 파일이라고 먼저 인지하게 된다.

예를 들어 제일 첫 번째에 GIF89A 가 들어가져 있으면 이미지 파일이라고 인식하여, 밑에 이미지가 아니더라도 이미지로 인식이 된다. 이것을 시그니처 넘버, 매직 넘버라고 한다.


| 시그니처 | 의미 |
|---|---|
| MZ (4D5A) | Windows 실행 파일 (EXE, DLL 등) |
| GIF89A | GIF 이미지 파일 |
| PE | PE 실행 파일 표시 |

파일 아래쪽으로 내려가면 우리가 봤던 명령어들과 문자열들이 보여진다. 선택하는 부분에 따라 오른쪽의 텍스트 표시도 함께 바뀐다.

이 헥사코드는 16진수 헥사코드에 대응하는 데이터들을 이렇게 볼 수 있도록 제공해 놓은 것 이 된다.

010 Editor의 경우도 HxD와 유사하게 동작한다.

### 7. 패킹 도구

#### 7-1. UPX를 통한 패킹 확인

도구들 안에 다양한 패킹 툴들이 존재한다. 이 도구들은 패킹 툴이자 패킹된 것들을 언패킹 하는 도구들이다.

현재 Lab01-01.exe  같은 경우에는 패킹은 되어지지 않고 비주얼 C++로 컴파일만 이루어진 것이기 때문에 이 도구를 이용할 수는 없다.

특정 프로그램을 분석했을 때 PEID나 PE Studio 등을 통해 구조를 봤을 때 UPX 라는 단어 가 보여진다면 UPX를 통해서 패킹이 이루어졌다는 것이다. 그러한 경우에는 UPX 도구를 통해서 언패킹을 해볼 수 있다.

## 173. 악성코드 분석 환경 설정 및 바이러스토탈을 이용한 기초 정적 분석

토탈을 이용한 기초 정적 분석

### 1. 실습 환경 준비

#### 1-1. 플레이어 VM 기본 설정

실습은 플레이어 VM(가상 머신)에서 진행된다. 이 VM에는 어제 설치한 환경이 기반이 된 다.

오늘은 어제 설치했던 플레이어 VM을 가지고 샘플 악성 코드를 다운로드 받아서 기본적인 분석 방법에 대해 다양한 도구를 확인하고 테스트를 진행한다.

#### 1-2. 실시간 보호 비활성화

샘플 악성코드를 다운로드하기 위해서는 보안 기능을 사전에 비활성화해야 한다. 설치 완료 후에는 실시간 보호 기능이 다시 켜져 있을 수 있으므로 반드시 확인이 필요하다.

⚠️ 두 가지 설정 중 하나라도 되어 있지 않으면 다운로드가 제대로 이루어지지 않는다.


| 설정 항목 | 경로 | 변경 값 |
|---|---|---|
| 실시간 보호 기능 | 바이러스 및 위협 탐지 > 설정 관리 | OFF |
| 세이프 브라우징 | Chrome 설정 > 개인정보 보호 및 보안 > 세이프 브라우징 | 보호되지 않음 |

바이러스 및 위협 탐지에서 실시간 보호를 끄지 않으면 "바이러스 발견됨" 메시지와 함 께 다운로드가 차단된다.

세이프 브라우징을 설정하지 않으면 브라우저 자체에서 다운로드가 차단된다.

### 3. 분석 도구 설치

#### 3-1. PEID

PEID는 PE 실행 파일을 분석하는 도구이다. 검색 엔진에서 PEID 로 검색 후 블로그 등의 페 이지에서 ZIP 파일을 다운로드할 수 있다. PEID 0.95 버전 압축 파일을 다운로드하면 된다.

참고: 플레이어 VM의 PE 폴더 안에 PEID가 이미 포함되어 있을 수 있으므로 사전 확인 이 필요하다.

#### 3-2. Sysinternals Suite

Sysinternals(시스 인터널즈)는 MS에서 제공하는 유틸리티들의 모음이다. 시스템과 관련 된 여러 도구들을 모아놓은 묶음이 된다. Strings 외에도 파일 및 디스크 관련 유틸리티, 프 로세스 관련, 시스템 정보 관련 등 다양한 분야의 유틸리티가 포함되어 있다.

개별 도구보다는 Sysinternals Suite 전체를 다운로드하는 것이 권장된다.

다운로드: MS 공식 사이트 > Sysinternals Suite (약 184.6MB)

다운로드 후 압축을 해제하고 바탕화면의 tools  디렉토리 안으로 이동시킨다.

#### 3-3. 도구 정리

도구들은 바탕화면의 tools  디렉토리에 정리하여 보관한다.


| 도구 | 분류 | 역할 |
|---|---|---|

### 4. 기초 분석: 바이러스토탈(VirusTotal)

#### 4-1. 바이러스토탈 개요

바이러스토탈(virustotal.com)은 많이 사용하고 있는 자동화 분석 웹사이트 중 하나이다. 파일이나 URL 등을 올릴 수 있도록 되어 있으며, 전 세계에서 사용하고 있는 백신들의 탐지 결과를 한 번에 확인할 수 있다.

웹에서 자동으로 악성 코드나 의심되는 파일들을 올리면 지금과 같은 방식으로 분석을 해주 는 웹사이트들이 존재한다. 무료로 제공해주는 것도 있고 유료로 제공해주는 사이트들도 있 다. 유료 서비스는 코드에 대한 분석을 조금 더 세밀하게 진행한다.

#### 4-2. 분석 실습: Lab01-01.exe

Lab01-01.exe  파일을 바이러스토탈에 업로드하여 기본 정보를 확인한다.

탐지 결과 예시 바이러스토탈에 올려주게 되면 현재 올려 선택한 파일이 전 세계에 있는 백신들에 의해 탐지 되는지 확인할 수 있다. V3 같은 경우에는 트로잔(Trojan) Win32/VM 에이전트라고 나오 고, 알약 같은 경우에도 트로잔 에이전트라고 나온다. 트로잔은 숨겨서 들어오는 악성 코드 를 나타내며, 트로이 목마로 생각하면 된다.

모든 백신 툴에서 다 탐지가 되는 것은 아니며, 일부 백신에서는 Undetected (탐지 안 됨)로 표시된다. 약 57% 정도의 탐지율을 가지고 있다는 것을 확인할 수 있다.

Details 탭에서 확인 가능한 정보


| 항목 | 내용 |
|---|---|
| 파일 타입 | Win32 EXE |
| 매직 넘버 | MZ (4D5A) |
| 컴파일 도구 | Visual C++ (33.3% 확률로 추정) |
| 최초 생성일 | 2010년 12월 19일 |

똑같은 파일이 다른 이름들로 탐지되고 있는 것도 확인할 수 있다.

#### 4-3. PE 정보 및 임포트 함수 확인

바이러스토탈의 Details 탭에서 PE 구조 정보도 확인할 수 있다. 섹션 부분에 .text , .data 부분에 어떠한 것들이 있는지 보여진다.

Lab01-01.exe 가 실행될 때 임포트하는 파일들을 보면 다음 두 개가 임포트된다.


| DLL | 역할 |
|---|---|
| kernel32.dll | 메모리 관리 등 시스템에서 중요한 역할을 하는 라이브러리 |
| msvcrt.dll | 서비스와 관련 있는 DLL 파일 |

임포트 항목을 펼쳐 보면 파일을 카피하는 것, 파일을 생성하는 것, 생성된 것을 맵핑하는 것 등이 주로 이루어지고 있음을 확인할 수 있다.

msvcrt.dll 에 들어가면 서비스와 관련해서 환경 설정을 초기화하는 것, 커맨드 모드 진입, 핸들러를 통한 제어 등이 보여진다.

추출된 스트링 정보만을 보더라도 이 악성코드가 감염되면 서비스 관련 내용들을 참조해서 파일을 복제하고 맵핑하는 작업이 있다는 것을 확인할 수 있다.

기초 분석 단계에서 확인해야 할 핵심 항목은 다음과 같다.

이러한 것들을 종합했을 때 이 악성 코드들의 목적은 무엇인지, 실제 시스템에 어떠한 영향 을 미치는지 등을 파악하게 된다.

바이러스토탈닷컴에서 자동화된 도구를 통해 기본적으로 알 수 있는 기본 정보들은 다 확 인할 수 있다. 그 외에 릴레이션 정보, 실제 어떤 IP에서 올라오는지 등도 여기에서 보여진 다. Behavior 탭에서는 현재 올려놓은 것에 대한 속성값 정보들이 보여진다.

⚠️ 이러한 정보를 본다고 해도 암호화 알고리즘에 대한 이해, PE 구조에 대한 이해, DLL 파일에 대한 내용 등에 대한 이해가 없으면 내용이 나오더라도 무엇을 말하는 건지 알 수 없다. 악성코드 분석은 모의해킹, 보안 관제, 시스템, 네트워크와 완전히 다른 리버싱 (Reversing) 이라는 분야가 된다. 이쪽으로 관심이 있는 경우 리버싱에 대해서 심도 있 게 학습을 해야 하고, 기본적으로 나오는 도구에 대한 사용법도 익혀두는 것이 좋다.
